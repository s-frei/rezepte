---
title: "0011: Admin role checks in handlers, own password on auth/me"
description: Role read from the session user, the userapi package boundary, self-service password change, session revocation, the last-admin guard, and the theme attribute contract
---

**Status:** accepted · 2026-09-18

## Context

Phase 7 lets admins create, list, re-role, reset the password of, and delete users, lets any user change their own password, and adds a persisted light/dark theme choice plus a command palette. The household has at most a handful of members and two roles, so whatever authorization model is picked must stay proportionate to that scale. Deleting a user must not lose the recipes they created, and every credential change needs a well-defined effect on that user's other sessions.

## Decision

- Authorization is the `role` column read from the session's user: `userapi.requireAdmin` returns 403 `admin role required`; no permission tables, no per-resource ACLs (household scale, two roles).
- User management lives in package `userapi`, not `user`, because `auth` imports `user` and the handlers need `auth.UserFrom`/`auth.SessionSecurity`.
- The own-password change is `PATCH /api/v1/auth/me` (`{currentPassword, password}`), not `PATCH /users/{id}`: it is the one user write a member may do, it verifies the current password (`user.ErrWrongPassword` → 422 at `body.currentPassword`) and it lives next to `me`.
- Every password change revokes the user's other sessions via `auth.Service.DeleteUserSessionsExcept`; the own change keeps the calling session, an admin reset keeps none.
- The last admin is protected inside the write transaction (`guardLastAdmin` after `CountAdmins`, under `_txlock=immediate`), for both delete and demotion (`user.ErrLastAdmin` → 409); self-delete is refused (`user.ErrSelfDelete` → 409).
- Deleting a user reassigns the recipes they created to the acting admin (`ReassignRecipes` in `queries/users.sql`) instead of cascading or nulling `created_by`.
- Theme: `data-theme` on `<html>` holds only an explicit `light`/`dark`; absence means system. Stored in `localStorage` under `rezepte-theme`, applied by an inline script in `app.html` before first paint and by `$lib/theme.svelte.ts` afterwards; dark tokens are declared twice (`:root[data-theme='dark']` and `@media (prefers-color-scheme: dark) { :root:not([data-theme='light']) }`) and the `dark:` variant is redefined with `@custom-variant` to follow the same rule.

## Consequences

- Authorization stays two comparisons (`requireAdmin`, self/last-admin guards) instead of a data-driven permission model; a third role or per-resource rules would need a new ADR, not a config change.
- A deleted user's recipes keep a valid, visible owner, so nothing downstream (listings, the FTS index, `created_by` joins) needs to special-case a missing user.
- A compromised or forgotten password stops working on every other device the moment it is changed, without a separate "sign out everywhere" feature.
- The dark token block has no single source: light-mode dark override and system-preference dark override must be edited together by hand (see [Design system](/memory/architecture/design-system)).
- `PATCH /users/{id}` does not special-case an admin's own id: the UI hides the reset-password action on the admin's own row and routes self-service through `PATCH /auth/me` instead, but an admin who calls the endpoint on themselves anyway would end their own session like any other reset (see [HTTP API](/memory/architecture/api)).
- Because a `401` already redirects the SPA to `/login` (see [HTTP API](/memory/architecture/api)), the password-change forms use the shared `isSignedOut(error)` helper in `frontend/src/lib/api/client.ts` to skip showing an error toast for that case - the redirect is already handling it.

<Accordions type="single">
  <Accordion title="Alternatives considered">

    - A permission table or per-resource ACLs: overkill for two roles at household scale, and adds a schema and a lookup for authorization checks that are otherwise one field comparison.
    - Soft-deleting users (a `deleted_at` column): nothing in the schema references a user except their recipes and sessions, so reassigning recipes and cascading sessions is simpler than adding a filtered-everywhere status.
    - A server-set cookie for the theme: `ssr = false` is set for the whole app (see [ADR 0006](/memory/decisions/0006-session-cookie-auth)), so nothing on the server would ever read it; `localStorage` plus a pre-paint script is the only place the choice can apply before first render.
    - `class="dark"` on `<html>` (the common Tailwind convention): the design handoff specified `data-theme`, and it composes with an explicit `light` under a dark system preference more directly than a single boolean class would.
