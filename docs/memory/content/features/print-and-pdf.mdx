A member can print a recipe or save it as a PDF; both are the same document, rendered by the service with Typst: "Kochbuch" (layout B, A4) or "Karte" (layout C, A5), with or without the cover photo and the footer (QR code and credit). The browser formats the recipe (`buildClientRecipe` in `frontend/src/lib/recipe/pdf-document.ts`) and hands it to the browser's print, a tab or a download (`frontend/src/lib/recipe/print.ts`); `service/internal/pdf` holds the `data.json` contract, the renderer, the fonts and the built-in Typst templates.

<Callout type="warn" title="Traps">

- Playwright's default headless Chromium (the headless shell) has no PDF viewer: `pdfViewerEnabled` is false and a PDF in a frame downloads instead of loading. `e2e/print.test.ts` runs on `channel: 'chromium'`, the full Chromium, whose new headless mode has the viewer ([Printing](#printing)).
- `test.use({ channel })` cannot sit in a `describe`: it forces a new worker. Every spec that prints through the frame lives in `e2e/print.test.ts`, the PDF tab's Print included.
- Firefox's PDF viewer in a frame is a cross-origin window: `contentWindow.print()` and even `addEventListener` on it throw. Firefox prints from a tab, never a frame. Playwright's Firefox ships with pdf.js off (`pdfjs.disabled`).
- The tab is opened before the PDF request, inside the click or key press: after the `await` a popup blocker refuses `window.open`.
- A segment carries both `amount` and `minutes`, `null` when its kind has none: huma requires every key of `pdf.Segment`, so an omitted one is a `422` (`TestBrowserShapeAccepted` posts the client's exact shape).
- Never decide "typst cannot run" with `errors.Is(err, syscall.EACCES)` on a `Render` error: the work dir, the template copy and the photos can fail with it as well, and one unreadable file would switch PDFs off for everyone. Check `pdf.ErrCannotRun` only (`TestOtherEACCESIs500`).
- A Typst error in a template surfaces only as the error string (`typst: exit status 1: <stderr>`); the work dir is already gone, so reproduce with `prepare` into a temp dir and run `typst compile` by hand ([PDF pipeline](#pdf-pipeline)).
- `prepare` fails on a recipe whose `photo.path` has no entry in the `photos` map, so the handler sends the cover whenever one exists, even with the Photo option off; the template decides by `options.photo` whether to show it.
- The OS temp dir is shared: every Rezepte process of one user (other worktrees, a dev server, tests through `typstbin.Path`) sweeps `rezepte-typst-*` at startup, so a starting instance can remove a running one's binary dir. Renders self-heal, but a typst run in flight at that moment can fail once.
- The server's QR code is bare, its view box the modules alone: the band's 3 mm gaps and the page margin are its quiet zone. A template that sets it against other ink must leave four modules of white around it. Typst reads the mascot from the SVG's data URI and ignores CSS `clip-path`; the mascot PNG is round already.
- In Typst markup, `#metadata(v) <label>` with a space leaves a space in the text; test labels are written `#metadata(v)<label>`, or step text gets double spaces.
- A Typst heading keeps its own default size under `show heading: it => it.body`; the title is sized by a `show heading: set text(...)`, never by styling the heading's body, or the contents list inherits the title's size.
- In Typst a bare tag (`#metadata(v)<label>`) followed by spacing reports the position after the spacing, and a `context` reports the position of what follows it, so footer placement read from `here()` never converges. Position markers sit in a zero-height block of their own (`column-end`), and the footer measures from `<body-end>`, not from `here()` ([Footer band and pagination](#footer-band-and-pagination)).
- A Typst block's `inset` repeats on every page the block breaks across: the space between the card's list and its method is a weak `v`, or every continuation page starts 3.5 mm low (`TestContinuationStartsAtTop`).
- The built-in templates are embedded in the Go binary: a running demo renders the old `lib.typ` until it is restarted.
- In Typst a tag inside a paragraph reports the paragraph's origin, not the spot after the text before it, so `#n#metadata(v)<label>` never tells where `n` ends. A test that reads where inline content sits puts the tag in a `box` with it, which reports the box's own position (`<step-number>`, `TestStepNumbersHang`).
- jsQR misreads round dots with gaps between them at 400 and 600 dpi; the dots are a module wide, touching their neighbors, which decodes at 300 to 600 dpi. A failed decode at 200 dpi of a 22 mm code is the module size against the raster, not the style: check a phone or a blurred render before calling a code broken.

</Callout>

## How it works

### Printing

**Print renders the PDF and hands it to the browser.** The "Print" item in the recipe's "..." menu (after "Pass on", printer icon, the shortcut hint on desktop: ⌘P on Apple platforms, else `detail_print_shortcut`), ⌘P on Apple platforms and Ctrl+P elsewhere on the recipe page (a `keydown` handler on the window, only while PDFs are available; it leaves IME composition alone and falls back to `event.code` on a layout without Latin letters) and the PDF tab's Print all call `printRecipe` with the body from `recipeRequest`: a `single` PDF with the remembered options (`printOptions` from `print-options.svelte.ts`, `localStorage` key `rezepte-print`) at the page's servings, read back from storage with `createServings`. A print asked for while one is in flight joins it. Until the PDF is handed to the browser (the frame's `print()` ran, the tab or the download got it) the menu's "..." trigger shows a spinner (`aria-busy`), the tab's button "Creating PDF"; a failure is the `share_pdf_failed` toast, and a tab opened for it closes. File → Print cannot be intercepted and prints the screen page as it is.

**`printRoute` picks how, by evidence per engine.** Desktop Chromium (Chrome, Edge) loads the PDF blob in a hidden same-origin iframe (laid out, not `display: none`, or no viewer loads) and calls its `contentWindow.print()`, so the print dialog shows the PDF. Firefox (cross-origin viewer), Safari (prints the page around the frame) and every phone or tablet with a PDF viewer open the PDF in a tab, opened before the request; without a viewer (`navigator.pdfViewerEnabled` false: Android Chrome, a viewer turned off) or with the popup blocked, or with the tab closed while it rendered, the PDF downloads through `saveBlob`. A frame print that throws downloads too. The frame and its blob URL go on the frame window's `afterprint`, or when the next print replaces the frame; never on a timeout, which could pull it while the dialog is open. A tab's blob URL is never revoked: its viewer may fetch it again to share or save, and it goes with the page.

**Without PDFs (`pdf.available === false`)** there is no Print in the menu and no PDF tab in the pass-on sheet (a stored PDF tab opens on Image), and Ctrl+P is left to the browser, which prints the screen page. Settings that failed to load offer the PDF; a failed request says so.

**Tests.** `e2e/print.test.ts` runs on `channel: 'chromium'` (the full Chromium, see Traps) and records every `print()` as `page` or `frame` (`observePrints` in `e2e/helpers.ts`, which stubs it). Its `mobile` project is phone emulation on a Chromium with a PDF viewer, so it covers the tab route of iOS and Firefox on Android, not Android Chrome; the download route runs in `share-pdf.test.ts` on the headless shell, which has no viewer. The `webkit` project does not run `print.test.ts`, so WebKit's tab route rests on `printRoute`'s unit test.

### The PDF tab

**The pass-on sheet's third tab is `SharePdfPanel.svelte`.** It lays out like the Link tab ([Recipe card](/features/recipe-card)): one column in the phone sheet's tab cell, the dialog's two columns from 768px. The preview is page 1 as Typst renders it, the custom template's too: the effect builds `recipeRequest(…)` synchronously, so it tracks every input, and debounces only the send (`requestPreview`) when the tab shows and after a change of Format, Photo or Footer; the image is a blob URL in an `img` tilted like the Image tab's picture. A paper-shaped placeholder stands in until the first image, a spinner lies over it while one renders, and a change aborts the request in flight, which cancels its render on the server and frees its slot. Format, Photo and Footer write `printOptions` through `setPrintOption`, so the preview, the menu's Print and Ctrl+P all follow at once.

**Download, Print and Share render the PDF when tapped.** Download PDF calls `requestPdf(recipeRequest(…))` (a `single` bundle from `buildClientRecipe` at the page's servings), then `saveBlob`; Print calls `printRecipe` ([Printing](#printing)); each button shows "Creating PDF" and `busy` meanwhile, and a failure is a toast. On a phone the sheet always offers downloading and printing: `[Share PDF][○ Download][○ Print]` with file sharing, else `[Download PDF][○ Print]`, the round secondaries as on the Image tab.

**Share keeps a refused PDF for a second tap.** Share (desktop) and Share PDF (the phone's primary) show only where `canShareFiles('application/pdf')`. The request spends the tap's user activation, so Safari may refuse `navigator.share` with `NotAllowedError`: the panel keeps the file and the button turns into "Share now", whose tap shares at once without a request. A change of Format, Photo or Footer drops the held file, a PDF that finishes rendering after such a change is not shared, and a refusal that arrives after one holds nothing, so Share now never shares what the preview no longer shows. `AbortError` changes nothing; any other failure is a toast. This is why it does not reuse `shareImage`, which downloads on `NotAllowedError`. The held file lives in the panel, which unmounts with the sheet, so closing drops it.

**Tests.** `e2e/share-pdf.test.ts` runs in `desktop`, `mobile` and `webkit`; the share specs stub `/api/v1/pdf` with `page.route`, and `pdf.available` is switched by a `page.route` on the settings.

### Long list first

**A4 sets a long list above a short method, measured in Typst.** `recipe()` in `lib.typ` measures the rail and the steps beside it unbroken (`overhang`); a list that runs on more than `list-first` (about six rows) below the steps goes first. Paella's 31 rows beside four short steps go first; Rinderrouladen and Sauerbraten stay beside (`TestIngredientsFirst`). Then the list takes the full width under its heading, in three balanced columns over a hairline, and the steps follow at the reading measure; beside the steps the rail would leave a hole under them, and past half a page the footer could not keep the last two steps. The card always sets its list above the steps.

**The QR code is drawn by the server.** `qr.go` (`rsc.io/qr`) draws it at level H: a round dot a module wide per dark module, rounded eyes for the three finders, all in pure black ink (so an office driver prints it with black toner alone rather than as a misregistering CMY+K composite; `TestQRStyle`), and a white rounded hole of 9 × 9 modules in the center holding the mascot (`templates/mascot.png`, a copy of `assets/brand/lockups/rezepte-favicon-192.png`, which the book's title page uses too), which level H's error correction covers. `TestQRStyle` checks the SVG against the encoder's modules for a short and an 83-character URL and reads level H back from the format bits; `TestQRMascotCopy` holds the mascot byte-equal to the brand file. A long URL takes a larger version, so its modules are finer: still read at 160 px, not at 96 px.

**The footer follows the instance's rules.** Footer on: the QR code (to `<instance.url>/recipes/<slug>`: `REZEPTE_PUBLIC_URL` when set, else the origin the browser sends, `location.origin`), its caption and "Added by" with the author's display name, plus " · Rezepte" only when `publicShareAttribution` is on. Footer off: the hairline and the source line only, at the same place; with no source either, no band.

### The PDF endpoint

**`POST /api/v1/pdf` (`create-pdf`) takes formatted recipes and adds what only the server knows.** `pdf.Service` (`service/internal/pdf/handler.go`) gets the client's `labels`, `locale`, `options`, `book` and `ClientRecipe`s; the schema refuses unknown keys, so a client cannot send `author` or a photo. It then loads every recipe with `recipe.Service.ByID` before anything renders (an unknown id is a `404` and no `pdf-*` dir is made), and merges in slug, URL, author (the creator's display name), timestamps and the cover (`detail` variant, as `photos/<n>.jpg`). A cover file that is gone prints without a photo.

**`POST /api/v1/pdf/preview` (`preview-pdf`) answers page 1 as a PNG, for the PDF tab's preview.** It takes create-pdf's body, bundle `single` only (`422` for book and zip), goes through the same `create` and then `Renderer.Preview`, and sends no `Content-Disposition`: it is an image to show, not a file to keep. Its own route keeps `/api/v1/pdf` answering what its name says, always a PDF or a zip.

**Who may ask for what.** `single` takes exactly one recipe and is open to every member, since every member can view every recipe; `book` and `zip` are admin only (`auth.RequireRole`, `403`), and `book` needs a `book` block (`422`); single and zip get `book: null`. `locale` must be one of `i18n.Locales()` (`422`). `origin` must be a bare http(s) origin (schema pattern, `422`); `instance.url` is `REZEPTE_PUBLIC_URL` when set, else that origin, and each recipe's URL is `<instance.url>/recipes/<slug>`. `instance.product` is always the product name `Rezepte`, never an operator's text, and `instance.attribution` is `publicShareAttribution`.

**The response is the file, served from the work dir.** `http.ServeContent` sets the exact length; `Result.Close` removes the dir after the body is written. Names: single `FileName(title, labels.recipeFallback)`, book `rezepte-<date>.pdf`, zip `rezepte-pdf-<date>.zip`. `Content-Disposition` always has a quoted ASCII `filename` (non-ASCII as `_`) and, when the name needs it, the RFC 6266 `filename*=utf-8''…` from `mime.FormatMediaType`, which the client prefers.

**Availability is one flag, read by the settings response.** `pdf.Available()` at startup is "typst embedded, or on PATH"; without it main.go logs `pdf: typst unavailable, PDF downloads are off`. The first render that fails with `pdf.ErrCannotRun` flips it to false with one log line until a restart; from then on the endpoint answers `503` without running anything. `Render` returns that error only when `typstbin.Path` reports `ErrUnavailable` or `cmd.Start` fails with `EACCES` or `ENOEXEC` (a `noexec` temp dir, a wrong-platform binary). Any other error, a permission error on the work dir or a photo included, is a `500` and leaves PDFs on. `GET /settings` reports `pdf: {available}`; the client hides PDF actions on `available: false`.

### Bulk PDF

**Admins export ticked recipes as one cookbook or a zip of PDFs** from the Export card ([Import and export](/features/import-export)). `bulkPdfRequest` in `frontend/src/lib/recipe/bulk-pdf.ts` builds the body: `bundle` `book` or `zip`, paper from the format, each recipe through `buildClientRecipe` at the dialog's servings or its own, and for a book `{ title: pdf_label_book_title, date, dateDisplay, countDisplay }` with the browser's local day, "month year" in the UI locale and the count as the title page prints it ("12 recipes", from `settings_transfer_pdf_count*`).

**The order is the list's sort, never its search.** The card sorts the ticked recipes with the comparator the list uses (title or last changed); a ticked recipe the search hides still goes in.

**Servings is one value for all.** "As in recipe" stores `servings: null`; "Adjust" stores a number (2 to start) and shows the recipe page's `ServingsStepper`. Like the other options it is remembered in `printOptions`, but it stays in the browser: each recipe arrives already scaled, and `recipes[].servings` is the only servings the server sees.

### PDF pipeline

**`pdf.Renderer` turns a `Data` into a file.** `Render(ctx, data, photos)` returns a `Result` (`Path`, `ContentType`) that the handler serves and then `Close`s; `Preview` is the same render of page 1 of a single recipe into `out.png` (`previewArgs`), through the same work dir, sandbox, semaphore and cleanup. It gets the binary from `typstbin.Path`, waits for a slot of a semaphore (`maxParallel`, `max(1, NumCPU/2)` from main), then renders under a timeout of 30 s for a single recipe and 30 s plus 1 s per recipe, at most 10 min, for book and zip.

**The work dir holds `fonts/` beside the typst root.** `Render` copies the embedded fonts into `pdf-*/fonts/` once per render (zip sub-renders share it) and renders single and book in `pdf-*/root/`, zip's recipes in `pdf-*/<i>/`. `prepare` fills a root: it copies one whole template tree (the built-in `templates/` or an operator's, never merged), writes `data.json` (templates read it with `json("data.json")`, never `--input`), copies each cover from the `photos` map to its `photo.path`, and with the footer on writes `qr/<i>.svg` per recipe and sets `qr`; with the footer off `qr` is null. Tests reuse `prepare` to run `typst eval` themselves.

**Typst runs sandboxed.** The call is `typst compile --root <dir> --font-path <fonts> --ignore-system-fonts --package-path <dir>/packages --package-cache-path <dir>/.cache`, with only `HOME=<dir>` and a dead proxy (`127.0.0.1:9`) in its environment: no system fonts, nothing outside the work dir, and a `@preview` import fails within milliseconds instead of downloading. `fonts/` is a sibling of every `--root`, so a template reads nothing outside its own tree, font files included.

**Bundles pick the tree.** `single` renders `recipe.typ`, `book` renders `book.typ`. `zip` renders each recipe as its own `single` Data in a subdirectory, stores the PDF uncompressed in `out.zip` under `FileName(title, labels.recipeFallback, taken)` and removes the subdirectory at once. `FileName` strips characters that are invalid on common file systems, cuts at 120 bytes on a rune boundary, and numbers duplicates case-insensitively (` (2)`), since macOS and Windows would overwrite `Flammkuchen.pdf` with `flammkuchen.pdf`.

**Fonts are static TTFs** (OFL, licenses beside them in `service/internal/pdf/fonts/`): Literata Regular, Italic, Medium, SemiBold and Bold from the googlefonts/literata 3.103 release (default optical size), and Karla Regular, Medium, SemiBold and Bold from googlefonts/karla. Static, not variable: Typst picks weights from static faces reliably. Not the frontend's woff2, which Typst cannot read.

### Cleanup

**Every way out of a render removes its dir.** `Render` creates `pdf-*` in the data dir with `os.MkdirTemp`, and the very next statement defers its removal, which is skipped only when the `Result` takes ownership. `Result.Close` removes it after the response. Success, a Typst error, a canceled request and a timeout all leave nothing, and tests assert each case.

**No Typst process outlives its request.** Typst runs in its own process group (`Setpgid`). `cmd.Cancel` sends SIGKILL to the group when the context ends, and `WaitDelay` (2 s) bounds the wait for its pipes. `TestCancelStopsProcess` checks that the pid is gone.

**The startup sweep is the safety net only**, for `kill -9`, OOM or power loss. `pdf.SweepTemp(dataDir)` removes every `pdf-*`, beside `transfer.SweepTemp`. `typstbin.SweepStale(os.TempDir())` removes every `rezepte-typst-*` dir of another version.

### Templates

**The Typst templates are the only design.** `templates/recipe.typ` (one recipe, page or card) and `templates/book.typ` (title page, clickable contents from `outline()`, each recipe on a new page) both call `recipe()` in `lib.typ`, which composes `head`, then `stacked-body` (the list above the steps: the card, or A4's long list) or `side-body` (A4's rail), then `foot`. Print, download, share and the PDF tab's preview all show what they render. Check a design change by rendering the fixtures as PNGs (`typst compile --format png` on a `prepare`d dir).

**The book's title page looks intentional with and without photos.** With photos, up to three covers fill the page down to the title block at its foot (`TestBookCollageFillsThePage`); without, the mascot stands as a seal over the title in the upper third (`TestBookTitlePlacement`, A4 and A5). A short structure rule, the count and the date follow. `instance.product` signs the foot over a hairline only when `instance.attribution` is on, as in the recipe footer (`TestBookSignatureNeedsAttribution`), and it is not the title already, so a book titled "Rezepte" never says it twice (`TestBookSignatureOnlyWhenNotTheTitle`).

**The contents double as a menu.** On A4 the list keeps the steps' solo measure, `measure-alone`, left-aligned, so the leaders stay short enough to follow to the folio (`TestContentsMeasure`). Each entry sets its title, dotted leaders and the folio on one baseline, and under the title the servings and total time as the card's meta set a little larger (`facts` and `meta-line` in `lib.typ`), so no new data field is needed. An entry finds its recipe with `recipe-at`, the same lookup the page header uses (`TestContentsShowServingsAndTime`, whose book fixture gives each recipe its own facts). The list stands a third down the free space of its page, so a short contents never floats at the top of an empty sheet, and a long one starts at the top and runs on (`TestContentsPlacement`).

**The sheet is made for a binder.** `geometry(card)` in `lib.typ` holds the page's numbers: a wide left margin as the punching gutter (no mirroring, home binders are one-sided), the content width, `cue` (one gap from the content to the running head's baseline and to the foot hint's cap height, so the two mirror each other across a page break), the QR size, the gap above the footer band, the photo's height and the type sizes per format. Beside `geometry()`, named values hold the A4 measure and rail (`measure-alone`, `rail`, `rail-gap`). Three rules only: `hairline` (facts row, card list rule, footer rule, and dotted the contents' leaders), `structure` (the card head's underline) and `rail-rule` (A4's ingredient rail), an ink rule lighter than the structure so it never outweighs the title from a distance.

**Two colors exist for paper only, as named values in `lib.typ`, not app tokens.** `rule`, the hairlines' color, is a tint dark enough that an office laser prints it solid instead of dithering it into dots. `text-ink` is a neutral near-black (R = G = B) for the small text, the steps, the ingredient rows and the footer's values, which drivers print with black toner alone, so small Karla stays sharp on a color device; display type, the facts' values, the contents and the structure rules keep the warm `ink`. `TestPrintColors` reads both from the PDF's content streams. Amounts in step text print in `amount`, a dark brown that stays dark gray on a mono printer.

**The steps hang their numbers.** Each number is right-aligned in a column of its own with a fixed gap before the text (`num-w`, `num-gap` in `geometry()`), so "9" and "12" share a right edge and the text edge never moves (`TestStepNumbersHang`). An ingredient named in a step is SemiBold and its amount regular in `amount`: bold and a medium amount turned a step dense with references into spots.

**One quantity and unit column per recipe.** `ingredient-columns` measures the widest quantity (bold) and unit (regular) across every group of the recipe, each plus its gap, and `recipe()` adds them to `g` (`qw`, `uw`), so every group, in the rail or in columns, shares one vertical for its units and one for its names, and a list of short units has no hole before the names (`TestIngredientColumnsPerRecipe`).

**Line heights are CSS-style line boxes.** `lh(h)` turns a `line-height` into Typst `top-edge`/`bottom-edge` from each font's ascender and descender, with zero leading and zero block spacing, so every gap is an explicit value. A step number's `top-edge` is the absolute distance to the text's first baseline, so number and text share it.

**A number keeps its unit.** `buildClientRecipe` puts a no-break space between a number and a word, a fraction glyph, `°` or `%` after it in notes, step text, amount hints and the description (`glueAmounts`), so the PDF never breaks "etwa 300 g", "1 ½ TL" or "180 °C". The no-break space is in `data.json`, so custom templates get it too, and the user docs say so.

**Ingredient names hyphenate, and nothing is clipped.** An ingredient's name is the one text that hyphenates: `hyphenate: true` in the cell of `group` in `lib.typ`, by the recipe's language, with the note set `hyphenate: false`, since Typst would split a short word ("gele-sen"). A word that hyphenation cannot fit breaks between any two letters: `fit` in `lib.typ`, which inserts zero-width spaces into a word only when `measure` at the cell's width comes back clamped to that width (an overflowing line). `TestIngredientNameHyphenates` (Paella's "Artischockenherzen, geviertelt" in three columns), `TestLongIngredientNameIsNeverClipped` hold it.

**User text is data, never markup.** Every user string is placed as `text(v)` or `[#v]`; nothing is `eval`ed, so a title such as `#set text(red) $x$` prints as typed (`TestMarkupIsLiteral`).

**Groups keep together up to 12 rows.** Quantities use tabular lining figures. An ingredient group of up to 12 rows never splits; a longer one flows on and repeats its name with `labels.continued` in a repeated grid header. The group's `<group-start>` marker rides in its first row, so a group moved whole to the next page does not read as continued there.

**Columns of groups balance by their set height.** `balance` in `lib.typ` measures each group at the column's width and finds the lowest height at which a column-major fill takes the columns, each as full as it gets; a group over 12 rows may be cut once between rows, its second part repeating the heading with `labels.continued`. The card and the A4 list-first layout share it. Typst's `columns()` would fill the first column instead of balancing, and counting rows misjudges groups whose notes wrap.

**Servings printed at another count say so.** When a recipe's `servings.value` differs from `servings.original`, A4's facts row sets `labels.scaledFrom` small and muted under the value and the card's meta adds `labels.scaledFromShort` in parentheses, each with `{n}` replaced by the recipe's own servings; the client keeps `{n}` in both labels for that (`TestScaledFromNote`). A sheet filed later then still tells that its amounts are for another count.

**The source prints as `source.display`**, which `buildClientRecipe` sets to the name, else the host of the URL (`host` drops `www.`), so the built-in and custom templates print the same; the schema describes it. The band's caption shows the host of the QR target (`host` in `lib.typ`), so no data field carries the instance's host. `labels` carry only what a template prints: the folio "x / y" needs none.

### Footer band and pagination

**The footer band is a constant height at the foot of the recipe's last page.** `foot-band` draws a hairline, 3 mm, then one bottom-aligned row: the source and "Added by" lines left, "Open recipe" and the host right, then the QR code, 3 mm apart. Every last line sets `bottom-edge: "baseline"`, so the text's baseline, the QR ink's bottom and the content's bottom edge are one line. A credit line is cut with "…" to the width its grid cell leaves (`fill-line`), a caption line to `caption-max`. With the footer off the band is the hairline and the source line; with no source either there is no band. `foot` puts it after `v(1fr)`, so one page or five, it ends on the content's bottom edge.

**The QR code is bare, and the page gives its quiet zone.** The SVG's view box is the modules alone, so the image is the ink at `g.qr` square, its right edge on the content's right edge. The 3 mm gaps above and beside it and the page margins below and right are the quiet zone: four modules are 2 to 3 mm at these sizes (a URL of up to 24 bytes, version 3, is the edge at 3.03 mm).

**The footer keeps with the last two steps.** The last step's unbreakable block holds room below itself for the gap and the band and, beside A4's rail, for the list where it runs on below the steps (the difference of their unbroken heights, at most `list-first`, see `side-body`). The second-to-last step is `sticky`, so the footer's page always holds the last two steps. When the room does not fit, both move on with the band. The band then backs up into the room, from `<body-end>` to the lower `<column-end>` on that page. With the list running on below up to three steps there is no room: the first step is sticky, and of three the second as well (as the second-to-last), so the room would carry the whole method, and with it the list beside it, off the list's page (R3); the band follows the list.

**The card's method moves on whole when it fits a page.** A zero-height `<method-start>` marker before the card's steps, after the weak space below the list, gives the space left on the page; the method (steps plus the footer's room) measured at the card's width either fits there, or fits a page and becomes one unbreakable block, or flows. The marker, not `here()`, keeps the decision stable. The first step is `sticky`, so with the sticky heading the first two steps never part. A book applies the same per recipe; each recipe still starts on a new page, with no right-hand forcing.

**Page furniture is read from markers, never from the body's flow.** The page header finds the recipe a page belongs to from the last `<recipe-page>` on or before it; from that recipe's second page on it prints "`<title> (cont.)`" with `labels.continued`, left on the content edge. The page footer prints `labels.nextPage` on every page before that recipe's `<recipe-end>` page. A book's header also prints the folio "x / y" from page 2 (the contents) on, continuous over the book, which is the number the contents list shows. Header and footer have a fixed height, so none of this moves the body and the layout converges.

**Pagination tests.** `<step>` labels carry each step's page, position and long flag. `checkPagination` in `templates_test.go` asserts the rules every recipe keeps: the last two steps share the footer's page, the method's first page holds two steps and, on A4, the method starts on the recipe's first page (`<recipe-page>`). The page-count tests hold real recipes from `testdata/` to their pages: Rinderrouladen one page on A4 and A5, Sauerbraten three on A4 with photo and footer, as its seventh step does not fit page 1 and the last two steps with the band do not fit page 2.

**Templates expose test labels.** `metadata` elements, each named after what it marks (`grep '#metadata' lib.typ`), let `templates_test.go` check content with `typst eval 'query(<label>)…' --in`, since Typst's SVG output draws glyphs as paths and holds no text. A query that prints any warning fails, which is how a layout that does not converge shows (Typst only warns). The layout markers `<recipe-page>`, `<recipe-end>`, `<group-start>`, `<column-end>`, `<body-end>` and `<method-start>` steer the layout itself; tests read some of them too.

## Why it is this way

Printing goes through the PDF so there is one implementation of the design. A browser print version needed a second one in HTML and CSS, kept in step by hand, and still broke in real print dialogs: CSS cannot target a recipe's last page, `vh` resolved against the window in Chrome's dialog, and Firefox started pages on descenders. Typst paginates, keeps the footer with the last steps and repeats a continued group's name on every engine alike, and the PDF tab's preview is the real page.

The PDF is typeset by Typst rather than by a headless browser: Typst is one static binary that ships inside the Go binary, starts in milliseconds and needs no cgo, while a browser would add hundreds of megabytes and a process to manage.

`printRoute` decides by engine and `pdfViewerEnabled`, measured in Playwright's Chromium, Firefox and WebKit, because no feature test tells whether `contentWindow.print()` on a PDF frame prints the PDF: it exists everywhere and fails silently or throws only when called.

`rsc.io/qr` encodes the footer QR code: a small, pure-Go, dependency-free encoder. A hand-rolled encoder (Reed-Solomon, masking, version selection) would be real work for no gain, and Typst QR packages would need a bundled package tree inside every template.

## Rejected

- **A browser print version** (`RecipePrint.svelte`, CSS pagination): a second implementation of the design that real print dialogs kept breaking ([Why it is this way](#why-it-is-this-way)).
- **A print stylesheet for File → Print**: the menu and the shortcut print the PDF; the browser's own menu prints the screen page, which is enough for the rare reader who takes it.
- **Printing a PDF frame in Firefox or Safari**: Firefox's viewer is cross-origin to the page and Safari prints the page around the frame.

## Limits

- Printing needs the server: offline, Print fails with the `share_pdf_failed` toast and prints nothing; with PDFs off, only the browser's own print is left, which prints the screen page.
- File → Print in the browser's menu prints the screen page, not the PDF.
- Outside desktop Chromium, Print opens the PDF in a tab or downloads it; the reader prints from there.
- Automated tests prove only that `print()` runs on the PDF frame (they stub it; a headless print has no dialog). That Chrome's and Edge's dialog shows the PDF, and that the frame window's `afterprint` fires after it, is checked by hand in real desktop Chrome and Edge; where `afterprint` does not fire, the frame stays until the next print or a reload.
- Beside A4's rail, a method of one or two long steps next to a list that runs on past the page (but not so far past the method that the list goes first) leaves the footer to follow the list, without the last steps.
- The footer always keeps the last two steps (R6); no recipe was found where keeping one would save a page.
- The public share page prints as it is.
