title: Notifications
description: The mails people can switch off - a new comment, the daily new recipes digest, an accepted invitation - their preferences, the signed unsubscribe link and the two pages

Rezepte mails three things a person may not want: a new comment on a recipe they follow, a daily digest of the recipes others added and, to admins and the owner, an invitation of theirs that was accepted. Each can be switched off in Settings → Notifications or from the link in the mail. The sender, the templates and the SMTP setup belong to [Email](/features/email); the fan-out, the preferences and the unsubscribe live in `service/internal/notify`. Password and address notices are security notices, not notifications, and nothing here reaches them.

## How it works

**Notification preferences.** `service/internal/notify` owns the switchable mails. A `Kind` (`comment` and `recipe` in `household`, `invite_accepted` in `admin`, in the order the settings show them) belongs to a `Group`; the values are stored and mailed, so they never change. `KindsFor(role)` gives the admin group only to admins and the owner. Every kind is on until the account opts out: `notification_optouts` holds a row per kind switched off, so a new kind needs no backfill. The flip side: a group switched off before a kind existed holds rows for its kinds of then only, so the new kind starts on even for that account. `Preferences` lists every kind the account may have; `SetPreferences` takes a partial map in one transaction and answers `ErrUnknownKind` (`422`) for a kind the account may not have; `Wants(userID, kind)` is the check before a send. The session's own switches are `GET`/`PUT /api/v1/auth/me/notifications`, session only.

**Notifications are decided in `notify`, sent by `mail`.** `notify.Mailer` is `Enabled`, `SendComment`, `SendRecipeDigest` and `SendInviteAccepted`; `mail.Comment`, `mail.RecipeDigest` and `mail.InviteAccepted` carry the recipient, the copy's facts, the locale and the `Unsubscribe` links. Each goes only to a confirmed address of an account that did not switch the kind off. The code is `service/internal/notify/fanout.go` and `digest.go`.

- **New comment.** `recipe.Service.AddComment` calls its `CommentNotifier` (`SetCommentNotifier`, nil is off) after the insert committed, so the REST handler and MCP `add_comment` both mail; the demo seed writes comments through the query and mails nothing. `notify.Service.CommentAdded` returns at once and runs `mailComment` in a goroutine on `context.WithoutCancel` with a 10 minute bound and a `recover` that logs, the `forgot-password` pattern. Each follower's send has a 15 second timeout of its own (`sendTimeout`), so a server that stalls for one follower costs that follower, not every one after them (`TestCommentMailStallCostsOneFollower`). `ListCommentMailRecipients` picks the followers, as the unread dot defines them: the recipe's `created_by` and everyone with a comment on it, never the author. One mail per follower and comment, in the follower's locale, saying whether the recipe is theirs or they commented on it ("is yours", not "you created": `created_by` may be an admin who inherited the recipes of an account they deleted); its button opens `/recipes/<slug>?tab=comments`. The comment's photos ride along inline, loaded once per comment and not per follower ([Email](/features/email)). The author's circle shows their picture when they have one: `picture` reads the file through `avatar.Service.Open` and `mail.Comment.AuthorAvatar` carries it into the mail (see [Email](/features/email) for the inline part); an unreadable file is logged and the mail falls back to the initial. Without a picture the circle inlines the light `--color-user-*` pair from `app.css` (`userColors` in `mail/notifications.go`), since a mail cannot read the stylesheet. Mail off stops the loop quietly; a refused send is logged by `deliver`, any other failure by `mail.LogUnsent` (user ID, never the address; also for the invitation mail and the security notices), and the next follower still gets theirs.
- **New recipes digest.** Once a day the household hears of the recipes others added, as one mail (see [Email](/features/email) for its layout). A recipe is queued by `recipes.announce_pending`, which only `recipe.Service.CreateAnnounced` sets, in the create's own insert: the HTTP create (the form and URL/text import) and MCP `create_recipe` call it, archive import and the demo seed call `Create` and never queue (`TestDigestIgnoresUnannounced`; see [Recipes](/features/recipes)). `notify.Service.StartRecipeDigest` (started in `main.go` beside the sweep loops) ticks once a minute (`digestTick`) and calls `RunRecipeDigest(ctx, time.Now())`, logging an error and recovering a panic per tick; the channel it returns closes once it has stopped. A run does nothing with mail off, so nothing is claimed and the run happens once mail is on (`TestDigestMailOffClaimsNothing`); it does nothing before the owner's hour (`instance_settings.recipe_digest_hour`, default 17, in `time.Local` from `TZ`, set on Settings → Mail) or when `recipe_digest_last_day` already holds today's local date. Otherwise one transaction claims the day (`ClaimRecipeDigestDay` must change one row, so two ticks or a restart cannot run twice), takes every queued recipe created more than an hour ago (`ListDueAnnouncements`; a younger one stays queued for the next day, a deleted one is gone) and clears their flag. A day missed entirely sends nothing extra; its recipes join the next run. An hour moved earlier after the day's run waits for tomorrow (`TestDigestRunsOncePerDay`). `ListRecipeDigestRecipients` (confirmed address, `recipe` not switched off; the group link switches off each kind) is read before the claim, so its failure leaves the day unclaimed. After the commit the run detaches from its context (`context.WithoutCancel`), so a shutdown does not cut it short (`TestDigestOutlivesItsContext`): `main.go` waits for that channel after the server stopped, at most `digestShutdownWait` (2 minutes, so a hung SMTP server cannot hold the exit; `TestDigestStopWaitsForTheRun`), and a creator that cannot be read is logged and named a former member rather than ending the run (`TestDigestSurvivesACreatorLookupFailure`). Each recipient gets, with `sendTimeout`, the recipes others created in creation order; whoever is left with none gets no mail (`TestDigestSkipsOwnRecipes`). Each recipe carries its cover read from `_thumb.jpg` through `image.MailPhoto` (unreadable: logged, a card without photo, `TestDigestMissingPhoto`) and its creator's name, color and picture; a creator whose account is gone has an empty name, which the mail shows as a former member.
- **Invitation accepted.** `notify.Service.InviteAccepted` is the `auth.Notifier` (`sessions.SetNotifier` in `main.go`): synchronous, one mail to the admin who issued the setup link, naming the newcomer's display name and username, with a button to `/settings/users`. Skipped when the inviter is the newcomer, is gone, is no longer admin or owner, has no confirmed address, or switched `invite_accepted` off.

**Unsubscribing needs no session.** `Service.UnsubscribeLinks(userID, kind)` returns the `mail.Unsubscribe` a mail carries: `/unsubscribe?u&k&s` for the page, the same with `&scope=group`, and `/api/v1/unsubscribe/one-click?u&k&s` for `List-Unsubscribe`. `s` is a `sign` token over `userID:kind` under the label `rezepte unsubscribe`, for 90 days, keyed by `instance_settings.link_preview_key` (`settings.Service.LinkPreviewKey`): one instance key, and the label keeps a link preview token from verifying as an unsubscribe token or the other way round. The token is checked with `Signer.Verify` before anything is read; a forged or expired token, or one naming an account that is gone or a kind its role no longer has, answers `410` alike (`httpserver.PublicError`). `GET /api/v1/unsubscribe` changes nothing and answers the username, the address masked by `mail.MaskAddress` (an old link may sit in the mailbox the account left, so it never learns the new address), kind, group, both states and `groupKinds`, each kind of the group the account may have with its state; `POST /api/v1/unsubscribe {u, k, s, scope, subscribed, kinds?}` switches the kind or every kind of its group the account may have, and `subscribed: true` is the undo. With the group scope, `kinds` limits the switch to those kinds (a kind outside the group is `422`), so an undo turns back on only what the click turned off (`TestUnsubscribeGroupUndoRestoresOnlyNamedKinds`). The one-click route is `POST` only, so a scanner following the address with `GET` unsubscribes nobody. It never reads the body: RFC 8058 asks for `List-Unsubscribe=One-Click` as multipart form data, many senders post it urlencoded, and huma would make a declared raw body required, so the signed address alone decides (`TestOneClickOptsOutKindOnly` posts all three, empty included); it switches off that kind only and answers `200` with no body. The token reaches only `u`'s preferences and never signs anybody in. It is not bound to the address it went to: whoever reads that mailbox can switch the account's notification preferences for the link's 90 days, even after the account changed its address; security notices it cannot touch.

**The two pages.** Settings → Notifications (`frontend/src/routes/settings/notifications/`, `NotificationsCard.svelte`) is every member's, in "For you" right after Profile, since the address it writes to lives there. It names the address and links to the profile; without a confirmed address it shows only a line linking there, because nothing would arrive. It draws one block per group the account has a kind of (`KIND_GROUP` in `frontend/src/lib/api/notifications.ts` mirrors the server's grouping) with a switch for the group, on when all its kinds are, and one per kind, then a Security block marked "always" with no switch. A flip `PUT`s at once and snaps back with a toast when it fails. With `mailEnabled` off a line says nothing goes out yet, also beside the unconfirmed hint, since confirming takes a mail too; the switches stay, since a preference outlives the mail setup. `/unsubscribe` (`frontend/src/routes/unsubscribe/`) is in `authPages`, so it opens bare and without a session. Its `load` only `GET`s, so a scanner opening the link changes nothing; the buttons post the link's kind and its group, the one the mail's link named (`scope=group` or not) first as the primary, and only what is still on is offered: the kind button while the kind is on, the group button while any kind of the group is. With nothing left the page says "Already unsubscribed" and offers nothing to click. The answer to a click shows "Unsubscribed" with an Undo that posts `subscribed: true` with the kinds that were on before the click, so it never turns on a kind the person had off. A `410` (or a `422` for a link missing its parameters) shows "This link no longer works". Every state links to Settings → Notifications; signed out, the root layout's login redirect carries it as `next`. The shell for `/unsubscribe` gets `Referrer-Policy: no-referrer` and `noindex` like `/s/…` (`share.ShellHeaders`), since the token is in its address.

## Why it is this way

- **Opt-outs, not opt-ins.** Notifications are on by default, so only the exceptions are stored and a new kind needs no backfill.
- **A signed link, not a token table.** It needs no row and no sweep; the cost is that a link cannot be revoked before its 90 days, and it can only switch mails.
- **Decided in `notify`, sent by `mail`.** The rules of who is told stay out of the sender, which knows only how to build and deliver a letter.

## Rejected

- **A row per kind and account.** It would need a backfill for every new kind.
- **Unsubscribing on `GET`.** Mail scanners follow links; only a `POST` changes anything.

## Limits

- One mail per comment: three comments in a row are three mails; only new recipes are batched, into the daily digest. A comment digest is on the [Roadmap](/roadmap).
- The digest's claim commits before its mails go out: only a crash mid-run, mail switched off mid-run (logged with the number left unsent) or a run outlasting the shutdown wait (logged; also the container runtime's own stop timeout, which kills the process first when shorter; the shipped `docker-compose.yaml` sets `stop_grace_period: 2m30s` and the `docker run` line `--stop-timeout 150` for that) loses that day's remaining digests rather than sending any twice (at most once, never twice; the `ponytail:` mark on `claimRecipeDigest`). One send time for the whole instance, by the hour.
- Only a confirmed address is mailed.
- No token or identity mails are kinds: setup links, resets, confirmations and security notices cannot be switched off.
- No outbox, no retry: a failed send is logged and the next recipient still gets theirs.
