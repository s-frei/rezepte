---
title: Languages
description: The two interface languages, where the choice lives, and how it reaches the browser
---

Rezepte's interface exists in English and German. `en` is the base locale - the one a string falls back to if nothing else applies - and it is also the instance default: an operator who sets nothing gets an English instance. Every account carries its own choice, so two people signed into the same instance can each read the app in a different language.

## How it works

**The set of languages is written down once, in `service/internal/i18n/locales.json`**: `{"baseLocale": "en", "locales": ["en", "de"]}`, and nothing else. Both sides read that file.

- **Go** embeds it in `service/internal/i18n`, which parses it once. `user.Locales` and `user.BaseLocale` in `service/internal/user/profile.go` are derived from it, and `ParseLocale` accepts exactly that set.
- **The frontend** generates Paraglide's inlang settings from it. `frontend/vite.config.ts` calls `writeInlangSettings` (`frontend/scripts/inlang-settings.ts`) before it hands `./project.inlang` to `paraglideVitePlugin`, so every vite run - dev, build, vitest - compiles against the current list. The rest of the settings - the plugin modules, the `pathPattern` onto the catalogs in `frontend/messages/` - is frontend build configuration and is written down in that script. The generated `project.inlang` directory is gitignored.

The file sits in the Go module because `go:embed` cannot leave it, and a symlink from there into `frontend/` does not help: `go:embed` refuses symlinks as irregular files. It holds only the languages, so the frontend's build configuration does not move into the service. Being source rather than build output, it is what `go test`, `//service:dev` and the OpenAPI export see without building the frontend first.

The database does not repeat the set: the `locale` column is `TEXT NOT NULL` with no `CHECK`, and `ParseLocale` guards every write - account creation, the profile PATCH and `REZEPTE_LOCALE` at startup. A `CHECK` would be a second list, and adding a language would then take a migration. `service/internal/i18n/i18n_test.go` checks that the file parses, that `baseLocale` is one of `locales`, and that every locale has a catalog in `frontend/messages/`: Paraglide would compile a locale without one and fall back to English for every message. Tests that need a locale the app does not have use `xx`, which no language will ever claim.

Everything else derives from that file. The API's enum comes from `user.Locales` through `Locale.Schema` (huma's `SchemaProvider`), so no request or response field carries an `enum:"..."` tag of its own. The frontend's `Locale` type is Paraglide's, re-exported by `frontend/src/lib/api/auth.ts`. The language picker's entries come from Paraglide's `locales` and are named by `Intl.DisplayNames` in `frontend/src/lib/i18n/languages.ts`, so no catalog holds a language's name. The sample recipes are matched by filename (`//go:embed testdata/recipes.*.json`), so a set is added by dropping a file in, and a language without one seeds the English set. And `frontend/messages/*.json` hold the same keys as each other, enforced by `frontend/scripts/message-parity.ts` in `mise run check`.

**Every account has a `locale` in the `users` table**, `NOT NULL` like `role` and `color` beside it. `REZEPTE_LOCALE` (default `en`) sets `user.Service`'s `defaultLocale`, which a new account gets when nothing more specific is given: `POST /api/v1/users` accepts an optional `locale` field that overrides it for one new member, and the instance owner created at startup always gets it. `REZEPTE_LOCALE` also selects which demo fixture `--demo` seeds, falling back to English for a language without its own - see [Demo mode](/features/demo-mode).

**Changing it afterwards is self-service.** `PATCH /api/v1/auth/me/profile` accepts `locale` alongside `displayName` and `color`, and only ever targets the caller's own row - the admin-only `PATCH /api/v1/users/{id}` has no `locale` field in its body at all, the same way a rename is the owner's alone (`user.CanEditProfile`). Nobody but the account holder can change what language their own screen renders in.

**The Go service writes a `PARAGLIDE_LOCALE` cookie so the SPA can resolve a locale before it renders anything.** `auth.localeCookie` sets it on login and, unconditionally, on every call to `PATCH /api/v1/auth/me/profile` that succeeds - not only one that changes the locale - always from the just-loaded `users` row; `auth.expiredLocaleCookie` clears it on logout. The cookie is deliberately not `HttpOnly` - Paraglide's cookie strategy reads it from JavaScript, and it carries a display preference, nothing a session could be hijacked with.

**Paraglide resolves a locale by trying three strategies in order: `cookie`, `preferredLanguage`, `baseLocale`.** Signed in, the cookie above wins, so the account's own choice is what renders regardless of the browser. Signed out - the login screen - there is no cookie yet, so the browser's own language (`preferredLanguage`, read from `navigator.languages`) decides; a browser reporting a language this app doesn't have falls through to `baseLocale`, which is `en`. `<html lang>` is kept in step with whichever locale actually rendered by a `$effect` in the root layout that reads `getLocale()`. The cookie is not reactive, so the effect also reads `session.user`: login and sign-out change the cookie without a reload and set `session.user` right after, which re-runs it; every other locale change reloads the page.

**The SPA reconciles the cookie against the row on every session load.** `adoptAccountLocale` in `frontend/src/lib/auth.svelte.ts` compares the `locale` that `GET /auth/me` just returned with Paraglide's `getLocale()`, and calls `setLocale` when they differ; the root `+layout.ts` load is its only caller, right after it assigns `session.user`. Without it a device that signed in before the language was changed on another one would keep rendering the old language for a year, the cookie's `MaxAge`. The reload is left to `setLocale`'s own default here, unlike in `LanguageControl.svelte`, where the PATCH response has already installed the new cookie and Paraglide therefore sees no change to reload for. It cannot loop: `setLocale` writes the cookie before it reloads, `cookie` is the first strategy, and the row is untouched, so the comparison after the reload comes out equal.

**Both Playwright suites run in English, and each pins it against a developer's own `REZEPTE_LOCALE`.** `mise/tasks/e2e.sh` starts its instance with `REZEPTE_LOCALE=en` set directly in the binary's environment, after mise has applied its config, and `frontend/e2e/helpers.ts` pins the `PARAGLIDE_LOCALE` cookie to English before every login. `docs/user/screenshots` is pinned by `RZP_DEMO_LOCALE = "en"` on the `//docs/user:screenshots` and `screenshots:check` tasks, which `mise/tasks/demo.sh` prefers over `REZEPTE_LOCALE`. Setting `REZEPTE_LOCALE` on those tasks would not hold: the nested demo task (`mise/tasks/demo.sh`) applies the config env again, so a `REZEPTE_LOCALE` from a developer's `mise.local.toml` would win. That way a developer who wants a German `mise run demo` still gets an English suite and English pictures (see [Add a screenshot](/howtos/add-screenshot)).

German is covered where it is the subject, not by running everything twice. `frontend/e2e/locale.test.ts` creates German accounts and checks the German UI, the `<html lang>` switch and the decimal comma. Recipe content is English too (`loadFixture` in `helpers.ts` reads `recipes.en.json`), except in the tests about German text: the umlaut-tolerant search and the page-width sweep, whose long compound word sets the layout's floor. They ask for `loadFixture(index, 'de')` and say why.

## Why it is this way

The cookie exists because Paraglide has to pick a locale before the first paint, and the account's language lives in the database behind an API call the SPA cannot wait for. A cookie sent with the very first request closes that gap; a `PARAGLIDE_LOCALE=de` on the wire is all Paraglide needs to render the right strings on the first render, with no flash of the wrong language and no second render once `/auth/me` comes back.

It is not `HttpOnly` because Paraglide's cookie strategy is client-side: the generated runtime reads `document.cookie` directly to resolve and to change the active locale. An `HttpOnly` cookie would be invisible to exactly the code that needs to read it, defeating the reason it exists.

The `users` row, not the cookie, is the source of truth, because a cookie is scoped to one browser and a language choice is not: signing in from a second device or a fresh browser profile has no cookie to read, and a person still expects their own language. The service always writes the cookie from the row it just loaded, never the other way around, so the cookie can be deleted, forged to a supported value, or simply absent, and the next authenticated request still resolves to what the account actually has stored.

`REZEPTE_LOCALE` decides the *default*, not a ceiling: it is read once, at account-creation time (startup for the instance owner, `POST /api/v1/users` for everyone else unless that call names a `locale` of its own), and never again. An instance run with `REZEPTE_LOCALE=de` still lets any member switch to English in their own settings; the variable only ever answers "what does a brand new account start as."

In practice the API's fallback to `REZEPTE_LOCALE` is what the seed and a bare `POST /api/v1/users` use, because the create-member dialog always names a locale: `CreateUserDialog.svelte` seeds its picker from `getLocale()`, the language the admin filling the form is reading. A household sets up accounts in the language it speaks, whatever the instance was installed with, and the new member can change it afterwards - it is the one profile field an admin cannot reach once the account exists.

## Rejected

- **URL-prefixed locales (`/en/…`, `/de/…`).** Every route would need a language segment threaded through routing, links and the SvelteKit config for a choice that is a per-account preference, not a per-page one - two people looking at the same recipe URL want their own language, not a language baked into the link. The cookie strategy gives that without touching a single route.
- **An instance-wide language with no per-account choice.** `REZEPTE_LOCALE` could have been the only knob, with every account stuck in whatever the operator picked at install time. A household is not one person, and the whole point of a per-account `locale` column is that it does not have to be.

## Limits

- Recipe content itself is never translated by this feature, in either direction: an instance seeded in German and one seeded in English hold two different sets of sample recipes, not the same recipes in two languages, and nothing translates a recipe a real user writes.
- The login screen's language follows the browser, not any account - there is no account to read a cookie from yet. A shared machine's login screen shows whatever the browser is configured for, not the language the next person to sign in will actually get once they are in.
