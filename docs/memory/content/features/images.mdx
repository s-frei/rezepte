Recipes carry photos: a cover on the card, a gallery on the detail page and a lightbox over it, uploaded from the phone that took them. The service renders every upload into three JPEGs on disk and serves them as plain files. [Data model](/architecture/data-model) owns the `images` table; [HTTP API](/architecture/api) owns the endpoints and their status codes.

<Callout type="warn" title="Traps">

- The editor's photo requests must go one at a time through `serial`: an order request racing an upload or delete names the wrong set and is refused ([The editor's photos](#the-editors-photos)).
- Reordering never uses svelte-dnd-action: it removes its dragged element while Svelte reuses it by key, and every drag deleted a tile.
- An overhang past the right edge for one layout lowers Chrome's mobile scroll for good; the app root keeps `overflow-x: clip`, not `hidden`.
- A mouse swipe in the lightbox without `select-none` leaves a selection that cancels the next swipe, and only Linux and Windows Chromium show it.
- A huma schema name is global: two exported types named `List` panic at registration ([The cover](#the-cover-and-step-links)).
- Any new multipart endpoint needs both `MaxBodyBytes` and `LimitUpload` ([Limits](#limits)).

</Callout>

## How it works

### Rendering and storage

**Three JPEG variants, rendered once on write.** `service/internal/image/process.go` writes `<id>.jpg` (longest side at most 2400 px, JPEG quality 90), `<id>_detail.jpg` (1600 px, quality 85) and `<id>_thumb.jpg` (960 px, quality 80), in that order; the first is also the source the other two scale from, and its dimensions are what the `images` row stores. Nothing is resized on request: `thumb` serves the recipe card, the gallery's thumbnail row, the lightbox's strip and the editor's image tiles; `detail` the gallery's main image; `original` the lightbox's own image and its download link. A mail's photo is the one thing made on the fly: `image.MailPhoto` (`mail.go`) scales a `_thumb.jpg` to at most 800 px wide at quality 72 for the new recipes digest ([Email](/features/email)), and writes nothing to disk.

**Decoding.** JPEG and PNG come from the standard library, WebP from `golang.org/x/image/webp`; only those three formats are accepted, and the format is the one `image.DecodeConfig` reports from the bytes, not the one the client declared. Scaling runs through `golang.org/x/image/draw` with Catmull-Rom filtering onto a white background, so transparent areas of a PNG or WebP come out white rather than black in a format that has no alpha channel.

**EXIF orientation is applied, not preserved.** `service/internal/image/exif.go` walks a JPEG's segment headers — no image data — as far as the first APP1 segment, reads the TIFF header and IFD0, and returns the Orientation tag (`0x0112`, type SHORT), defaulting to 1 for anything missing or malformed. `applyOrientation` then redraws the pixels for orientations 2 through 8, the last four of which swap width and height. Only the JPEG path does this, and it does it after the first downscale to 2400 px, because the two operations commute and a per-pixel loop over 2400 px costs far less than over 12000 px. The variants carry no metadata at all.

**Storage layout.** Files live under `<REZEPTE_DATA_DIR>/images/<recipeId>/`, beside the SQLite database rather than inside it. Each variant is encoded to a `.tmp` sibling and renamed into place, so a reader never sees a partial file; if any variant fails, the ones already written are removed again. Directories are created `0700` and files `0600` — this process is the only reader, since it serves the bytes itself. When the database write of an upload fails, `removeFiles` deletes the variants that the render step already produced, so no orphaned files survive a rolled-back transaction. Deleting a recipe removes its whole directory after the transaction commits, through the image directory `recipe.NewService` is given.

**Limits and where each is enforced.**

| Limit | Enforced by |
|---|---|
| upload at most 10 MiB | `LimitUpload` in `service/internal/image/handler.go` answers `413` on a declared `Content-Length` above the cap and wraps the body in `http.MaxBytesReader`; `Upload` reads at most the cap plus one byte as a backstop |
| JPEG, PNG or WebP | huma validates the multipart part's declared content type before the handler runs; `decode` then judges the bytes themselves, and the format it refuses comes back as `415` |
| 64 to 12000 px per side, at most 60 megapixels | `decode` reads them from `image.DecodeConfig`, so an oversized image is rejected from its header before its pixels are allocated |
| 20 images per recipe | `Upload` counts once before decoding and again inside the write transaction, which closes the race between two concurrent uploads on the same recipe |
| 2 uploads decoding at a time | a counting semaphore around the decode-and-resize step in `service/internal/image/service.go`; a decoded image plus its resize target dominate the memory cost of an upload, so this bounds peak memory however many clients upload at once. A client that gives up while queued releases its place through the request context |

### Gallery and lightbox

**Thumbnail rows scroll, center only while they fit, and fade at the hidden side.** The gallery's thumbnail row (`ImageGallery.svelte`, desktop) and the lightbox's strip (`Lightbox.svelte`) wrap their scroller in `ScrollFade.svelte`. The strip centers with `justify-center-safe`: plain `justify-center` on an overflowing row pushes the first thumbnails past the left edge, where no scroll reaches. The active thumbnail's outline sits outside the button, so a row needs padding as wide as outline plus offset on every side, or `overflow-x-auto` clips it. The fades are gradient overlays in the background color, shown per side only while pictures hide there: a `mask-*` would fade the scrollbar too, and fading padding instead widens the row past the cover.

**A picture swap waits for the next picture, then crosses over.** The desktop cover and the lightbox both keep the shown picture's id apart from the picked one (`shownId`) and move it only once `decoded()` (`#lib/images/decoded.ts`) has the next rendition decoded, so a crossfade never fades through an empty frame; the thumbnail's outline and the counter move at once. The cover fades the new picture in over the old, which stays opaque under it, since two pictures fading together dip to the page color: that is an outro with an easing of `() => 0`, because Svelte runs an outro from 1 down by the eased progress and `() => 1` hid it at once. The lightbox slides both the way the reader went (the wrap from the last picture still counts as forward), and only fades under reduced motion. The cover's button keeps the one `data-cover` the [page transition](/architecture/design-system#patterns-in-feature-components) names.

**The lightbox's swipe area selects nothing.** The swipe is plain pointer events on the `role="group"` area (`swipeDirection` in `#lib/recipe/swipe.ts`), and the dialog is text-selectable, so without `select-none` a mouse swipe leaves a selection behind; the next press inside a selection starts dragging it, that drag's `pointercancel` reaches `cancelSwipe`, and the swipe is lost. Chromium starts that drag on the first move on Linux and Windows but not on macOS in Playwright, so the swipe e2e test asserts that a swipe leaves no selection, which fails everywhere. The area also carries `touch-pan-y touch-pinch-zoom`: left at `auto`, a phone takes a finger's horizontal pan itself and cancels the pointer, so the swipe test runs on the mobile project with real touches ([Verify UI](/howtos/verify-ui#what-playwright-cannot-do); [Cooking](/features/cooking) has the same trap).

**The lightbox is the one dialog that locks the page's scroll everywhere.** Every other dialog follows the rule in [Sheets](/architecture/design-system#sheets). The lightbox covers the whole screen, so no jump from the lock can be seen, while without it the page's scrollbar stayed visible at its right edge (classic scrollbars) and the wheel scrolled the recipe behind the photo. The lock leaves the page's `scrollbar-gutter: stable` room empty, and `inset-0`, `100vw` and `100%` all stop short of it, so the lightbox sets its width from `innerWidth` (`<svelte:window bind:innerWidth>`), the one measure that counts the gutter. Dropping the gutter while the lightbox is open instead reflows the page under the fading overlay, on open and again on close. `e2e/lightbox-window.test.ts` covers width and a steady page; it has a file of its own because it needs classic scrollbars (`--hide-scrollbars` off, which launch options allow only per file).

### The editor's photos

**The editor's photos are one grid, and the order is the cover.** `ImagesSection.svelte` lays the photos out as square tiles; the first is the larger cover tile, and the add tile is the last cell, gone at 20. There is no cover state in the UI: "Make cover" moves a photo to position 0 and saves the order, which the server turns into the cover ([The cover](#the-cover-and-step-links)). Each tile has a ⋯ menu (Bits UI `DropdownMenu`), a tap on the photo opens the `Lightbox`, and the whole section card is the file drop target (`data-dropping` on the `<section>`). Paste (Cmd/Ctrl+V) of image files goes through the same `addFiles` as a drop; the listener is on the window while the editor is mounted, skipping text fields, because Safari focuses no button on click and the focus is often on the page itself.

**Reordering is `#lib/sortable`, not svelte-dnd-action.** The shared sortable (also the diary's photos and the comment collage, see [Recipe comments](/features/recipe-comments)) lifts a tile by long-press on touch and by a short press or a small move under a mouse; the caller's `onmove` only updates its list, and the sortable runs it inside `flip` (`#lib/sortable/flip.ts`) so the others slide. Held near the window's top or bottom edge, the page scrolls, and each scroll picks the slot now under the pointer, so a photo reaches places off screen on a phone. The held tile keeps the size it was picked up at, even over the cover slot; the collage passes `faceFollowsSlot` instead. The press and lift thresholds are in the comments of `sortable.svelte.ts`.

- **A click opens the lightbox only before the lift.** A release after it, moved or not, puts the tile down and its click is swallowed. Chrome sends no click at all after a mouse drag that ends over another slot, since the pressed node moved, but does after a release within the tile's own slot, so a test covers both.
- **Alt+Arrow moves a photo one place,** Left and Up earlier, Right and Down later: with the larger cover tile a row step lands nowhere a reader expects. The sortable keeps every Alt+Arrow on an item from the browser, moving or not, since Alt+Left is Back on Windows and Linux. After `onmove` it reads where the item really went: the editor stops a photo at the last stored tile, so a key move that went nowhere is neither announced nor saved. A menu move takes the same slide.
- **The ⋯ trigger carries `data-sortable-ignore`,** or a press that moved a little, or a long-press, lifted the tile under the opening menu.
- **A finger-lifted tile lets pointers through** (`pointer-events: none`); a mouse-held one keeps them for its `grabbing` cursor, and the sortable skips it when it looks under the pointer (`elementsFromPoint`).

**Three drag traps on a phone**, each found by measuring frame by frame on a real Android phone:

- **An overhang widens Chrome's mobile layout viewport.** Anything past the right edge for even one layout grows it, and at the page's end Chrome lowers the scroll to fit and leaves it lowered, so the rest of the drag landed on other cells. The app root `[data-app]` carries `overflow-x: clip` (`+layout.svelte`): `clip`, not `hidden`, makes no scroll container, so sticky headers and bars keep sticking, and clipping `html` or `body` does not stop it. The sortable also places the held face over its new slot in `flip`'s `after` hook, before anything is measured; placed later, the first measurement laid it out past the edge.
- **The hit test sees a neighbor where it slides, not where it rests,** so with `elementFromPoint` a sliding neighbor counted as the target and two photos traded places back and forth on a diagonal drag. The sortable picks the target from the items' layout offsets (`offsetLeft`/`offsetTop`, which ignore transforms), made screen coordinates through the held slot, which never slides; the order changes once per slot entered.
- **Chrome's own long-press lands behind a finger-lifted tile,** selecting the nearest word and ending the drag. From the press to the release the sortable prevents `selectstart` and `contextmenu` on its list and clears any selection on the lift; the photos carry `draggable="false"` and `-webkit-user-drag: none`.

**Testing a drag.** `e2e/images.test.ts` ("at the end of the page") and the composer drags in `e2e/kitchen-diary.test.ts` record every frame's scroll and each order change on both projects. A test that lets go of a photo near the window's edge lets go inside the scroll band, where the page scrolls every frame until the release lands, so "a photo held at the window's bottom edge" drops over the slot's middle, not its top. Only `longPress` (`e2e/helpers.ts`, [Verify UI](/howtos/verify-ui#what-playwright-cannot-do)) triggers Chrome's long-press; it cannot move while it holds, so no emulated test covers a long-press and a drag in one gesture, and the two long-press tests guard on a Mac and not in CI.

**Tiles are keyed by `key`, and nothing else touches their DOM.** `key` is the image id for a stored photo and a local id for a new file, and it stays when the upload lands and `id` turns into the server's, so the tile keeps its element and its photo does not blank. The sortable and `flip` only read the items and set transforms; Svelte alone inserts and moves them. svelte-dnd-action broke exactly that: it removed its dragged element on drop while Svelte reused it, keyed by `key`, as the shadow placeholder, so every drag deleted a tile and saved the old order. A new tile scales in only when its key is in `fresh`, which `addFiles` fills; the intro is `|global`, because the first photo creates the whole list with it.

**Photo requests of one editor go one at a time.** The order request must name every photo the server holds, so an upload or delete landing while it was on the way made the server refuse it. `serial` in `ImagesSection` queues uploads, deletes and order saves, and each job commits its own change to `tiles` (the landed upload, the deleted photo, the saved order) before the next one starts, so the queue does not lean on microtask order. An order save reads the tiles when its turn comes and names what the server holds by then, a pending delete included (last). Uploads join one by one through their own chain, so a move waits for the upload in flight, not for the whole batch. A refused order puts the tiles back in the last order the server accepted (`savedKeys`, which a landed upload extends, since the server appends it). A `422` means the server holds other photos than the request named - another member added or removed one - so `savedKeys` is stale too: the section reloads the recipe (`getRecipe`) through the queue and shows the server's photos in its order, keeping its own tiles for the photos it knows and its uploading and failed tiles at the end, with the same error toast; if that reload fails too, the tiles go back to `savedKeys` like any refused order, with no second toast. The e2e test "shows what the server holds when another member changed the photos" covers it. The e2e test "keeps a photo that finished uploading during a reorder" fails without the queue.

**Upload state per tile.** An uploading tile shows its local preview under `ProgressRing.svelte` (the comment composer's too), fed by `uploadImage`'s `onProgress`. A failed upload stays where it is (`state: 'failed'`), marked in `destructive`; the whole tile is the retry button, its ⋯ offers retry and remove, and `retry` puts it back on the upload chain. Stored tiles stay a prefix: an upload that lands moves ahead of a failed tile still waiting, because the server appended it after the photos it holds.

**A removal waits for its undo toast.** Remove takes the tile off the screen at once and parks it in `pendingDeletes` behind a sonner toast with an undo action; the `DELETE` goes out when the toast closes (`onAutoClose`/`onDismiss`), when the editor unmounts, or - past the queue and with `keepalive` - when the page unloads (`beforeNavigate` with `willUnload`). A pending delete still counts against the 20-photo limit, because the server still holds it. A failed upload is removed at once, with nothing to undo.

- **A flushed tile stays in `pendingDeletes`** (marked in `deleting`, which also blocks a second flush and the undo) until its queued `DELETE` has been answered, so an order request queued ahead of it still names it; dropped at flush time, such a request left out a photo the server still held and was refused.
- **Undo puts the tile back at its index,** on its side of the stored prefix, and saves the order if moves were made meanwhile. A refused `DELETE` puts the tile back at its rank in `savedKeys`, where the server still keeps it, so the cover badge stays on the server's cover.
- **Save awaits the section's `settle()`** (the upload chain and the queue, no deletes) before it builds the payload, so a step's photo link names an uploaded photo by its new id and a removed one not at all, and the full `flush()` only after the save went through, so a refused save leaves a removal undoable ([Step photos](/features/step-photos)).
- **Cancel and Discard await `flush()` before `goto`.** `flush()` sends every pending delete, then settles: otherwise the next page's `load` ran before the unmount flushed them and still showed the removed photo, and a photo still going up was cut off. Waiting for `lock` alone is not enough: an upload enters the queue only when the chain reaches it ("leaving the editor waits for the photos still going up" fails without `await chain`). A Cancel that the discard dialog stops flushes only on Discard, so staying keeps the undo.

### Account pictures

**An account picture is one square, 320 px.** `RenderAvatar` in `service/internal/image/avatar.go` decodes the upload exactly as a recipe photo is decoded - same formats, limits, orientation and decode slots, so an avatar upload and a photo upload share the two-slot bound - crops it, scales the square to at most 320 px (Catmull-Rom, JPEG quality 85) and writes one file through a `.tmp` sibling, directory `0700`, file `0600`. There is one variant because the largest circle is the 96 px profile photo, 288 px on a 3x screen, and the 20 px circles lose nothing by the same file. [Users and authentication](/features/users-and-auth) owns where the file lives and who may replace it.

**The crop is fractions of the upright image.** The `crop` query parameter is `x,y,size` (`ParseCrop`): `x` and `y` place the square's top-left corner against the image's width and height, `size` is its side against the shorter side, all within 0 to 1 and `size` above 0. Fractions rather than pixels, because the browser shows the camera's original and the service decodes after its first downscale to 2400 px (JPEG) and after orientation, so only a fraction means the same square in both. `cropRect` turns it into pixels of the image the service decoded: a square that reaches past an edge by at most half a pixel, which is the browser's rounding, is pulled back inside, one that reaches further is refused, and so is one smaller than 64 px - measured on the decoded image, not on the camera's original pixels. All three refusals are `ErrBadCrop`, a `422`. Without the parameter the centered square over the shorter side is used. A value that is not three numbers in range is the same `422`.

### The cover and step links

**Deleting a photo drops its step links.** `step_photos.image_id` cascades from `images`, so a photo linked to a phrase of a step ([Data model](/architecture/data-model)) takes only the link with it; the step's text is untouched and the next save of the recipe needs no cleanup. Reordering never touches the links, which name the image id.

**The cover.** `recipes.cover_image_id` is always the recipe's first image, the one with the lowest `position` (NULL when the recipe has none), and the column stays only so a card listing needs no join. Every write keeps the two equal: the first upload onto an empty recipe sets it, delete moves it to the first remaining image, reorder sets it to the first id of the list, and the set-cover endpoint moves the chosen image to position 0 (the others shift down) and refuses an image that does not belong to the recipe. Migration `0022_cover_first` renumbered existing recipes that had a cover further back, and gave a recipe with photos but no cover its first photo by position (positions of old data need not start at 0). Positions stay a compact `0..n-1` permutation: delete renumbers what is left, and reorder requires a list naming every image of the recipe exactly once. Any of these writes that does not already touch the recipe row still calls `TouchRecipe`, so a photo change moves `updated_at` too - and `updated_by` with it, which is why all four service methods take the acting `user.User` (see [Recipes and search](/features/recipes)). The reorder response body is `OrderResult`, not `ImageList` — that stutters as `image.ImageList` and revive flags it — and not `List` either: an OpenAPI schema name is global across the API, and huma panics at registration when two exported types claim the same one, so a name that generic is a trap.

### Comment photos

**Comment photos are staged, then claimed.** A comment's photos ([Recipe comments](/features/recipe-comments)) are rows of `comment_images`, never of `images`, and live in `images/<recipeId>/comments/<imageId>/` in the same three variants (`service/internal/image/comment.go`). `POST /api/v1/recipes/{id}/comment-images` (multipart, `LimitUpload`) renders one photo and records it with `comment_id` NULL for the uploader; it checks that the recipe exists and nothing more, not `GuardEdit`, because comments are allowed on locked recipes. A member holds at most 8 staged photos (`maxStagedCommentImages`); a ninth evicts that member's oldest staged photo inside the same transaction (`DeleteOldestStagedCommentImage`, files removed after the commit) instead of being refused. Staged photos pile up only from failed sends, so a refusal would lock the member out of photos for up to a day for something they cannot see or fix; the oldest one is the least likely to be in the draft still open. Rendering happens before the transaction, so a crash in between leaves a directory without a row that the sweep never sees (marked `ponytail:` in `StageCommentImage`). A staged photo nobody claimed is swept after 24 hours, or at once when its uploader is gone, at startup and on the share sweep interval (one goroutine in `main.go` sweeps both); the files go after the database delete, so a failure leaves wasted disk, never a row without files, and one failed removal does not stop the rest of the batch (the errors are joined and logged at warn).

**Serving comment photos.** `GET /images/{recipeId}/comments/{imageId}/{file}` (`get-comment-image-file`) checks that the row is attached and belongs to that recipe before it opens the file; only `ErrNotFound` answers `404`, any other failure is a `500`. The `get-image-file` route cannot reach them: `comments` is not an id, so it fails `IsID`.

**Adding a comment photo to the recipe photos.** `POST /api/v1/recipes/{id}/images/from-comment` takes `{commentImageId}`, needs `GuardEdit`, respects the 20-photo cap, becomes the cover when the recipe has none and touches the recipe; a photo already in the recipe is a `409`. The three files are copied into the recipe directory through `.tmp` and rename (`copyFile`), so deleting either side never touches the other. `comment_images.recipe_image_id` (`ON DELETE SET NULL`) is what `inRecipe` reads.

### Signed links and serving

**Uploading through a signed link.** `POST /api/v1/recipes/{id}/images/link?user=…&token=…` (`upload-image-by-link`, `service/internal/image/link.go`) takes a multipart `file` like `upload-image`, behind the same `LimitUpload`, and carries no `Security`: the token is the whole credential. Its middleware `requireLink` checks the token before huma parses the body, so a stranger without a valid link is refused without the route reading megabytes for them. The part's declared type is not checked (`linkForm`, unlike `uploadForm`): curl sends `application/octet-stream` for a `.webp` or a file without extension, and `decode` sniffs the bytes anyway. `UploadLinks.Issue` signs `recipeId + "\n" + userId` with `internal/sign` under the label `rezepte photo upload`, valid 15 minutes and for any number of photos within them; the key is drawn per process, so a restart ends every open link. The handler reloads the user (a deleted account gets `403`) and leaves editing rights to `Upload`'s own guard. `Issue` builds the absolute link from `REZEPTE_PUBLIC_URL` only and refuses with `ErrNoPublicURL` without it, never from the request's `Host`. The [MCP server](/features/mcp) is the only one that hands such links out, so the operation is hidden from the OpenAPI document.

**Serving.** `GET /images/{recipeId}/{imageId}/{file}` is the operation `get-image-file` in `service/internal/image/file.go`, outside `/api/v1` because the SPA puts these addresses straight into `<img>` tags. A session of any role or an API token carrying `recipes:read` may reach it.

- It returns `image.JPEG`, a `huma.StreamResponse` that writes the file through `humago.Unwrap`, since huma would otherwise frame the answer as JSON; the avatar, public-image and link-preview routes return the same.
- Ids are checked against the UUID alphabet before they ever reach a path, so no component can escape the image directory, and anything that is not an existing variant is a `404`.
- The file goes out through `http.ServeContent` (Range and conditional requests) as `image/jpeg` with `Cache-Control: private, max-age=31536000, immutable`: an image id is never reused and a file never changes after it is written, while `private` keeps shared caches out of a route that requires authentication.
- Two routes reach a photo without a session, both deliberately: a recipe's cover on `GET /link-preview/{recipeId}/{imageId}`, as the thumb and only for a link preview token while link previews are on ([Link previews](/features/link-previews)); and any of a recipe's photos on `GET /public-images/{token}/{imageId}/{thumb|detail|original}.jpg`, only while the token's public share serves that recipe and the image still belongs to it ([Public shares](/features/public-shares)).

## Why it is this way

The deployment is a single binary with SQLite for one household. There is no object store, no CDN and no image service to lean on, so the service does the work itself, once, and everything after that is a file read.

**`golang.org/x/image` fills what the standard library's `image` lacks**: a WebP decoder (`webp`), a resampling scaler for the three sizes (`draw`; the standard library can only copy pixels), and the fonts that draw a person's initial and a placeholder's letter (`font`). It is pure Go, so the binary keeps building without cgo.

The three sizes the UI needs are known up front — a thumbnail for cards and strips, a larger rendition for the gallery, and the largest for the lightbox — so rendering all three on write beats resizing on request: the expensive path runs once per photo instead of once per view.

The thumbnail is 960 px rather than something card-sized because the card shows the photo in its own ratio, clamped to 4:5 through 16:9 (`coverWidth` and `coverHeight` on the card tell it the shape), cropped to the center beyond that: the width a card shows is the thumbnail's width or less (a 4:3 landscape is 960 px wide, a 3:4 portrait 720), and a card of about 300 CSS px needs 600 px of it on a 2x screen. A smaller thumbnail leaves less than a 2x screen draws the card at, and the card looks soft on every high-density display.

Baking the orientation into the pixels means every viewer shows the photo upright, including the ones that never consult EXIF at all: a CSS `background-image`, an `object-fit: cover` thumbnail. As a side effect no camera metadata — GPS, device — ever reaches the disk, because the upload it came with is not stored.

## Rejected

- **An EXIF library.** One tag is needed; the available readers are either unmaintained or far larger than a segment walker with tests against crafted APP1 payloads.
- **Resize on request with a cache.** Cache eviction and a thundering herd on first view, in exchange for nothing at this scale, where the needed sizes are known before the upload arrives.
- **Object storage.** A second service in a deployment that is one container with one volume.
- **Images as BLOBs in SQLite.** `http.ServeContent` wants a seeker, backups would balloon with the database, and WAL checkpoints slow down with multi-megabyte rows.
- **Deriving the cover from `position = 0` instead of a column.** It makes "cover unset" indistinguishable from "no images yet", and every card listing would need a join or a subquery where `recipes.cover_image_id` already sits on the row it selects.
- **Keeping the untouched original.** It doubles disk use and keeps camera metadata on disk.
- **One canonical size scaled by CSS.** The recipe overview is the most-visited page in the app; letting its cards pull multi-megabyte originals is the worst place to spend bandwidth.

## Limits

- Originals are not kept. Re-rendering at a different size means uploading the photo again; the 2400 px variant is what the download link serves.
- The limits above are compile-time constants in `service/internal/image/image.go` and `service/internal/image/service.go`, not configuration. Changing one is a code change and a redeploy, not an environment variable.
- The upload size and the accepted types are mirrored outside the image package, and a change moves all of them: `MaxUploadBytes` also caps avatars (`service/internal/avatar/handler.go`, which declares its own content types); the browser checks before uploading with `MAX_IMAGE_BYTES` and `ACCEPTED_IMAGE_TYPES` in `frontend/src/lib/api/recipes.ts` and the `accept` list in `AvatarControl.svelte`; the rejection messages in both catalogs name the size; and the nginx snippet in `docs/user/content/(hosting)/operations/reverse-proxy.mdx` sets `client_max_body_size` to match.
- huma (since v2.40.0) applies `Operation.MaxBodyBytes` to the multipart path only while parsing: a body over the cap is read up to the cap and then answered `413`. `LimitUpload` refuses a declared `Content-Length` above the cap before reading anything, which huma does not, and both carry the same `MaxUploadBytes`; `TestUploadRejections` covers the declared and the chunked case. The import ([Import and export](/features/import-export)) avoids multipart altogether and streams its body to a temp file under its own cap, since up to 1 GiB must not be parsed in memory. Any further multipart endpoint needs both, `MaxBodyBytes` and `LimitUpload` — see [Add an API endpoint](/howtos/add-endpoint).
- The upload response carries exactly one image, and the editor uploads a multi-selection one file after another. That keeps error handling per file, at the cost of no parallelism in the browser.
- A failed upload stays in the editor until it is retried or removed; nothing retries on its own, and leaving the editor drops it (it never reached the server).
- A removed photo is deleted only when its undo toast closes or the editor is left. A tab that crashes or is killed before that keeps the photo; a normal close sends the delete with `keepalive`.
- Backups must cover the images directory next to the database. The database alone restores recipes without their photos.
- The same holds for the `avatars` directory and the accounts' pictures.
- Only a JPEG's orientation tag is applied, so a PNG or WebP that carries one can be cropped differently than the dialog previewed it.
- An avatar's original is not kept; changing the crop means uploading the picture again.
