---
title: OIDC
description: Sign-in through one OpenID Connect provider, linked to existing accounts only and matched by issuer and subject, ending in an ordinary session
---

An instance may name one OpenID Connect provider, set in the environment or by the owner in Settings → Sign-in - Google, or a self-hosted one such as Authelia, Authentik, Pocket ID, Keycloak or Dex - and people whose account is connected to it sign in with "Continue with …" instead of a password. The provider only tells Rezepte who someone is; roles, rights and the session stay Rezepte's own. `service/internal/oidc` is the whole service side (`oidc.go` runs the flow, `api.go` its six huma operations, start and callback among them as stream responses that write a redirect, `settings.go` resolves the provider and `settingsapi.go` is the owner's `/api/v1/settings/sign-in`, session-only, which never returns the client secret); `(*user.Service).LinkIdentity` and its neighbors in `service/internal/user/identity.go` own the `user_identities` table. [Data model](/architecture/data-model) owns the table, [HTTP API](/architecture/api) the operations, [Users and authentication](/features/users-and-auth) the session a sign-in ends in.

## How it works

**Two sources, one resolver, asked on every request.** The provider comes from the environment (`REZEPTE_OIDC_ISSUER`, `REZEPTE_OIDC_CLIENT_ID`, optional `REZEPTE_OIDC_CLIENT_SECRET` and `REZEPTE_OIDC_NAME`) or from the four `oidc_*` columns of `instance_settings` the owner saves in the UI. `oidc.Settings.Effective` (`settings.go`, the twin of `mail.Service.Effective`) returns the provider in force and its `Source`: `env` when `REZEPTE_OIDC_ISSUER` is set, `settings` when `instance_settings.oidc_issuer` is not empty, `none` otherwise; an empty name means `single sign-on`. The environment wins and never seeds the columns. `config.load` refuses `REZEPTE_OIDC_ISSUER` without `REZEPTE_OIDC_CLIENT_ID` and `REZEPTE_PUBLIC_URL`, and a public URL with a path or query, since Rezepte is served from the root of its host. `REZEPTE_PUBLIC_URL` stays environment-only for both sources; without it nothing is offered and the owner's page cannot turn sign-in on. With a provider already stored the card still shows it and keeps Turn off (clearing needs no public URL) but offers no Edit and no redirect URI. `cmd/rezepte` always builds the `*oidc.Login`, which asks `(*Login).config` for the provider on every request, so a saved change applies without a restart; `oidc.New` never contacts the provider. `(*Login).discover` runs discovery under a mutex on first use and caches the provider keyed by its issuer, so a changed issuer discovers anew; a failure is returned and not cached, so the next press tries again. go-oidc and oauth2 read their HTTP client from the context, which `(*Login).ctx` fills with one ten-second-timeout client.

**The owner configures it through `/api/v1/settings/sign-in`.** `get-sign-in-settings`, `update-sign-in-settings` and `delete-sign-in-settings` (`settingsapi.go`) are session-only and superadmin-only (`403` otherwise). `GET` answers `source`, the issuer, client ID, `secretSet` (never the secret), the name as stored, the `redirectUri` to register, `publicUrlMissing` and how many accounts are connected at the issuer in force and how many of those have no password. `PUT` and `DELETE` answer `409` while the environment configures sign-in (`ErrEnvLocked`) and, for `PUT`, while `REZEPTE_PUBLIC_URL` is unset. `Save` runs discovery against the typed issuer before storing anything (`422` on `body.issuer` when no provider answers; a trailing slash the provider does not use is retried without) and stores the issuer the provider confirmed. A `clientSecret` that is omitted keeps the stored one, `""` removes it (a public client with PKCE) and anything else replaces it; a kept secret is refused (`422` on `body.clientSecret`, `ErrSecretRequired`) when the issuer or client ID changed, so the stored secret never goes to another provider. `DELETE` clears the columns and leaves `user_identities` alone: the connections apply again once the same provider is set up again.

**The page is the owner's alone.** `/settings/sign-in` (`OidcCard.svelte`, with `OidcSettingsDialog.svelte`) shares the `Letterhead` of the mail card ([Email](/features/email)): provider and client rows, a stamp (`On`, `Set by the server`, `Off`), the redirect URI with a copy button, and Edit and Turn off. Under the environment the card is read-only and says where to change it. Switching the issuer asks first in a `ConfirmDialog` when accounts are connected, naming how many of them have no password and need a setup link (`connectedWarning` in `frontend/src/lib/settings/sign-in.ts`). Turning sign-in off always asks, like mail's Turn off, since the stored secret cannot be read back: the dialog says the provider, client ID and secret go, and adds the connected accounts when there are any (`turnOffWarning`). `+page.ts` sends anyone but the owner to `/settings`, and the nav entry is the owner's too.

**The flow cookie carries everything from start to callback.** `POST /api/v1/auth/oidc/start` is a real form post from the SPA's `ProviderButton` (`frontend/src/lib/components/auth/ProviderButton.svelte`) - a `fetch` would not follow the `303` to the provider - with `intent` (`login`, `link` or `setup`), `next` and, for setup, the setup token.

Start draws `state` and `nonce` with `rand.Text()` and a PKCE verifier with `oauth2.GenerateVerifier()`, and stores them with the intent, `next`, the signed-in user's id (link) and, for setup, the setup link's hash (`auth.SetupLinkHash`, the digest `setup_links.id` holds - never the token itself) and the issuer the flow started at in the `rezepte_oidc` cookie: JSON, base64url, a dot, and an HMAC-SHA256 over the JSON with a key drawn per process.

The cookie is `HttpOnly`, `SameSite=Lax` (the callback is a top-level navigation coming from the provider's site, which Strict would strip it from), `Secure` whenever `REZEPTE_PUBLIC_URL` is `https://` and otherwise as `REZEPTE_SECURE_COOKIES` says, `Path=/api/v1/auth/oidc/`, ten minutes both as `Max-Age` and as an expiry inside the MAC. The authorize URL asks for `openid email` with an `S256` challenge and the nonce; the redirect URI is `REZEPTE_PUBLIC_URL + /api/v1/auth/oidc/callback`.

The tests' fake provider (`fakeidp_test.go`) holds the flow to what a real one checks: its token endpoint refuses a `code_verifier` whose S256 is not the challenge approved at authorize time and a `redirect_uri` other than that callback.

**The callback verifies everything before it writes anything.** It expires the flow cookie first, whatever follows, then checks the MAC and the expiry, refuses an `error=` answer, compares `state` in constant time, refuses a flow whose issuer is no longer the one in force (`issuer changed`, `TestCallbackRefusesFlowFromOtherIssuer`), exchanges the code with the PKCE verifier, and has go-oidc verify the ID token - signature against the provider's JWKS, `iss`, `aud` against the client id, `exp` - before comparing its `nonce`. Every refusal logs at `Info` with a reason and never the code, a token or the cookie value (the request log records the path, never the query), and answers `303` back to the page the flow started from with `?oidc=failed`: `/login`, `/settings` or `/welcome`. Only then does the intent decide:

- **login** looks up `(iss, sub)` with `ByIdentity`. Unknown: `/login?oidc=unlinked`. Known: `StartSession`, the session and locale cookies exactly as password login sets them (`auth.SessionCookie`, `auth.LocaleCookie`), and `303` to `safeNext(next)`, the Go twin of the SPA's `safeNext` in `frontend/src/lib/api/auth.ts` - a path on this origin, never `//`, `/\`, a scheme or `/login`.
- **link** re-authenticates the session cookie the callback arrives with; it must still be the account that started the flow, else `/settings?oidc=failed`. `LinkIdentity` answers `ErrIdentityTaken` when the identity belongs to another account or this account already has one at this issuer (`/settings?oidc=taken`); otherwise the email is offered to `SetEmailIfEmpty` and the browser lands on `/settings?oidc=linked`.
- **setup** peeks the setup link again by its hash (`PeekSetupLinkByHash`), links the identity to its account (`/welcome?oidc=taken` when taken), consumes the link with `ConsumeSetupLinkByHash` (`/welcome?oidc=failed` if it was used meanwhile), offers the email, ends every session the account had and starts a new one - the same end state as setting a password through the link.

**Only `(iss, sub)` identifies a person.** The issuer stored and looked up - by login, link, setup, the identity lookup and both unlinks - is always the configured issuer (the flow's `Issuer`, which the callback checked against the effective one), never the ID token's `iss`: go-oidc accepts Google's scheme-less `accounts.google.com` for `https://accounts.google.com`, and taking `iss` as written would split one person across two keys. `TestIdentitiesKeyedByConfiguredIssuer` hands the three callback endings such a token directly, since the fake provider cannot issue one. Email is never matched on: the provider's address goes through `SetEmailIfEmpty`, which fills the profile only while it is empty, with `email_verified` copied from the claim, so a typed address always outranks a provider's. The claim is read leniently, since some providers send it as a string: JSON `true` or the string `"true"` in any case means verified, and anything else - `false`, `"false"`, a number, an object, nothing - means unverified. Email claims that do not decode are logged and left out; they never fail a sign-in whose ID token verified.

**The session is an ordinary one.** Nothing marks a session as having come from the provider; it slides, expires and ends on logout like any other. A sign-in through the provider goes through neither the password throttle nor argon2.

**Disconnecting yourself needs a password to fall back on; an admin disconnecting you does not.** `DELETE /api/v1/auth/me/identity` calls `UnlinkIdentity`, which refuses with `ErrLastCredential` (`409`) while the account has no password; the profile's Sign-in card disables its button with the same hint. Like every credential change it then ends the account's other sessions and keeps the caller's (`DeleteUserSessionsExcept` with the request's session cookie).

`DELETE /api/v1/users/{id}/identity` (`unlink-user-identity`) is the admin's: session-only, admin role, and `RemoveIdentity` applies `user.CanManage` - the rank rule of a password reset and a setup link, so an admin reaches members, the owner reaches admins, and nobody the owner (`409`). It skips the password check, since the admin's next step for a passwordless account is a setup link, and it ends every session of the account. It lives in `oidc/api.go` beside the own-identity operations because it needs the configured issuer; `404` when the account has no identity or OIDC is off.

`GET /api/v1/auth/oidc` tells the SPA whether to offer the button at all and what to call it; it and the identity operations are registered with or without OIDC configured, answering `enabled: false` and `404`, so the OpenAPI document does not change with configuration.

**The SPA offers it in three places, and lets an admin take it away in a fourth.** `getOidc()` in `frontend/src/lib/api/oidc.ts` decides whether any of them renders.

- The login page puts the button under the password form and reads `?oidc=unlinked|failed` into an alert.
- `/welcome` puts the button, with the in-memory setup token, above the password form. A flow that comes back there has lost the token (the service redirects without a fragment), so `?oidc=failed|taken` shows the reason and asks the person to open their link again.
- The profile's `SignInCard.svelte` connects or disconnects and turns `?oidc=linked|taken|failed` into a toast before dropping the query.
- The admin's people list learns which accounts are connected from `hasIdentity` on `list-users`, filled by one `ListLinkedUserIDs` query for the issuer in force, which `userapi.Register` asks a function for on every request (`oidc.Settings.Provider` in `cmd/rezepte`; empty, and `hasIdentity` always false, with OIDC off). An identity left behind at an earlier provider does not count, so a row never offers a disconnect that would answer `404`. [Users and authentication](/features/users-and-auth) owns what the row shows for it.
- "Disconnect …" is offered on rows the admin may manage (`rowPermissions(...).manageAccount`) and asks first in a `ConfirmDialog`, as deleting does: it signs the person out everywhere, and without a password they need a setup link to get back in. It then calls `unlink-user-identity` and clears the row's `hasIdentity`.

## Why it is this way

Accounts are only ever *linked*, never created, from a provider: somebody signed in to Rezepte (or holding a setup link an admin issued) connects their own identity. That is what makes a public provider such as Google safe to configure - anyone in the world can hold a Google account, and none of them gets into the household by it.

**The environment locks the card instead of seeding it.** A deployment that pins the provider in its compose file expects the file to be the truth: seeding the columns once would leave a second copy to drift from it, and an editable card over an environment that wins on restart would let the owner save something that silently does nothing. So `env` is read-only in the UI and the API, and unsetting the variables hands the (possibly empty) stored settings back.

`REZEPTE_PUBLIC_URL` builds the redirect URI rather than the request's `Host` or `X-Forwarded-*` headers, for the reason the login throttle does not trust proxies: a header anyone can send must not decide where a provider sends an authorization code.

`github.com/coreos/go-oidc/v3` is a deliberate exception to standard-library-first ([Go conventions](/conventions/go)): signature verification is security code, and a maintained, widely used verifier beats one written here. `golang.org/x/oauth2` does the exchange and PKCE.

The flow state lives in an authenticated cookie rather than a table, so a flow that is never finished leaves nothing behind to sweep, and a restart only fails the flows in progress.

## Rejected

- **Creating an account on first sign-in (auto-provisioning).** Anybody with an account at the provider would become a member; with Google that is anybody.
- **Matching an existing account by email.** An address is profile data, not unique and not always verified; whoever controls a matching address at the provider would take the account over.
- **GitHub and other OAuth-2.0-only providers.** No ID token, so nothing standard to verify; each would need its own user-info adapter.
- **Seeding the stored settings from the environment.** See Why: two copies to drift, and a card that edits nothing.
- **More than one provider.** One issuer keeps configuration, the button and the Sign-in card simple; `user_identities` already keys by issuer, should that change.
- **RP-initiated logout.** Signing out of Rezepte ends the Rezepte session only; ending the person's session at Google on the way would surprise them.
- **Hand-rolled JWT verification.** See Why: security code is taken from go-oidc, not written here.

## Limits

- One provider per instance. Changing it leaves the old provider's identities in place but dormant: they count again if that issuer returns.
- The client secret is stored as plain text, like `smtp_password`; the API never returns it.
- Signing out at the provider does not end a Rezepte session; it runs its normal course.
- A restart draws a new flow-cookie key, so a sign-in in progress across a restart fails and has to be started again; so does a sign-in in progress when the owner changes the provider (`issuer changed`).
- A failed flow tells the person only that it failed; the reason is in the service log at `Info`.
