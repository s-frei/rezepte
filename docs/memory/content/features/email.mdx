title: Email
description: SMTP the owner configures, and the mails sent through it - setup links, password resets, sign-in hints and address confirmations

Rezepte sends mail through an SMTP server the owner names, in the environment or in the settings. It carries five messages: the setup link an admin creates for a new account, a test mail that proves the configuration works, a link for a new password, a hint for an account that has no password, and a link that confirms an address. The sending, the settings and the templates live in `service/internal/mail`; the owner's HTTP surface is `service/internal/mailapi`; the card and its dialogs are `MailCard.svelte`, `MailSettingsDialog.svelte` and `TestMailRow.svelte` under `frontend/src/lib/components/settings/`. The card is the whole of Settings → Email (`frontend/src/routes/settings/mail/`), a page only the owner has: the nav entry, in the sidebar, the contents sheet and the phone's You sheet, is gated on `superadmin`, and the page's load redirects anyone else to Settings.

## How it works

**One resolver decides what is configured.** `mail.Service.Effective` returns the effective `Config` and its `Source`: `env` when `REZEPTE_SMTP_HOST` is set, `settings` when `instance_settings.smtp_host` is not empty, `none` otherwise. With `none` the `Config` is still the stored row, whose defaults (port 587, `starttls`, sender name Rezepte) are what the settings API answers and the edit dialog starts from, so no caller invents its own. Nothing else reads the environment or the columns. `Enabled` adds the one other condition, a non-empty `REZEPTE_PUBLIC_URL`: a mailed link has to be absolute and the server learns its own address only from that variable, so without it mail is off and the card says so. `config.LoadFrom` refuses a `REZEPTE_SMTP_HOST` without `REZEPTE_SMTP_FROM`, without `REZEPTE_PUBLIC_URL`, or with a security outside `starttls`, `tls` and `none`.

**The environment locks the card.** With `source=env` the settings API answers `409` to a save, a turn-off and a test that carries unsaved values, and the card shows the letterhead read-only with the test-mail row as its one control. The two sources are never mixed and the environment never seeds the database: a value shown in the card is the value in force, and removing the variables returns the card to whatever the database holds.

**Turning off asks first.** "Turn off" opens a `ConfirmDialog` that says the stored server, sign-in and password go with it, since the password cannot be read back and setting mail up again means typing it anew. The dialog checks the port itself (a whole number from 1 to 65535) and shows a field error, so a typo never reaches the API's generic `422`.

**The card is a letterhead, and its rows wrap together.** Each value is a main part with a smaller line under it (name over address, `host:port` over encryption, username over "Password set"), right-aligned beside the key and its dotted leader. `fitRows`, an attachment with a `ResizeObserver` on the `<dl>`, lays the rows out on one line each, checks whether any row overflows, and sets `data-stacked` on the list when one does: then every value moves under its leader and long addresses break anywhere. All rows or none, never a mix, and nothing is cut off with an ellipsis. Under it, `TestMailRow` is an always-visible "Send a test mail to" field prefilled with the owner's own address from `/auth/me`, with the result right under it; the dialog uses the same row with the unsaved values. It is not a `<form>`, because in the dialog it sits inside the settings form and Enter must send the test, not save.

**The sender dials itself.** `send` in `service/internal/mail/sender.go` opens the connection with one 10 second deadline over dial, TLS, dialog and data, so a server that accepts the connection and then goes silent fails the request instead of hanging the dialog (`TestSendDeadline`). `EHLO` names the domain of the sender address, because some servers refuse `localhost`. `tls` is an implicit TLS connection, normally port 465. `starttls` demands the extension: a server that does not offer it is `ErrNoSTARTTLS`, never a silent fall back to plain text. `none` is plain text, and `Validate` refuses a username with `none` unless the host is loopback, because `net/smtp` itself refuses to send credentials over an unencrypted link to anything else. Every error `Send` returns wraps `mail.ErrSend`, and a server's reply stays reachable as `net/smtp`'s own `*textproto.Error`, which is what lets the owner read `535 "5.7.8 ..."` after a test. `mailapi.mapErr` turns `ErrSend` into `502` with that text and leaves every other error a `500`.

**Messages are assembled, not templated by a library.** `html/template` and `text/template` files embedded from `service/internal/mail/templates` become a `multipart/alternative` message: an HTML letter sheet in inline-styled tables with a dark block, and a plain-text part with the raw link. The subject is Q-encoded and display names are escaped (`TestInviteMessageEncodesAndEscapes`). The recipient's account `locale` picks the language and an unknown one falls back to English. `link.txt.tmpl` is the plain-text part of every link mail (setup, reset and confirmation), with the greeting and the validity line optional; the hint has no link and uses the same layout. `deliver` in `service/internal/mail/service.go` is the one send-and-log path every mail goes through: it checks that mail is on, builds the envelope from the effective config, sends, and logs a failure with the recipient's domain and the reply code only.

**The copy is generated.** Mail strings are `mail_*` keys in `frontend/messages/en.json` and `de.json`, because UI copy lives only there; the prefix is reserved for what the templates read, and the settings page's own copy about mail is `settings_mail_*`. `go:embed` cannot reach outside the Go module, so `mise run //service:generate` copies those keys to `service/internal/mail/messages` with `service/internal/mail/copymessages`, and the copies are committed. Both the generator and `TestMessagesMatchFrontend` pick the keys with `mail.FilterCatalog`; the test compares them with the catalogs, so a stale copy fails `mise run check`; the copies are never edited by hand.

**The password never leaves the server.** `GET /api/v1/settings/mail` returns `passwordSet`, not the password. A `PUT` without `password` keeps the stored one (`TestPutKeepsPasswordWhenOmitted`), so the dialog can open with the field empty and "leave empty to keep" beside it. The stored value is plain text in `instance_settings.smtp_password`, like `link_preview_key`: whoever reads the database already holds everything mail could protect. The only way to remove it is "Turn off", which clears every mail column. A test with unsaved dialog values (`config` in the test body) falls back to the stored password when the form has none. Either fallback holds only for the stored host and username: with another one, `withStoredPassword` answers `ErrPasswordRequired` (`422`, "enter the password for a different server"), so the stored password never goes to a server it was not typed for (`TestKeptPasswordStaysWithItsServer`). An empty username means no sign-in, so a keep then drops the password instead of refusing (`TestKeptPasswordDroppedWithoutSignIn`).

**A mailed link remembers where it went.** `setup_links.sent_to` holds the address a link was mailed to, empty when the admin handed it over by hand. `userapi.mailLink` sends after the account and the link are committed, then calls `auth.Service.MarkSetupLinkSent` keyed by the link's own hash, so a link replaced in the meantime is never marked. Redeeming a link (`consumeWith`, behind the password and the OIDC setup paths alike) verifies the account in the same transaction when `sent_to` equals the account's current stored address: opening the link proves the mailbox. An address changed between sending and redeeming verifies nothing (`TestConsumeVerifiesOnlyMatchingAddress`).

**A failed send never loses the account.** The setup link in `create-user`'s and `issue-setup-link`'s answer carries `mailedTo`, the address a send went to or failed for, and adds `mailError: "send_failed"` when it failed; both are `201`, and the link is there either way. Neither field appears when mail is off or the account has no address. `SetupLinkDialog.svelte` reads the address from `mailedTo` in both cases. The SMTP detail is logged with the recipient's domain only, never the token, and an admin sees none of it; the owner finds it by sending a test mail. If the mail was sent but marking it failed, the response still says `mailedTo`, and the only cost is that redeeming does not verify the address.

**`userapi` and `auth` see mail through seams.** `userapi.Mailer` is one method, `SendInvite(ctx, mail.Invite)`; the invite carries the link's path and `mail.Service` puts `REZEPTE_PUBLIC_URL` in front. `mail.ErrDisabled` back means mail is off and no send started, so `mailLink` reports nothing. `auth.Mailer` is `Enabled`, `SendReset`, `SendHint` and `SendConfirm`, handed to the service with `auth.Service.SetMail(mailer, auth.Provider{Issuer, Name})` in `main.go`; `Provider` is the identity provider of the hint, zero while OIDC is off. A nil `Mailer` is mail off too, which is what every test that does not care passes.

**Who gets a reset mail.** `auth.Service.ForgotPassword` takes what the person typed, trimmed. With an `@` it is first an address and reaches every account whose confirmed address it is (`ListByVerifiedEmail`, case folded); otherwise, or when no confirmed address matches (a username may hold an `@`), it is a username, whose address has to be confirmed. The owner is always dropped: their way back in is `--reset-superadmin-password`. Each account is let through once per five minutes by a per-account `cooldown`, so a repeated request mails nothing. An account with a password gets `IssueResetLink` and the reset mail; one with only an identity at the configured provider gets the hint, named after `REZEPTE_OIDC_NAME` or "your sign-in provider"; one that never set up gets nothing, its setup link being its way in, and so does one whose admin setup link is open. A reset never replaces that link. The handler (`forgot-password`) answers `204` at once and works in a goroutine on `context.WithoutCancel` with a 15 second timeout and a `recover` that logs a panic instead of ending the process, so neither the answer nor its timing tells whether an account exists. A failed lookup logs a fixed message, never the typed text, which may be someone else's address; for the same reason `/login` carries the typed name to `/forgot-password` in SvelteKit navigation state (`App.PageState.login`), never in the URL, and the page shows "isn't set up here" instead of its form while mail is off.

**Confirming an address.** A confirmation mail goes out when a person saves a new address in their profile, when an admin's `PATCH` sets one (the mail names the admin, and goes only after the whole request succeeded), when `create-user` takes an address with a password, and when `issue-setup-link {email}` changes the address without mailing the link; not when the setup link itself is mailed, since redeeming it confirms. `auth.Service.ConfirmChangedAddress(before, after, by)` is the one place that decides it: a new, unconfirmed, non-empty address. The mail names the account's username, so accounts sharing an address can tell their mails apart. `email_confirmations` holds one open row per account for 7 days; `Confirm` verifies the address only while it still equals the one mailed to, answers `200 {address}` and never signs anybody in, and every new address mails its own confirmation, replacing the previous link. "Send again" (`resend-email-confirmation`) is limited to one per account per minute (`429` with `Retry-After`), and the automatic mail after the account holder's own change takes the same minute: a save inside it mails nothing, so repeated saves cannot mail a stranger without end, and "Send again" right after a save cannot invalidate the link just mailed. An admin's change is not held back. A confirmation whose send failed is dropped by its own token, so a newer one issued meanwhile stays, and `emailConfirmationPending` on `/auth/me`, which the profile reads to choose between "sent" and "not confirmed", never claims a mail that did not go out; the profile's answer carries the same flag. After a save the form shows a sent mail as "sent" and anything else, a failed send or one the minute held back, as "not confirmed" with the send button; only a `502` on "Send again" says the mail could not be sent.

**The UI follows `mailEnabled`.** `GET /api/v1/settings` carries `mailEnabled` for every role. "Add account" always has an optional email field, since an address is profile data either way; with mail on, its submit reads "Create and send link" when link mode is chosen and an address typed; the row action "Setup link" opens a step first (`SendSetupLinkDialog.svelte`) and only then the result dialog. The step is a radio choice in the markup of Add account's sign-in group: "Send by mail", the default, with the address field under it even when the account has none yet, or "Pass it on myself", which hides the field; the one primary button reads "Send link" or "Show link" to match. With it off, neither offers mail: the submit creates the account and "Setup link" goes straight to the result dialog. After a mailed result closes, focus returns to the row's menu trigger (`menuTriggerId` in `frontend/src/lib/settings/person-focus.ts`).

**Mailpit stands in for a provider.** `docker-compose.test.yaml` runs a pinned Mailpit that accepts any login; `mise run mail:up` and `mail:down` start and stop only it, and its two ports follow the worktree's offset ([Toolchain](/architecture/toolchain)). `mise run demo` writes the Mailpit configuration into the demo database through `PUT /api/v1/settings/mail` when Mailpit answers, as a best-effort step that leaves a demo without mail rather than no demo, never as `REZEPTE_SMTP_*`, so the card the demo is there to click through stays editable ([Demo mode](/features/demo-mode)). `mise run e2e` hands the suite `MAILPIT_URL` and `MAILPIT_SMTP_PORT`; `frontend/e2e/mail.test.ts` configures mail through the UI, reads the mails through `frontend/e2e/mailpit.ts` and skips without Mailpit, the way the OIDC specs skip without Dex.

## Why it is this way

- **Synchronous inside the request.** An admin pressing "Create and send link" wants to know in that dialog whether it worked, and the link is on screen as a fallback either way. A queue would turn a visible failure into a silent one.
- **Plain `net/smtp`.** The standard library covers STARTTLS, implicit TLS and `PlainAuth`; the sender only adds the dial, so the deadline and the TLS mode are explicit. No new dependency.
- **Environment wins and locks, rather than seeding.** A deployment that pins mail in its compose file must not find the UI contradicting it, and a "seed once" copy in the database would outlive the variable.
- **The owner only.** Mail settings carry a credential and decide where every invitation goes; they are session-only and `403` for everyone but the owner, and not part of `get-settings`, which a `recipes:read` token can read.
- **Verify on redeeming, not on sending.** A typed address proves nothing; a person who opens a link from that mailbox proves it.

## Rejected

- **An outbox with retries.** It adds a table, a worker and a state to explain for one message an admin is watching. Mail nobody waits for would need one.
- **Mixing the sources, field by field.** Which value is in force would depend on two places.
- **Sending the SMTP error to every admin.** A server's reply can name internal hosts; the owner already has the test button.
- **Mail templates the owner edits.** Two languages and one frame stay in the repository.

## Limits

- Notifications are [still ahead](/roadmap); the five mails above are all it sends.
- No rate limit per IP: the reset mail and the resend are limited per account, so a stranger can mail an account's owner a reset link once in five minutes, and nothing more.
- The owner is never reset by mail.
- No outbox, no retry: a failed send is reported once, and the admin passes the link on or sends it again.
- Nothing checks SPF, DKIM or deliverability; the user documentation points at the provider for the sender domain.
- One sender for the whole instance.
