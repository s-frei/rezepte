---
title: Email
description: SMTP the owner configures, and the mails sent through it - setup links, password resets, sign-in hints, address confirmations, security notices and the notifications people can switch off (see [Notifications](/features/notifications))
---

Rezepte sends mail through an SMTP server the owner names, in the environment or in the settings. It carries these messages: the setup link an admin creates for a new account, a test mail that proves the configuration works, a link for a new password, a hint for an account that has no password, a link that confirms an address, three security notices (a password set or changed, an email address changed or removed, a sign-in method added) and the notifications people can switch off, which [Notifications](/features/notifications) owns. The sending, the settings and the templates live in `service/internal/mail`; the owner's HTTP surface is `service/internal/mailapi`; the card and its dialogs are `MailCard.svelte`, `MailSettingsDialog.svelte` and `TestMailRow.svelte` under `frontend/src/lib/components/settings/`. The card is the whole of Settings → Email (`frontend/src/routes/settings/mail/`), a page only the owner has: every nav entry to it is gated on `superadmin`, and the page's load redirects anyone else to Settings.

## How it works

**One resolver decides what is configured.** `mail.Service.Effective` returns the effective `Config` and its `Source`: `env` when `REZEPTE_SMTP_HOST` is set, `settings` when `instance_settings.smtp_host` is not empty, `none` otherwise. With `none` the `Config` is still the stored row, whose defaults (port 587, `starttls`, sender name Rezepte) are what the settings API answers and the edit dialog starts from, so no caller invents its own. Nothing else reads the environment or the columns. `Enabled` adds the one other condition, a non-empty `REZEPTE_PUBLIC_URL`: a mailed link has to be absolute and the server learns its own address only from that variable, so without it mail is off and the card says so. `config.LoadFrom` refuses a `REZEPTE_SMTP_HOST` without `REZEPTE_SMTP_FROM`, without `REZEPTE_PUBLIC_URL`, or with a security outside `starttls`, `tls` and `none`.

**The environment locks the card.** With `source=env` the settings API answers `409` to a save, a turn-off and a test that carries unsaved values, and the card is read-only apart from the test mail. The two sources are never mixed and the environment never seeds the database: a value shown in the card is the value in force, and removing the variables returns the card to whatever the database holds.

**Turning off asks first.** "Turn off" opens a `ConfirmDialog` that says the stored server, sign-in and password go with it, since the password cannot be read back and setting mail up again means typing it anew. The settings dialog (`MailSettingsDialog.svelte`) checks the port itself (a whole number from 1 to 65535) and shows a field error, so a typo never reaches the API's generic `422`.

**The card's rows stack all together or not at all.** The rows are `Letterhead.svelte`, shared with the Sign-in card: `fitRows` there watches the `<dl>` with a `ResizeObserver` and sets `data-stacked` when any row would overflow on one line; then every value moves left-aligned under its key, breaks inside a word only when nothing else lets it fit, and nothing is cut off with an ellipsis. A line marked `url` breaks only after a path slash (`<wbr>`), never inside the scheme; one marked `address` (the sender and sign-in lines) only before `@` or `.`. `e2e/settings.test.ts` checks the stacked card at 320px with a mocked long sender, down to where its lines break. `TestMailRow` is prefilled with the owner's own address from `/auth/me`, and the settings dialog reuses it with the unsaved values. It is not a `<form>`, because in the dialog it sits inside the settings form and Enter must send the test, not save. Below it, while mail is on, the card has the hour of the new recipes digest: a `Select` of 0 to 23 labeled in the locale's time format, read from `GET /api/v1/settings` and saved on pick with `PATCH {recipeDigestHour}`, snapping back on failure; the page is the owner's alone, so no one else sees it (see [Notifications](/features/notifications) for the run).

**The sender dials itself.** `send` in `service/internal/mail/sender.go` opens the connection with one 10 second deadline over dial, TLS, dialog and data, so a server that accepts the connection and then goes silent fails the request instead of hanging the dialog (`TestSendDeadline`). `EHLO` names the domain of the sender address, because some servers refuse `localhost`. `tls` is an implicit TLS connection, normally port 465. `starttls` demands the extension: a server that does not offer it is `ErrNoSTARTTLS`, never a silent fall back to plain text. `none` is plain text, and `Validate` refuses a username with `none` unless the host is loopback, because `net/smtp` itself refuses to send credentials over an unencrypted link to anything else. Every error `Send` returns wraps `mail.ErrSend`, and a server's reply stays reachable as `net/smtp`'s own `*textproto.Error`, which is what lets the owner read `535 "5.7.8 ..."` after a test. `mailapi.mapErr` turns `ErrSend` into `502` with that text and leaves every other error a `500`.

**Real sends report how the setup is doing.** `deliver` in `service/internal/mail/service.go` tells its `DeliveryReporter` (`SetReporter`; nil, the default, reports nothing; `notify.Service` in `main.go`) `MailReset` after every accepted send and `MailFailed(reason)` only for a setup failure: `send` wraps what breaks before any recipient is named in a `setupError` whose reason is `connect` (dial, greeting, `EHLO`), `tls`, `auth` or `sender` (`MAIL FROM` refused), and `setupFailure` reads it. A refusal at `RCPT TO` or later is about one address and reports nothing (`TestRecipientRefusalDoesNotReport`). `Save` and `Clear` report `MailReset` too. The test send goes around `deliver` and never reports (`TestSendTestDoesNotReport`): the owner reads its error on screen. What the owner is told, and how often, is the mail-failing push in [Notifications](/features/notifications).

**The comment mail embeds the comment's photos.** `notify` loads them once per comment, from the thumb variant through `image.MailPhoto`, and the mail inlines them like the author's picture; an unreadable photo is logged and skipped. The plain-text part says `mail_comment_photos_one` / `_other` ("+ 1 photo") instead.

**Messages are assembled, not templated by a library.** `html/template` and `text/template` files embedded from `service/internal/mail/templates` become a `multipart/alternative` message: an HTML letter sheet in inline-styled tables with a dark block, and a plain-text part with the raw link. The subject is Q-encoded, one encoded word of at most 75 characters per folded line, so a 200-character title never makes a header line too long (`TestLongSubjectIsFolded`); an ASCII subject is not encoded and stays under 998 characters. Display names are escaped (`TestInviteMessageEncodesAndEscapes`). The recipient's account `locale` picks the language and an unknown one falls back to English. Each mail is a template pair, `templates/<name>.html.tmpl` and `<name>.txt.tmpl`, that defines the `content` (and in HTML the `footer`) block of `layout.html.tmpl` and `layout.txt.tmpl`; the button, the fallback link, a person's `circle` (picture or initial, at a size the caller names), the quote and the unsubscribe footer are `{{define}}`s in `partials.html.tmpl`. The sheet's content cell in `layout.html.tmpl` carries `word-break:break-word;overflow-wrap:anywhere`, which every block inherits, so a long word in a heading, a name, a quote or a link breaks instead of widening the sheet past a phone; below 480 px a media query narrows that cell's padding (class `inner`), so a phone keeps a usable column (`TestSamplesRender` checks the rule is there; a 24-letter German recipe title at 320 px is how to see it). The quote keeps a comment's line breaks with `white-space:pre-line`; the unsubscribe footer takes `dict "links" .Unsubscribe "kind" <key> "group" <key>`, the catalog keys of its two links (`mail_unsubscribe_kind_<kind>`, `mail_unsubscribe_group_<group>`), and shows both links when the kind's URL is set (the two are always set together), so no mail carries `href=""`. `render.go` parses each pair into a clone of the layouts once, and clones it again per mail to bind the funcs `t` (copy in the letter's locale), `datetime` (`mail_datetime_format`) and `dict` (arguments for a partial); `t` and `dict` fail the render on an odd argument count and `dict` on a key that is not a string, rather than drop the argument. `Text`, behind `t`, every subject and the push copy, fails on a key that neither the letter's catalog nor the English one holds, so a key built at run time (`printf "%s_body_%s" .Data.Prefix .Data.Origin`, `mail_comment_reason_<reason>`) never renders an empty line; `TestEveryBuiltKeyExists` builds every such key for every enum value in both languages. It fills `{placeholders}` in one pass with a `strings.Replacer`, so a name or title holding `{title}` stays as typed (`TestPlaceholdersFillInOnePass`). A builder names the subject by catalog key (`letter.SubjectKey`); `render` fills it. The HTML part passes the two owner lines that name `rezepte --reset-superadmin-password` through `command`, which escapes the copy and sets the command as code whose flag has `white-space:nowrap`, so a phone never breaks it at a hyphen; the text part keeps it plain. `mail_datetime_format` reads inside a sentence: "on October 27, 2026 at 1:32 PM", "am 27.10.2026 um 13:32". A variant with its own copy passes a key prefix in `Data` (`mail_invite_existing`, `mail_password_set`, `mail_email_changed_removed`). `TestSamplesRender` also fails a part that contains `ZgotmplZ` (html/template's mark for a value it refused) or `<no value>`. **A picture travels inside the mail.** The author's picture in a comment mail sits behind a login, and clients block remote pictures anyway, so `letter.Inline` carries it as a JPEG: `build` then wraps the alternative body in `multipart/related` (RFC 2387) with the picture as a base64 part whose `Content-ID` the HTML names. The Content-ID is `avatar.<id>@<sender domain>`, with the same random `<id>` as the Message-ID (`BuildComment` draws it with `newID` and hands it to `build` as `letter.ID`): RFC 2392 wants it unique, and a client that caches by cid would otherwise show one author's picture in another's mail. The URL reaches the template as `html/template.URL`, since html/template refuses a `cid:` URL otherwise (`TestCommentMailCarriesTheAuthorsPicture`). A mail without a picture stays `multipart/alternative`. **The new recipes digest** (`BuildRecipeDigest`, `templates/recipe_digest.*`) takes `RecipeDigest.Recipes` in creation order: the first 6 are cards (the cover photo across the sheet when there is one, linked like the button; title; the creator's circle and name; servings and, when prep plus cook is above 0, minutes; a "View recipe" button), the next 30 a plain list of title links and creator names, and anything beyond one "and N more" line linking `/recipes`, so 80 recipes still make a small mail (`TestRecipeDigestCardsAndList`). An empty list is an error, so a caller skips a recipient with nothing to read; an empty `CreatorName` (the account is gone) reads as `mail_recipe_digest_former_member`, and `circle` shows "?" for an empty name rather than U+FFFD (`TestRecipeDigestFormerMember`, `TestCircleWithoutName`). The subject names the title for one recipe and the count for more (`mail_recipe_digest_subject_one`/`_many`); servings pick `_one` or `_other` in Go. Each card sits in its own bordered box (class `card`, darkened in the layout's dark block) with the creator, when the recipe was added (`mail_recipe_digest_added` with `datetime`) and the short facts on lines of their own; a line under the heading counts the recipes (`mail_recipe_digest_count_one`/`_other`). Each card photo is an inline part `photo.<n>.<id>@<domain>`, each distinct creator picture (by its bytes) one `avatar.<n>.<id>@<domain>`, the list carries none. The photo comes from `image.MailPhoto`, which turns the cover's `_thumb.jpg` into at most 800 px wide at JPEG quality 72, never scaling up: 800 covers the 504 px sheet column at 1.5x and keeps a demo photo at 60 to 80 KB, so six cards stay well under a megabyte. Its footer is kind `recipe` in group `household`, with `List-Unsubscribe` like the comment mail. `build` writes `List-Unsubscribe` and `List-Unsubscribe-Post` (RFC 8058) only for a letter with a one-click URL, and refuses one holding a line break, the one value it writes into a header. `mise run //service:mail-preview` renders every `mail.Samples` entry, each template in English and German and every variant (`invite` new and existing, `confirm` by an admin and by the person, `password_changed` per origin and a first password per possible origin, `email_changed` changed and removed by the person and by an admin, `identity_linked` from the profile, through a setup link and for the owner, `comment` to the creator and to a commenter, `recipe_digest` with one recipe, one without photo and eight), into an ignored `out` folder beside `service/internal/mail/preview/main.go` and prints the path of its index page. The index files the templates under their kind of mail (account, security notices, notifications, owner tools), shows each variant as a scaled live frame of its HTML part with its subject, and finds mails by name or subject and by the role they reach (`/` focuses the search); a bar in the header jumps to each kind and counts what the filters leave, scrolling rather than linking because the hash holds language and theme. `Sample.Section`, `Sample.Audience`, `Sample.Roles` and `Sample.OptOut` come from `audiences` in `samples.go`, which restates for a reader who gets each template under which conditions the code sends it (confirmed address, not switched off, inviter still admin), which roles that can be, and which unsubscribe group switches it off, tagged "no opt-out" when none does, and `TestSamplesRender` fails for a template without one, so a new mail has to say. The comment sample to the creator carries demo person mila's picture from `service/internal/demo/avatars`, the other the initial; the digest samples carry the first photo of the English demo recipes (`service/internal/demo/photos/en/*/1.jpg`, in directory order) through `image.MailPhoto`, which `Samples` takes as `photos`; the preview walks nested multiparts and turns each `cid:` URL into a data URL. Each template variant gets a folder of its own (`out/comment.created/`) with a page that shows the headers, the HTML part at 760 and 360 px and the text part, and switches language and theme; both live in the hash (`#lang=de&theme=dark`) and every link to another page of the preview carries it, since a browser may keep `localStorage` apart per `file://` page; the arrow keys step to the previous and next mail. The pages come from `preview.html.tmpl`, with their style and script in `preview.css` and `preview.js` beside it, embedded and inlined so each page stands alone under `file://`. A frame does not take its color scheme from the page around it, so for light and dark the page loads copies of the HTML part (`de.light.html`, `de.dark.html`) in which `@media (prefers-color-scheme: dark)` is forced off or on; the command fails when the layout no longer holds that exact query. `TestEveryTemplateHasASample` fails for a template without one. `deliver` in `service/internal/mail/service.go` is the one send-and-log path every mail goes through: it checks that mail is on, builds the envelope from the effective config, sends, and logs a failure with the recipient's domain and the reply code only. It also tells the `DeliveryReporter` set with `SetReporter` (`notify.Service`, which warns the owner by push, see [Notifications](/features/notifications)): `MailReset` after every accepted send and `MailFailed(reason)` after a setup failure. `send` marks a setup failure as an unexported `setupError` whose reason is `connect` (dial, greeting, `EHLO`), `tls` (implicit TLS handshake, missing STARTTLS, STARTTLS), `auth` (any `AUTH` error, a `535` or a `4xx`) or `sender` (any `MAIL FROM` refusal); a refusal at `RCPT TO` or later is about one mail, not the setup, and reports nothing (`TestRecipientRefusalDoesNotReport`). `SendTest` never reports, since the owner reads its error on screen (`TestSendTestDoesNotReport`); `Save` and `Clear` call `MailReset` too.

**The copy is generated.** Mail strings are `mail_*` keys in `frontend/messages/en.json` and `de.json`, because UI copy lives only there; the prefix is reserved for what the templates read, and the settings page's own copy about mail is `settings_mail_*`. `go:embed` cannot reach outside the Go module, so `mise run //service:generate` copies those keys to `service/internal/mail/messages` with `service/internal/mail/copymessages`, and the copies are committed. Both the generator and `TestMessagesMatchFrontend` pick the keys with `mail.FilterCatalog`; the test compares them with the catalogs, so a stale copy fails `mise run check`; the copies are never edited by hand.

**The password never leaves the server.** `GET /api/v1/settings/mail` returns `passwordSet`, not the password. A `PUT` without `password` keeps the stored one (`TestPutKeepsPasswordWhenOmitted`), so the dialog can open with the field empty and "leave empty to keep" beside it. The stored value is plain text in `instance_settings.smtp_password`, like `link_preview_key`: whoever reads the database already holds everything mail could protect. The only way to remove it is "Turn off", which clears every mail column. A test with unsaved dialog values (`config` in the test body) falls back to the stored password when the form has none. Either fallback holds only for the stored host and username: with another one, `withStoredPassword` answers `ErrPasswordRequired` (`422`, "enter the password for a different server"), so the stored password never goes to a server it was not typed for (`TestKeptPasswordStaysWithItsServer`). An empty username means no sign-in, so a keep then drops the password instead of refusing (`TestKeptPasswordDroppedWithoutSignIn`).

**A mailed link remembers where it went.** `setup_links.sent_to` holds the address a link was mailed to, empty when the admin handed it over by hand. `userapi.mailLink` sends after the account and the link are committed, then calls `auth.Service.MarkSetupLinkSent` keyed by the link's own hash, so a link replaced in the meantime is never marked. Redeeming a link (`consumeWith`, behind the password and the OIDC setup paths alike) verifies the account in the same transaction when `sent_to` equals the account's current stored address: opening the link proves the mailbox. An address changed between sending and redeeming verifies nothing (`TestConsumeVerifiesOnlyMatchingAddress`).

**A failed send never loses the account.** The setup link in `create-user`'s and `issue-setup-link`'s answer carries `mailedTo`, the address a send went to or failed for, and adds `mailError: "send_failed"` when it failed; both are `201`, and the link is there either way. Neither field appears when mail is off or the account has no address. `SetupLinkDialog.svelte` reads the address from `mailedTo` in both cases. The SMTP detail is logged with the recipient's domain only, never the token, and an admin sees none of it; the owner finds it by sending a test mail. If the mail was sent but marking it failed, the response still says `mailedTo`, and the only cost is that redeeming does not verify the address.

**`userapi` and `auth` see mail through seams.** `userapi.Mailer` is one method, `SendInvite(ctx, mail.Invite)`; the invite carries the link's path and `mail.Service` puts `REZEPTE_PUBLIC_URL` in front. `mail.ErrDisabled` back means mail is off and no send started, so `mailLink` reports nothing. `mail.Invite.Existing` marks an account that can sign in already (`auth.Service.CanSignIn`: a password, or an identity at any provider, the same rule as `HadCredential` below), whose mail says a setup link was sent instead of an account created. `auth.Mailer` is `Enabled`, `SendReset`, `SendHint`, `SendConfirm`, `SendPasswordChanged`, `SendEmailChanged` and `SendIdentityLinked`, handed to the service with `auth.Service.SetMail(mailer, oidcSettings.Provider)` in `main.go`, a function asked on every request; its `auth.Provider{Issuer, Name}` is the identity provider of the hint and of the sign-in method notice, zero while OIDC is off. A nil `Mailer` is mail off too, which is what every test that does not care passes.

**Who gets a reset mail.** `auth.Service.ForgotPassword` takes what the person typed, trimmed.

- With an `@` it is first an address and reaches every account whose confirmed address it is (`ListByVerifiedEmail`, case folded); otherwise, or when no confirmed address matches (a username may hold an `@`), it is a username, whose address has to be confirmed.
- The owner is always dropped: their way back in is `--reset-superadmin-password`.
- Each account is let through once per five minutes by a per-account `cooldown`, so a repeated request mails nothing.
- An account with a password gets `IssueResetLink` and the reset mail; one with only an identity at the configured provider gets the hint, named after the provider in force ([OIDC](/features/oidc)) or "your sign-in provider"; one that never set up gets nothing, its setup link being its way in, and so does one whose admin setup link is open. A reset never replaces that link.
- The handler (`forgot-password`) answers `204` at once and works in a goroutine on `context.WithoutCancel` with a 15 second timeout and a `recover` that logs a panic instead of ending the process, so neither the answer nor its timing tells whether an account exists.
- A failed lookup logs a fixed message, never the typed text, which may be someone else's address. For the same reason `/login` carries the typed name to `/forgot-password` in SvelteKit navigation state (`App.PageState.login`), never in the URL. While mail is off the page shows "isn't set up here" instead of its form.

**Confirming an address.** `auth.Service.ConfirmChangedAddress(before, after, by)` is the one place that decides whether a confirmation goes out: for a new, unconfirmed, non-empty address.

- It goes out when a person saves a new address in their profile, when an admin's `PATCH` sets one (the mail names the admin, and goes, with the old address's notice, as soon as the address is written: a later step of the same request that fails, such as the password with a full argon2 queue, cannot leave the change unannounced; `TestAddressNoticesSurviveALaterFailure`), when `create-user` takes an address with a password, and when `issue-setup-link {email}` changes the address without mailing the link. Not when the setup link itself is mailed, since redeeming it confirms.
- The mail names the account's username, so accounts sharing an address can tell their mails apart.
- `email_confirmations` holds one open row per account for 7 days; every new address mails its own confirmation, replacing the previous link. `Confirm` verifies the address only while it still equals the one mailed to, answers `200 {address}` and never signs anybody in.
- "Send again" (`resend-email-confirmation`) is limited to one per account per minute (`429` with `Retry-After`), and the automatic mail after the account holder's own change takes the same minute: a save inside it mails nothing, so repeated saves cannot mail a stranger without end, and "Send again" right after a save cannot invalidate the link just mailed. An admin's change is not held back.
- A confirmation whose send failed is dropped by its own token, so a newer one issued meanwhile stays, and `emailConfirmationPending` on `/auth/me` (and on the profile's answer) never claims a mail that did not go out. The profile shows "sent" only for a sent mail and "not confirmed" with the send button otherwise; only a `502` on "Send again" says the mail could not be sent.

**Security notices.** They go only to a confirmed address, carry no unsubscribe link or header, and the footer says they cannot be unsubscribed; whoever takes over an account would switch them off first. Each is sent after the change committed, and a failure is logged and changes nothing. Times are `datetime` in `time.Local`, the server's `TZ`, written without a zone: UTC unless the deployment sets `TZ`, which works in the distroless image because `main.go` imports `time/tzdata`.

- `auth.Service.PasswordChanged(u, origin, admin)` mails `mail.PasswordChanged` to `u` when `u` has a confirmed address and mail is on. The origin names how it happened: `profile` (`change-own-password`), `admin` (an admin's `PATCH` with a password, naming their display name; `guardTarget` refuses a `PATCH` on oneself, and the notice goes to the address confirmed before the request, so one that also changes the address still reaches the old one), `reset_link` (a reset link redeemed), `setup_link` (a setup link redeemed with a password on an account that could already sign in, naming the issuing admin) and `command_line` (`--reset-superadmin-password`, which builds a `mail.Service` and sends before it exits). The button opens `/forgot-password`, except in the owner's notice: that page never resets the owner, so it says instead that whoever has access to the server sets the password with `--reset-superadmin-password`. The notice is sent as soon as the password is written, before the sessions are ended, so a failure there cannot swallow it. `PasswordChanged` takes the account as it was before the change: one without a password (it signed in through the provider) gets `First`, and the copy says a password was set, not changed (`mail_password_set_*`, for the origins in `mail.FirstOrigins`; any other origin falls back to the "changed" copy rather than fail the render). The setup-link path reads that from `UserHasCredential`'s `has_password`, in the redeem's transaction.
- Redeeming decides between a notice and an invitation in `afterConsume` in `service/internal/auth/setup.go`, after the commit. `consumeWith` returns the link's `created_by` and `purpose` from the delete-returning `ConsumeSetupLink`, and `UserHasCredential` (a password, or a `user_identities` row created before the link's `created_at`), read in the same transaction before the password is written. The time matters because `oidc.setup` links the identity before it consumes the link: that fresh identity is not a credential the account had (`TestOIDCSetupOfNewcomerCallsNotifier`). A setup link on an account without a credential is a new person, handed to the `auth.Notifier` seam (`SetNotifier`; nil is off). One with a credential redeemed through OIDC mails `identity_linked` (below), naming the issuing admin, when `oidc.setup` added an identity: `user.Service.LinkIdentity` reports whether it inserted a row and `ConsumeSetupLinkByHash(ctx, hash, linked)` carries that on, so signing in with the identity the account had all along mails nothing (`TestOIDCSetupOnExistingAccountNoticesTheHolder`). Either notice goes to the address as it was before the redeem: `UserHasCredential` returns `email` and `email_verified` read before the mailed link verifies its own address, so whoever proved that mailbox by redeeming is never the one told (`TestSetupNoticeSkipsAnAddressTheRedeemConfirmed`).
- `auth.Service.EmailChanged(before, after, by)` mails `mail.EmailChanged` to `before`'s address when it was confirmed and differs from `after`'s, naming `by` when an admin did it. It shows the new address masked by `mail.MaskAddress` (`m…@example.org`), since the old mailbox may not be the holder's any more; an empty one says "removed" in subject, heading and body. `ConfirmChangedAddress` is `EmailChanged` then `ConfirmNewAddress`, which covers the profile save, the admin `PATCH` and `create-user`; `issue-setup-link {email}` calls `EmailChanged` right after the address is written, then either mails the link (which confirms) or calls `ConfirmNewAddress`.
- `auth.Service.IdentityLinked(u, origin, admin)` mails `mail.IdentityLinked` when a sign-in identity is linked to an account that could sign in already: `profile` from `oidc.link` when `LinkIdentity` added a row (the profile's "link provider"; `u` is the session's account from before the link, so an address the provider fills in just then hears nothing; `TestLinkFromProfileNoticesTheHolder`) and `setup_link` from `afterConsume`. It names the provider (the one in force, as `oidcSettings.Provider` resolves it from `REZEPTE_OIDC_NAME` or Settings → Sign-in, or the hint's stand-in when it has no name; [OIDC](/features/oidc)), the time and, for a setup link, the issuing admin; "Wasn't you?" says to sign in, remove the sign-in method in the profile and change the password, and to tell an admin (named for a setup link) when signing in fails; the owner's variant says the command line sets a new password, after which the owner signs in and removes it. It has no button. Unlinking sends nothing.

**The UI follows `mailEnabled`.** `GET /api/v1/settings` carries `mailEnabled` for every role. "Add account" always has an optional email field, since an address is profile data either way; with mail on, a link-mode create with an address mails the link. A row's "Setup link" then opens a send step first (`SendSetupLinkDialog.svelte`): mail the link to an address, prefilled and becoming the account's when changed (`issue-setup-link {email}`), or only show it. With mail off, neither offers mail and "Setup link" goes straight to the result dialog.

**Mailpit stands in for a provider** in development and e2e; [Verify UI with Playwright](/howtos/verify-ui#mail) owns how it is started, wired into the demo and read by the suite.

## Why it is this way

- **Synchronous inside the request.** An admin pressing "Create and send link" wants to know in that dialog whether it worked, and the link is on screen as a fallback either way. A queue would turn a visible failure into a silent one.
- **Plain `net/smtp`.** The standard library covers STARTTLS, implicit TLS and `PlainAuth`; the sender only adds the dial, so the deadline and the TLS mode are explicit. No new dependency.
- **Environment wins and locks, rather than seeding.** A deployment that pins mail in its compose file must not find the UI contradicting it, and a "seed once" copy in the database would outlive the variable.
- **The owner only.** Mail settings carry a credential and decide where every invitation goes; they are session-only and `403` for everyone but the owner, and not part of `get-settings`, which a `recipes:read` token can read.
- **Verify on redeeming, not on sending.** A typed address proves nothing; a person who opens a link from that mailbox proves it.

## Rejected

- **An outbox with retries.** It adds a table, a worker and a state to explain for one message an admin is watching. Mail nobody waits for would need one.
- **Mixing the sources, field by field.** Which value is in force would depend on two places.
- **Sending the SMTP error to every admin.** A server's reply can name internal hosts; the owner already has the test button.
- **Mail templates the owner edits.** Two languages and one frame stay in the repository.

## Limits

- The mails above are all it sends; a further notification is a new kind in [Notifications](/features/notifications) on the same sender.
- No rate limit per IP: the reset mail and the resend are limited per account, so a stranger can mail an account's owner a reset link once in five minutes, and nothing more.
- The owner is never reset by mail.
- No outbox, no retry: a failed send is reported once, and the admin passes the link on or sends it again.
- Nothing checks SPF, DKIM or deliverability; the user documentation points at the provider for the sender domain.
- One sender for the whole instance.
