A recipe is an aggregate, not a row: one `recipes` row plus ordered ingredient groups, the ordered ingredients inside them, ordered steps and a set of tags. Search covers the title, the description, the ingredient names and the tags, and the overview narrows that result down by tags, by total time and by the reader's own favorites, in any combination. [Data model](/architecture/data-model) owns the schema; [HTTP API](/architecture/api) owns the endpoints and their validation.

## How it works

**A source is a name, a link, or both.** `source_name` is free text (a book with its page, a website, a person) and `source_url` the http(s) link, kept apart so a cookbook can be credited without a URL and a website by name. `sourceLabel` in `frontend/src/lib/recipe/source.ts` owns the credit line's name-or-host rule (`SourceCredit`, see [Design system](/architecture/design-system)). Only the link is a target: it keeps the `^https?://` pattern that keeps `javascript:` out, and its `rel="noreferrer noopener external"` keeps the household's own address, or a public share's token, from the source site (see [Public shares](/features/public-shares)). The name is shown as typed - a leading "From" is not guessed away - and is not searched.

**One write path, the whole document.** `Service.Create` and `Service.Update` in `service/internal/recipe/service.go` each run inside a single `db.Tx`; there is no patch path for children.

- Before the transaction opens, `resolveRefs` resolves every step's ingredient references against the submitted document into ids `writeChildren` reuses. [Ingredient references](/features/ingredient-references) owns that resolution and its 422 on ambiguity.
- `Create` inserts the `recipes` row, writes the children (including the `step_references` and `step_times` rows) and the tags, then indexes the result. `CreateAnnounced` is the same write with `announce_pending` set, which queues the recipe for the household's daily new recipes mail ([Notifications](/features/notifications)). The paths that queue are an allowlist, the HTTP `create-recipe` (which the form and the URL and text import go through) and MCP `create_recipe`; archive import and the demo seed call `Create`, so restoring 80 recipes mails nobody.
- `Update` first runs `recipe.GuardEdit` (`ErrNotFound` when the row is gone, `ErrEditForbidden` for a caller the recipe is locked to), updates the editable fields, then deletes and rewrites everything below: `DeleteIngredientGroupsByRecipe` (cascades to `ingredients`), `DeleteStepsByRecipe` (cascades to `step_references` and `step_times`), `DeleteRecipeTags`, then `writeChildren`, `writeTags`, `DeleteOrphanTags` and the reindex.
- `Delete` runs in its own transaction and checks `CanDelete` before removing anything. Who passes either check is [Editing rights](/features/editing-rights).

**Positions are rewritten, never edited in place.** `writeChildren` assigns each ingredient group, each ingredient within its group and each step its 0-based `position` from the submission order, on every save.

**Every recipe names its author and its last editor.** `created_by`/`created_at` are written once; `updated_by`/`updated_at` move together on every change. `Create` seeds all four from the author, so "never edited" needs no NULL to handle. Reading it back takes **both** columns, which is what `hasBeenEdited` in `frontend/src/lib/recipe/authorship.ts` does: timestamps have second resolution ([Data model](/architecture/data-model)), so an edit landing in the same second as the create leaves `updated_at` identical, and a timestamp comparison alone would drop somebody else's name from the detail page. `Service.Update` takes the acting `user.User` as an argument, and so do `image.Service`'s `Upload`, `Delete`, `Reorder` and `SetCover` — each of them already moved `updated_at` through `TouchRecipe` or `SetRecipeCover`, and a photo change that left `updated_by` behind would credit the wrong person for it. Every handler reads that user from `auth.UserFrom(ctx)` the way `create-recipe` does, and the same user is what [Editing rights](/features/editing-rights) checks.

**The author and the last editor travel with the recipe, as people.** `Recipe` carries `createdBy` and `updatedBy` as a `Person` each - `{id, username, displayName, color}` - filled by `GetRecipeAuthors`, a join onto `users` that `load` runs once per detail response.

- The display name and the palette token (see [Users and authentication](/features/users-and-auth)) are joined on every read rather than copied onto the recipe, so a rename or a recolor reaches every card at once; the username is there because `?author=` filters by it.
- They are on the response, not resolved by the frontend, so a card needs no second request and a token scoped to `recipes:read`, which cannot read `/api/v1/people`, still gets the names.
- The query is separate from `GetRecipe` on purpose: that row is also what the image service reads to check a recipe exists.
- `Card` carries the same two, loaded per page by `ListAuthorsForIDs` in the same batched shape as its tags and favorites rather than joined into the list query. It also carries the cover photo's pixel width and height (`coverWidth`, `coverHeight`, null without a cover), loaded per page by `CoverSizesForRecipes`, so a card can reserve the photo's shape before it loads. A card draws one initial when author and editor are the same person, decided by id: a display name is deliberately not unique.

**Slugs are generated once.** `Slugify` in `service/internal/recipe/slug.go` transliterates German umlauts and `ß` the way German speakers spell them without diacritics (`ä`→`ae`, `ö`→`oe`, `ü`→`ue`, `ß`→`ss`, upper case included), strips the remaining diacritics through NFD, lower-cases, collapses every run outside `[a-z0-9]` into a single hyphen, trims hyphens off both ends and caps the result at 80 characters. `uniqueSlug` then walks `base`, `base-2`, `base-3` … until it finds one that is neither stored (`SlugExists`) nor reserved — `new` is reserved because the frontend routes `/recipes/new` to the editor itself. The slug is assigned in `Create` and `UpdateRecipe` never touches it.

**Tags are implicit.** There is no create-tag endpoint. `NormalizeTags` trims and lower-cases each name, drops the empty ones and dedupes while keeping first-occurrence order. `writeTags` calls `UpsertTag` — an upsert on the unique `name` — and links the result with `SetRecipeTag`. `DeleteOrphanTags` (`DELETE FROM tags WHERE id NOT IN (SELECT tag_id FROM recipe_tags)`, in `service/internal/db/queries/tags.sql`) runs on every update and every delete, so the `tags` table holds exactly the names at least one recipe carries, and `ListTagCounts` returns them with their counts, most used first.

**The search index is contentless and maintained in Go.** `recipes_fts` is declared in `service/internal/db/migrations/0002_recipes.sql` as an FTS5 virtual table over `title, description, ingredients, tags` with `content=''`, `contentless_delete=1` and `tokenize='unicode61 remove_diacritics 2'`: it stores the index, not a second copy of the text, and it is keyed by the host recipe row's SQLite `rowid`. `reindex` resolves that rowid, calls `DeleteFTS` and then `InsertFTS` with the title, the description, the ingredient names joined by spaces and the tag names joined by spaces — inside the same transaction as the write it indexes. `Delete` reads the rowid before dropping the row and removes the index entry the same way. No SQL triggers are involved, so every index write is plain Go that a test can call directly.

**Query translation.** `ftsQuery` in `service/internal/recipe/search.go` turns what the user typed into an FTS5 `MATCH` expression: it splits on whitespace, lower-cases each term and quotes it as a prefix match (`"term"*`, embedded quotes doubled). `variants` then adds the term's alternate German spelling in both directions — `kaese` gains `käse`, `käse` gains `kaese` — because the tokenizer's `remove_diacritics` folds `ä` to `a`, not to `ae`, so the two spellings would otherwise never meet in the index. The spellings of one term are combined with `OR` inside parentheses, and the terms are combined with an explicit `AND`: FTS5's implicit `AND` only holds between bare phrases, and two adjacent parenthesized groups without an operator are a syntax error. An empty query yields `""`, which the caller treats as "no search", not as a query.

**One list query, built from the filters that are set.** `ListRecipes` and `CountRecipes` in `service/internal/db/sqlc/recipe_list.go` take a `sqlc.RecipeFilter` — `Match`, `Tags`, `MaxMinutes`, `FavoritesOf`, `Author` — whose zero fields are filters that are off. `RecipeFilter.where` appends one `AND` condition per field that is set, so the list and its count share one `WHERE` by construction and a new filter axis is one field and one `if`. `List` in `service/internal/recipe/search.go` fills the filter and calls both; it does not branch on which filters are set. The statement is assembled from fixed fragments only: every value, the full-text expression and each tag name included, is a bound `?`.

**Full text is one more condition.** A set `Match` adds `r.rowid IN (SELECT rowid FROM recipes_fts WHERE recipes_fts MATCH ?)`. Because the condition is left out entirely when there is no search term, `recipes_fts` never sees an empty or `NULL` match expression, which are both errors in FTS5.

**Tags are plural and they narrow.** `?tags=dessert,schnell` keeps only the recipes carrying *all* of the listed names — huma reads a `[]string` query parameter as one comma-separated value, so this is a single parameter and not a repeated one. What turns "any of" into "all of" is `HAVING COUNT(DISTINCT t.name) = ?`, bound to the number of names, inside a subquery over `recipe_tags` and `tags` that binds one placeholder per name; the `HAVING` sits inside that subquery so the outer query stays one row per recipe. `List` runs the names through `normalizeTagQuery` in `service/internal/recipe/search.go`, which trims, lower-cases, drops blanks, de-duplicates and caps the list at 20 — the ceiling `Input.Tags` already carries on write, so a request cannot build an unbounded subquery. The handler and MCP pass the raw list and leave this to `List`, the one place every caller goes through: a duplicate would push the bound count past the distinct count and silently match nothing.

**Total time.** `MaxMinutes` keeps recipes whose `prep_minutes` and `cook_minutes`, each `COALESCE`d to 0, sum to `BETWEEN 1 AND` the bound — so a recipe with neither time set is excluded by any active bound rather than counted as instant. `0` is off. `List` ignores a negative value and does not clamp upwards, since an oversized bound merely fails to narrow anything further; the API caps the parameter at 1440. [Design system](/architecture/design-system) owns the scale of stops the control offers and how the URL is held to it.

**Favorites.** `favorites=true` narrows the list to the caller's own stars, and every card carries its own star whether that filter is on or not. [Favorites](/features/favorites) owns both.

**Added by.** `author=<username>` narrows the list to what one person wrote, matched against `users.username` through a subquery - an empty value is off, an unknown name matches nothing. It narrows by `created_by` alone: `updated_by` moves whenever anybody touches a recipe, images included, so filtering on it would hand a recipe to whoever last uploaded a photo. `GET /api/v1/authors` feeds the control with the writers and their counts, each a whole person (`id`, display name, color, `avatarId`), so its chips show the picture or the initial a card shows; `Service.Authors` leaves out anyone who has only edited, since selecting them could only ever return an empty grid. The chip's label is the display name, the filter itself is still the username - a link carrying `?author=` therefore survives a rename, and only what the chip reads changes.

**Sorting.** `sort` is `updated` (the default), `created`, `title` or `tasty`; [HTTP API](/architecture/api) owns how the parameter is validated. `normalizeSort` in `service/internal/recipe/search.go` maps it onto a `sqlc.RecipeSort`, and `ListRecipes` picks the matching `ORDER BY` from a fixed map, so the request never contributes SQL text. Anything outside that set falls back to `updated` in both places - a defense for in-process callers such as demo seeding, not a path an HTTP request can reach. Every order ends on `id DESC`, the tiebreak [Data model](/architecture/data-model) explains.

**The order is remembered on the device.** `$lib/recipe/sort-preference.ts` keeps the reader's last choice in `localStorage` (`rezepte-sort`), as the theme and the servings are kept: only the browser needs it, so it has no column on the account, and a phone and a laptop may well want different orders. `setSort` in `frontend/src/routes/+page.svelte` is the only writer, so only a choice made with the sort control or the phone's sort chip is stored; the default is stored as no entry. `applyRememberedSort` applies it in `load` and in `followUrl` alike wherever the address names no `sort` - in `followUrl` too, or arriving at a bare `/` would read as a change of order - so a link that names an order shows it without becoming the reader's own. `followUrl` first lets the page's own URL writes through untouched: `syncUrl` leaves the default order out, so a `?sort=updated` link is written back as a bare `/`, which would otherwise pick up the remembered order and refetch. The phone's sort chip forgets the stored order only when it is the one showing (`sort === readSort()`); a link's order it drops for the view alone. "Reset all filters" leaves the order alone, as before.

- `title` orders with the `unicode` collation that `service/internal/db/collate.go` registers with the driver (`golang.org/x/text/collate`): an umlaut sorts beside its base letter and case only breaks ties. SQLite's own `LOWER()` and `NOCASE` fold ASCII alone, which puts `Äpfel` or `Überbackene …` after `Z`.
- `tasty` counts each recipe's marks in a correlated subquery and falls back to the `updated` order on a tie; [Tasty](/features/tasty) says why there is no counter column.

**Tag counts follow the filters.** `GET /api/v1/tags` takes the list's `tags`, `maxMinutes`, `favorites` and `author`, and `Service.TagsFor` builds its filter through the same `ListParams.filter()` as `List`, so `ListTagCounts` counts tags among exactly the recipes the grid shows. Every tag it returns therefore narrows the grid without emptying it, and its count is what the grid holds once it is added; a tag none of those recipes carries is not returned. The search suggestions leave the search text out, since the overview types it to find a tag and a pick from them clears it: their counts are for the grid after the pick. The desktop row keeps the text when a tag is picked from it, so while there is a text it gets a second list with `q` passed too (`textTags`), and its counts stay true for the grid it narrows. `Tags(ctx)` is `TagsFor` without filters, for the import and the MCP tool. The suggestions' list refetches only when those four filters change, the row's only while a text is on (`refreshTags` and `tagList` in `frontend/src/routes/+page.svelte`), each on an AbortController of its own because "Load more" aborts the list's, and puts the chosen tags first, in the order they were picked, as every other active filter leads its row - adding back with a count of 0 every chosen tag the server no longer counts: a filter that empties the grid, or a link to a tag since removed, would otherwise take the chosen tag off the desktop row and out of the suggestions, with nothing left on screen to say what narrows the grid.

**Paging.** `List` clamps the page size to 24 by default and to `[1, 100]` otherwise, and the page number to at least 1. `CountRecipes` over the same filter is where the total comes from, so an empty page is a normal answer rather than a `404`.

**Six hand-written statements.** Two files in `service/internal/db/sqlc/` hold SQL that sqlc does not generate, written against the same `DBTX` abstraction it generates everywhere else. `fts.go` holds `GetRecipeRowID`, `DeleteFTS` and `InsertFTS`: sqlc's SQLite engine resolves the implicit `rowid` pseudo-column only through the FTS5 table-valued call form, and as a plain column reference — in a SELECT list, an INSERT column list or a WHERE equality — it is rejected on real and virtual tables alike. `recipe_list.go` holds `ListRecipes`, `CountRecipes` and `ListTagCounts`, because which conditions and which order they need depends on the request, and sqlc generates fixed statements.

## Why it is this way

The editor always submits the whole form, so there is nothing to diff: a partial update would have to reconstruct the submitted document anyway. Rewriting the whole document instead removes an entire class of position and ordering bugs, because positions are never patched, only re-derived from the order the client sent.

Because there is exactly one write path, the search index cannot drift structurally from the rows it describes. A bug can leave one recipe's entry stale until its next save; it cannot leave the index shaped differently from the data.

Slugs are fixed at creation so a permalink survives a title edit — the URL a household member bookmarked or pasted into a chat keeps working.

Tags being implicit means the tag list is always "the tags in use". There is no vocabulary to curate, no empty tag to clean up, and no second place where a tag can exist without a recipe behind it.

## Rejected

- **External-content FTS5 (`content='recipes'`) kept in sync by triggers.** The indexed row aggregates four tables — the recipe, its ingredients through their groups, and its tags through `recipe_tags` — so the triggers would have to reimplement `reindex` in SQL, where it is markedly harder to test than a Go function.
- **Hand-writing the whole query layer.** Six hand-written statements beside more than forty generated ones are a documented exception, not a reason to give up compile-time query checking for everything else.
- **Partial or `PATCH` updates to ingredient groups, ingredients or steps.** There is nothing to diff against a client that always sends the complete document.
- **`sqlc.slice()` beside `sqlc.arg()`.** Combined in the same query, it fails to bind for zero items and for two or more, and only appears to work for exactly one. `ListFavoriteRecipeIDs` needs both, so its recipe ids travel as one JSON array read back with `json_each()`.
- **A join per selected tag.** One `recipe_tags` join per chip is the textbook `AND` across a junction table, but it multiplies the rows the outer query has to collapse again, where one grouped subquery keeps it at one row per recipe.
- **One generated statement with switchable conditions.** Each filter as `(? = 0 OR ...)` keeps the list query inside sqlc, but the full-text match cannot be switched off from inside a query, `ORDER BY` cannot take a parameter, and sqlc only types a parameter it can compare against a column. It takes four copies of the same condition chain (list and count, with and without search), a `CAST` around every flag and the sort keys computed as `CASE` columns in a CTE — more workaround than query.
- **`OR` across the selected tags.** Picking a second chip would widen the grid. Narrowing is what picking another filter means to the person picking it.
- **Counting the tags in the browser.** The pages already fetched hold only part of the grid, so the counts would depend on how far the reader scrolled - the same flaw as narrowing there, below.
- **Counting the suggestions under the search text too.** There the text is what finds the tag, and picking it clears the text: counts taken with it would describe a grid the reader is about to leave.
- **Clearing the search text on a pick from the desktop row as well.** One list of counts would then do for both, but someone who searched "soup" and clicks "vegetarian" wants vegetarian soups.
- **Narrowing the extra tags in the browser.** Sending one tag to the server and filtering the rest against the pages already fetched under-reports every match sitting on a page nobody has scrolled to, and makes "no results" depend on how far the reader got rather than on the collection.

## Limits

- Every save rewrites the whole aggregate — the recipe row, its ingredient groups, its ingredients, its steps, its tag links and its index entry — so there is no cheap "rename one tag" or "reorder steps" path. At household scale that costs nothing worth optimizing, and it keeps the aggregate's invariants in one place.
- The credit line shows a link's host as it was typed, because `URL` hands an umlaut domain back as punycode and browsers offer no way back; `readableHost` uses the typed text only when `URL` parses it to the same host, which keeps a port or credentials out.
- Only the title, description, ingredient names and tags are indexed. A word that appears solely in a step is not findable through search.
- Terms are prefix-matched from the start of a token, so `kuchen` does not find `Apfelkuchen`.
- `ListRecipes`, `CountRecipes` and `ListTagCounts` are not checked by sqlc: a typo in a fragment surfaces when the query runs, not at generation. `service/internal/recipe/search_test.go` runs every filter, alone and combined, for that reason, and `TestTagsForCountsUnderTheFilter` holds every count `TagsFor` offers to what `List` then finds.
- A tag count costs a grouped join over `recipe_tags` per filter change, about as much as the filtered list query itself even at two hundred times a household's recipes, so it is not cached.
- `service/internal/db/sqlc/fts.go` can be deleted and its statements regenerated as soon as sqlc supports `rowid` outside the table-valued call form.
