A recipe is an aggregate, not a row: one `recipes` row plus ordered ingredient groups, the ordered ingredients inside them, ordered steps and a set of tags. Search covers the title, the description, the ingredient names and the tags, and the overview narrows that result down by tags, by total time and by the reader's own favorites, in any combination. [Data model](/architecture/data-model) owns the schema; [HTTP API](/architecture/api) owns the endpoints and their validation.

## How it works

**One write path, the whole document.** `Service.Create` and `Service.Update` in `service/internal/recipe/service.go` each run inside a single `db.Tx`. Before the transaction opens, `resolveRefs` resolves every step's ingredient references against the submitted document into ids `writeChildren` reuses ([Ingredient references](/features/ingredient-references) owns that resolution and refuses ambiguity with a 422 rather than write anything). `Create` inserts the `recipes` row, writes the children - including the resolved `step_references` rows - and the tags, then indexes the result. `Update` first runs `recipe.GuardEdit`, which loads the row (`ErrNotFound` when it is gone) and refuses a caller the recipe is locked to (`ErrEditForbidden`), then updates the editable fields, then deletes and rewrites everything below it: `DeleteIngredientGroupsByRecipe` (which cascades to `ingredients`), `DeleteStepsByRecipe` (which cascades to `step_references`), `DeleteRecipeTags`, followed by `writeChildren`, `writeTags`, `DeleteOrphanTags` and the reindex. There is no patch path for children. `Delete` runs in its own transaction and checks `CanDelete` before removing anything. Who passes either check is [Editing rights](/features/editing-rights).

**Positions are rewritten, never edited in place.** `writeChildren` assigns each ingredient group, each ingredient within its group and each step its 0-based `position` from the submission order, on every save.

**Every recipe names its author and its last editor.** `created_by`/`created_at` are written once; `updated_by`/`updated_at` move together on every change. `Create` seeds all four from the author, so "never edited" needs no NULL to handle. Reading it back takes **both** columns, which is what `hasBeenEdited` in `frontend/src/lib/recipe/authorship.ts` does: timestamps have second resolution ([Data model](/architecture/data-model)), so an edit landing in the same second as the create leaves `updated_at` identical, and a timestamp comparison alone would drop somebody else's name from the detail page. `Service.Update` takes the acting `user.User` as an argument, and so do `image.Service`'s `Upload`, `Delete`, `Reorder` and `SetCover` — each of them already moved `updated_at` through `TouchRecipe` or `SetRecipeCover`, and a photo change that left `updated_by` behind would credit the wrong person for it. Every handler reads that user from `auth.UserFrom(ctx)` the way `create-recipe` does, and the same user is what [Editing rights](/features/editing-rights) checks.

**The author and the last editor travel with the recipe, as people.** `Recipe` carries `createdBy` and `updatedBy` as a `Person` each - `{id, username, displayName, color}` - filled by `GetRecipeAuthors`, a join onto `users` that `load` runs once per detail response. The display name and the palette token (see [Users and authentication](/features/users-and-auth)) are joined on every read rather than copied onto the recipe, so a rename or a recolor reaches every card that names that person at once; the username is there because it is what `?author=` filters by. They are on the response rather than resolved by the frontend because user management is admin-only, so a member can look up neither an id nor a color. The query is separate from `GetRecipe` on purpose: that row is also what the image service reads to check a recipe exists, and it has no use for people. `Card` carries the same two, loaded per page by `ListAuthorsForIDs` in the same batched shape as its tags and favorites rather than joining `users` into the list query - the overview draws them as colored initials on every card, one circle when both are the same person. That is decided by id: a display name is deliberately not unique, two members may both be "Mia".

**Slugs are generated once.** `Slugify` in `service/internal/recipe/slug.go` transliterates German umlauts and `ß` the way German speakers spell them without diacritics (`ä`→`ae`, `ö`→`oe`, `ü`→`ue`, `ß`→`ss`, upper case included), strips the remaining diacritics through NFD, lower-cases, collapses every run outside `[a-z0-9]` into a single hyphen, trims hyphens off both ends and caps the result at 80 characters. `uniqueSlug` then walks `base`, `base-2`, `base-3` … until it finds one that is neither stored (`SlugExists`) nor reserved — `new` is reserved because the frontend routes `/recipes/new` to the editor itself. The slug is assigned in `Create` and `UpdateRecipe` never touches it.

**Tags are implicit.** There is no create-tag endpoint. `NormalizeTags` trims and lower-cases each name, drops the empty ones and dedupes while keeping first-occurrence order. `writeTags` calls `UpsertTag` — an upsert on the unique `name` — and links the result with `SetRecipeTag`. `DeleteOrphanTags` (`DELETE FROM tags WHERE id NOT IN (SELECT tag_id FROM recipe_tags)`, in `service/internal/db/queries/tags.sql`) runs on every update and every delete, so the `tags` table holds exactly the names at least one recipe carries, and `ListTagsWithCount` returns them with their counts, most used first.

**The search index is contentless and maintained in Go.** `recipes_fts` is declared in `service/internal/db/migrations/0002_recipes.sql` as an FTS5 virtual table over `title, description, ingredients, tags` with `content=''`, `contentless_delete=1` and `tokenize='unicode61 remove_diacritics 2'`: it stores the index, not a second copy of the text, and it is keyed by the host recipe row's SQLite `rowid`. `reindex` resolves that rowid, calls `DeleteFTS` and then `InsertFTS` with the title, the description, the ingredient names joined by spaces and the tag names joined by spaces — inside the same transaction as the write it indexes. `Delete` reads the rowid before dropping the row and removes the index entry the same way. No SQL triggers are involved, so every index write is plain Go that a test can call directly.

**Query translation.** `ftsQuery` in `service/internal/recipe/search.go` turns what the user typed into an FTS5 `MATCH` expression: it splits on whitespace, lower-cases each term and quotes it as a prefix match (`"term"*`, embedded quotes doubled). `variants` then adds the term's alternate German spelling in both directions — `kaese` gains `käse`, `käse` gains `kaese` — because the tokenizer's `remove_diacritics` folds `ä` to `a`, not to `ae`, so the two spellings would otherwise never meet in the index. The spellings of one term are combined with `OR` inside parentheses, and the terms are combined with an explicit `AND`: FTS5's implicit `AND` only holds between bare phrases, and two adjacent parenthesized groups without an operator are a syntax error. An empty query yields `""`, which the caller treats as "no search", not as a query.

**One list query, built from the filters that are set.** `ListRecipes` and `CountRecipes` in `service/internal/db/sqlc/recipe_list.go` take a `sqlc.RecipeFilter` — `Match`, `Tags`, `MaxMinutes`, `FavoritesOf`, `Author` — whose zero fields are filters that are off. `RecipeFilter.where` appends one `AND` condition per field that is set, so the list and its count share one `WHERE` by construction and a new filter axis is one field and one `if`. `List` in `service/internal/recipe/search.go` fills the filter and calls both; it does not branch on which filters are set. The statement is assembled from fixed fragments only: every value, the full-text expression and each tag name included, is a bound `?`.

**Full text is one more condition.** A set `Match` adds `r.rowid IN (SELECT rowid FROM recipes_fts WHERE recipes_fts MATCH ?)`. Because the condition is left out entirely when there is no search term, `recipes_fts` never sees an empty or `NULL` match expression, which are both errors in FTS5.

**Tags are plural and they narrow.** `?tags=dessert,schnell` keeps only the recipes carrying *all* of the listed names — huma reads a `[]string` query parameter as one comma-separated value, so this is a single parameter and not a repeated one. What turns "any of" into "all of" is `HAVING COUNT(DISTINCT t.name) = ?`, bound to the number of names, inside a subquery over `recipe_tags` and `tags` that binds one placeholder per name; the `HAVING` sits inside that subquery so the outer query stays one row per recipe. `NormalizeTagQuery` in `service/internal/recipe/handler.go` trims, lower-cases, drops blanks, de-duplicates and caps the list at 20 — the ceiling `Input.Tags` already carries on write, so a request cannot build an unbounded subquery — and `List` normalizes again instead of trusting the handler: a duplicate would push the bound count past the distinct count and silently match nothing.

**Total time.** `MaxMinutes` keeps recipes whose `prep_minutes` and `cook_minutes`, each `COALESCE`d to 0, sum to `BETWEEN 1 AND` the bound — so a recipe with neither time set is excluded by any active bound rather than counted as instant. `0` is off. `List` ignores a negative value and does not clamp upwards, since an oversized bound merely fails to narrow anything further; the API caps the parameter at 1440. [Design system](/architecture/design-system) owns the scale of stops the control offers and how the URL is held to it.

**Favorites.** `favorites=true` narrows the list to the caller's own stars, and every card carries its own star whether that filter is on or not. [Favorites](/features/favorites) owns both.

**Added by.** `author=<username>` narrows the list to what one person wrote, matched against `users.username` through a subquery - an empty value is off, an unknown name matches nothing. It narrows by `created_by` alone: `updated_by` moves whenever anybody touches a recipe, images included, so filtering on it would hand a recipe to whoever last uploaded a photo. `GET /api/v1/authors` feeds the control with the writers, their counts and the display name and color its chips show; `Service.Authors` leaves out anyone who has only edited, since selecting them could only ever return an empty grid. The chip's label is the display name, the filter itself is still the username - a link carrying `?author=` therefore survives a rename, and only what the chip reads changes.

**Sorting.** `sort` is `updated` (the default), `created` or `title` — [HTTP API](/architecture/api) owns how the parameter is validated. `normalizeSort` in `service/internal/recipe/search.go` maps it onto a `sqlc.RecipeSort`, and `ListRecipes` picks the matching `ORDER BY` from a fixed map; anything outside that set falls back to `updated` in both places, which is a defense for in-process callers such as demo seeding rather than a path an HTTP request can reach. The request never contributes SQL text, only the key into that map. `title` orders with the `unicode` collation that `service/internal/db/collate.go` registers with the driver, a Unicode collation from `golang.org/x/text/collate`: an umlaut sorts beside its base letter and case only breaks ties. SQLite's own `LOWER()` and `NOCASE` fold ASCII alone and compare bytes, which puts every title with a non-ASCII initial — `Äpfel`, `Überbackene …` — after `Z`. Every order ends on `id DESC`, the tiebreak [Data model](/architecture/data-model) explains.

**Paging.** `List` clamps the page size to 24 by default and to `[1, 100]` otherwise, and the page number to at least 1. `CountRecipes` over the same filter is where the total comes from, so an empty page is a normal answer rather than a `404`.

**Five hand-written statements.** Two files in `service/internal/db/sqlc/` hold SQL that sqlc does not generate, written against the same `DBTX` abstraction it generates everywhere else. `fts.go` holds `GetRecipeRowID`, `DeleteFTS` and `InsertFTS`: sqlc's SQLite engine resolves the implicit `rowid` pseudo-column only through the FTS5 table-valued call form, and as a plain column reference — in a SELECT list, an INSERT column list or a WHERE equality — it is rejected on real and virtual tables alike. `recipe_list.go` holds `ListRecipes` and `CountRecipes`, because which conditions and which order they need depends on the request, and sqlc generates fixed statements.

## Why it is this way

The editor always submits the whole form, so there is nothing to diff: a partial update would have to reconstruct the submitted document anyway. Rewriting the whole document instead removes an entire class of position and ordering bugs, because positions are never patched, only re-derived from the order the client sent.

Because there is exactly one write path, the search index cannot drift structurally from the rows it describes. A bug can leave one recipe's entry stale until its next save; it cannot leave the index shaped differently from the data.

Slugs are fixed at creation so a permalink survives a title edit — the URL a household member bookmarked or pasted into a chat keeps working.

Tags being implicit means the tag list is always "the tags in use". There is no vocabulary to curate, no empty tag to clean up, and no second place where a tag can exist without a recipe behind it.

## Rejected

- **External-content FTS5 (`content='recipes'`) kept in sync by triggers.** The indexed row aggregates four tables — the recipe, its ingredients through their groups, and its tags through `recipe_tags` — so the triggers would have to reimplement `reindex` in SQL, where it is markedly harder to test than a Go function.
- **Hand-writing the whole query layer.** Five hand-written statements beside more than forty generated ones are a documented exception, not a reason to give up compile-time query checking for everything else.
- **Partial or `PATCH` updates to ingredient groups, ingredients or steps.** There is nothing to diff against a client that always sends the complete document.
- **`sqlc.slice()` beside `sqlc.arg()`.** Combined in the same query, it fails to bind for zero items and for two or more, and only appears to work for exactly one. `ListFavoriteRecipeIDs` needs both, so its recipe ids travel as one JSON array read back with `json_each()`.
- **A join per selected tag.** One `recipe_tags` join per chip is the textbook `AND` across a junction table, but it multiplies the rows the outer query has to collapse again, where one grouped subquery keeps it at one row per recipe.
- **One generated statement with switchable conditions.** Each filter as `(? = 0 OR ...)` keeps the list query inside sqlc, but the full-text match cannot be switched off from inside a query, `ORDER BY` cannot take a parameter, and sqlc only types a parameter it can compare against a column. It takes four copies of the same condition chain (list and count, with and without search), a `CAST` around every flag and the sort keys computed as `CASE` columns in a CTE — more workaround than query.
- **`OR` across the selected tags.** Picking a second chip would widen the grid. Narrowing is what picking another filter means to the person picking it.
- **Narrowing the extra tags in the browser.** Sending one tag to the server and filtering the rest against the pages already fetched under-reports every match sitting on a page nobody has scrolled to, and makes "no results" depend on how far the reader got rather than on the collection.

## Limits

- Every save rewrites the whole aggregate — the recipe row, its ingredient groups, its ingredients, its steps, its tag links and its index entry — so there is no cheap "rename one tag" or "reorder steps" path. At household scale that costs nothing worth optimizing, and it keeps the aggregate's invariants in one place.
- Only the title, description, ingredient names and tags are indexed. A word that appears solely in a step is not findable through search.
- Terms are prefix-matched from the start of a token, so `kuchen` does not find `Apfelkuchen`.
- `ListRecipes` and `CountRecipes` are not checked by sqlc: a typo in a fragment surfaces when the query runs, not at generation. `service/internal/recipe/search_test.go` runs every filter, alone and combined, for that reason.
- `service/internal/db/sqlc/fts.go` can be deleted and its statements regenerated as soon as sqlc supports `rowid` outside the table-valued call form.
