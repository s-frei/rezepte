title: Recipes and search
description: The recipe aggregate, whole-document writes, slugs, implicit tags, the contentless FTS5 index and the filters over it

A recipe is an aggregate, not a row: one `recipes` row plus ordered ingredient groups, the ordered ingredients inside them, ordered steps and a set of tags. Search covers the title, the description, the ingredient names and the tags, and the overview narrows that result down by tags, by total time and by the reader's own favourites, in any combination. [Data model](/architecture/data-model) owns the schema; [HTTP API](/architecture/api) owns the endpoints and their validation.

## How it works

**One write path, the whole document.** `Service.Create` and `Service.Update` in `service/internal/recipe/service.go` each run inside a single `db.Tx`. `Create` inserts the `recipes` row, writes the children and the tags, then indexes the result. `Update` loads the row (`ErrNotFound` when it is gone), updates the editable fields, then deletes and rewrites everything below it: `DeleteIngredientGroupsByRecipe` (which cascades to `ingredients`), `DeleteStepsByRecipe`, `DeleteRecipeTags`, followed by `writeChildren`, `writeTags`, `DeleteOrphanTags` and the reindex. There is no patch path for children.

**Positions are rewritten, never edited in place.** `writeChildren` assigns each ingredient group, each ingredient within its group and each step its 0-based `position` from the submission order, on every save.

**Every recipe names its author and its last editor.** `created_by`/`created_at` are written once; `updated_by`/`updated_at` move together on every change. `Create` seeds all four from the author, so "never edited" needs no NULL to handle. Reading it back takes **both** columns, which is what `hasBeenEdited` in `frontend/src/lib/recipe/authorship.ts` does: timestamps have second resolution ([Data model](/architecture/data-model)), so an edit landing in the same second as the create leaves `updated_at` identical, and a timestamp comparison alone would drop somebody else's name from the detail page. `Service.Update` takes the editor's id as an argument, and so do `image.Service`'s `Upload`, `Delete`, `Reorder` and `SetCover` — each of them already moved `updated_at` through `TouchRecipe` or `SetRecipeCover`, and a photo change that left `updated_by` behind would credit the wrong person for it. Every handler reads the id from `auth.UserFrom(ctx)` the way `create-recipe` does; there is no ownership check anywhere, since any signed-in member may edit any recipe.

**The author's name and colour travel with the recipe.** `Recipe` carries `createdByName`, `createdByColor`, `updatedByName` and `updatedByColor` beside the two ids, filled by `GetRecipeAuthors` — a join onto `users` that `load` runs once per detail response. The name is the person's display name and the colour their palette token (see [Users and authentication](/features/users-and-auth)); both are joined on every read rather than copied onto the recipe, so a rename or a recolour reaches every card that names that person at once. They are on the response rather than resolved by the frontend because user management is admin-only, so a member can look up neither an id nor a colour. The query is separate from `GetRecipe` on purpose: that row is also what the image service reads to check a recipe exists, and it has no use for names. `Card` carries the same four, loaded per page by `ListAuthorsForIDs` in the same batched shape as its tags and favourites rather than joining `users` into the four filter queries - the overview draws them as coloured initials on every card.

**Slugs are generated once.** `Slugify` in `service/internal/recipe/slug.go` transliterates German umlauts and `ß` the way German speakers spell them without diacritics (`ä`→`ae`, `ö`→`oe`, `ü`→`ue`, `ß`→`ss`, upper case included), strips the remaining diacritics through NFD, lower-cases, collapses every run outside `[a-z0-9]` into a single hyphen, trims hyphens off both ends and caps the result at 80 characters. `uniqueSlug` then walks `base`, `base-2`, `base-3` … until it finds one that is neither stored (`SlugExists`) nor reserved — `new` is reserved because the frontend routes `/recipes/new` to the editor itself. The slug is assigned in `Create` and `UpdateRecipe` never touches it.

**Tags are implicit.** There is no create-tag endpoint. `NormalizeTags` trims and lower-cases each name, drops the empty ones and dedupes while keeping first-occurrence order. `writeTags` calls `UpsertTag` — an upsert on the unique `name` — and links the result with `SetRecipeTag`. `DeleteOrphanTags` (`DELETE FROM tags WHERE id NOT IN (SELECT tag_id FROM recipe_tags)`, in `service/internal/db/queries/tags.sql`) runs on every update and every delete, so the `tags` table holds exactly the names at least one recipe carries, and `ListTagsWithCount` returns them with their counts, most used first.

**The search index is contentless and maintained in Go.** `recipes_fts` is declared in `service/internal/db/migrations/0002_recipes.sql` as an FTS5 virtual table over `title, description, ingredients, tags` with `content=''`, `contentless_delete=1` and `tokenize='unicode61 remove_diacritics 2'`: it stores the index, not a second copy of the text, and it is keyed by the host recipe row's SQLite `rowid`. `reindex` resolves that rowid, calls `DeleteFTS` and then `InsertFTS` with the title, the description, the ingredient names joined by spaces and the tag names joined by spaces — inside the same transaction as the write it indexes. `Delete` reads the rowid before dropping the row and removes the index entry the same way. No SQL triggers are involved, so every index write is plain Go that a test can call directly.

**Query translation.** `ftsQuery` in `service/internal/recipe/search.go` turns what the user typed into an FTS5 `MATCH` expression: it splits on whitespace, lower-cases each term and quotes it as a prefix match (`"term"*`, embedded quotes doubled). `variants` then adds the term's alternate German spelling in both directions — `kaese` gains `käse`, `käse` gains `kaese` — because the tokenizer's `remove_diacritics` folds `ä` to `a`, not to `ae`, so the two spellings would otherwise never meet in the index. The spellings of one term are combined with `OR` inside parentheses, and the terms are combined with an explicit `AND`: FTS5's implicit `AND` only holds between bare phrases, and two adjacent parenthesized groups without an operator are a syntax error. An empty query yields `""`, which the caller treats as "no search", not as a query.

**Four list queries, one shape.** `service/internal/db/queries/recipes.sql` holds `ListRecipesFiltered`, `CountRecipesFiltered`, `SearchRecipesFiltered` and `CountSearchRecipesFiltered`. Every filter but the full-text one is a switchable `AND` condition — a clause that is a no-op at its zero value, such as `(CAST(sqlc.arg(max_minutes) AS INTEGER) = 0 OR ...)` — so another filter axis is one more `AND (...)` line in all four queries rather than another Go branch per combination. `listRows` in `service/internal/recipe/search.go` branches exactly once: on whether a search term is set.

**Why the full-text axis still needs two variants.** A match cannot be switched off from inside a query. `recipes_fts(NULL)` and `recipes_fts('')` are both errors, and SQLite does not promise to skip the subquery on the right of an `OR` whose left side already settled the row, so this condition cannot be made a no-op the way the others are. The search half therefore exists as its own pair of statements, matching through FTS5's table-valued call form (`SELECT rowid FROM recipes_fts(sqlc.arg(query))`) and carrying the same tag, time and favourite conditions verbatim.

**Tags are plural and they narrow.** `?tags=dessert,schnell` keeps only the recipes carrying *all* of the listed names — huma reads a `[]string` query parameter as one comma-separated value, so this is a single parameter and not a repeated one. What turns "any of" into "all of" is `HAVING COUNT(DISTINCT t.name) = CAST(sqlc.arg(tag_count) AS INTEGER)` inside a subquery over `recipe_tags` and `tags`; the `HAVING` sits inside that subquery so the outer query stays one row per recipe. `NormalizeTagQuery` in `service/internal/recipe/handler.go` trims, lower-cases, drops blanks, de-duplicates and caps the list at 20 — the ceiling `Input.Tags` already carries on write, so a request cannot build an unbounded subquery — and `List` normalises again instead of trusting the handler: a duplicate would push `tag_count` past the distinct count and silently match nothing.

**The names travel as a JSON array.** `listRows` marshals the normalised names and passes them as one `sqlc.arg(tag_names)`, which the query reads back with `SELECT value FROM json_each(sqlc.arg(tag_names))`. An empty slice has to marshal as `"[]"` and not as `"null"`, because the parameter must still be readable JSON when the condition is switched off. `sqlc.slice()` is the obvious form for an `IN (...)` list and works where it stands alone — `ListTagNamesForRecipes` uses it — but it cannot be combined with `sqlc.arg()` in the same query, and this one needs `sqlc.arg()` for `tag_count` whatever the tag list does.

**Once one parameter is `sqlc.arg()`, every parameter is.** `sqlc.arg()` compiles to an explicitly numbered `?N`. SQLite numbers the plain `?` placeholders in the same statement *after* the highest explicit index, and the Go driver then never binds them — a silent mismatch rather than an error at generation or at run time. So `limit`, `offset` and `query` are `sqlc.arg()` too, although nothing about them on its own asks for it: a bare `?` beside a `sqlc.arg()` is the mismatch, so the rule is all or none per statement.

**A `CAST` is what gives a parameter a Go type.** A `sqlc.arg()` that is only ever compared against a literal leaves sqlc no column to infer from, and comes out as `interface{}` — whose Go zero value is `nil`, not `0`. A caller that leaves such a field unset, meaning "filter off", then binds SQL `NULL`, and the condition's `= 0` test is false instead of switching anything off. `CAST(... AS INTEGER)` around `tag_count`, `max_minutes` and `favourites_only`, and `CAST(... AS TEXT)` around `sort`, are what make them `int64` and `string` in the generated params structs. `tag_names` stays `interface{}` on purpose: nothing compares it, `json_each` reads it.

**Total time.** `maxMinutes` keeps recipes whose `prep_minutes` and `cook_minutes`, each `COALESCE`d to 0, sum to `BETWEEN 1 AND` the bound — so a recipe with neither time set is excluded by any active bound rather than counted as instant. `0` is off. `List` floors a negative value to 0 and does not clamp upwards, since an oversized bound merely fails to narrow anything further; the API caps the parameter at 1440. [Design system](/architecture/design-system) owns the scale of stops the control offers and how the URL is held to it.

**Favourites.** `favourites=true` narrows the list to the caller's own stars, and every card carries its own star whether that filter is on or not. [Favourites](/features/favourites) owns both.

**Added by.** `author=<username>` narrows the list to what one person wrote, matched against `users.username` through a subquery in the same switchable shape as the other axes - an empty value is the no-op, an unknown name matches nothing. It narrows by `created_by` alone: `updated_by` moves whenever anybody touches a recipe, images included, so filtering on it would hand a recipe to whoever last uploaded a photo. `GET /api/v1/authors` feeds the control with the writers, their counts and the display name and colour its chips show; `Service.Authors` leaves out anyone who has only edited, since selecting them could only ever return an empty grid. The chip's label is the display name, the filter itself is still the username - a link carrying `?author=` therefore survives a rename, and only what the chip reads changes.

**Sorting.** `sort` is `updated` (the default), `created` or `title` — [HTTP API](/architecture/api) owns how the parameter is validated. `normalizeSort` in `service/internal/recipe/search.go` maps anything outside that set onto `updated` for every caller of `List`, which is a defence for in-process callers such as demo seeding rather than a path an HTTP request can reach. `ORDER BY` cannot be parameterised: a `sqlc.arg()` there binds a value, it does not splice in a column or a direction. Each list query therefore computes three sort keys in a CTE's select list (`CASE WHEN CAST(sqlc.arg(sort) AS TEXT) = 'created' THEN r.created_at END` and its two siblings) and orders by their aliases, `sort_created DESC, sort_title ASC, sort_updated DESC, id DESC`; the two keys the request did not ask for are `NULL` on every row and order nothing, and an unknown value falls into the third arm, which is the default order. The `id DESC` tiebreak is the one [Data model](/architecture/data-model) explains. The CTE is not cosmetic: sqlc's SQLite engine does not rewrite a `sqlc.arg()` that appears *solely* inside `ORDER BY` into a bind parameter — it leaves the call as literal SQL text, adds no field to the params struct, and SQLite rejects the statement at run time. Computing the keys as columns keeps the call inside a select list, where the rewrite does happen. Because the CTE carries three columns beyond the recipe's own, the outer `SELECT` names the recipe columns instead of using `*`, and sqlc synthesises `ListRecipesFilteredRow` and `SearchRecipesFilteredRow` — identical to `sqlc.Recipe` field for field, which is what lets `toRecipesFromList` and `toRecipesFromSearch` convert them one element at a time.

**Paging.** `List` clamps the page size to 24 by default and to `[1, 100]` otherwise, and the page number to at least 1. The count query beside each list query is where the total comes from, so an empty page is a normal answer rather than a `404`.

**Three hand-written statements.** `GetRecipeRowID`, `DeleteFTS` and `InsertFTS` live in `service/internal/db/sqlc/fts.go` rather than in a `.sql` file. sqlc's SQLite engine resolves the implicit `rowid` pseudo-column only through the FTS5 table-valued call form; as a plain column reference — in a SELECT list, an INSERT column list or a WHERE equality — it is rejected on real and virtual tables alike, so these three cannot be generated. They are written against the same `DBTX` abstraction sqlc generates everywhere else, and the file's header says why.

## Why it is this way

The editor always submits the whole form, so there is nothing to diff: a partial update would have to reconstruct the submitted document anyway. Rewriting the whole document instead removes an entire class of position and ordering bugs, because positions are never patched, only re-derived from the order the client sent.

Because there is exactly one write path, the search index cannot drift structurally from the rows it describes. A bug can leave one recipe's entry stale until its next save; it cannot leave the index shaped differently from the data.

Slugs are fixed at creation so a permalink survives a title edit — the URL a household member bookmarked or pasted into a chat keeps working.

Tags being implicit means the tag list is always "the tags in use". There is no vocabulary to curate, no empty tag to clean up, and no second place where a tag can exist without a recipe behind it.

## Rejected

- **External-content FTS5 (`content='recipes'`) kept in sync by triggers.** The indexed row aggregates four tables — the recipe, its ingredients through their groups, and its tags through `recipe_tags` — so the triggers would have to reimplement `reindex` in SQL, where it is markedly harder to test than a Go function.
- **Hand-writing the whole query layer.** Three hand-written statements beside more than fifty generated ones are a documented exception, not a reason to give up compile-time query checking for everything else.
- **Partial or `PATCH` updates to ingredient groups, ingredients or steps.** There is nothing to diff against a client that always sends the complete document.
- **`sqlc.slice()` for the tag list.** Combined with `sqlc.arg()` in the same query it fails to bind for zero tags and for two or more, and only appears to work for exactly one. The query needs `sqlc.arg()` for `tag_count` whatever the tag list does.
- **A join per selected tag.** One `recipe_tags` join per chip is the textbook `AND` across a junction table, but the number of joins depends on the request, so the SQL would have to be assembled as a string — giving up compile-time checking on exactly the query that carries the most parameters.
- **`OR` across the selected tags.** Picking a second chip would widen the grid. Narrowing is what picking another filter means to the person picking it.
- **Narrowing the extra tags in the browser.** Sending one tag to the server and filtering the rest against the pages already fetched under-reports every match sitting on a page nobody has scrolled to, and makes "no results" depend on how far the reader got rather than on the collection.

## Limits

- Every save rewrites the whole aggregate — the recipe row, its ingredient groups, its ingredients, its steps, its tag links and its index entry — so there is no cheap "rename one tag" or "reorder steps" path. At household scale that costs nothing worth optimising, and it keeps the aggregate's invariants in one place.
- Only the title, description, ingredient names and tags are indexed. A word that appears solely in a step is not findable through search.
- Terms are prefix-matched from the start of a token, so `kuchen` does not find `Apfelkuchen`.
- The tag, time and favourite conditions are repeated verbatim in all four list queries. A new filter axis has to be added to each of them in step, which is mechanical but real — the price of a condition sqlc can check over one it would have to be handed as a string.
- `service/internal/db/sqlc/fts.go` can be deleted and its statements regenerated as soon as sqlc supports `rowid` outside the table-valued call form.
