title: Favorites
description: A per-user star kept in its own join table, derived from the session and loaded one batch per page

The household shares one recipe collection, but a star on a recipe is personal: several people use the same instance, and one person's favorites are not another's. The overview can narrow down to the caller's own stars, and every card shows the star as the person looking at it set it. [Data model](/architecture/data-model) owns the table; [HTTP API](/architecture/api) owns the endpoints.

## How it works

**One row per (user, recipe).** A star is a row in `favorites`, declared in `service/internal/db/migrations/0002_recipes.sql`: starring inserts it, unstarring deletes it, and there is no per-recipe state to update. [Data model](/architecture/data-model) owns the columns, the key and the cascades.

**The caller comes from the auth context and from nowhere else.** `set-favorite` (`PUT /api/v1/recipes/{id}/favorite`) and `delete-favorite` (`DELETE` on the same path) each read `auth.UserFrom(ctx)` and answer `401` when there is none; the list handler takes the caller from the same place and falls back to an empty id rather than to a parameter, and `fillCaller` returns without touching the flag when there is no caller. MCP's `add_favorite` and `remove_favorite` act the same way, through a token, as the token owner - see [MCP](/features/mcp). No path, query or body parameter names a user anywhere on this surface, so one person cannot address another person's stars — by construction, rather than by a check somebody has to remember to repeat on the next endpoint.

**The star is a state, not an event.** `SetFavorite` in `service/internal/recipe/service.go` writes with `INSERT OR IGNORE`, so starring twice is not an error, and clears with a plain `DELETE`, so unstarring something that was never starred is not one either. Starring checks the recipe exists first and maps a missing one to `ErrNotFound`, which the handler turns into `404`: `favorites.recipe_id` carries a foreign key, and `INSERT OR IGNORE` swallows only its own uniqueness conflict, never a foreign-key violation, so an unchecked insert against a missing recipe would surface as a raw constraint error instead. Unstarring is deliberately not checked that way — deleting a favorite that was never there is the same "already in the desired state" idempotency `DELETE` has everywhere else in the package.

**Every list request carries the caller's id, not only a filtered one.** The list handler fills `ListParams.UserID` from the context on every request, because `Card.Favorite` has to be right on every card of every page, not only on the pages a `favorites=true` request returns. The filter itself is one more condition on `sqlc.RecipeFilter`: `List` sets `FavoritesOf` to the caller's id when `favorites=true`, which adds `r.id IN (SELECT recipe_id FROM favorites WHERE user_id = ?)`. An empty `UserID` leaves it unset, so a request without a caller gets the unfiltered list rather than an empty one. [Recipes and search](/features/recipes) owns how the filter is built.

**One batched lookup per page, not one per card.** `toCards` marshals the page's recipe ids to a JSON array and runs `ListFavoriteRecipeIDs` once, beside the tag batch it already runs, then reads each card's state out of the resulting set. A detail page takes the same query with a one-element array through `(*Service).IsFavorite`, called by `(*Service).FillCaller`.

**An empty user id disables the lookup rather than matching rows.** `IsFavorite` returns false without querying, `toCards` skips the batch entirely, and `List` copies the id into `FavoritesOf` only when the request asks for favorites, while `sqlc.RecipeFilter` adds the favorites condition only for a non-empty `FavoritesOf` - so an empty id turns the filter off instead of comparing `user_id` against an empty string. `(*Service).Count` - the one caller with no user behind it, used by demo seeding to decide whether a database already holds recipes - passes an empty `sqlc.RecipeFilter{}` and so counts every recipe.

**The star is optimistic in the browser.** `FavoriteStar.svelte` flips the icon, calls the endpoint, and on failure puts the previous value back and raises a toast. It never sits inside a link: a `<button>` inside an `<a>` is invalid HTML and a focus trap, and the whole card *is* one link, so `RecipeCard.svelte` wraps both in a `relative` container and positions the star absolutely over the image as the anchor's sibling — Tab then reaches the star and the card link as two separate stops. The detail page puts it in the line under the title, outside any link, for the same reason. The component guards its click with `preventDefault` and `stopPropagation` anyway, since it sits visually over a link on a card.

**The card shows the star from `md` up only.** On a phone the card image is about 150px wide and the 36px circle covers a large part of the photo, so the star's wrapper is `hidden md:block` and a phone sets the star on the recipe page, where the star is 44px, the phone floor for an action, and 36px from `md` up. The [tasty](/features/tasty) mark follows the same split, in the image's opposite corner. The split follows the layout, not the card's size: `md` is where the whole app turns from bottom nav to top bar, so the controls come and go exactly once while a window is resized. The room they need from `md` up is the grid's to guarantee - `RecipeGrid.svelte` never lets a column fall below 220px (three columns just past `md`, where four fixed ones would leave 160px cards mostly covered) and never adds a fifth.

## Why it is this way

A column on `recipes` can hold exactly one answer, and the question has as many answers as the household has members. A join table is the shape that has somewhere to put "whose" — and, as a side effect, the referential integrity that keeps a favorite from outliving either end of it.

Deriving the user from the session makes isolation a property of the code's shape rather than of its discipline. There is no parameter to forget to validate, because there is no parameter.

Loading the state one batch per page keeps a list at a fixed number of queries however many cards it shows, which is the same bargain the tag lookup beside it already made. Loading it on every list rather than only on a filtered one is what keeps the star from lying: a page that showed every star empty until the reader switched a filter on would be wrong far more often than right.

## Rejected

- **The star on phone cards.** It covers too much of a photo that narrow, and a card is mostly tapped to open the recipe; the recipe page has the room for the star.
- **Hiding the controls on cards below a width (a container query).** It would cover the photo less, but a button that appears and vanishes several times while a window is resized, with no visible reason, reads as broken. The grid keeps cards wide enough instead.

- **A `favorite` boolean column on `recipes`.** One flag for a household of several people: there is nowhere to put the second person's answer, which is the whole requirement.
- **A JSON array of user ids on `recipes`.** It avoids the join table, but turns "is this one of mine" into a per-row JSON scan instead of an indexed lookup, and gives up the foreign keys that clean up after a deleted user.
- **Taking the user id from the request and trusting it for an authenticated caller.** It makes whose favorites are being read a value the client chooses rather than a fact the server derives — exactly the class of mistake the session-only rule exists to rule out.
- **Asking per card.** A star per card is a query per card on the busiest page in the app, for state a single `IN (...)` already answers for the whole page.

## Limits

- `Recipe.Favorite` is filled by the handler, not by `ByID` or `BySlug`: get, get by slug, create and update each call `fillCaller`, which takes the caller from the auth context and hands it to `(*Service).FillCaller`; that one method sets the star, the tasty mark and the [editing rights](/features/editing-rights) fields, and MCP's `get_recipe`, `create_recipe` and `update_recipe` call it too, through `caller.fill` (see [MCP](/features/mcp)). Any further handler or tool that loads through `ByID` or `BySlug` answers `false` unless it calls `fillCaller` or `IsFavorite` itself.
- Favorite rows disappear with the user (`ON DELETE CASCADE`), which is what personal state should do and worth knowing before deleting a household member.
- `favorites.created_at` is written and nothing reads it. There is no "recently starred" order and no date on the star.
- An authenticated list costs one query more than an unauthenticated one would, per page.
