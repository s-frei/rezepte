A household cooks the same recipe for different numbers of people without editing it. The detail page carries a servings stepper, and `/recipes/[slug]/cook` is a full-screen step-by-step mode for a phone propped up on the counter. Both live in the browser: the chosen servings and the cook's position in the steps never reach the service, which stores only what the author wrote.

## How it works

**The detail page keeps the method readable.** `RecipeView.svelte` sets ingredients and method side by side only from 840px, so the method column keeps at least 420px for its text and its "Method | Comments" tabs; below that they stack. Stacked, between 600px and 840px, an `IngredientList` given the `columns` prop - only the detail page passes it, cook mode's sheet keeps one column - splits a list of `MIN_ROWS` or more into two columns through `splitColumns` in `frontend/src/lib/recipe/ingredient-columns.ts`. That is not CSS multi-column, which leaves a divider under the first column's last row and gives no say over where the break falls; every row keeps its `ingredientKey`. A step's text stops near 68 characters a line (`StepList.svelte`) however wide the method column grows.

**An ingredient row is a number, then a sentence.** `IngredientList.svelte` lays every row out on one grid, `22px max-content minmax(0,1fr)`: the checkbox, the number right-aligned in a column as wide as the list's widest number, then the unit, the name and the note as one wrapping run of text. Number and unit are `text-primary` semibold - the color a quantity has in a step's text - and the name stays `text-text`, so the orange block is the amount and the ingredient starts where the color stops. The groups reach that grid through `grid-cols-subgrid` on the column, the `ul` and the `li`, so while the columns stack every number of every group ends on one edge; side by side on a tablet each column carries a grid of its own. The checkbox sits on the first line (`self-start`, offset by half of `1lh` minus its size) rather than mid-row, so a row whose name wraps keeps box, number and unit together. The text cell carries `break-words hyphens-auto`, because a German compound such as "Rinderhackfleischbällchen" is wider than a 320px row's text column and `minmax(0,1fr)` only keeps the cell's box inside the card, not its glyphs. `[hyphenate-limit-chars:12_6_6]` confines the hyphenation to words of twelve letters or more: without it the browser splits every word it can ("Muskat-nuss", "Hack-fleisch") rather than moving a short one to the next line, and the list reads restless. Browsers without the property hyphenate by their own defaults. A ticked row turns all of it `text-text-muted`; unit and name sit in one struck span, so the line runs through the space between them, and the note stays unstruck. `e2e/cooking.test.ts` holds the row at 320px with a long unit beside a wide number and a long compound, and measures number and text by their own extent through a `Range`: a cell keeps a clean box while its text spills into the name or past the card, so the box alone passes a broken row.

**The arithmetic runs in the browser, against the recipe's own servings.** The stored `servings` is the baseline every quantity is written for. `scaleQuantity` in `frontend/src/lib/recipe/scale.ts` is `quantity × to / from`, and the chosen `to` never leaves the browser — there is no query parameter, no endpoint and no column for it. A base or target that is zero or negative, and the identity case, return the stored value untouched, so no `x × n / n` drift and no `Infinity` from a nonsensical input. Units are free text and are never converted; only the number moves.

**Rounding, by band.** `roundScaled` keeps the sign and works on the absolute value:

| Value | Rule |
|---|---|
| below 1 | snaps onto 0, ¼, ⅓, ½, ⅔, ¾ or 1 when within `SNAP_TOLERANCE` (0.04), otherwise one decimal |
| 1 up to 10 | a fractional part within 0.04 of ⅓ or ⅔ keeps that third, everything else rounds to the nearest quarter |
| from 10 | whole numbers |

`SNAP_TARGETS_BELOW_ONE` is `[0, 0.25, 1/3, 0.5, 2/3, 0.75, 1]` and `THIRDS` is `[1/3, 2/3]`; the comparison adds `1e-9` to the tolerance, because a window edge such as `0.29 - 0.25` is `0.04000000000000004` in binary floating point and would otherwise fall outside its own band.

**One formatter for every quantity.** `formatScaled` hands the rounded number to `formatQuantity` in `frontend/src/lib/recipe/format.ts`, the same function the unscaled list uses. It renders whole numbers plain, looks the fractional part up in one glyph table (`0.5` → ½, `0.25` → ¼, `0.75` → ¾, `0.33` → ⅓, `0.67` → ⅔) after rounding it to two decimals, prefixes an integer part when there is one (`1 ½`), and otherwise falls back to at most two decimals with the current locale's own decimal separator (a period in English, a comma in German). That two-decimal rounding is what makes `n + 1/3` from `roundScaled` come out as ⅓ rather than as `1,33`.

**The baseline is rendered exactly.** `formatQuantityFor` short-circuits when `from === to` and formats the stored number directly, skipping the rounding path entirely. Returning the stepper to the recipe's own servings can therefore never change a number the author typed.

**A step's text renders through `StepText`, never as a plain string.** `StepList.svelte` on the detail page and the cook route both hand their steps to `frontend/src/lib/components/recipe/StepText.svelte`, which resolves each step's stored ingredient references against the current servings through the same `formatQuantityFor` the ingredient list uses - a reference's quantity therefore scales with the stepper exactly as the list does, and moves the moment cook mode's own stepper does. [Ingredient references](/features/ingredient-references) owns what a reference is and how it is resolved; this is only the render path both surfaces share. `StepText` also marks a step's stored times, in cook mode too, which [Step times](/features/step-times) owns.

**The choice persists per recipe, in `localStorage`.** `servingsKey` builds `rezepte-servings:<recipeId>` from `SERVINGS_STORAGE_PREFIX`. `Servings` in `frontend/src/lib/recipe/servings.svelte.ts` is a `$state` class whose `value` starts from the stored entry and falls back to the baseline; `set` clamps through `clampServings` to whole numbers in `[SERVINGS_MIN, SERVINGS_MAX]` (1 to 99, the editor's own bounds) and writes the key only while the value differs from the baseline — returning to the baseline removes it, so a recipe nobody scaled leaves nothing behind. `parseServings` trusts a stored string only when it is one or two digits inside the range. Every read and write is wrapped in `try`/`catch`, because `window.localStorage` throws outright when site data is blocked. `clearServings` drops the key when the recipe is deleted. The detail page and cook mode each build their own instance through `createServings` and share only the key, which is how a scaling choice carries into cook mode without any URL state. The pure rules live in `frontend/src/lib/recipe/servings.ts`, separate from the rune class, so they are unit-testable without a browser.

**The ingredient list copies as text, in two shapes.** Both are scaled through `formatQuantityFor` to the chosen servings, and both go through `copyText` in `share.svelte.ts`, the one clipboard-and-toast call that is also behind "Copy link"; [Recipe card](/features/recipe-card) owns its fallback without https.

- The stub at the foot of a `copyable` `IngredientList` (the detail page and a public share page, which renders the same `RecipeView`) copies `shoppingList` from `frontend/src/lib/recipe/ingredient-text.ts`: every ingredient not ticked off, one per line, without group names or notes, because Reminders, Todoist and Keep turn every pasted line into an item and a group name or "(sifted)" would become one too. With everything ticked it is disabled.
- The copy on the ingredients heading copies `fullList`, the list as the page shows it with group names and notes, for a message or a note.
- Cook mode's ingredient sheet leaves `copyable` off: by then the shopping is done.

**Cook mode is a bare route.** `frontend/src/routes/+layout.svelte` compares `page.route.id` against `/recipes/[slug]/cook` — the route id, not the pathname, so the check is exact and independent of the slug — and renders it without `AppShell`, without the command palette and without its `Cmd+K` handler, the same way it treats `/login`. The page shows one step per view with a step counter and a segmented `role="progressbar"`; next becomes "finish" on the last step. The step on screen lives in the URL as `?step=N` (1-based): it opens there through `clampStep`, a missing or invalid value at the first, and every step change replaces it (`replaceState`, no history entry per step), so a reload, a shared link and a timer all land on that step; any value that is not the step on screen is rewritten after the navigation. Under the progress bar sits a banner per ended timer, and between the step and the footer the timer dock - both owned by [Cook timers](/features/cook-timers).

**The step is set in one of five type sizes, for this visit only.** `TYPE_SIZES` and `TYPE_SIZE_CLASSES` in `frontend/src/lib/recipe/type-size.ts` own the sizes and their tokens: a smaller scale on a phone, where a long step and a long word have to fit, a larger one from `md` for a tablet read from across the kitchen, and `DEFAULT_TYPE_SIZE` in the middle so there are two steps down and two up. The choice is a plain `$state` on the cook page, with no storage key and no URL state, so every visit starts at the default (see Rejected).

- `frontend/src/lib/components/cook/TypeSpecimen.svelte` is the control, a Bits UI `Popover` around a `RadioGroup`; its comments explain why letters, rule and marks are one grid and why the trigger's letters use `text-box` trimming rather than a fixed em shift, which lands a pixel off depending on pixel density.
- The step paragraph in the cook route carries three phone traps, each commented there: `hyphenate-limit-chars: 12 4 4`, because a quantity follows its word with a margin, not a space, so Chrome counts "potatoes(1" as one word and a smaller limit would split it; `w-full`, because Chromium otherwise sizes a word with its quantity attached as one unhyphenated block and clips it on a narrow phone; and `justify-center-safe` on the section, so a step taller than the view starts at the top and scrolls.

**Keyboard, pointer and motion.** A `svelte:window` handler takes `ArrowRight`, `ArrowLeft` and `Escape`; it stands down when the event is already `defaultPrevented`, when `Alt`, `Meta` or `Control` is held — `Cmd+Left` is the browser's own Back and must not page a step — while the ingredient sheet or the type specimen is open, and while focus is inside the timer dock. The specimen's `Escape` needs no extra guard: Bits UI's escape layer calls `preventDefault` on it, so it closes the popover and the page handler stands down. A pointer gesture is measured from `pointerdown` to `pointerup` and needs `SWIPE_THRESHOLD` (50 px) of horizontal travel to page, with `pointercancel` and `pointerleave` forgetting the start so an unrelated later `pointerup` is not measured against it. Each step change is a 200 ms fly-in against a fade-out, dropping to 0 ms under `prefersReducedMotion`. Leaving calls `history.back()` when the cook arrived from the detail page and replaces the entry otherwise, so the browser's Back button does not drop them into cook mode again.

**The screen stays awake while it can.** `ScreenWakeLock` in `frontend/src/lib/recipe/wake-lock.svelte.ts` wraps requesting and releasing a `screen` lock; the cook page's `onMount` acquires one, registers the `visibilitychange` listener that acquires it again when the tab becomes visible — the browser drops the lock while the tab is hidden — and releases it on teardown. A generation counter is bumped by every `acquire` and `release`, so a request that resolves after the page is gone releases its sentinel instead of installing one nobody owns. `active` is `$state` and false whenever no sentinel is held — the API is missing outside a secure context and the request rejects for a hidden tab, a policy or a low battery — so the "screen stays on" caption appears only when the lock is real.

**The ingredient sheet is a plain fixed panel.** It carries `role="dialog"` and `aria-modal="true"`, moves focus into itself when it opens and back onto the collapsed toggle when it closes, and owns `Escape` while open: its own handler closes it and calls `preventDefault`, which is exactly what stops the page handler from leaving cook mode. The rest of the page is marked `inert` through a `display: contents` wrapper, so the flex column keeps its shape while everything behind the sheet becomes unreachable. The collapsed toggle stays mounted but `invisible`, which keeps its height in the column and takes it out of both the tab order and the accessibility tree. Inside, the sheet reuses `ServingsStepper` and `IngredientList`, so the servings and the ticked-off ingredients are the same state as on the detail page.

## Why it is this way

Scaling in the browser is zero backend work and zero schema risk. The service stores what the author wrote and nothing else, so there is no migration, no endpoint and no cache to invalidate behind a feature that is arithmetic over numbers the client already holds.

A per-cook preference is not recipe data. Two people can have the same recipe open at different servings, and neither of them is editing anything.

The rounding the kitchen wants is opinionated: `2.6` reads as "2 ½" and `1.1` as "1". That is a cookbook number rather than an exact one, and below 10 it costs at most an eighth. Anyone who needs the exact arithmetic edits the recipe's baseline instead.

A unit is free text, and German ones run long - "Messerspitze", "Packungen". A cell that holds number and unit has to be as wide as the longest unit any recipe uses, and on a 320px phone that leaves the name too little room; numbers stay short however the stepper scales them, so only the number gets a column and the unit wraps with the name. The orange carries the split between amount and ingredient: it measures 4.8:1 on `surface` in light and 5.2:1 in dark, above AA but a third of the text's contrast, which is why it marks the amount only and never the name.

The step is in the URL and the type size is not: where the cook is in a recipe is an address a timer, a notification and a reload all need to reach, while the type size is a setting for the moment.

`inert` is what makes the sheet's `aria-modal="true"` truthful. The alternative is a hand-rolled focus trap that would then have to be reconciled with the step view's own key handling, for a panel whose modality lasts as long as a glance at the ingredients.

## Rejected

- **A `?servings=` query parameter.** The choice would be lost on the way back to the detail page and on every card link out of it; a key by recipe id survives both, and the reload.
- **A `servings` column or a `PATCH` endpoint for the chosen value.** It turns a personal preference into shared recipe data and forces a write on every tap of "+".
- **Nearest-quarter rounding everywhere, without the thirds snap.** A stored "1 ⅓ EL" would come back as "1 ¼" the moment the stepper moved away and back, which reads as a bug rather than as rounding.
- **A Bits UI `Dialog` for the sheet.** Two Escape handlers to reconcile and a focus trap, for a panel that is not modal in spirit.
- **Markdown, CSV or JSON copies of the ingredients.** Plain lines already paste cleanly into Markdown editors, and machines read the recipe through the API and MCP.
- **The share sheet for the shopping list on phones.** Sharing text to a reminders app tends to make one item holding every line; pasting makes one per line, which is the point of the list.
- **Showing the open ingredients again on the stub.** The list is right above it; the stub carries only the count.
- **A fixed amount cell for number and unit.** "1 Messerspitze" broke out of the 70px it had and ran into the name.
- **An amount column as wide as the widest amount.** One long unit narrows the names of every row in the recipe; at 320px "Petersilie, glatt" wraps.
- **Amount and name as one sentence, or the amount on a line of its own above the name.** The first loses the column the eye runs down for the numbers; the second makes the list a third longer, which the cook-mode sheet pays for in scrolling.
- **The name first and the amount flush right.** A short name leaves the amount across the card from it.
- **Only the number in orange, or none.** A unit in `text-text` beside the name reads as part of it - "Messerspitze Muskatnuss" - and the amount loses its edge.
- **A `(shell)` route group.** It moves every existing route to make one page bare; the layout's route-id check already does that job.
- **Remembering the type size, per device or per recipe.** A long step is what calls for a smaller size, and the next recipe's steps may not be long; a size that stayed would greet the next cook with a page they did not set up.
- **Sizing a step to fit on its own.** Type that changes size from step to step reads as a layout bug, and the cook, not the length of the text, knows how far away the phone is.
- **Pinch to zoom the step.** Nobody finds a gesture that nothing shows, it competes with the browser's own zoom, and it cannot be reached from a keyboard or a screen reader.

## Limits

- A scaled value is never shareable — a link always opens at the baseline — and lives per browser rather than per account.
- Keys accumulate one per scaled recipe. Deleting a recipe in the UI clears its key, but a database reset on the server leaves orphans behind; they are harmless, since a key is only ever read by recipe id.
- The Screen Wake Lock API needs a secure context, so over plain HTTP on a LAN address the lock is silently absent and the caption never appears. HTTPS, directly or through a reverse proxy, is what turns it on.
- A second full-screen route means extending the route-id check in the root layout, not hiding shell parts from inside the page.
