Rezepte installs as an app on Android and in Chrome or Edge on a computer and, through Safari's own steps, on an iPhone or iPad. The installed app has its own icon and window, three shortcuts and an entry in the system share menu. `service/internal/httpserver/manifest.go` serves the manifest; `frontend/src/lib/install.ts` and `install.svelte.ts` hold the install decision; `frontend/src/lib/components/install/` and `components/settings/AppCard.svelte` draw the hints. The page that receives a share is owned by [Recipe import](/features/recipe-import); the icon and the manifest's look by [Design system](/architecture/design-system).

## How it works

**The manifest.** There is one file per locale in `frontend/static/` (`manifest.webmanifest` for English, `manifest.de.webmanifest`), generated by `//frontend:brand` from the message catalogs, so the description and the shortcut names (`app_shortcut_*`) are in that locale. `ManifestHandler` serves the file for the instance's locale (`REZEPTE_LOCALE`) and falls back to the English one; it is `no-cache`, so an installed app picks up changed shortcuts. The manifest is not per user, which is why the shortcut names follow the instance and not the member's own language. It declares `display: standalone`, the shortcuts Import, New recipe and Favorites, a `share_target` to `/import` and `launch_handler: focus-existing`. It has a `background_color` (the splash) and no `theme_color`: Chrome paints an installed app's navigation bar with `theme_color`, and a manifest holds one color for both themes, so a phone in dark mode got a light bar. Without it the bar follows the phone. The status bar follows the two `theme-color` metas in `app.html`, which `applyThemeColor` (`frontend/src/lib/theme.ts`) and the inline script point at the member's own light or dark choice. A changed manifest reaches an installed app only when Chrome updates its WebAPK (checked on launch, about once a day) or on a reinstall.

**One decision.** `installOffer` answers how this device can install now: `'prompt'` (a captured `beforeinstallprompt`), `'ios'` (Safari's steps) or nothing. It is nothing on plain HTTP, inside the installed app (`display-mode: standalone`) and after `appinstalled`. `appCardState` adds one case, `'https'`, for the owner on plain HTTP. Every hint, the banner, the settings card, the menu row and the iOS sheet, starts from these two and adds only its own condition (the banner: a phone, meaning `(max-width: 767.98px) and (pointer: coarse)` so a narrow desktop window never gets it, and not dismissed). Safari on iOS cannot detect a home-screen install, so there the card, the menu row and the banner (until ×) stay in Safari; only the installed app itself (`display-mode: standalone`) hides them.

**The owner is the role `superadmin`.** `$lib/roles` has no owner helper, so `AppCard` compares `session.user?.role`. A member on plain HTTP sees no card at all, since only the owner can put the instance behind HTTPS; the card links the user guide's reverse-proxy page.

**The banner** is a cookbook note: a "Tip" label with a dotted leader that echoes the overview's running head below it, the app icon, a lead sentence and detail, and a full-width Install button. The copy is the same on every platform; on an iPhone the button opens the steps sheet. **Its dismissal** is `localStorage` key `rezepte-install-banner-dismissed` with the value `'1'`, per browser. Every access is in try/catch and `dismissBanner` sets the in-memory flag first, so the × works with blocked storage. Accepting the browser's dialog does not hide the hints; only `appinstalled` does, because the user can still cancel the OS step.

**iOS gets steps, not a button.** Safari fires no `beforeinstallprompt` and has no API to start the install, so `IosInstallSteps` shows the three steps (Share, Add to Home Screen, Add). `isIos` also catches iPadOS, which reports a Mac user agent: a `MacIntel` platform with touch points.

**The install prompt is captured in `app.html`.** Chromium can fire `beforeinstallprompt` before SvelteKit has dynamically imported the layout module, and an event nobody listened for is lost. The inline script in `frontend/src/app.html` therefore calls `preventDefault` and stores the event in `window.__installPrompt`; `install.svelte.ts` takes it over once, when it initializes, and listens itself afterwards.

**The service worker is for push only.** `frontend/src/service-worker.ts` handles `push` and `notificationclick` and nothing else: no `fetch` handler and no cache, so the app still works only online and nothing needs invalidating. A push has two jobs, told apart by its `kind`: a timer's end (`kind: 'timer'`, see [Cook timers](/features/cook-timers)) and a notification (`comment`, `recipe`, `tasty`, `invite_accepted`, `mail_failing`, the push side of [Notifications](/features/notifications), and `test` from the device box). `parsePayload` in `frontend/src/lib/push-worker.ts` requires `{kind, title, body, url, tag}` and accepts an optional `collapse: {title, bodyMany}` only as strings; a `bodyOne` in it, which older servers sent, is ignored, not refused, since a push sent before an update can arrive after it. The url must be a path that stays on the origin, resolved rather than matched: `new URL(url, origin).origin === origin` with the worker's `self.location.origin` passed in (the page passes `location.origin` to `parseToastMessage`), because browsers read `/\evil.example` as `//evil.example`. `notificationOptions` gets whether any window is visible and `shownCount`, what the notification already shown under the tag stands for (its `data.count`, 1 without one, read with `getNotifications({ tag })`). A notification other than a timer rings even with a window visible, a comment on the very page that is open included: the recipe page does not refresh its comments, so the push is the only news. It always sets `renotify` (its `tag` is always set), so one that replaces a notification under its tag - a second test push, tomorrow's digest, a repeated mail alert - rings again instead of swapping in silently. One with `collapse` shown a second time under its tag (a comment's tag is per recipe) becomes `collapse.title` and `bodyMany` with `{count}` filled and `data.count` raised. Both functions are unit-tested in `push-worker.test.ts`. A notification other than a timer also goes to every visible window as a `postMessage` (`toastMessage`: `{type: 'rezepte-push', title, body, url, tag}` with the title and body as shown, so a collapsed comment says the count there too); `listenForPushToasts` in `frontend/src/lib/push-toast.ts`, started by the root layout, checks it with `parseToastMessage` (the worker's type, a url inside the app) and, only with `session.user` set, shows a svelte-sonner toast for 8 seconds with an "Open" button styled as a pill, unlike the muted text actions of other toasts, since it is the way to the page. Signed out (after a `401`) the device may still get pushes, and a toast on `/login` would only bounce back. The toast's `id` is the tag, so a later push under it replaces the toast as it collapses the notification. "Open" navigates with `goto(url, { invalidateAll: true })`, since the recipe page's `load` depends only on the slug and would not run again on the recipe already open, so its new comment would not show, and closes the notification of that tag. The system notification still shows beside it, so it stays in the notification centre for whoever did not look; a timer gets no toast, its page rings and shows the banner itself (`frontend/e2e/notifications.test.ts` dispatches the message, Playwright's Chromium having no push service).

**The device box reads the live permission.** `frontend/src/lib/push.svelte.ts` keeps `Notification.permission` and whether a subscription was registered this page view in `$state`; `deviceState()` is `'unsupported'` without `pushSupported()`, `'blocked'` for `denied`, `'enabled'` for `granted` with a subscription, `'off'` otherwise. The permission is read again on every `visibilitychange` to visible, because it can be revoked or reset in the browser or OS settings while a subscription still exists, and the box must say blocked or off then, not "receives notifications": anything but `granted` sets the subscription flag false, and `granted` drops the cached endpoint and subscribes again (the browser may have dropped its subscription with the revoke), so revoke and allow again ends with a fresh subscription - but only when the permission changed since it was last read or the device is not subscribed: a `PUT` on every return to the tab would meet a session that ran out while hidden with a `401`, and `api()` would send the cook mid-recipe to the login page. `subscribe()` reuses the browser's subscription only when its `options.applicationServerKey` holds the same bytes as the key from `GET /api/v1/push/key`; otherwise, or without a key, it unsubscribes and subscribes anew, because a browser keeps its subscription when the instance on the origin is set up again with a new VAPID key, and the push service refuses every push for the mismatch. The cached endpoint is reused only while the permission is `granted`, so "Enable on this device" after a reset asks again. `enableDevice()` goes the timers' way (`requestPermission` inside the click, then subscribe) and rejects when the member declines; `sendPushTest()` posts this device's endpoint to `POST /api/v1/push/test` (`postPushTest`) and rejects on a `404` (unknown subscription, also one the push service has just forgotten), a `429` (a test within 10 s) or the network, so the card can show its line; the `404` also sets the device to `'off'`. Tested in `push-store.test.ts`. The worker is registered only where push works (a secure context with `PushManager`), not for installing: Chromium's installability check (`Page.getInstallabilityErrors` over CDP, in `frontend/e2e/install.test.ts`) passes with the manifest and the icons alone, so a browser without push installs as before. `spa.go` serves `/service-worker.js` `no-cache`.

**Neighbors that the share needed.**

- The overview's `syncUrl` (`frontend/src/routes/+page.svelte`) returns while another navigation runs or the route is not `/`: a late list answer would otherwise `replaceState` the overview over a navigation away, which is how a share into `/import` lost to a fast draft.
- `ImportForm` takes `importDialog.prefill` in an `$effect`, not only on mount, so a share into an already open dialog gets the link too.

**Testing.** `frontend/e2e/install.test.ts` holds the flows. Chromium never offers an install under automation, so the tests dispatch a synthetic `beforeinstallprompt` on `load`; the user-docs screenshots do the same with `offerInstall` in `docs/user/screenshots/helpers.ts`. Run the file from the repository root, see [Verify UI with Playwright](/howtos/verify-ui).

**Testing on a phone.** Checking install and Share → Rezepte on a real phone needs HTTPS. Put the running demo behind a TLS tunnel such as `tailscale serve --bg <demo port>` (the port is in `mise run ports`) rather than a dev server with a self-signed certificate, which Android and iOS will not install from. On Android install from Chrome: Brave makes a home-screen shortcut, not a WebAPK, and Share → Rezepte then never appears, which looks like a broken `share_target` but is not. A WebAPK is listed under Settings → Apps.

## Why it is this way

- **One decision function.** Five places show an install hint, and each needs the same four checks. A pure function is unit-tested without a browser (`install.test.ts`).
- **Per-locale manifest files, not a handler that renders them.** The manifest is static data the brand export already produces and checks; the handler only picks a file.
- **The owner learns about HTTPS, members do not.** A card that explains a fix nobody but the owner can make is noise for everyone else.

## Rejected

- **A service worker only to be installable, or one that caches.** Chromium installs without one, and a cache brings invalidation for no user-visible gain; the worker that exists does push and nothing more.
- **A manifest per member language.** The manifest is fetched without a session and shared by every member; the instance language is the one value all of them have.
- **Opening the browser's install dialog from a banner shown in the installed app or on iOS.** Neither can use it; the offer function returns nothing there.

## Limits

- The share target works only on Android, Windows and ChromeOS: Safari does not support it, and neither does Chrome on macOS or Linux, so everyone else pastes the link.
- On Android only a WebAPK gets the share target, which Chrome mints and Brave, for one, does not: Brave's install is a home-screen shortcut that never shows in the share menu.
- Shortcut names are in the instance language, not the member's.
- `launch_handler` is Chromium-only; elsewhere a second share opens a new window.
- Checked on an Android phone: install from Chrome and Share → Rezepte. Not checked on a device: the shortcuts and a share into an editor with unsaved changes (both covered by e2e only).
- iPhone and OIDC are unverified: whether the SSO redirect returns into the home-screen app is not known, and the user docs promise only that the iPhone app signs in once on its own.
