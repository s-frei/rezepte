---
title: Public shares
description: A member turns a recipe into a read-only link anyone can open without an account, until it is revoked or expires
---

A member shares a recipe with people outside the household through a link that opens a read-only page without signing in. Creating one is a deliberate act, separate from [link previews](/features/link-previews) or from the internal "Copy link": it makes the recipe reachable to a stranger for as long as the link stands, so the owner decides whether the instance allows it at all, and every link a member opens is listed and revocable. The code is `service/internal/share`; the SPA route is `frontend/src/routes/s/[token]`, the recipe page's dialog is `PublicShareDialog.svelte`, the settings pages are `frontend/src/routes/settings/shares` and `PublicSharingCard.svelte`. [Data model](/architecture/data-model) owns the `shares` table; the OpenAPI document holds the routes ([HTTP API](/architecture/api)).

## How it works

**One link per person and recipe.** The `shares` table carries `id` (UUIDv7), `token` (16 bytes from `crypto/rand`, base64url without padding - 22 characters, 128 bits, stored in plain text so the list can show the link again), `recipe_id`, `created_by`, `created_at` and a nullable `expires_at`, under `UNIQUE (recipe_id, created_by)`. A member who already has a link for a recipe gets that link back instead of a second one, from the menu item, the dialog and a race on `Create` alike - the database's own unique constraint is what a concurrent double-create resolves against. Revoking deletes the row outright; there is no soft-delete state.

**Two switches, at two scopes.** `instance_settings.public_shares` is the owner's household-wide switch, off by default so an upgraded instance changes nothing until the owner turns it on. `users.can_share_publicly` is a per-person switch, on by default, which [Users and authentication](/features/users-and-auth) owns: who may flip it for whom, and where. Both are re-read from the database on every request that matters, never trusted from a stale value.

**Any recipe, whoever wrote it.** Those two switches are the whole check `Service.Create` makes: a member whose `canSharePublicly` is on, in a household with sharing on, may create a link for any recipe, including one somebody else wrote and one its author locked. [Editing rights](/features/editing-rights) play no part.

**Lifetimes and the validity rule.** A link's own lifetime is one of `settings.ShareLifetimes` (1, 7, 30 or 365 days) or permanent; the owner also sets `public_share_default_days` (preselected when a member creates a link) and `public_share_max_days` (the longest a link may run), each independently permanent or one of the same four counts. `share.evaluate` decides a share's `Status` on every read:

- **paused** when the household switch is off or the creator's own right is withdrawn. This takes priority over everything else, so a link is never "limited" while it is also switched off.
- **limited** when `public_share_max_days`, counted from the link's own `created_at`, has passed.
- **active** otherwise.

Paused and limited both reverse: switching the household setting back on, restoring the person's right, or raising the maximum again revives the link at once. A link's own `expires_at` passing is terminal, not a `Status`, because nothing reverses it: `Mine` and `List` report it as gone (`ErrNotFound` / left out of the list) even before the hourly sweep in `main.go` deletes the row, and `Create` clears an own-expired row on the spot rather than block a fresh link on the sweep. The effective expiry a member sees is the earlier of the link's own `expires_at` and `created_at` plus the maximum.

**Lowering the maximum lowers the default with it.** `Service.SetShareLifetimes` writes both columns in one statement: a maximum set below the stored default pulls the default down to match, so a reader can never see a default the maximum has just outlawed. SQLite's `ALTER TABLE` cannot add a table-level constraint, so the cross-column rule - the default may never exceed the maximum - sits as a column constraint on `public_share_max_days`, the column the migration adds last; a column constraint may name any column that already exists, and `ADD COLUMN` tests it against every existing row as soon as the column exists.

**Creating a link.** `POST /api/v1/recipes/{id}/public-share`, body `{days}`; the OpenAPI document lists its answers. Two of them carry more than a status:

- A refusal (`403`) carries `reason` (`RefusedError`): `sharing-off` or `not-allowed`, so the dialog's toast switches on that word rather than on the `detail` wording.
- A caller who already has a live link gets it back as a `409` whose problem body carries it in `share` (`ExistingShareError`), and that check runs **before** `days` is validated: a member who already shares gets their link, not a lifetime error for a request a since-lowered maximum no longer allows. Only without a live link does `days` matter: one of `settings.ShareLifetimes` or `null`, not above the maximum (`null` exceeds any non-null maximum), else `422` at `body.days`.

**Reading and managing links.** `GET /api/v1/shares/by-recipe/{recipeId}` (get-my-public-share) answers `{share}` with the caller's own link or `null` - never a `404`, since `frontend/src/routes/recipes/[slug]/+page.ts` calls it on every recipe view and "nobody has shared this yet" is not an error. It sits under `/shares` for a routing reason (see Why it is this way). `GET /api/v1/shares` lists the caller's own links, newest first, or with `?all=true` (admin only) every link with its creator (`createdBy`, which carries the id because display names need not be unique); `DELETE /api/v1/shares/{id}` revokes one's own link or, as an admin, anybody's; `DELETE /api/v1/shares` (admin only) revokes all. All five routes are session-only (`auth.SessionSecurity`), so a bearer token gets the `403` [API tokens](/features/api-tokens) describes.

**The public side.** `GET /api/v1/public/shares/{token}` answers `PublicRecipe` (`service/internal/share/public.go`): the recipe's content plus the owner's credit setting, its own type built field by field rather than `recipe.Recipe`, so a field added to the real recipe cannot reach a stranger by accident. Every invalid token - unknown, revoked, paused, limited or expired - answers the identical `404` `"not available"`, so nobody learns which case they hit. `GET /public-images/{token}/{imageId}/{thumb|detail|original}.jpg` (registered by `RegisterPublic` like the recipe) serves only a photo that still belongs to the share's recipe while the share serves; everything else is the same `404`. `/s/{token}`'s link preview is filled by `Service.ForRequest`, composed in `main.go` ahead of the internal link-preview one (`httpserver.PreviewFuncs(shares.ForRequest, previews.ForRequest)`), so a public share's own card wins when both could apply - in practice they never do, since previews answer for `/recipes/{slug}` and shares for `/s/{token}`.

**Headers, on every public route.** The public API, the public image route and the `/s/*` app shell (`share.ShellHeaders`, installed as the `httpserver.ShellHeaderFunc`, which also covers `/unsubscribe`, another page with a token in its address - see [Email](/features/email)) all send `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex` and `Cache-Control: private, no-cache`: no `Referer` leaves the page carrying the token, no search engine indexes it, and nothing caches a page that a revoke must stop showing at once. The recipe's source link (`SourceCredit.svelte`) carries `rel="noreferrer noopener external"` everywhere it renders, not only on the public page, so the rule needs no branch for which page it is on.

**The public page.** `/s/[token]` renders the shared `RecipeView` without the app shell - `+layout.ts` lets `/s/…` through without a session and without calling `me()`, so neither a stranger nor a signed-in member with a stale cookie is redirected. The page never learns the recipe's real id: `PublicRecipe` carries none, and the client builds a synthetic one, `"share:" + token`, only for `RecipeView`'s own client-side bookkeeping (the servings memory key, gallery keys) - nothing sends it back to the server. `RecipeView`, `ImageGallery` and `Lightbox` all take an optional image `src` override (`(imageId, variant) => string`), defaulting to the session-authenticated `imageUrl`; the public page passes `publicImageUrl`, which points at `/public-images/{token}/…` instead. A token that serves nothing renders the page's own friendly "not available" state, never SvelteKit's generic error page.

**The theme button.** A stranger gets two theme states rather than the app's three: the first visit follows the device (`prefers-color-scheme`, read through Svelte's `MediaQuery`), and the button flips between light and dark. It calls the app's `setTheme`, so the choice lands in the same `rezepte-theme` storage and an owner opening their own link keeps the theme they chose in the app.

**The credit.** At the page's foot an invitation names Rezepte and links to the project's site and the repository (both constants in `$lib/docs.ts`). It is an invitation rather than fine print on purpose - a shared recipe is the one page of Rezepte a stranger sees - and a slim bar rather than a card so the recipe stays the page's subject. `instance_settings.public_share_attribution` switches it, owner only, on by default; the same setting switches the foot of the [recipe card](/features/recipe-card), which is why the People page shows it whether public shares are on or not. The page has no session to read `GET /settings` with, so `PublicRecipe` carries the setting as `attribution`, re-read on every request; a token that serves nothing gets no credit, since the `404` stays identical.

**The recipe page.** The "…" menu offers "Share publicly…" while the household switch and the member's own right are both on, or whenever the member already has a link - then it opens the dialog regardless, which shows the link as paused if either has since gone off and still offers Revoke (`canCreateShare` / `showShareMenuItem` in `frontend/src/routes/recipes/[slug]/+page.svelte`). With a link, a "Shared publicly" marker in the tag row (`RecipeView`'s `kicker` snippet) and a colophon line (`RecipeColophon`) say so and open the same dialog. Both describe the viewer's own link and nobody else's: the page asks `get-my-public-share`, so another member's link to the same recipe shows only under Shared links. `PublicShareDialog.svelte` offers lifetimes capped at the maximum with the default preselected, and handles a `409` on create inline by swapping in the problem body's `share`.

**Settings.** "Shared links" (`frontend/src/routes/settings/shares`) lists the signed-in member's own links as `ShareRow`s, built like the API token list ([API tokens](/features/api-tokens)): the shared `LifetimeBar` runs from creation to the effective expiry, and a paused or limited link carries the shared `Stamp` and one sentence saying why.

- An admin's "Everyone in the household" switch adds every member's links with their creator; with two or more creators a person filter narrows the list, and a status filter (active, paused, limited) narrows any member's list once it holds more than one status. They filter the list already loaded, each filter's counts are taken within the other filter's choice, and a person whose last link goes falls back to everyone rather than to an empty list.
- All three are view filters, not settings, so they live in the URL (`?all=1&user=<id>&status=paused`): a reload keeps them, and the page opened from the navigation starts with the viewer's own, unfiltered list.
- A notice above the list says why links do not open: the household switch being off (`GET /settings`), or else the viewer's own right being withdrawn (the session's `canSharePublicly`). "Revoke all" and the household view are the only admin extras.
- The People page carries the "Public sharing" card for admins: the owner gets the switch (turning it on asks first, since it puts recipes in front of anyone holding a link; turning it off applies at once), the default/maximum selects with the default capped at the current maximum, and the credit switch, shown even while public shares are off; every other admin sees one sentence stating what applies.

## Why it is this way

A self-hosted instance defaults to private, so making a recipe reachable by a stranger is the owner's decision at the household scale and each member's decision at the recipe scale, and either can be taken back. Deleting a recipe or a user removes the links with it - there is nothing left to point at - and a household that never turns public sharing on pays nothing for the feature beyond the schema.

Sharing a recipe to read is not editing it. Every member can already read every recipe in the household, and a lock decides who may change a recipe, not who may see it or show it to someone; so a public link needs the right to share, not the right to edit, and the household switch and the per-person right are the controls for who may hand recipes out.

The token carries the whole authorization, the way a link preview's does ([Link previews](/features/link-previews)): 128 bits from `crypto/rand` makes guessing infeasible without a rate limit, which a public route serving a stranger cannot easily apply in the first place.

`GET get-my-public-share` living at `/shares/by-recipe/{recipeId}` rather than nested under the recipe is a routing fact, not a design choice: Go's `ServeMux` picks the more specific of two patterns that could both match a path, and `/recipes/by-slug/{slug}` and `/recipes/{id}/public-share` are equally specific at `/recipes/by-slug/public-share` - the mux has no tiebreaker for that, so the route moved instead.

Paused and limited stay distinct from an own-expired link because they mean different things to the person managing it: paused and limited both come back on their own once whatever caused them is undone, and a link should keep showing as "yours" while that is still true. An own expiry is a decision the creator already made when they chose the lifetime, and nothing should revive it - so it is cleared rather than kept in a third dormant state nobody could reverse anyway.

## Rejected

- **One link per recipe, shared by the whole household.** A link two different members could both hand out would need to say whose it is to revoke it sanely; one per person and recipe keeps that answer trivial and matches how sharing actually happens - a member decides to show one recipe to one outside person or group.
- **Deleting a member's links when their right to share is withdrawn.** Withdrawing is meant to be reversible - an admin correcting a mistake, or a household pausing sharing for someone temporarily - and a deleted link cannot come back with its own token; pausing does.
- **A server-rendered public page.** The recipe detail page already exists as SvelteKit components (`RecipeView`, `ImageGallery`, `Lightbox`); a second rendering path for the same content would drift from the first the next time either changes. Reusing the components, fed by the narrow `PublicRecipe` API, keeps one place that draws a recipe.
- **Hashing the token like a session id.** A session token authenticates a login; this token *is* the link a person sends someone else, and a member has to be able to see it again in "Shared links" to copy it a second time. Hashing it would mean generating a fresh one on every re-share, which breaks a link already sent.

## Limits

- A public link shows the recipe as it is right now - editing it after sharing changes what the link shows, and there is no versioning or snapshot.
- No rate limit on the public routes; token entropy is the only defense against guessing (see Why it is this way).
- Every request is logged with its full path; a failing one (4xx or worse) logs at `WARN` or above, on by default - so a bad, revoked, paused, limited or expired token on `GET /public/shares/{token}` or `GET /public-images/{token}/…` lands in the log at that level too, not only when an operator turns on debug logging. Operators should treat that log the way they treat the tokens themselves.
- A public link never gates by ingredient references, cook mode or any other member-only view - it is the recipe read-only: the servings scaler, ticking off ingredients and copying the list work as on the member's page, but there is no editing, cook mode, favorite, tasty mark or comment.
