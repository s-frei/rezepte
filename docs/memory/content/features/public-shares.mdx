---
title: Public shares
description: A member turns a recipe into a read-only link anyone can open without an account, until it is revoked or expires
---

A member shares a recipe with people outside the household through a link that opens a read-only page without signing in. Creating one is a deliberate act, separate from [link previews](/features/link-previews) or from the internal "Copy link": it makes the recipe reachable to a stranger for as long as the link stands, so the owner decides whether the instance allows it at all, and every link a member opens is listed and revocable. The code is `service/internal/share`; the SPA route is `frontend/src/routes/s/[token]`, the recipe page's dialog is `PublicShareDialog.svelte`, the settings pages are `frontend/src/routes/settings/shares` and `PublicSharingCard.svelte`. [Data model](/architecture/data-model) owns the `shares` table; [HTTP API](/architecture/api) owns the routes.

## How it works

**One link per person and recipe.** The `shares` table carries `id` (UUIDv7), `token` (16 bytes from `crypto/rand`, base64url without padding - 22 characters, 128 bits, stored in plain text so the list can show the link again), `recipe_id`, `created_by`, `created_at` and a nullable `expires_at`, under `UNIQUE (recipe_id, created_by)`. A member who already has a link for a recipe gets that link back instead of a second one, from the menu item, the dialog and a race on `Create` alike - the database's own unique constraint is what a concurrent double-create resolves against. Revoking deletes the row outright; there is no soft-delete state.

**Two switches, at two scopes.** `instance_settings.public_shares` is the owner's household-wide switch, off by default so an upgraded instance changes nothing until the owner turns it on; `users.can_share_publicly` is a per-person switch, on by default, withdrawn or restored from a person's row in the people list under the rank rule of [Users and authentication](/features/users-and-auth): any admin for a plain member, only the owner for an admin, and nobody for the owner's own row (`409` `the superadmin cannot be modified`). Both are re-read from the database on every request that matters, never trusted from a stale value.

**Any recipe, whoever wrote it.** Those two switches are the whole check `Service.Create` makes: a member whose `canSharePublicly` is on, in a household with sharing on, may create a link for any recipe, including one somebody else wrote and one its author locked. [Editing rights](/features/editing-rights) play no part.

**Lifetimes and the validity rule.** A link's own lifetime is one of `settings.ShareLifetimes` (1, 7, 30 or 365 days) or permanent; the owner also sets `public_share_default_days` (preselected when a member creates a link) and `public_share_max_days` (the longest a link may run), each independently permanent or one of the same four counts. `share.evaluate` decides a share's `Status` on every read: **paused** when the household switch is off or the creator's own right is withdrawn, whichever came first - this takes priority over everything else, so a link is never "limited" while it is also switched off; **limited** when `public_share_max_days`, counted from the link's own `created_at`, has passed; **active** otherwise. Paused and limited both reverse: switching the household setting back on, restoring the person's right, or raising the maximum again revives the link at once. A link's own `expires_at` passing is different - it is terminal, not a `Status` of its own, because nothing reverses it: `Mine` and `List` report it as gone (`ErrNotFound` / left out of the list) even before the hourly `SweepLoop` (like the session sweep) deletes the row, and `Create` clears an own-expired row on the spot rather than block a fresh link on the sweep's next run. The effective expiry a member sees is the earlier of the link's own `expires_at` and `created_at` plus the maximum.

**Lowering the maximum lowers the default with it.** `Service.SetShareLifetimes` writes both columns in one statement: a maximum set below the stored default pulls the default down to match, so a reader can never see a default the maximum has just outlawed. SQLite's `ALTER TABLE` cannot add a table-level constraint, so the cross-column rule - the default may never exceed the maximum - sits as a column constraint on `public_share_max_days`, the column the migration adds last; a column constraint may name any column that already exists, and `ADD COLUMN` tests it against every existing row as soon as the column exists.

**Creating a link.** `POST /api/v1/recipes/{id}/public-share`, body `{days}`, session only: `201` with the new share; `403` when the instance has sharing off or the caller's right is withdrawn, a problem+json body whose extra `reason` field (`RefusedError`) says which - `sharing-off` or `not-allowed` - so the dialog's toast switches on that word rather than on the `detail` wording; `404` for an unknown recipe. A caller who already has a live link gets it back as a `409` whose problem+json body carries it in an extra `share` field (`ExistingShareError`), ahead of validating `days` at all - a member who already shares gets their link, not a lifetime error for a request a since-lowered maximum no longer allows. Only once there is no live link does `days` matter: it must be one of `settings.ShareLifetimes` or `null`, and must not exceed the maximum (`null` exceeds any non-null maximum), or the answer is `422` at `body.days`.

**Reading and managing links.** `GET /api/v1/shares/by-recipe/{recipeId}` (get-my-public-share) answers `200` with `{share}`: the caller's own link for the recipe, or `null` when there is none, or the recipe is unknown - never a `404`, since `frontend/src/routes/recipes/[slug]/+page.ts` calls it on every recipe view, and "nobody has shared this yet" is not an error. It sits under `/shares`, not under `/recipes/{id}/`, because `GET /recipes/by-slug/{slug}` already claims that prefix in Go's `net/http.ServeMux`: `GET /recipes/by-slug/public-share` would match both patterns, and neither is more specific - the same reason [HTTP API](/architecture/api) gives for the share-link `POST`. `GET /api/v1/shares` (list-shares) is the caller's own links, newest first, or with `?all=true` every link in the household with its creator (`createdBy`: ID, display name, color - the ID because display names need not be unique) - admin only, `403` otherwise. `DELETE /api/v1/shares/{id}` revokes the caller's own link or, as an admin, anybody's; `DELETE /api/v1/shares` (admin only) revokes every link in the household. Every one of these five routes is session-only (`auth.SessionSecurity`): a bearer token cannot reach any of them, and `auth.Middleware`'s own rule for that case - a session-only operation asked for with an `Authorization: Bearer` header - answers `403` `API tokens cannot use this operation`, not the `401` a request with no credential at all gets.

**The public side.** `GET /api/v1/public/shares/{token}` answers `PublicRecipe` - `{title, description, servings, prepMinutes, cookMinutes, sourceUrl, sourceName, tags, ingredientGroups, steps, images: [{id, width, height}], coverImageId, attribution}`, the recipe's content plus the owner's credit setting (see The credit below), its own type built field by field rather than `recipe.Recipe`, so a field added to the real recipe cannot reach a stranger by accident. Every invalid token - unknown, revoked, paused, limited or expired - answers the identical `404` `"not available"`, so nobody learns which case they hit. `GET /public-images/{token}/{imageId}/{thumb|detail|original}.jpg` (get-public-image-file, registered by `RegisterPublic` like the recipe) serves only a photo that still belongs to the share's recipe while the share serves; everything else is the same `404`. `/s/{token}` is the SPA route: its link preview is filled by `Service.ForRequest`, composed in `main.go` ahead of the internal link-preview one (`httpserver.PreviewFuncs(shares.ForRequest, previews.ForRequest)`), so a public share's own card wins when both could apply to the same path - in practice they never do, since previews answer for `/recipes/{slug}` and shares for `/s/{token}`.

**Headers, on every public route.** The public API, the public image route and the `/s/*` app shell (`share.ShellHeaders`, installed as the `httpserver.ShellHeaderFunc`) all send `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex` and `Cache-Control: private, no-cache`: no `Referer` leaves the page carrying the token, no search engine indexes it, and nothing caches a page that a revoke must stop showing at once. The recipe's source link (`SourceCredit.svelte`) carries `rel="noreferrer noopener external"` everywhere it renders, not only on the public page, so the rule needs no branch for which page it is on.

**The public page.** `/s/[token]` renders the shared `RecipeView` without the app shell - `+layout.ts` lets `/s/…` through without a session and without calling `me()`, so neither a stranger nor a signed-in member with a stale cookie is redirected. The page never learns the recipe's real id: `PublicRecipe` carries none, and the client builds a synthetic one, `"share:" + token`, only for `RecipeView`'s own client-side bookkeeping (the servings memory key, gallery keys) - nothing sends it back to the server. `RecipeView`, `ImageGallery` and `Lightbox` all take an optional image `src` override (`(imageId, variant) => string`), defaulting to the session-authenticated `imageUrl`; the public page passes `publicImageUrl`, which points at `/public-images/{token}/…` instead. A token that serves nothing renders the page's own friendly "not available" state, never SvelteKit's generic error page.

**The theme button.** The header carries the horizontal lockup on the left and the outlined 40px `IconButton` on the right that flips between light and dark. A stranger gets two states rather than the app's three: the first visit follows the device (`prefers-color-scheme`, read through Svelte's `MediaQuery`), and the button shows where it goes - a moon while the page is light, a sun while it is dark - with "Switch to the dark theme" or "Switch to the light theme" as its name. It calls the app's `setTheme`, so the choice lands in the same `rezepte-theme` storage and an owner opening their own link keeps the theme they chose in the app.

**The credit.** At the page's foot a slim surface bar invites the stranger reading: the mascot (`Lockup`'s `mark` variant), "A cookbook like this one? Kept with Rezepte - a recipe manager you host yourself", a primary "Get Rezepte" button to the project's site and a quiet "Source" link to the repository (both constants in `$lib/docs.ts`). It is an invitation rather than a fine-print line on purpose - a shared recipe is the one page of Rezepte a stranger sees - and a bar rather than a full card so the recipe stays the page's subject. `instance_settings.public_share_attribution` switches it, owner only, on by default; the same setting switches the foot of the [recipe card](/features/recipe-card), which is why the People page shows it whether public shares are on or not. The page has no session to read `GET /settings` with, so `PublicRecipe` carries the setting as `attribution`, re-read on every request like the rest; a token that serves nothing gets no line at all, since there is nothing to credit and the `404` stays identical.

**The recipe page.** The "…" menu carries a globe-icon item, "Share publicly…" or "Public link…" once the member has one, shown while the household switch is on and the member's own right is on, or the member already has a link (in which case it opens the dialog regardless, which then shows the link as paused if either has since gone off, with Revoke still offered) - `frontend/src/routes/recipes/[slug]/+page.svelte`'s `canCreateShare` / `showShareMenuItem`. With a link, two things say so and open the same dialog. A "Shared publicly" marker closes the tag row above the title (`RecipeView`'s `kicker` snippet, which opens that row even for a recipe without tags): outlined in primary while the link is active and muted while it is paused or limited, so it never reads as one more tag, and in that row rather than in the line under the title so it wraps with the tags and leaves that line to the star, the heart and the people who find the recipe tasty. The colophon (`RecipeColophon`) adds a line with the details - "Shared publicly by you until …", "…without an end date", "Your public link is paused" or "…is limited by the maximum" - and "Manage link". Both are the viewer's own link and nobody else's: the page asks `get-my-public-share`, so the colophon says "by you", and another member's link to the same recipe shows only under Shared links, the same way it carries the lock line of [Editing rights](/features/editing-rights). `PublicShareDialog.svelte` without a link offers the lifetime choice (options capped at the maximum, the default preselected) and "Create public link"; with one, the link with Copy (and Share where `navigator.share` exists), its effective expiry or "permanent", a status pill for `paused`/`limited`, and Revoke behind a confirmation. A `409` on create is handled inline: the dialog swaps in the problem body's `share` rather than showing an error.

**Settings.** "Shared links" (`settings/shares`) lists the signed-in member's own links as key tags like the API token list (see [API tokens](/features/api-tokens)): `ShareRow` puts the creator's color on the edge, the recipe as heading, and the shared `LifetimeBar` from creation to the effective expiry (open for a permanent link); a paused or limited link fades and carries the shared `Stamp` - red for paused, the caution tone for limited, which also carries the end date because its bar is spent - beside one sentence saying why: paused for the household when `GET /settings` says sharing is off, else paused for the person, or limited by the maximum. "Copy link" is the tag's primary action and "Revoke" stays muted until hovered. The list comes with an admin-only "Everyone in the household" switch that adds each link's creator, and an admin-only "Revoke all" behind a confirmation. With the switch on and at least two people holding links, a "Created by" row of chips narrows the list to one person, the same chip - color dot, count - as the overview's author filter; it filters the list already loaded, by `createdBy.id`, and a person whose last link goes falls back to everyone rather than to an empty list. A "Status" row of chips (active, paused, limited) narrows any member's list the same way, shown once the list holds more than one status. Each row's counts are taken within the other row's choice, so a number always says what a click would show; a combination that matches nothing says so instead of showing the empty-list sentence. All three are view filters, not settings, so they live in the URL (`?all=1&user=<id>&status=paused`): a reload keeps them, and the page opened from the navigation starts with the viewer's own, unfiltered list. Above the list, a notice says why links do not open: the household switch being off (with a link to the People page for the owner), or else the viewer's own right being withdrawn - the page reads `GET /settings` for the first and the session's `canSharePublicly` for the second. It is for every member, not only admins; the "everyone" switch, its person filter and "Revoke all" are the only admin extras. The People page carries the "Public sharing" card for admins: the owner sees the switch - turning it on asks first, since it puts recipes in front of anyone holding a link, while turning it off applies at once - the default/maximum selects (the default options capped at whatever the maximum currently is) and, below the card's other rows and shown even while public shares are off, "Name Rezepte when sharing", which applies at once; every other admin sees one sentence stating what currently applies. "May share publicly" appears wherever the viewer may also reset that person (`rowPermissions.toggleSharing`) - any admin on a plain member's row, the owner on an admin's too: on a wide screen as a checkbox in the row's `ellipsis` menu beside the pencil in `PersonRow` - the menu that also holds reset, setup link, revoke, disconnect and delete, so the checkbox sits between separators - on a phone as a switch under the role in `PersonSheet`. `/people` leaves the right out, since it is an admin's business and every account reads that list, so the page reads it from `GET /users` alongside, for admins only.

## Why it is this way

A self-hosted instance defaults to private, so making a recipe reachable by a stranger is the owner's decision at the household scale and each member's decision at the recipe scale, and either can be taken back. Deleting a recipe or a user removes the links with it - there is nothing left to point at - and a household that never turns public sharing on pays nothing for the feature beyond the schema.

Sharing a recipe to read is not editing it. Every member can already read every recipe in the household, and a lock decides who may change a recipe, not who may see it or show it to someone; so a public link needs the right to share, not the right to edit, and the household switch and the per-person right are the controls for who may hand recipes out.

The token carries the whole authorization, the way a link preview's does ([Link previews](/features/link-previews)): 128 bits from `crypto/rand` makes guessing infeasible without a rate limit, which a public route serving a stranger cannot easily apply in the first place.

`GET get-my-public-share` living at `/shares/by-recipe/{recipeId}` rather than nested under the recipe is a routing fact, not a design choice: Go's `ServeMux` picks the more specific of two patterns that could both match a path, and `/recipes/by-slug/{slug}` and `/recipes/{id}/public-share` are equally specific at `/recipes/by-slug/public-share` - the mux has no tiebreaker for that, so the route moved instead.

Paused and limited stay distinct from an own-expired link because they mean different things to the person managing it: paused and limited both come back on their own once whatever caused them is undone, and a link should keep showing as "yours" while that is still true. An own expiry is a decision the creator already made when they chose the lifetime, and nothing should revive it - so it is cleared rather than kept in a third dormant state nobody could reverse anyway.

## Rejected

- **One link per recipe, shared by the whole household.** A link two different members could both hand out would need to say whose it is to revoke it sanely; one per person and recipe keeps that answer trivial and matches how sharing actually happens - a member decides to show one recipe to one outside person or group.
- **Deleting a member's links when their right to share is withdrawn.** Withdrawing is meant to be reversible - an admin correcting a mistake, or a household pausing sharing for someone temporarily - and a deleted link cannot come back with its own token; pausing does.
- **A server-rendered public page.** The recipe detail page already exists as SvelteKit components (`RecipeView`, `ImageGallery`, `Lightbox`); a second rendering path for the same content would drift from the first the next time either changes. Reusing the components, fed by the narrow `PublicRecipe` API, keeps one place that draws a recipe.
- **Hashing the token like a session id.** A session token authenticates a login; this token *is* the link a person sends someone else, and a member has to be able to see it again in "Shared links" to copy it a second time. Hashing it would mean generating a fresh one on every re-share, which breaks a link already sent.

## Limits

- A public link shows the recipe as it is right now - editing it after sharing changes what the link shows, and there is no versioning or snapshot.
- No rate limit on the public routes; token entropy is the only defense against guessing (see Why it is this way).
- Every request is logged with its full path; a failing one (4xx or worse) logs at `WARN` or above, on by default - so a bad, revoked, paused, limited or expired token on `GET /public/shares/{token}` or `GET /public-images/{token}/…` lands in the log at that level too, not only when an operator turns on debug logging. Operators should treat that log the way they treat the tokens themselves.
- A public link never gates by ingredient references, cook mode or any other member-only view - it is read-only prose, photos and the ingredient list, nothing interactive.
