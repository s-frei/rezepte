title: Recipe card
description: Passing a recipe on as one picture, drawn in the browser from an off-screen card in the active theme

A member can pass a recipe on as a picture: one long PNG with the cover, title, description, servings and times, every ingredient, every step and a credit line. It is for people without an account and for a phone's photo library - whoever gets it needs nothing to cook from it. The link stays the way to share a living page; [Public shares](/features/public-shares) owns the one that works without an account.

## How it works

**One entry, two ways out.** "Pass on" on the detail page - the share button over the cover on a phone, a top-bar button on a desktop, a "…" menu item on both - opens `ShareSheet.svelte`. On a phone it is a `BottomSheet` with **Link** (the existing `shareLink`) and **Card**; on a desktop a `BaseDialog` with `wide` (720px) offering **Copy image**, **Save image**, **Share…** and **Copy link**. The preview in both is the drawn PNG itself, tilted and scrolling in its frame, not a second rendering of the card.

**The card is drawn off-screen, once per opening.** While the sheet is open, `ShareSheet` mounts `ShareCard.svelte` in a host that is fixed, off the viewport, `inert` and `aria-hidden` - not `display: none`, which has no layout to draw. An attachment on that host calls `renderShareImage` (`$lib/recipe/share-image.ts`, the only importer of `modern-screenshot`): it waits for `document.fonts.ready` and every `<img>`'s `decode()`, gives a failed cover one `tick()` to swap in `PlaceholderTile`, then calls `domToBlob`. Closing the sheet unmounts the host, which revokes the preview's object URL and drops the blob.

**Laid out like the phone page.** The card is 420 CSS px wide with the page's own type sizes and tokens, and it inherits the active theme from `<html>`, so the picture looks like the page in light or dark. Quantities are scaled to the servings chosen on the page: `createServings` is read afresh on each opening, the same stored choice the stepper writes. Left off: the source, tags, further photos, favorite and tasty, author, dates and anything that names the instance.

**Sharp, but never too big.** `pickScale` draws at 3x and lowers the scale for tall recipes so width × height × scale² stays under 16,000,000 px, never going below 1x. Legibility depends on the proportion of type to width, not on pixels, so a messenger scaling the picture down leaves it as readable as a phone page.

**Nothing is drawn after the tap.** Every picture action is disabled until the blob exists. `shareImage` (`$lib/recipe/share.svelte.ts`) builds the `File` and awaits `navigator.share({ files, title })` first thing, falls back to a download without file sharing or on `NotAllowedError`, and does nothing on `AbortError`, which leaves the sheet open. **Copy image** (`ClipboardItem`) and **Share…** (`navigator.canShare({ files })`) show only where the browser has them.

**The credit follows the household setting.** `publicShareAttribution` ("Name Rezepte when sharing", owner only, on by default) switches the card's foot - the ingredient list's perforation, `Lockup` and `SOURCE_URL` - as well as the public page's. The People page shows the switch whether public shares are on or not.

**Tests.** `pickScale` in `share-image.test.ts`. `e2e/share-image.test.ts` runs in `desktop`, `mobile` and a `webkit` project (iPhone 15) that exists only for this file; it removes `navigator.share` so **Card** downloads deterministically, stubs it to reject with `AbortError` for the cancel case, and answers the cover with a `404` for the placeholder case. The credit test lives in the serial `public-shares.test.ts`, since it flips the instance-wide setting that file's public-page tests read.

## Why it is this way

Only the browser knows the active theme and the servings chosen on the page, and drawing there gives the service no renderer to run or secure. Photos are same-origin (`/images/…`, `detail` variant), so the canvas is never tainted.

One long picture, rather than several, matches how the card is used: one file in a chat or the photo library, sent in HD where a messenger offers it. The fixed 420px layout keeps that one picture readable however long it gets, since only its height grows.

A dedicated card, rather than a picture of the page, because the page is interactive and responsive: checkboxes, stepper, gallery, buttons. The card reuses `StepList`, `PlaceholderTile` and the quantity helpers, so it cannot drift from the page's formatting.

Drawing before the tap is forced by Safari: `navigator.share` only runs while the tap's user activation lasts, and an await spent on drawing uses it up.

## Rejected

- **Several pictures, split to a fixed aspect ratio.** Readable without HD, but an album instead of one recipe, and a harder layout; the one long picture was the choice.
- **Text alongside the picture.** Messengers treat a file plus text inconsistently, often dropping one; the link is the text alternative.
- **Drawing on the server** (headless Chrome or Go). Heavy in the container, and the server knows neither the theme nor the chosen servings.
- **`satori` with `resvg-wasm`.** About 2 MB of WASM, a subset of CSS, and the fonts loaded separately.
- **`html-to-image`.** Unmaintained since early 2025, with open Safari issues around fonts and images; `modern-screenshot` is maintained and sits behind one function should it need replacing.
- **Opening the preview in `Lightbox`.** It takes recipe photos only; the preview scrolls in its own frame instead.

## Limits

- `modern-screenshot` draws through an SVG `foreignObject`, and WebKit renders a `box-shadow` there as a smudge beside its box. The card uses no shadows; its pills carry a border, like `MetaPills`.
- iOS Safari hands back an empty canvas above 16,777,216 px; `pickScale` stays under it, but a recipe taller than about 38,000 CSS px would still exceed it at 1x.
- The picture is a snapshot: later edits to the recipe never reach it.
- A screen reader cannot read the picture; the link is the accessible way to pass a recipe on.
