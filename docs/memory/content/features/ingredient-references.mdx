---
title: Ingredient references
description: Linking a word in a step's text to the ingredient it names, resolved server-side, suggested in the editor
---

A word in a preparation step can point at one ingredient of the recipe. The detail page and cook mode then show that ingredient's quantity right after the word, in parentheses and in `text-primary`, scaled to whatever servings the reader chose. `service/internal/recipe/references.go` owns resolution and storage; `frontend/src/lib/recipe/references.ts` and `frontend/src/lib/components/editor/StepEditor.svelte` own the editor.

<Callout type="warn" title="Traps">

- Whole-word matching uses `unicode.IsLetter`/`IsNumber`, never Go's ASCII-only `regexp` `\b`, or `Öl` and `Äpfel` fail ([resolution](#the-anchor-and-its-resolution)).
- Write the step document's attributes back from the editor's state, not from `transaction.doc`, which lacks the appended transaction, and only for a transaction that changed them ([undo](#the-form-model-and-undo)).
- A link whose row was deleted carries stale names that can resolve onto another row: `validate` refuses the save rather than send them.
- A client that PUTs a recipe back without `references` silently drops every link ([Limits](#limits)).
- Playwright hides scrollbars by default, so a card's scrollbar in the rounded corners shows only with `--hide-scrollbars` off.

</Callout>

## How it works

### The anchor and its resolution

**The anchor is three names, never an index.** `IngredientRef` in `service/internal/recipe/references.go` carries `Word` (the word as it stands in the step's sentence), `IngredientName` (the name it means) and `GroupName` (the ingredient group that breaks a tie, `nil` for the unnamed group) - on the wire `word`, `ingredientName` and `groupName`. The two names say *Name* because that is what they hold: a client that read `group` could fairly expect an id there, and would only find out otherwise from a 422. `Step.Text` carries `Step.References`, so `Input.Steps` is `[]Step`, not `[]string`. `word` and `ingredientName` are deliberately separate fields: it is what lets "**Fleisch** in Öl anbraten" point at the ingredient `Rinderbraten`, and "Gurken- und Zwiebelstreifen" point at `Gewürzgurken` - names a lexical match alone could never bridge. `Word` may be as long as an ingredient name, 120 characters, because `@` inserts that name as the word; only a selection spanning several words can outgrow it, and "Link word" refuses one that does (`fitsWordLimit` in `step-references.ts`).

**Resolution runs once, before the transaction.** `resolveRefs` in `references.go` is a pure function `Service.Create` and `Service.Update` both call before `db.Tx` opens. For every reference it trims `word`, requires it to occur in the step's text as a whole word (`containsWord`, checked against `unicode.IsLetter`/`IsNumber`, the `\p{L}\p{N}` class the frontend's `wordPattern` uses, rather than Go's ASCII-only `regexp` `\b`, so `Öl` and `Äpfel` match correctly), finds the one group whose name equals `groupName` and the one ingredient in it whose name equals `ingredientName`. The result is a `map[[2]int]refTarget` keyed by step and reference index that `writeChildren` reuses to attach the ids it has just minted, and `InsertStepReference` writes the row inside the same transaction as everything else the save touches - the write path in [Recipes and search](/features/recipes) does not change shape for this.

**Ambiguity is refused, never guessed.** Two groups with the same name, two unnamed groups, or the same ingredient name twice within one group all fail resolution with a `RefError`, mapped to a `422` whose `location` names the exact path (`body.steps[3].references[0].ingredientName`, or `.groupName` and `.word` for the other two fields) - the sentinel-to-`huma.ErrorDetail` pattern [HTTP API](/architecture/api) already uses elsewhere. A step that references the same word twice fails the same way, because the storage key is `(step_id, word)`. Nothing ambiguous ever reaches `step_references`, so a dangling or duplicate reference is a state the database cannot hold - both foreign keys cascade with `DeleteStepsByRecipe` and `DeleteIngredientGroupsByRecipe`, which already run on every update.

**The editor says which names stand in the way, before a link is tried.** `findDuplicates` in `step-references.ts` applies the picker's rule (`shapeGroups`, so a still empty unnamed group does not count) and `IngredientGroupEditor.svelte` shows its result: a group named like one above it, or a second unnamed group holding a row, gets a red error under its name, and `validate` refuses the save with `group:<id>` (scrolled to `ingredient-group-name-<id>`); every row whose name occurs twice in its group gets the gray "Duplicate – can't be linked" line and still saves - unless a step links into it, which `validate` refuses under the step (`editor_validation_reference_duplicate`), since the server would refuse the whole save. The server stays as lenient as before - only a reference into such a row fails - because a web import puts every line into one unnamed group, so "200 g sugar" for the dough and "80 g sugar" for the crumble arrive as the same name in one group, and refusing those would refuse the import; a second group of one name is nearly always a slip and costs one rename. A clash shows only once its field is left: while a name field has focus, a clash has to hold both with the name it had on focus and with the one typed so far, so passing through "Klopse" on the way to "Klopse in Soße" shows nothing, and typing a clash away clears it at once (`points out a repeated name once its field is left` in `frontend/e2e/recipes.test.ts`).

### Proposals, choices and cards

**The editor has two layers, and only one of them is ever stored.** Proposals are ProseMirror decorations in `StepField.svelte` that never touch the document's text; what is stored is only what the author accepted or made, and every stored reference is identical however it was produced. The matcher never runs outside the editor.

- `suggestReferences` in `frontend/src/lib/recipe/references.ts`: an exact match on an ingredient's head noun always wins and is never filtered. Failing that, a compound-overlap match in either direction (`Hackfleisch` inside `Rinderhackfleisch`), gated at a four-character head noun and a three-character remainder so `Kreis` never resolves against `Reis`, and filtered by `NOT_INGREDIENTS` (the verb prefixes and intermediate-product endings the corpus measurement below found).
- A name that occurs in several groups gets no plain proposal - the case only the author can decide - but a choice: `matchStep` reports it with its candidates, and `choicesFor` in `step-references.ts` turns them into one option per group, guessing the group most of the step's other links and proposals come from when exactly one leads (`because` holds the words that point there). A guessed choice is an ordinary proposal as well - `pendingFor` holds its guess, so "Accept all" takes it; an unguessed one waits for a pick, is underlined like a proposal and is counted in the note above the steps ("waiting for your choice", `waitingChoices`). Only an exact head-noun match becomes a choice: a compound match into two groups ("Rohrzucker" against Zucker in two groups) is dropped and left to the `@` picker. `proposals` computes both lists in one matcher run; `StepField` derives them from it once per edit.
- The card at a choice lists every option as a radio row, the guess first (`guessFirst`) and preselected, and "Accept" links the picked one; without a guess nothing is picked and "Accept" is disabled, so a stray tap never links the wrong group, and a pick of a row that has since gone counts for nothing - the guess stands. A plain proposal's card is the same card with one option. The rows are a Bits UI `RadioGroup`, valued by row index (an option's `ingredientId` may be null); a phone's sheet walks them with Up and Down, and the desktop card forces `tabindex=-1` through the item's `child` snippet, so it never takes focus. A row's title is what tells the options apart: the group, or the ingredient when they all share one, with the other name under it when it differs; a title is clamped to two lines and the reason to three words. The match is on the head noun, so the options can be different ingredients ("Salz", "grobes Salz") or share a group, and the head says "2 options" unless every option has a group of its own.
- **From `md` up a card is a popup at the word,** framed in the color of what it is about - primary for ingredients, the time color for durations - the frame the ingredient picker and "Mark as time" wear too. Proposed against stored is told by the line in the sentence and the card's actions, never by the border. It never takes focus, so the caret stays in the word; Escape closes it until the caret moves (`escapedAt`).
- **`placeCard` places it within `visibleArea()`:** below the word, else above, and where it fits neither, on the roomier side capped to that room, scrolling inside with its action bar pinned to the foot. The area is the client area without scrollbars (`window.innerWidth` counts a classic scrollbar, and a card clamped against it slid under it), below the bars marked `data-covers-top` and above the on-screen keyboard (`visualViewport`). It measures the drawn card's body (`cardScroll`): the frame clips and the body scrolls, so a scrollbar that takes room ends in the rounded corners. Playwright hides scrollbars by default, so check one with `ignoreDefaultArgs: ['--hide-scrollbars']` and a forced `::-webkit-scrollbar`. Cards and picker are sized in `rem` and measured, never assumed, so they grow with the reader's text size.
- **The `@` picker uses the same area,** chooses its side again on scroll, keyboard resize and an iOS pan of the visual viewport, and caps its height to the room. Its rows read like the list under a step (`CELL`): the name with its group beside it (what tells two "Salz" apart), the amount at the right end, the letters typed in `primary` within the name (`matchedPart`), each option named "Name · amount · group" for a screen reader. Rows of one name stay together where the first of them ranks (`matchEntries`), so two "Salz" are compared side by side. The typed letters on the active row's `accent` fill fall under 4.5:1, accepted by the owner for two letters in a row the fill already marks; `accent-foreground` there turned peach in dark mode and read as another color.
- **The actions of a card or sheet sit in one bar across the foot** (`actionBar` in `StepField.svelte`): equal fields with icon and label, the main action on the right. Color sits in the text only, the main action in `primary` (the app's main-action color, not `success`, which only reports that something worked) and "Remove" in `destructive`. A label wraps instead of clipping.
- `StepLinks` lists a choice's word once with every option below it on a guide line, each with its own "Accept" and nothing to dismiss, and counts an unguessed choice as "waiting" like the note above the steps. After any of its buttons it says what it did in a `role=status` line and moves focus to the button now in the same place, so a run of accepts needs no walk back down; with the list empty, to its summary line. "Accept all" says how many it took - `acceptAll` returns it, fewer than were counted when a time overlapped a word it just linked - and moves focus to its box, or the first step's list toggle, never into a step. A link's remove button shows an unlinked chain and a time's a crossed-out timer (`offers every group of a name that occurs in two` in `frontend/e2e/recipes.test.ts`).
- No suggestion and no choice for a row in a group that occurs twice (two unnamed groups included), which resolution refuses. An unnamed group with no named row yet, which "Add group" leaves behind and `toInput` drops, is not counted, or adding one would break every link into the unnamed group above it.
- `pendingFor` in `step-references.ts` keeps only proposals it can find in the picker's own list, which is also where each picks up its row id: "Accept all" accepts every open proposal at once, and an unusable one would fail the next save under a step the author never looked at.
- Three ways to link: accepting a proposal; `@` (Tiptap Suggestion), whose picker lists every ingredient with quantity and group so a name that occurs twice is told apart where it would bite, and which inserts the name with a space after it when the `@` stood right before a word (`ZuckerSahne` is not a word the API finds in the sentence); and "Link word", which links a word already in the sentence (`wordAt` grows the selection or caret to whole words) and writes nothing into the document.
- A press outside the `@` picker closes it (`closePickerOutside` in `StepField.svelte`); a press in the step stays with Tiptap, so a caret still inside the `@query` keeps the list. Both pickers show every matching row, never the first few: the list scrolls (`max-h-64`), so a cap would hide rows behind a scrollbar that reads as the whole list; the arrows scroll the active row into view (`offers every ingredient in the @ picker` in `frontend/e2e/recipes.test.ts`).

### The list under a step

**The sentence is where a link is seen; the folded list under it is where it is counted.** `StepLinks.svelte` lists the step's links in sentence order behind one count line. That list is what keeps every link reachable from the keyboard and a screen reader, which a decoration is not, and a link whose ingredient is gone is never folded away because it needs a decision before the save goes through.

- The card at a marked word (`wordAtCaret` in `step-references.ts`) opens with the caret strictly inside the word, so it never pops up under somebody finishing the word they type. An accept closes it, like "Dismiss": the job is done, and the link card that would take its place only repeats what the solid underline now says. `closed` remembers the word with its state, so an undo that turns the link back into a proposal brings the card back.
- **On a phone a tap on a marked word opens its card as the app's `BottomSheet`; the caret opens nothing.** Phone is the `phone` of [Sheets](/architecture/design-system#sheets), shared with the step photo preview; turning between the two layouts closes an open sheet. The tap is answered at `touchend` (`tapped`): its default is prevented, so the caret stays and no keyboard comes, and whatever had focus lets go, so an open keyboard goes. A touch that moved past `TAP_SLOP`, lasted past `TAP_TIME` (a press-and-hold selects), was canceled or had a second finger is no tap, and neither is a lift the browser no longer lets be prevented. A later occurrence carries `data-repeat-word`, so a tap on it opens its note the same way.
- **The sheet's dim leaves the step out** (`BottomSheet`'s `spotlight`, [Sheets](/architecture/design-system#sheets)): one rounded hole around the field together with its number pill and × (`data-spotlight-with` in the step's `data-spotlight-scope`), which stick out over the field's top border, `SPOTLIGHT_MARGIN` out from all of them so none touches the hole's edge. The dim is portaled over the `EditorBar`, so the hole is cut flat at it (`data-covers-top`).
- **Inside the sheet, a tap into the step closes it at once** (`flushSync`, or its focus trap would take the focus back) and writes there; a tap on another marked word of the step swaps the content and leaves the sheet up, since every kind of card renders into one frame (`cardBody`, `cardMeta`). The keyboard button (`editWord`) does the one thing a tap cannot, the caret at the end of the word, synchronously inside the tap ([User activation](/conventions/svelte#user-activation)); "Change" opens the picker the same way. Closing by an action, the handle, Escape or the dim (`closeSheet`) hands focus to the step's list toggle (`step-links-toggle-<id>`).
- **The word stays in sight.** It scrolls clear of the sheet on opening and once more when the keyboard has gone (`revealWord`, by `sheet.end`, through `BottomSheet`'s `revealAbove`), so the fourth "Salz" as much as the first, and that occurrence is framed in the step (`ref-active`; `sheet.end` is part of `decoratedWords`, which redraws the decorations). The sheet's options are a radio group the arrows walk, and its primary text reads in `accent-foreground`, since primary on the sheet's `background` falls short of 4.5:1. The e2e tests reach a card through `openWordCard` in `e2e/helpers.ts` (a tap with the phone layout, the caret in the word elsewhere).
- **The list and the "Accept all" row share one look** (`link-list.ts`): a grouped surface with rows of one height split by hairlines, the row's text starting where the step field's does, and quiet circle buttons for both taking and taking away, the icon saying which and the color coming only on hover. A proposal in the list is marked as in the sentence, by the dotted line under its name (`ref-suggestion`, `time-proposal`), and nothing else in its row is colored: names, amounts and buttons in primary made a list of proposals one block of orange. A choice is one row: the word on its own line, its groups hung from it on a guide line, each with its own accept. "Accept all" is the list's first row, and from `md` up it repeats the step rows' grid so its circle heads the column of circles under the steps. A row's amount drops under its name when both do not fit (`CELL`), never into a squeezed column of its own.
- `refView` shows the group only where it tells two rows apart.
- **A save takes no proposal.** Only what the author accepted - on the card, in the list under the step, or with the "Accept all" row above the steps in `StepEditor.svelte`, which carries the count of open proposals - is linked; an open proposal stays a proposal and comes back the next time the recipe is edited. That is what lets "Remove" on a link turn the word back into a proposal: when a save took every open proposal, removing had to dismiss too, or the link came straight back on save, and the author was left with a word that was neither linked nor offered. **Nothing remembers a proposal turned down:** "Dismiss" on a card only closes it (`closed` in `StepField.svelte`, until the caret leaves the word), and the word stays proposed, as if the recipe were opened again - a remembered dismissal was keyed by word and quietly silenced every later mention of it, and could not be seen or undone; a proposal left open costs nothing, since no save takes it.

### The form model and undo

**A link is anchored to three different things, one per layer.** On the wire and in the editor's output it is the names (`word`, `ingredientName`, `groupName`); in the database it is a foreign key; in the editor's form model, while a recipe is open, it is the ingredient row itself.

- `FormRef` in `frontend/src/lib/recipe/form.ts` carries the `FormIngredient.id` of its row beside the names it arrived with. `fromRecipe` resolves every stored reference to a row once, by the rule `findGroup`/`findIngredient` use server-side, and `toInput` reads the row's *current* group and ingredient name at save time. That is why renaming a group - naming the unnamed one above all - or an ingredient carries every link along. `PickerEntry` carries the same row id, so the list, the card and `isResolved` compare rows, not names.
- A link that found no row when the recipe loaded keeps the names it arrived with and is sent with them: the API refuses it with a 422 naming the reference, which is louder than a link that vanishes on its own.
- A link whose row was deleted while the recipe was open - or had its name cleared, which `toInput` treats the same - carries known-stale names: delete the group `Vanillesoße`, rename `Grütze` to `Vanillesoße`, and the server would resolve it onto 100 g where the author linked 50 g. So `validate` refuses the save under the step (the `step:<id>` key `applyServerErrors` and `StepEditor` render) and `toInput` drops it; the author takes the link off themselves.
- **A word's link and time live and end with the word, and Cmd+Z covers them.** Each step's editor carries its `references` and `times` as attributes of its ProseMirror document (`step-doc.ts`), mirrored with the form both ways in `StepField.svelte`: the form's changes - a card's or the list's button, "Accept all" - become a transaction each (`closeHistory`, so they are undo steps of their own), and a transaction that changed the attributes - an undo, a redo, a deleted word - is written back. `dropAbsent` drops whatever names a word the text no longer holds in a transaction appended to the edit, so it shares the edit's undo step: deleting a linked word ends its link, typing the word again gets at most a proposal (a revived link once came back fully confirmed inside an unrelated new sentence), and Cmd+Z brings word and link back together. Write the attributes back from the editor's state, not from `transaction.doc`, which Tiptap hands over without the appended transaction; and only for a transaction that changed them, or a caret move right after a pick copies the document's old words over the form's new ones. `presentReferences` in `form.ts` remains a guard for what the API would refuse. An `@` pick writes its word and its link in one transaction (the Suggestion's `command`), so one undo takes both.

**Times share this machinery.** A duration in a step is marked the same way - proposed in the editor, accepted, stored beside the references. A word and a time may not overlap (`isMarked`). [Step times](/features/step-times) owns the rest.

**Photo links share it too.** A phrase can point at one of the recipe's photos: `FormStep.photos` is a third attribute of the step document beside `references` and `times` (`STEP_WORDS`), so `dropAbsent` ends a photo link with its phrase and Cmd+Z brings both back. [Step photos](/features/step-photos) owns the rest, the editor side included.

### Rendering

**Rendering resolves nothing; it only looks a stored reference up.** `segmentStep` in `references.ts` splits a step's text into plain and referenced segments by re-finding each reference's word with the same `wordPattern` the editor's decorations use, looks up the ingredient by group and name, and formats its quantity with `formatQuantityFor` from `frontend/src/lib/recipe/scale.ts` - the function [Cooking](/features/cooking) uses for the ingredient list, so a reference and the list can never disagree, and scaling to the chosen servings is free. `StepText.svelte` renders the segments for both `StepList.svelte` (the detail page) and the cook route. A reference whose ingredient or group no longer resolves - renamed or deleted since the save - degrades to the plain word with no parenthesis, never to a guess. A step's `photos` (phrase and image id) cut those segments too: every segment inside a photo phrase carries `photo`, so a referenced word inside keeps its quantity. `StepText` turns consecutive segments of one photo into a single inline `span role=button` (a `<button>` cannot wrap across lines) when given `onphoto`, and `StepPhotoPreview.svelte` opens the photo as a card on a desktop or a bottom sheet on a phone (`ui/phone.svelte.ts`); without `onphoto` (share card, print) the phrase is plain text.

## Why it is this way

Ingredients have no stable identity *across saves*: `writeChildren` mints a fresh UUIDv7 for every ingredient on every save, because `Update` deletes and rewrites the whole document, and the API's `Ingredient` type carries no id at all. An anchor by ingredient id would not survive the next save, and a positional anchor - "the third ingredient in this group" - would silently point at a neighbor the moment anything above it is deleted or reordered. A name is the anchor that degrades usefully: when it stops resolving, the word is still the word the author wrote and the sentence reads exactly as it did before. Every failure mode is "no reference," never "wrong reference," and a wrong quantity in someone's kitchen is worse than a missing one. The editor's client id is not a counter-example: it is minted by `newId()` when a recipe is loaded into the form, it never leaves the browser, and it is gone when the page is. It anchors a link only for as long as the author is editing - exactly the window in which the names the wire uses are the thing being changed.

Names were chosen over ids for a second reason beyond the schema: REST clients with an [API token](/features/api-tokens) and the [MCP server](/features/mcp) resubmit whole documents, and a client that drops an id field on `PUT` would silently regenerate every ingredient id and break every reference in the recipe at once.

Suggestions never reach storage on their own because nothing unreviewed may reach a cook. The matcher is allowed to be aggressive - compound splitting over the conservative exact match - precisely because a human always looks at the suggestion in the sentence it will appear in before it is saved; a wrong proposal costs one click, not a wrong number at the stove. This is also why rendering never runs the matcher: the detail page and cook mode read only what somebody has already confirmed.

A throwaway matcher run over the twelve German sample recipes (122 ingredient entries, 65 steps) decided the matching strategy. Exact whole-word matching covers 66% of steps with zero false positives; adding compound splitting reaches 82%, at the cost of three failure classes (verbs, intermediate products, cooking water) that `NOT_INGREDIENTS` exists to filter. Inflection stemming was measured and rejected: against the same corpus it bought one real hit for three false ones. The decisive finding, though, was not about matching at all - seven of the twelve sample recipes list the same ingredient name twice, three of those with different quantities, and no amount of name matching can tell which occurrence a given step means. That is why an explicit, authored reference exists as a concept in the first place, independent of how good the matcher gets. The shipped matcher, running the compound strategy, proposes references on 52 of the 65 sample steps.

## Rejected

- **A card docked on the on-screen keyboard, or hung at the word, on a phone.** Nothing pins a popup to the keyboard in every browser: iOS keeps `position: fixed` behind it (only the visual viewport shrinks), Chrome on Android moves the fixed layer with the address bar, and the VirtualKeyboard API is Chromium only - a card placed by `visualViewport` sat behind the keyboard or a bar's height above it, depending on the address bar. Chromium shrinks the layout with the keyboard and iOS does not ([Sheets](/architecture/design-system#sheets)), so a card hung on the keyboard would still need two paths. At the word, a card covered the sentence and hid every option after the first. A tap that closes the keyboard and opens a sheet has the screen to itself in every browser. The login's sheet does live above the keyboard, but there the whole frame (`main`) follows the visible area and everything inside it is in flow, rather than a card placed on its own.

- **Positional anchors** (the step's Nth word, or the group's Nth ingredient). Rejected for the same reason as ids: ingredients and steps are rewritten wholesale on every save, so a position drifts the moment anything above it changes, and it drifts silently.
- **Stable ingredient ids added to the API contract.** Would fix the anchor today at the cost of a new failure mode tomorrow: any client - including the MCP server's `update_recipe` tool - that resubmits a document without carrying the ids forward regenerates all of them and breaks every reference in the recipe at once, with nothing loud to say so.
- **Markup inside `steps.text`** (e.g. wrapping the referenced word in a tag the frontend parses out). Would make the stored text depend on the feature that annotates it, and every reader of `text` - the search index, a future export, an MCP client - would have to strip markup it has no reason to know about.
- **A parallel `stepReferences` array keyed by step index.** The same positional fragility as an index-based anchor, one level up: reorder the steps and every reference points at the wrong one. Keeping `references` on the `Step` object it belongs to means a reordered step carries its references with it for free.
- **Inflection stemming in the matcher.** Measured directly against the sample corpus and rejected on the numbers: one real hit (`Semmelbröseln`) against three false ones (`salzen` → Salz and its like).
- **A stop-list of generic ingredient names** (salt, water, pepper) that the matcher would never suggest. `NOT_INGREDIENTS` already filters the compound-overlap branch by ending, not by naming ingredients, and an exact head-noun match is never filtered at all - a stop-list would stop the ingredient "Salz" from ever matching the word "Salz", which is the opposite of what the feature is for.
- **A save that accepts every open proposal.** It linked recipes nobody had looked over - compound matches, and the guessed group of a name in two groups - and forced "Remove" to dismiss as well; the dotted underlines already ask for a decision, and "Accept all" is one click.
- **An icon that reveals the open-suggestion count only on click.** The count belongs beside the button that acts on it ("3 suggestions open", "Accept all"), not behind a second interaction that could be skipped.

## Limits

- A recipe carries references only once it has been saved with them: reaching an existing collection happens one recipe at a time, because nothing is ever resolved except through a save a human has reviewed.
- One word carries at most one reference per step, at its first occurrence - which is right for the cook, since a second "(250 g)" reads as another 250 g; referencing the same word twice with two different meanings, or a portion per mention, is not expressible (it would need an occurrence index in the `(step_id, word)` key, and a positional anchor drifts as the text is edited). The editor makes the rule visible: a linked or proposed word's later occurrences get the faint `ref-repeat` line, the card at one says only the first is linked (`repeatAtCaret`), and "Link word" on a later occurrence says the same instead of quietly re-linking the first. The detail page and cook mode mark only the first.
- The matcher does not reach 13 of the 65 steps in the German sample corpus (roughly 20%), and 10 of the 65 in the English one, although its compound splitting and `NOT_INGREDIENTS` are German through and through; English mostly names an ingredient with a whole word it can match exactly. A word that differs from the ingredient's name - "Fleisch" for `Rinderbraten` - is never proposed, because the matcher only ever compares words that already share text. Both need a link the author makes: `@` where the ingredient's own name belongs in the sentence, "Link word" where it does not.
- A client that GETs a recipe and PUTs it back without `references` silently drops every link in it, recorded rather than guarded ([HTTP API](/architecture/api)): nothing in the request tells "this step has no links" apart from "this client does not know about links". The links are then gone until somebody makes them again in the editor - loud enough on the detail page, where the quantities stop appearing, but not at the moment of the write. Over MCP the field is required, so a model cannot drop links by omission ([MCP](/features/mcp)).
- Deleting an ingredient row that a step links to blocks the save until the author removes the link. It is the one edit the editor cannot carry out on their behalf: re-pointing the link is a decision only they can make, and both silent answers - sending the stale names, or dropping the link - are worse than being asked.
- Emptying all four fields of a linked row instead of removing it is not caught before the save: the row is still in the form, so the deleted-row check does not fire, while `toInput` drops it as empty and sends `ingredient: ""`, which the API refuses on `minLength` and the editor shows under the same step. Loud rather than wrong, and left as the one way in which a link can reach the server knowing it will be refused.
- Only the first occurrence of a referenced word in a step is annotated, deliberately: `segmentStep` looks up each reference without the `g` flag, so it always finds the earliest match. Repeating a quantity on a later mention of the same word would read as an additional amount rather than the same one, and a number that can be misread is exactly what this feature must never produce.
