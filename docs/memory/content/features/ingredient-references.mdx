---
title: Ingredient references
description: Linking a word in a step's text to the ingredient it names, resolved server-side, suggested in the editor
---

A word in a preparation step can point at one ingredient of the recipe. The detail page and cook mode then show that ingredient's quantity right after the word, in parentheses and in `text-primary`, scaled to whatever servings the reader chose. `service/internal/recipe/references.go` owns resolution and storage; `frontend/src/lib/recipe/references.ts` and `frontend/src/lib/components/editor/StepEditor.svelte` own the editor.

## How it works

**The anchor is three names, never an index.** `IngredientRef` in `service/internal/recipe/references.go` carries `Word` (the word as it stands in the step's sentence), `IngredientName` (the name it means) and `GroupName` (the ingredient group that breaks a tie, `nil` for the unnamed group) - on the wire `word`, `ingredientName` and `groupName`. The two names say *Name* because that is what they hold: a client that read `group` could fairly expect an id there, and would only find out otherwise from a 422. `Step.Text` carries `Step.References`, so `Input.Steps` is `[]Step`, not `[]string`. `word` and `ingredientName` are deliberately separate fields: it is what lets "**Fleisch** in Öl anbraten" point at the ingredient `Rinderbraten`, and "Gurken- und Zwiebelstreifen" point at `Gewürzgurken` - names a lexical match alone could never bridge. `Word` may be as long as an ingredient name, 120 characters, because `@` inserts that name as the word; only a selection spanning several words can outgrow it, and "Link word" refuses one that does (`fitsWordLimit` in `step-references.ts`).

**Resolution runs once, before the transaction.** `resolveRefs` in `references.go` is a pure function `Service.Create` and `Service.Update` both call before `db.Tx` opens. For every reference it trims `word`, requires it to occur in the step's text as a whole word (`containsWord`, checked against `unicode.IsLetter`/`IsDigit` rather than Go's ASCII-only `regexp` `\b`, so `Öl` and `Äpfel` match correctly), finds the one group whose name equals `groupName` and the one ingredient in it whose name equals `ingredientName`. The result is a `map[[2]int]refTarget` keyed by step and reference index that `writeChildren` reuses to attach the ids it has just minted, and `InsertStepReference` writes the row inside the same transaction as everything else the save touches - the write path in [Recipes and search](/features/recipes) does not change shape for this.

**Ambiguity is refused, never guessed.** Two groups with the same name, two unnamed groups, or the same ingredient name twice within one group all fail resolution with a `RefError`, mapped to a `422` whose `location` names the exact path (`body.steps[3].references[0].ingredient`) - the sentinel-to-`huma.ErrorDetail` pattern [HTTP API](/architecture/api) already uses elsewhere. A step that references the same word twice fails the same way, because the storage key is `(step_id, word)`. Nothing ambiguous ever reaches `step_references`, so a dangling or duplicate reference is a state the database cannot hold - both foreign keys cascade with `DeleteStepsByRecipe` and `DeleteIngredientGroupsByRecipe`, which already run on every update.

**The editor has two layers, and only one of them is ever stored.** `suggestReferences` in `frontend/src/lib/recipe/references.ts` proposes hits: an exact match on an ingredient's head noun always wins; failing that, a compound-overlap match in either direction (`Hackfleisch` inside `Rinderhackfleisch`, `Gurken` inside `Gurkenstreifen`), gated at a four-character head noun and a three-character remainder so `Kreis` never resolves against `Reis`, and filtered by `NOT_INGREDIENTS` against the verb and intermediate-product endings the corpus measurement below found (`brat-`, `röst-`, `salz-` prefixes; `-puffer`, `-kuchen`, `-salat`, `-suppe`, `-wasser`, `-teig`, `-masse`, `-füllung` suffixes). A name ambiguous within the recipe gets no suggestion at all - that is exactly the case only the author can decide - and neither does a row in a group that occurs twice (two unnamed groups included), which resolution refuses for the same reason - an unnamed group with no named row yet, which is what "Add group" leaves behind and `toInput` drops, is not counted, or adding one would break every link into the unnamed group above it; `pendingFor` in `step-references.ts` keeps only the proposals it can find in the picker's own list as well - which is also where each one picks up the row id it is anchored to - because a save accepts what is still open and an unusable proposal would fail it with a message about the ingredient list under a step the author never touched. `StepField.svelte` renders every proposal as a ProseMirror decoration (a dotted underline that never touches the document's own text) and offers three ways to link: `@` through the Tiptap Suggestion extension, which opens a picker listing every ingredient with its quantity and group - "Zucker · 100 g · Grütze" right beside "Zucker · 50 g · Vanillesoße" at the moment the ambiguity would otherwise bite - and inserts the chosen name, with a space after it when the `@` stood right in front of a word - `ZuckerSahne` is a word the API cannot find in the sentence; "Link word", which links a word already in the sentence (`wordAt` grows the selection or the caret out to whole words) to any ingredient, writing nothing into the document because the word is already there; and accepting a proposal.

**The sentence is where a link is seen; one folded line under it is where it is counted.** Under a step, `StepLinks.svelte` shows only "6 linked" (and "2 suggestions" while the matcher has open ones), which opens into a list of one row per link - name, amount in its own right-aligned column, remove button - in the order the words stand in the sentence. The list is also what keeps every link reachable from the keyboard and a screen reader, which the underline, a decoration, is not. A link whose ingredient is gone is never folded away: it needs a decision before the save goes through. "Link word" is offered only on the step that has focus. Putting the caret inside an underlined word opens a card at the word (`wordAtCaret` in `step-references.ts`) with what it points at and "Change" / "Remove", or "Accept" / "Dismiss" for a proposal; the card never takes focus, so typing carries on in the word, and a caret at either edge of it does not count, so it never opens under somebody finishing the word they are typing. The group is shown only where it tells two rows apart - `refView` - because on every link of a step it was the noise that made a full list of chips read as clutter. On a phone the step's handle, number and remove button sit in a row above the field, which then gets the full width. `StepEditor.svelte` shows what saving will do with the open proposals - "Saving accepts 7 suggestions" beside a button that accepts them now instead - and every accepted or authored reference is identical once stored: the API and the resolution rules above never see how a row was produced. The matcher itself never runs outside the editor.

**A link is anchored to three different things, one per layer.** On the wire and in the editor's *output* it is the names (`word`, `ingredientName`, `groupName`); in the database it is a foreign key; and in the editor's form model, while a recipe is open, it is the ingredient row itself. `FormRef` in `frontend/src/lib/recipe/form.ts` carries the `FormIngredient.id` of the row it points at beside the names it arrived with: `fromRecipe` resolves every stored reference to a row once, by the same rule `findGroup`/`findIngredient` use server-side, and `toInput` reads that row's *current* group and ingredient name back off it at save time. That middle layer is why renaming a group - giving the unnamed one a name above all - or renaming an ingredient carries every link along instead of breaking it; names recorded when the link was made would be stale the moment the author edits the list they name. `PickerEntry` carries the same row id, so the list, the card and `isResolved` in `step-references.ts` compare rows, not names. A link that resolves to no row is drawn as broken, and which of the two ways it got there decides what happens on save. One that never found a row when the recipe was loaded keeps the names it arrived with and is sent with them - they are all there is, and the API refuses it with a 422 naming the reference, which is louder than a link that vanishes on its own. One whose row was deleted while the recipe was open - or had its name cleared, which `toInput` treats the same - is different: the names it remembers are known-stale, and delete the group `Vanillesoße` then rename `Grütze` to `Vanillesoße` and they describe a *different* row, which the server would resolve happily onto 100 g where the author linked 50 g. So `validate` refuses the save and reports it under the step ("This link points at a deleted ingredient", the `step:<id>` key `applyServerErrors` and `StepEditor` already render), and `toInput` drops such a reference rather than send it. Neither silently changes the link nor silently loses it: the author takes it off themselves. Editing a step never removes a link either. One whose word an edit took out stays on the step, out of sight - `presentReferences` in `form.ts` decides what the list, the card, the decorations, `validate` and `toInput` see - because the editor's undo history covers the text alone: a link dropped on the keystroke would be gone for good by the time Cmd+Z restored its word. Undoing the edit, or pasting the sentence back, brings the link back with the word, and a save leaves out any link whose word is still missing.

**Rendering resolves nothing; it only looks a stored reference up.** `segmentStep` in `references.ts` splits a step's text into plain and referenced segments by re-finding each reference's word with the same `wordPattern` the editor's decorations use, looks up the ingredient by group and name, and formats its quantity with `formatQuantityFor` from `frontend/src/lib/recipe/scale.ts` - the function [Cooking](/features/cooking) uses for the ingredient list, so a reference and the list can never disagree, and scaling to the chosen servings is free. `StepText.svelte` renders the segments for both `StepList.svelte` (the detail page) and the cook route. A reference whose ingredient or group no longer resolves - renamed or deleted since the save - degrades to the plain word with no parenthesis, never to a guess.

## Why it is this way

Ingredients have no stable identity *across saves*: `writeChildren` mints a fresh UUIDv7 for every ingredient on every save, because `Update` deletes and rewrites the whole document, and the API's `Ingredient` type carries no id at all. An anchor by ingredient id would not survive the next save, and a positional anchor - "the third ingredient in this group" - would silently point at a neighbour the moment anything above it is deleted or reordered. A name is the anchor that degrades usefully: when it stops resolving, the word is still the word the author wrote and the sentence reads exactly as it did before. Every failure mode is "no reference," never "wrong reference," and a wrong quantity in someone's kitchen is worse than a missing one. The editor's client id is not a counter-example: it is minted by `newId()` when a recipe is loaded into the form, it never leaves the browser, and it is gone when the page is. It anchors a link only for as long as the author is editing - exactly the window in which the names the wire uses are the thing being changed.

Names were chosen over ids for a second reason beyond today's schema: the roadmap holds a public REST API and an MCP server, and a client that drops an id field on `PUT` would silently regenerate every ingredient id and break every reference in the recipe at once. That hazard is worth designing out now rather than discovering later.

Suggestions never reach storage on their own because nothing unreviewed may reach a cook. The matcher is allowed to be aggressive - compound splitting over the conservative exact match - precisely because a human always looks at the suggestion in the sentence it will appear in before it is saved; a wrong proposal costs one click, not a wrong number at the stove. This is also why rendering never runs the matcher: the detail page and cook mode read only what somebody has already confirmed.

A throwaway matcher run over the twelve German sample recipes (122 ingredient entries, 65 steps) decided the matching strategy. Exact whole-word matching covers 66% of steps with zero false positives; adding compound splitting reaches 82%, at the cost of three failure classes (verbs, intermediate products, cooking water) that `NOT_INGREDIENTS` exists to filter. Inflection stemming was measured and rejected: against the same corpus it bought one real hit for three false ones. The decisive finding, though, was not about matching at all - seven of the twelve sample recipes list the same ingredient name twice, three of those with different quantities, and no amount of name matching can tell which occurrence a given step means. That is why an explicit, authored reference exists as a concept in the first place, independent of how good the matcher gets. The shipped matcher, running the compound strategy, proposes references on 52 of the 65 sample steps.

## Rejected

- **Positional anchors** (the step's Nth word, or the group's Nth ingredient). Rejected for the same reason as ids: ingredients and steps are rewritten wholesale on every save, so a position drifts the moment anything above it changes, and it drifts silently.
- **Stable ingredient ids added to the API contract.** Would fix the anchor today at the cost of a new failure mode tomorrow: any client - including the roadmap's MCP server - that resubmits a document without carrying the ids forward regenerates all of them and breaks every reference in the recipe at once, with nothing loud to say so.
- **Markup inside `steps.text`** (e.g. wrapping the referenced word in a tag the frontend parses out). Would make the stored text depend on the feature that annotates it, and every reader of `text` - the search index, a future export, an MCP client - would have to strip markup it has no reason to know about.
- **A parallel `stepReferences` array keyed by step index.** The same positional fragility as an index-based anchor, one level up: reorder the steps and every reference points at the wrong one. Keeping `references` on the `Step` object it belongs to means a reordered step carries its references with it for free.
- **Inflection stemming in the matcher.** Measured directly against the sample corpus and rejected on the numbers: one real hit (`Semmelbröseln`) against three false ones (`salzen` → Salz and its like).
- **A stop-list of generic ingredient names** (salt, water, pepper) that the matcher would never suggest. `NOT_INGREDIENTS` already filters the compound-overlap branch by ending, not by naming ingredients, and an exact head-noun match is never filtered at all - a stop-list would stop the ingredient "Salz" from ever matching the word "Salz", which is the opposite of what the feature is for.
- **An icon that reveals the pending-suggestion count only on click.** The count is exactly what informed consent needs before the click that accepts every proposal at once ("Saving accepts 7 suggestions"), so it is shown beside the button that acts on it rather than behind a second interaction that could be skipped.

## Limits

- A recipe carries references only once it has been saved with them: reaching an existing collection happens one recipe at a time, because nothing is ever resolved except through a save a human has reviewed.
- One word carries at most one reference per step; referencing the same word twice with two different meanings in one sentence is not expressible.
- The matcher does not reach 13 of the 65 steps in the German sample corpus (roughly 20%), and 10 of the 65 in the English one, although its compound splitting and `NOT_INGREDIENTS` are German through and through; English mostly names an ingredient with a whole word it can match exactly. A word that differs from the ingredient's name - "Fleisch" for `Rinderbraten` - is never proposed, because the matcher only ever compares words that already share text. Both need a link the author makes: `@` where the ingredient's own name belongs in the sentence, "Link word" where it does not.
- `Step.references` is `required:"false"` in the generated OpenAPI, so a client that GETs a recipe and PUTs it back without carrying `references` silently drops every link in it. That is inherent to a full-document PUT, and it is recorded rather than guarded: nothing in the request tells "this step has no links" apart from "this client does not know about links", so the write cannot refuse. The links are then gone until somebody makes them again in the editor - loud enough on the detail page, where the quantities stop appearing, but not at the moment of the write.
- Deleting an ingredient row that a step links to blocks the save until the author removes the link. It is the one edit the editor cannot carry out on their behalf: re-pointing the link is a decision only they can make, and both silent answers - sending the stale names, or dropping the link - are worse than being asked.
- Emptying all four fields of a linked row instead of removing it is not caught before the save: the row is still in the form, so the deleted-row check does not fire, while `toInput` drops it as empty and sends `ingredient: ""`, which the API refuses on `minLength` and the editor shows under the same step. Loud rather than wrong, and left as the one way in which a link can reach the server knowing it will be refused.
- Only the first occurrence of a referenced word in a step is annotated, deliberately: `segmentStep` looks up each reference without the `g` flag, so it always finds the earliest match. Repeating a quantity on a later mention of the same word would read as an additional amount rather than the same one, and a number that can be misread is exactly what this feature must never produce.
