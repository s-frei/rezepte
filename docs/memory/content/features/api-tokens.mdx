---
title: API tokens
description: Scoped bearer tokens for programmatic access, issued and revoked from Settings
---

An admin issues a named, scoped, optionally expiring API token from Settings → API and uses it in place of the session cookie: `Authorization: Bearer rzp_...` authenticates a request the same way a browser session does, and is the credential the [MCP server](/features/mcp) uses and a future instance sync will use (see [Roadmap](/roadmap)). `service/internal/auth` (`token.go`, `middleware.go`, `require.go`) issues and verifies tokens and decides whether an operation may accept one; `service/internal/tokenapi` exposes token management itself; `frontend/src/routes/settings/api` and the components under `frontend/src/lib/components/settings` are the UI. [Data model](/architecture/data-model) owns the `api_tokens` table; [HTTP API](/architecture/api) owns the three `/api/v1/tokens` endpoints and their status codes.

## How it works

**Five scopes, and write always travels with its read.** `service/internal/auth/token.go` defines `ScopeRecipesRead`, `ScopeRecipesWrite`, `ScopeRecipesDelete`, `ScopeUsersRead` and `ScopeUsersWrite` as the closed set `knownScopes`. A token's scopes are stored as a space-separated string - the OAuth convention, and exactly the shape huma's `Security` already holds, so creating and checking a token speak the same language with no translation. Writing implies reading, and for recipes deleting implies both, only by convention: `CreateTokenDialog.svelte`'s Recipes row offers a fourth level, *Full*, beside *No access*, *Read* and *Read & write*; `scopesOf` builds each level's scopes from a ladder (`recipes:read`, `recipes:write`, `recipes:delete`) sliced to the chosen depth, so *Full* sends all three and *Read & write* sends the first two, and the middleware compares scope lists rather than applying an implication rule of its own. The Members row stops at *Read & write* - `users:write` already covers removing an account, so there is no `users:delete` to reach.

**The raw value exists once.** `TokenService.Create` draws 32 random bytes and encodes them as `TokenPrefix + base64.RawURLEncoding` (`rzp_` plus 43 characters), then stores only the SHA-256 digest in `token_hash`; the first eight characters go in `token_prefix` for display. `tokenapi.CreatedAPIToken` is the only response type carrying the raw value, embedding `APIToken` rather than adding an optional field to it, so the secret cannot leak into the list response as a matter of typing rather than of review discipline. `TokenRevealDialog.svelte` shows it once, in a monospace block with a copy button, and does not close on Escape or an outside click - only its own confirm button does, so one stray keystroke cannot destroy the only copy. When the freshly created token carries `recipes:read`, the same dialog adds a "Use with an AI assistant" section with a Claude Code and a JSON snippet, each carrying the token and the instance's `/mcp` URL - see [MCP](/features/mcp).

**A bearer request is checked at three call sites; two of them share the check.** `auth.Middleware`, `requireAuth` and `RequireToken` (`service/internal/auth/require.go`) each decide whether a request's bearer token is valid enough to proceed, but `requireAuth` and `RequireToken` are close enough in shape - both are mux middleware working with an `http.ResponseWriter`, not a huma operation - to share `authenticateBearer`: it runs `TokenService.Authenticate`, checks the required scopes, and writes the `401`/`403` body itself, so a change to how either failure is reported is made once. Either call site's bearer-failure `401` carries `WWW-Authenticate: Bearer`. `Middleware` cannot reuse it: it decides over a `huma.Context`, and its first outcome only a huma operation can produce - an operation whose `Security` names no `token` scheme answers `403` ("API tokens cannot use this operation") before authentication runs at all; an unknown token, an expired one, or one whose issuer is no longer an admin then answers `401` (`Authenticate` collapses all three into `ErrNoToken`, so the caller cannot tell which); a token missing a required scope answers `403` naming it - all three written through `huma.WriteErr`. `requireAuth` and `RequireToken` only ever reach the second and third outcome, since a mux route has no `Security` to consult; they differ from each other only in what happens when there is no bearer header at all - `requireAuth` falls through to a session cookie, `RequireToken` (used only for `/mcp`, see [MCP](/features/mcp)) refuses outright, so a page that could make a browser send a cookie can never reach it that way. See [Users and authentication](/features/users-and-auth) for the session half of `Middleware` and `requireAuth`.

**Reachability is a type, not a check inside a handler.** An operation declares `auth.Protected(scopes...)` instead of `auth.SessionSecurity` to accept a token at all; a `Security` requirement that never names the `token` scheme is structurally unreachable for one. That is what keeps these session-only: `/api/v1/tokens` itself, and everything a person does to their own session and account - `me`, `logout`, `change-own-password`, `update-own-profile` and `list-color-usage` under `/api/v1/auth` - plus `update-settings` (`PATCH /api/v1/settings`), whose reader `get-settings` does accept a `recipes:read` token. `auth.SecuritySchemes()` declares both schemes for the OpenAPI document, installed through `httpserver.WithSecuritySchemes` so the scheme names stay inside `auth` and `httpserver` keeps knowing nothing about authentication.

**A token never outlives the privilege that justified it.** `Authenticate` re-reads the issuer's row on every request: a deleted issuer (`ON DELETE CASCADE` removes the token too) or one demoted to `user` fails the same way an unknown token does. Holding a token is an admin capability in this design, so losing the admin role kills the token even though `recipes:*` would still be within a plain member's rights.

**Use is recorded at most once an hour.** `touchAfter` mirrors the session's `renewAfter` pattern: `last_used_at` is written back only when the stored value is more than an hour old, so a busy integration does not write on every request. The token list's "last used" column carries a tooltip saying so.

**Token management itself stays session-only.** `service/internal/tokenapi` exposes list, create and revoke - [HTTP API](/architecture/api) owns their paths and status codes - and none is reachable by a token: one able to mint or list tokens would defeat both expiry and revocation. `requireAdmin` gates all three; `canManageAllTokens` in `service/internal/tokenapi/handler.go` is `u.Role.IsAdmin()`, so every admin and the instance owner sees and revokes every token on the instance - a comparison against `RoleAdmin` would lock the owner out of their own instance's tokens. Narrowing the list to the instance owner alone would need it scoped by issuer and the revoke checked against that, neither of which exists.

**The Settings UI.** An "API" tab sits between "Profile" and "Members" in `SettingsLayout.svelte` and is open to every member, since any session may call the API and read the spec; only "Members" stays behind the admin guard. `settings/api/+page.ts` therefore resolves the role into `isAdmin` instead of redirecting, and the page gates the token half on that flag - the section, its three dialogs and the `GET /tokens` call alike, because a member firing that call would be answered `403` and left looking at the page's load-error state. `ApiReferenceCard.svelte` heads the page for everyone: the base URL to copy (read off `window.location.origin`, so it names whatever host the instance answers on), the endpoint and area counts from `/api/v1/openapi.json`, the instance version from `/healthz`, and links out to `/api/v1/docs` and the document itself. Both figures are decoration on a card that stands without them, so a failed fetch drops its own figure silently rather than turning the card into an error. `summarizeSpec` in `frontend/src/lib/settings/api-summary.ts` is the pure reduction, which is what keeps the 75 KB document out of component state; `frontend/src/lib/api/spec.ts` fetches. For a member the card carries one line saying a token is issued by an admin account - the UI half of the first entry under `Limits`. `CreateTokenDialog.svelte` offers two `SegmentedControl` rows - Recipes (No access / Read / Read & write / Full) and Members (No access / Read / Read & write) - and an expiry `Select` (30, 90, 365 days, or never - default 90). `TokenTable`/`TokenRow` list existing tokens with name, scopes, owner, last use and expiry, muting and badging an expired one; revoking goes through the app's existing confirm dialog. `frontend/src/lib/api/tokens.ts` is the client (`listTokens`, `createToken`, `deleteToken`).

## Why it is this way

A static bearer token in a client configuration is the deliberate simplification a self-hosted, single-household instance affords over OAuth 2.1: no token exchange, no client registration, no redirect flow to implement or to explain to whoever configures an integration.

The bearer branch lives inside `auth.Middleware` itself rather than arriving as a separate authenticator run in front of it, because the question it answers first - whether an operation accepts a token at all - can only be read off `ctx.Operation().Security`, and only a huma operation has one. A mux route has no such declaration, which is exactly why `requireAuth` and `RequireToken` cannot offer that outcome and do not try to: their allowed scopes are instead given directly by whichever caller wraps a route in them, such as the image files' `recipes:read` or `/mcp`'s. `Middleware` staying separate from the two is the consequence of that, not an oversight, and it is also the shape the [MCP](/features/mcp) endpoint follows: a mux route, since Streamable HTTP does not fit huma's typed operations, with its scope chosen explicitly by hand, the same way the image routes and the contract routes already are.

Two roles already keep authorization a field comparison (see [Users and authentication](/features/users-and-auth)); scopes add a second, independent comparison rather than a permission table, so a token's reach is still decided by comparing two short lists, never by a rule engine.

## Rejected

- **A token that authenticates as its issuer outright, with no scopes.** An integration that only needs to read recipes should not hold a credential that can also delete users; the five-scope closed set is what lets an admin match what a token can do to what the integration actually needs.
- **`PATCH` to rename or re-scope an existing token.** What a token may do is fixed for its whole lifetime; revoking and creating a replacement is the only path, so a scope change is always visible as a new credential rather than a silent widening of an old one.
- **Letting a token reach `/api/v1/tokens`.** A token that can mint or list tokens defeats both expiry and revocation - it could reissue itself past its own expiry.
- **A sweep job that deletes expired tokens.** Expired rows stay until an explicit revoke; a row that disappeared on its own would leave an admin unable to explain why an integration stopped working. The expiry check happens during authentication instead.
- **Exact `last_used_at`, written on every request.** A busy integration would write on every call for a level of precision nobody reads; the hourly throttle mirrors the pattern sliding sessions already use.

## Limits

- Tokens can be issued only by an admin; there is no self-service path for a plain member. A member sees the API page and everything on it except that section, and the card tells them who issues a token.
- A `users:write` token carries its issuer's rank: one issued by the instance owner can create an admin account, one issued by any other admin cannot (see [Users and authentication](/features/users-and-auth)). An admin account created through the owner's token looks like any other - on a household instance, the owner who issued the token is the person who would notice.
- `last_used_at` is accurate to the hour, not to the request; the UI's tooltip says so rather than implying more precision than the column has.
- Token-authenticated requests are not rate-limited; that belongs to the public REST API item in the [Roadmap](/roadmap).
