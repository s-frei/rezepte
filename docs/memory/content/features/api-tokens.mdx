---
title: API tokens
description: Scoped bearer tokens for programmatic access, issued and revoked from Settings
---

An admin issues a named, scoped, optionally expiring API token from Settings → API and uses it in place of the session cookie: `Authorization: Bearer rzp_...` authenticates a request the same way a browser session does, and is the credential the [MCP server](/features/mcp) uses; the instance sync on the [Roadmap](/roadmap) builds on it. `service/internal/auth` (`token.go`, `middleware.go`, `require.go`) issues and verifies tokens and decides whether an operation may accept one; `service/internal/tokenapi` exposes token management itself; `frontend/src/routes/settings/api` and the components under `frontend/src/lib/components/settings` are the UI. [Data model](/architecture/data-model) owns the `api_tokens` table; the OpenAPI document holds the three `/api/v1/tokens` endpoints and their status codes ([HTTP API](/architecture/api)).

## How it works

**Five scopes, and write always travels with its read.** `service/internal/auth/token.go` defines `ScopeRecipesRead`, `ScopeRecipesWrite`, `ScopeRecipesDelete`, `ScopeUsersRead` and `ScopeUsersWrite` as the closed set `knownScopes`. A token's scopes are stored as a space-separated string - the OAuth convention, and exactly the shape huma's `Security` holds, so creating and checking a token speak the same language. Writing implies reading, and for recipes deleting implies both, only by convention: `scopesOf` in `CreateTokenDialog.svelte` slices a ladder (`recipes:read`, `recipes:write`, `recipes:delete`) to the chosen depth, so *Delete* sends all three, and the middleware compares scope lists rather than applying an implication rule of its own. There is no `users:delete`: `users:write` already covers removing an account.

**The raw value exists once.** `TokenService.Create` draws 32 random bytes and encodes them as `TokenPrefix + base64.RawURLEncoding` (`rzp_` plus 43 characters), then stores only the SHA-256 digest in `token_hash`; the first eight characters go in `token_prefix` for display. `tokenapi.CreatedAPIToken` is the only response type carrying the raw value, embedding `APIToken` rather than adding an optional field to it, so the secret cannot leak into the list response as a matter of typing rather than of review discipline. `TokenRevealDialog.svelte` shows it once and closes only on its own confirm button, never on Escape or an outside click, so one stray keystroke cannot destroy the only copy. When the new token carries `recipes:read`, the dialog adds client snippets carrying the token and the instance's `/mcp` URL - see [MCP](/features/mcp).

**A bearer request is checked at two call sites.** `auth.Middleware` decides for every operation, and `RequireAuthOrLogin` (`service/internal/auth/require.go`) for the contract routes, which huma hangs off the mux rather than registering as operations. Both hand the reason an `Authenticate` failure gets to `bearerAuthFailureMessage`, so a session cookie pasted as a bearer token is told the same thing wherever it lands, and both send `WWW-Authenticate: Bearer` with that `401`. `Middleware`'s outcomes, in order, all written through `huma.WriteErr`:

- an operation whose `Security` names no `token` scheme answers `403` ("API tokens cannot use this operation") before authentication runs at all;
- an unknown token, an expired one, or one whose issuer is no longer an admin answers `401` - `Authenticate` collapses all three into `ErrNoToken`, so the caller cannot tell which;
- a token missing a required scope answers `403` naming it;
- a token that passes is stored for `auth.UserFrom` and its scopes for `auth.ScopesFrom`.

Without a bearer header, an operation marked `auth.TokenOnly` - only `/mcp`, see [MCP](/features/mcp) - answers `401` "api token required" with `WWW-Authenticate: Bearer` instead of falling through to the cookie, so a page that could make a browser send a cookie can never reach it that way. `RequireAuthOrLogin` requires no scope, so it only ever reaches the `401`. See [Users and authentication](/features/users-and-auth) for the session half of both.

**Reachability is a type, not a check inside a handler.** An operation declares `auth.Protected(scopes...)` instead of `auth.SessionSecurity` to accept a token at all; a `Security` requirement that never names the `token` scheme is structurally unreachable for one. That is what keeps these session-only: `/api/v1/tokens` itself, and everything a person does to their own session and account - `me`, `logout`, `change-own-password`, `update-own-profile` and `list-color-usage` under `/api/v1/auth` - plus `update-settings` (`PATCH /api/v1/settings`), whose reader `get-settings` does accept a `recipes:read` token. `auth.SecuritySchemes()` declares both schemes for the OpenAPI document, installed through `httpserver.WithSecuritySchemes` so the scheme names stay inside `auth` and `httpserver` keeps knowing nothing about authentication.

**A token never outlives the privilege that justified it.** `auth.TokenService.Authenticate` re-reads the issuer's row on every request, so a token acts as its issuer's account with the role that account holds now, and its scopes narrow what it may do within that role. A deleted issuer (`ON DELETE CASCADE` removes the token too) or one demoted to `user` fails the same way an unknown token does. Holding a token is an admin capability in this design, so losing the admin role kills the token even though `recipes:*` would still be within a plain member's rights.

**Use is recorded at most once an hour.** `touchAfter` mirrors the session's `renewAfter` pattern: `last_used_at` is written back only when the stored value is more than an hour old, so a busy integration does not write on every request. The token list's "last used" text carries a tooltip saying so.

**Token management itself stays session-only.** `service/internal/tokenapi` exposes list, create and revoke - the OpenAPI document has their paths and status codes - and none is reachable by a token: one able to mint or list tokens would defeat both expiry and revocation. `requireAdmin` gates all three; `canManageAllTokens` in `service/internal/tokenapi/handler.go` is `u.Role.IsAdmin()`, so every admin and the instance owner sees and revokes every token on the instance - a comparison against `RoleAdmin` would lock the owner out of their own instance's tokens. Narrowing the list to the instance owner alone would need it scoped by issuer and the revoke checked against that, neither of which exists.

**The Settings UI.** Settings → API (`frontend/src/routes/settings/api`) is open to every account, because any session may call the API and read the spec; `settings/api/+page.ts` resolves the role into `isAdmin` instead of redirecting, and the page gates the token half on that flag - the token card, its dialogs and the `GET /tokens` call alike, since a member firing that call would be answered `403`.

- `ApiAccessCard.svelte` names the two ways in, for AI assistants (`/mcp` and a token) and for scripts (`/api/v1` and a token *or* username and password, since a script may sign in the way the SPA does). Both addresses come off `window.location.origin`, so they name whatever host the instance answers on.
- The token step follows `tokenSupply` in `frontend/src/lib/settings/token-access.ts` over the viewer's own tokens only: missing, all expired, or valid; a member's step says an admin issues tokens. "Create token" lives only in the token card's head, so the page never carries two create buttons.
- The operation count is decoration, so a failed `/api/v1/openapi.json` fetch drops it silently; `countOperations` in `frontend/src/lib/settings/api-summary.ts` is the pure reduction, which keeps the whole document out of component state.
- `CreateTokenDialog.svelte` says so the moment both access ladders stand at None, since the server refuses a token with no scope (`minItems:"1"`); the expiry defaults to 90 days.
- The token card lists the viewer's own tokens; an admin's "Everyone in the household" switch and an issuer filter narrow the one `GET /tokens` answer, which already holds every token, and live in the URL (`?all=1&user=<id>`) like the shared links' filters. The list carries `ownerDisplayName` and `ownerColor` beside `ownerUsername` for this, joined in `ListAPITokens`.
- `TokenRow` draws each token's lifetime from `lifetime` in `token-access.ts`, which turns issue, last use and expiry into fractions of the bar; a token without expiry has no scale, so today sits at `OPEN_TODAY`. The access shown per area is `accessLevels`, the deepest level its scopes reach.
- `frontend/src/lib/api/tokens.ts` is the client (`listTokens`, `createToken`, `deleteToken`).

## Why it is this way

A static bearer token in a client configuration is the deliberate simplification a self-hosted, single-household instance affords over OAuth 2.1: no token exchange, no client registration, no redirect flow to implement or to explain to whoever configures an integration.

The bearer branch lives inside `auth.Middleware` itself rather than arriving as a separate authenticator run in front of it, because the question it answers first - whether an operation accepts a token at all, and whether it accepts anything else - can only be read off `ctx.Operation().Security`. That is also why every route that takes a token is an operation, the image files and `/mcp` included ([HTTP API](/architecture/api)): its scopes are declared where the document shows them, instead of being passed by hand to a mux wrapper the document knows nothing about.

Two roles already keep authorization a field comparison (see [Users and authentication](/features/users-and-auth)); scopes add a second, independent comparison rather than a permission table, so a token's reach is still decided by comparing two short lists, never by a rule engine.

## Rejected

- **A token that authenticates as its issuer outright, with no scopes.** An integration that only needs to read recipes should not hold a credential that can also delete users; the five-scope closed set is what lets an admin match what a token can do to what the integration actually needs.
- **`PATCH` to rename or re-scope an existing token.** What a token may do is fixed for its whole lifetime; revoking and creating a replacement is the only path, so a scope change is always visible as a new credential rather than a silent widening of an old one.
- **Letting a token reach `/api/v1/tokens`.** A token that can mint or list tokens defeats both expiry and revocation - it could reissue itself past its own expiry.
- **A sweep job that deletes expired tokens.** Expired rows stay until an explicit revoke; a row that disappeared on its own would leave an admin unable to explain why an integration stopped working. The expiry check happens during authentication instead.
- **Exact `last_used_at`, written on every request.** A busy integration would write on every call for a level of precision nobody reads; the hourly throttle mirrors the pattern sliding sessions already use.

## Limits

- Tokens can be issued only by an admin; there is no self-service path for a plain member. A member sees the API page and everything on it except the token card, and step one tells them who issues a token.
- A `users:write` token carries its issuer's rank: one issued by the instance owner can create an admin account, one issued by any other admin cannot (see [Users and authentication](/features/users-and-auth)). An admin account created through the owner's token looks like any other - on a household instance, the owner who issued the token is the person who would notice.
- `last_used_at` is accurate to the hour, not to the request; the UI's tooltip says so rather than implying more precision than the column has.
- Token-authenticated requests are not rate-limited.
