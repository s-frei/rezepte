---
title: API tokens
description: Scoped bearer tokens for programmatic access, issued and revoked from Settings
---

An admin issues a named, scoped, optionally expiring API token from Settings → API and uses it in place of the session cookie: `Authorization: Bearer rzp_...` authenticates a request the same way a browser session does, and is the credential the [MCP server](/features/mcp) uses and a future instance sync will use (see [Roadmap](/roadmap)). `service/internal/auth` (`token.go`, `middleware.go`, `require.go`) issues and verifies tokens and decides whether an operation may accept one; `service/internal/tokenapi` exposes token management itself; `frontend/src/routes/settings/api` and the components under `frontend/src/lib/components/settings` are the UI. [Data model](/architecture/data-model) owns the `api_tokens` table; [HTTP API](/architecture/api) owns the three `/api/v1/tokens` endpoints and their status codes.

## How it works

**Five scopes, and write always travels with its read.** `service/internal/auth/token.go` defines `ScopeRecipesRead`, `ScopeRecipesWrite`, `ScopeRecipesDelete`, `ScopeUsersRead` and `ScopeUsersWrite` as the closed set `knownScopes`. A token's scopes are stored as a space-separated string - the OAuth convention, and exactly the shape huma's `Security` already holds, so creating and checking a token speak the same language with no translation. Writing implies reading, and for recipes deleting implies both, only by convention: `CreateTokenDialog.svelte`'s Recipes row offers a fourth level, *Delete*, beside *None*, *Read* and *Write*; `scopesOf` builds each level's scopes from a ladder (`recipes:read`, `recipes:write`, `recipes:delete`) sliced to the chosen depth, so *Delete* sends all three and *Write* sends the first two, and the middleware compares scope lists rather than applying an implication rule of its own. The Accounts row stops at *Write* - `users:write` already covers removing an account, so there is no `users:delete` to reach.

**The raw value exists once.** `TokenService.Create` draws 32 random bytes and encodes them as `TokenPrefix + base64.RawURLEncoding` (`rzp_` plus 43 characters), then stores only the SHA-256 digest in `token_hash`; the first eight characters go in `token_prefix` for display. `tokenapi.CreatedAPIToken` is the only response type carrying the raw value, embedding `APIToken` rather than adding an optional field to it, so the secret cannot leak into the list response as a matter of typing rather than of review discipline. `TokenRevealDialog.svelte` shows it once, in a monospace block with a copy button, and does not close on Escape or an outside click - only its own confirm button does, so one stray keystroke cannot destroy the only copy. When the freshly created token carries `recipes:read`, the same dialog adds a "Use with an AI assistant" section with a Claude Code and a JSON snippet, each carrying the token and the instance's `/mcp` URL - see [MCP](/features/mcp).

**A bearer request is checked at two call sites.** `auth.Middleware` decides for every operation, and `RequireAuthOrLogin` (`service/internal/auth/require.go`) for the contract routes, which huma hangs off the mux rather than registering as operations. Both hand the reason an `Authenticate` failure gets to `bearerAuthFailureMessage`, so a session cookie pasted as a bearer token is told the same thing wherever it lands, and both send `WWW-Authenticate: Bearer` with that `401`. `Middleware`'s outcomes, in order: an operation whose `Security` names no `token` scheme answers `403` ("API tokens cannot use this operation") before authentication runs at all; an unknown token, an expired one, or one whose issuer is no longer an admin then answers `401` (`Authenticate` collapses all three into `ErrNoToken`, so the caller cannot tell which); a token missing a required scope answers `403` naming it - all three written through `huma.WriteErr`. A token that passes is stored for `auth.UserFrom` and its scopes for `auth.ScopesFrom`. Without a bearer header, an operation marked `auth.TokenOnly` - only `/mcp`, see [MCP](/features/mcp) - answers `401` "api token required" with `WWW-Authenticate: Bearer` instead of falling through to the cookie, so a page that could make a browser send a cookie can never reach it that way. `RequireAuthOrLogin` requires no scope, so it only ever reaches the `401`. See [Users and authentication](/features/users-and-auth) for the session half of both.

**Reachability is a type, not a check inside a handler.** An operation declares `auth.Protected(scopes...)` instead of `auth.SessionSecurity` to accept a token at all; a `Security` requirement that never names the `token` scheme is structurally unreachable for one. That is what keeps these session-only: `/api/v1/tokens` itself, and everything a person does to their own session and account - `me`, `logout`, `change-own-password`, `update-own-profile` and `list-color-usage` under `/api/v1/auth` - plus `update-settings` (`PATCH /api/v1/settings`), whose reader `get-settings` does accept a `recipes:read` token. `auth.SecuritySchemes()` declares both schemes for the OpenAPI document, installed through `httpserver.WithSecuritySchemes` so the scheme names stay inside `auth` and `httpserver` keeps knowing nothing about authentication.

**A token never outlives the privilege that justified it.** `Authenticate` re-reads the issuer's row on every request: a deleted issuer (`ON DELETE CASCADE` removes the token too) or one demoted to `user` fails the same way an unknown token does. Holding a token is an admin capability in this design, so losing the admin role kills the token even though `recipes:*` would still be within a plain member's rights.

**Use is recorded at most once an hour.** `touchAfter` mirrors the session's `renewAfter` pattern: `last_used_at` is written back only when the stored value is more than an hour old, so a busy integration does not write on every request. The token list's "last used" text carries a tooltip saying so.

**Token management itself stays session-only.** `service/internal/tokenapi` exposes list, create and revoke - [HTTP API](/architecture/api) owns their paths and status codes - and none is reachable by a token: one able to mint or list tokens would defeat both expiry and revocation. `requireAdmin` gates all three; `canManageAllTokens` in `service/internal/tokenapi/handler.go` is `u.Role.IsAdmin()`, so every admin and the instance owner sees and revokes every token on the instance - a comparison against `RoleAdmin` would lock the owner out of their own instance's tokens. Narrowing the list to the instance owner alone would need it scoped by issuer and the revoke checked against that, neither of which exists.

**The Settings UI.** An "API" tab follows "Profile" in `SettingsLayout.svelte`, ahead of "Shared links" and "People"; all four are open to every account, and the API tab because any session may call the API and read the spec. `settings/api/+page.ts` therefore resolves the role into `isAdmin` instead of redirecting, and the page gates the token half on that flag - the token card, its three dialogs and the `GET /tokens` call alike, because a member firing that call would be answered `403`. `ApiAccessCard.svelte` heads the page for everyone and reads like a cookbook page with two recipes, side by side on a wide screen and stacked on a phone, because there are two ways in and only one of them needs a token. *For AI assistants* lists the `/mcp` address and an API token as ingredients - both recipes name the address first and what signs in second, so their rows line up, then two steps: create the token, add it to the client (linking the MCP guide). *For your own scripts* lists the `/api/v1` address and "an API token *or* username and password", because a script may sign in the way the SPA does, then two steps: sign in, and get going (the operation count, links to `/api/v1/docs` and the document). Both addresses come off `window.location.origin`, so they name whatever host the instance answers on, and break only after a slash. The token ingredient and step one follow `tokenSupply` in `frontend/src/lib/settings/token-access.ts`: no token or only expired ones mark the ingredient in the primary color ("missing", "all expired") and point step one down to the token card; a valid one marks the step done; a member's step one says an admin issues tokens. The operation count is decoration on a step that reads fine without it, so a failed `/api/v1/openapi.json` fetch drops it silently; `countOperations` in `frontend/src/lib/settings/api-summary.ts` is the pure reduction, which keeps the 75 KB document out of component state. The "API tokens" card below is always there for an admin, an empty list showing a placeholder, and its head is the one home of "Create token" - step one only points to it, so the page never carries two create buttons. `CreateTokenDialog.svelte` offers two `AccessLadder` rows - Recipes (None / Read / Write / Delete) and Accounts (None / Read / Write) - and an expiry `Select` (30, 90, 365 days, or never - default 90). A token with no scope could do nothing and the server refuses one (`minItems:"1"`), so the moment both ladders stand at None the dialog says so under them, instead of waiting for the submit to find out. The "API tokens" card lists the viewer's own tokens; an "Everyone in the household" switch shows every admin's, and with two or more issuers a row of `TagChip`s with the issuer's color narrows the list to one - the shared links' filter, kept in the URL the same way (`?all=1&user=<id>`). Both are view filters over the one `GET /tokens` answer, which already holds every token for an admin; the access card's token count follows the viewer's own tokens only. The list answers carry `ownerDisplayName` and `ownerColor` beside `ownerUsername` for this, joined in `ListAPITokens`. `TokenRow`, one per list item on the page itself, draws each token as a key tag on a key board: a left edge in the issuer's color (`userColorEdge` in `frontend/src/lib/user/color.ts`), the name and prefix, the issuer's `PersonMark` in the household view, then a lifetime bar - `lifetime` in `frontend/src/lib/settings/token-access.ts` turns issue, last use and expiry into fractions of it, with "today" as a mark and the last use as a dot; a token without expiry has no scale, so today sits at `OPEN_TODAY` and the bar stays open. An expired tag fades and carries an "Expired" stamp across its spent bar, decoration over a screen-reader line that says the same. Below, one plaque per area holds that area's access ladder: the deepest level from `accessLevels`, drawn as dots in the create dialog's words. The plaques keep three fixed tracks on a phone - area, a ladder as wide as three steps, a level as wide as the longest word - so the ladders line up down the whole list and nothing moves while it scrolls; on a wide screen they sit side by side and wrap as areas are added. A name is never cut: it wraps, hyphenated in the page's language, and on a phone "Revoke" drops below the plaques so the name keeps the tag's width. Revoking goes through the app's existing confirm dialog. `frontend/src/lib/api/tokens.ts` is the client (`listTokens`, `createToken`, `deleteToken`).

## Why it is this way

A static bearer token in a client configuration is the deliberate simplification a self-hosted, single-household instance affords over OAuth 2.1: no token exchange, no client registration, no redirect flow to implement or to explain to whoever configures an integration.

The bearer branch lives inside `auth.Middleware` itself rather than arriving as a separate authenticator run in front of it, because the question it answers first - whether an operation accepts a token at all, and whether it accepts anything else - can only be read off `ctx.Operation().Security`. That is also why every route that takes a token is an operation, the image files and `/mcp` included ([HTTP API](/architecture/api)): its scopes are declared where the document shows them, instead of being passed by hand to a mux wrapper the document knows nothing about.

Two roles already keep authorization a field comparison (see [Users and authentication](/features/users-and-auth)); scopes add a second, independent comparison rather than a permission table, so a token's reach is still decided by comparing two short lists, never by a rule engine.

## Rejected

- **A token that authenticates as its issuer outright, with no scopes.** An integration that only needs to read recipes should not hold a credential that can also delete users; the five-scope closed set is what lets an admin match what a token can do to what the integration actually needs.
- **`PATCH` to rename or re-scope an existing token.** What a token may do is fixed for its whole lifetime; revoking and creating a replacement is the only path, so a scope change is always visible as a new credential rather than a silent widening of an old one.
- **Letting a token reach `/api/v1/tokens`.** A token that can mint or list tokens defeats both expiry and revocation - it could reissue itself past its own expiry.
- **A sweep job that deletes expired tokens.** Expired rows stay until an explicit revoke; a row that disappeared on its own would leave an admin unable to explain why an integration stopped working. The expiry check happens during authentication instead.
- **Exact `last_used_at`, written on every request.** A busy integration would write on every call for a level of precision nobody reads; the hourly throttle mirrors the pattern sliding sessions already use.

## Limits

- Tokens can be issued only by an admin; there is no self-service path for a plain member. A member sees the API page and everything on it except the token card, and step one tells them who issues a token.
- A `users:write` token carries its issuer's rank: one issued by the instance owner can create an admin account, one issued by any other admin cannot (see [Users and authentication](/features/users-and-auth)). An admin account created through the owner's token looks like any other - on a household instance, the owner who issued the token is the person who would notice.
- `last_used_at` is accurate to the hour, not to the request; the UI's tooltip says so rather than implying more precision than the column has.
- Token-authenticated requests are not rate-limited.
