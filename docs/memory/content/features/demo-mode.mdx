---
title: Demo mode
description: A flag that fills an empty instance with the twelve sample recipes and their embedded photos, or Go-rendered placeholders where a set has none
---

`rezepte --demo` fills an empty instance with sample recipes and their photos, so screenshots have realistic data and manual testing has something to click through. The flag is declared in `service/cmd/rezepte/main.go` and everything it does lives in `service/internal/demo/seed.go`.

## How it works

**It seeds like any other run, into the configured data directory.** `demo.Seed` builds the same `recipe.Service` and `image.Service` the API uses and writes through them, into `REZEPTE_DATA_DIR` (default `./data`) with the photos under its `images/` subdirectory. The flag does not invent a temporary directory of its own. Seeding runs after the instance owner is ensured and before the HTTP server starts listening, so `/healthz` answers only once the instance is fully populated.

**Idempotence is a recipe count.** `Seed` calls `recipe.Service.Count` first; anything above zero is logged and returns `Summary{Skipped: true}` with nothing written. A second `--demo` run and a `--demo` run against a directory that already holds recipes are therefore the same no-op.

**The fixtures are embedded Go data, one set per locale that has one.** `recipe.Samples(locale)` in `service/internal/recipe/samples.go` unmarshals `service/internal/recipe/testdata/recipes.<locale>.json`, embedded into the binary with `go:embed` — twelve recipes each, currently `de` and `en`. A locale without a file gets the base locale's set (`user.BaseLocale`, English), so a new interface language never needs sample recipes of its own. Each set is its own recipes, not a translation of another, and is reparsed on every call so a caller may modify what it gets. `demo.Seed` takes a `locale user.Locale` parameter and passes it straight through, so `REZEPTE_LOCALE` decides which set a demo instance seeds; `main.go` passes `cfg.Locale` at the one call site. The end-to-end suite reads the fixtures directly (`loadFixture` in `frontend/e2e/helpers.ts`) rather than going through demo mode, because every spec creates the recipes it needs: the English set by default, the German one where a test is about German text. `Seed` creates the chosen set back to front, because the overview sorts by `updated_at` descending and that puts the first sample on top. The user the recipes are created under is resolved by `ownerID`: the account whose name matches `REZEPTE_ADMIN_USER`, falling back to the first user by username, and `ErrNoUsers` when the instance has none at all.

**The demo credentials apply only when the operator configured none, and never to a reset.** `demo.AdminUser` is `demo` and `demo.AdminPassword` is `demo1234`. `useDemoDefaults` in `main.go` substitutes both — username and password together — when `--demo` is passed, `REZEPTE_ADMIN_PASSWORD` is empty and the run is a start; with that variable set, the operator's own user and password are what the instance gets, and the startup log says the password came from the environment rather than printing it. `--demo --reset-superadmin-password` gets no substitution at all: `demo1234` is printed in the user documentation, and writing it onto the instance owner's account is the one thing the fallback must never do, so a reset with no `REZEPTE_ADMIN_PASSWORD` is `ErrAdminPasswordRequired` whether `--demo` is there or not. The same pair is repeated once more, deliberately, in `docs/user/scripts/demo-user.ts`, which is where the build-time tools that drive a demo instance read it from.

**Both sample sets carry AI-generated photos, embedded in the binary.** `service/internal/demo/photos/<locale>/<slug>/<n>.jpg` is embedded with `go:embed`; `photosFor` finds a sample's set by its slug (`recipe.Slugify` of the title) under any locale directory and reads `1.jpg`, `2.jpg`, … until the first missing number. `Seed` uploads them in that order through `image.Service.Upload`, so the first becomes the cover and each becomes the usual three variants (see [Images](/features/images)). Nine samples of each set have three photos — cover, a close-up or served shot, and a preparation or cooking step. The three least photogenic have none and keep the card's own `PlaceholderTile`, so both states of a recipe card stay visible: Leek and Potato Soup, Coronation Chicken Sandwiches and Bangers and Mash in English, Linseneintopf, Kartoffelsalat and Frikadellen in German. `TestEveryPhotoSetBelongsToASample` fails when a set's slug matches no sample of its locale or its files are not numbered without gaps, because a renamed sample would otherwise lose its photos silently.

**The embedded photos are derived, the originals live in Git LFS.** `assets/demo-photos/<locale>/<slug>/` holds each photo exactly as the image generator returned it (2400 × 1792 JPEG), tracked by Git LFS through `.gitattributes`, with a `prompts.md` beside them that records the generator, model and settings and the prompt of every photo, so an adjusted photo can be made with the same settings. `.lfsconfig` excludes the folder from every clone, CI included; `mise run demo-photos` first runs `demo-photos:pull` to fetch it, then `service/cmd/demo-photos` scales each original to at most 1600 px (Catmull-Rom, JPEG quality 82, no metadata) and rewrites `service/internal/demo/photos`, dropping sets that left the originals. Its output depends only on the originals, so a rerun changes no byte and a reseed uploads identical files. The 54 photos add about 14 MB to the binary.

**A set without any photos gets placeholders drawn in Go.** `Seed` checks whether any sample of the chosen set has photos; only when none has does it fall back to `demo.Placeholder` for the first `imagedRecipes` (nine) samples, which is what a language with sample recipes of its own but no photos gets; `TestSeedFallsBackToPlaceholders` covers it by swapping the embedded photos for an empty file system. `service/internal/demo/placeholder.go` renders a 1200×900 image: a warm surface tint for the background, a 320 px-radius disc of that tint lightened halfway to white for the plate, and the recipe title's first rune, upper-cased (or `?` for an empty title), drawn in the embedded Go Bold face at 400 px and 72 DPI in the primary brown, positioned by its ink box rather than its advance box so narrow and wide letters both sit centered. The result is JPEG at quality 85. The tints are three warm surface colors from the design system, picked by `index % 3`, and every full rotation steps one shade darker — samples landing on the same base tint that also share an initial, of which the sample set has several, still get distinguishable tiles. Colors themselves belong to [Design system](/architecture/design-system). A placeholder depends on nothing but the index and the title, so it too is byte-identical across reseeds.

**The instance itself comes from one task, `//:demo`.** `mise run demo` starts the binary on the worktree's demo port and keeps it up until Ctrl-C; `mise run demo -- <cmd>` runs one command against it and stops it afterwards, which is how the screenshot and OpenAPI tasks get an instance they own. `mise/tasks/demo.sh` refuses to start when the port is already taken — a stranger's instance answering `/healthz` first would silently be screenshotted or scraped instead — creates a `mktemp -d` directory unless `REZEPTE_DATA_DIR` names one (a directory it did not create is never removed, and demo mode does not reseed a populated one), clears `REZEPTE_ADMIN_USER` and `REZEPTE_ADMIN_PASSWORD` out of the environment with `env -u` so an exported password cannot displace the credentials the callers log in with, polls `/healthz` until it answers, and removes both the process and its own directory from a trap. The port guard and the `/healthz` wait live in `mise/lib/instance.sh`, shared with `//:e2e`, which starts the same binary without `--demo` ([Toolchain](/architecture/toolchain)).

## Why it is this way

Seeding through the domain services into the configured directory keeps the flag useful for more than screenshots: pointed at a real data directory it is the fastest way to get a running instance with something in it, and the recipes it writes go down the same path an API client's would.

The fixtures are Go code rather than a file beside the binary, so demo mode has no external data dependency, works offline and cannot be run against a fixture that drifted from what the tests use.

Placeholders showed the layout but not what the app is for: a cookbook sells itself through its pictures, and the screenshots in the user documentation are the first thing a visitor sees. The photos are embedded rather than fetched because `--demo` has to run wherever the binary runs, offline included, and a seed that downloads could fail or change between runs. They are scaled to 1600 px because that is the largest variant the gallery shows; the full 2400 px originals would have quadrupled the size the binary grows by.

Keeping the untouched originals in the repository means a new size, crop or quality is a rerun of `mise run demo-photos`, not a new round of generation, which costs money and never returns the same picture twice. Git LFS keeps those 150 MB out of every clone's history, and the fetch exclude keeps them out of every checkout that does not regenerate photos.

Rendering the placeholders in Go keeps the one dependency demo mode must not have out of the fallback too: a browser at seed time. A deterministic function of an index and a title is stable across reseeds by construction rather than by care.

## Rejected

- **A temporary data directory built into the flag, plus a fixture file for the users.** The domain services already create the instance owner, and seeding into the configured directory is the more useful of the two behaviors; a script that wants a throwaway instance can make and delete a directory in three lines.
- **Downloading the photos at seed time.** The instance would need the network and a stable host for the pictures, and a reseed could get different bytes.
- **Embedding the originals as they are.** About 150 MB of binary for pixels the gallery never shows; the 1600 px copies look the same in the app.
- **Photos for a set chosen per sample in code.** The slug of a folder already names its sample; a list in Go would be a second place to keep in step.
- **Playwright-rendered HTML placeholders.** They need a working browser at seed time, which is exactly the dependency the flag cannot carry.
- **Seeding through the API from a script.** The fixtures would have to be reimplemented in TypeScript, and the result would be useless for manual testing, which wants the binary alone.

## Limits

- Only the English and German sets have photos. A new set gets placeholders unless photos are generated for it the same way.
- The photos are AI-generated, not pictures of the recipes as written; the originals carry the generator's C2PA provenance data, the embedded copies do not.
- The flag fills an empty instance; it does not reset a populated one. Starting over means removing the data directory first.
- The demo credentials are public — in this repository and in the binary — so an instance reachable beyond the household must set `REZEPTE_ADMIN_PASSWORD` of its own, whether or not it is seeded.
