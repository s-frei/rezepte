---
title: Demo mode
description: A flag that fills an empty instance with the twelve sample recipes and their embedded photos, or Go-rendered placeholders where a set has none
---

`rezepte --demo` fills an empty instance with sample recipes and their photos, so screenshots have realistic data and manual testing has something to click through. The flag is declared in `service/cmd/rezepte/main.go` and everything it does lives in `service/internal/demo/seed.go`.

## How it works

**It seeds like any other run, into the configured data directory.** `demo.Seed` builds the same `recipe.Service` and `image.Service` the API uses and writes through them, into `REZEPTE_DATA_DIR` (default `./data`) with the photos under its `images/` subdirectory. The flag does not invent a temporary directory of its own. Seeding runs after the instance owner is ensured and before the HTTP server starts listening, so `/healthz` answers only once the instance is fully populated.

**Idempotence is a recipe count.** `Seed` calls `recipe.Service.Count` first; anything above zero is logged and returns `Summary{Skipped: true}` with nothing written. A second `--demo` run and a `--demo` run against a directory that already holds recipes are therefore the same no-op.

**The fixtures are embedded Go data, one set per locale that has one.** `recipe.Samples(locale)` in `service/internal/recipe/samples.go` unmarshals `service/internal/recipe/testdata/recipes.<locale>.json`, embedded into the binary with `go:embed` — twelve recipes each, for `de` and `en`. A locale without a file gets the base locale's set (`user.BaseLocale`, English), so a new interface language never needs sample recipes of its own. Each set is its own recipes, not a translation of another, and is reparsed on every call so a caller may modify what it gets. `demo.Seed` takes a `locale user.Locale` parameter and passes it straight through, so `REZEPTE_LOCALE` decides which set a demo instance seeds; `main.go` passes `cfg.Locale` at the one call site. The end-to-end suite reads the fixtures directly (`loadFixture` in `frontend/e2e/helpers.ts`) rather than going through demo mode, because every spec creates the recipes it needs: the English set by default, the German one where a test is about German text. `Seed` creates the chosen set back to front, because the overview sorts by `updated_at` descending and that puts the first sample on top. The user the recipes are created under is resolved by `findOwner`: the account whose name matches `REZEPTE_ADMIN_USER`, falling back to the first user by username, and `ErrNoUsers` when the instance has none at all. The exception are the samples `Seed`'s `members` argument claims, below.

**The demo credentials apply only when the operator configured none, and never to a reset.** `demo.AdminUser` is `demo` and `demo.AdminPassword` is `demo1234`. `useDemoDefaults` in `main.go` substitutes both — username and password together — when `--demo` is passed, `REZEPTE_ADMIN_PASSWORD` is empty and the run is a start; with that variable set, the operator's own user and password are what the instance gets, and the startup log says the password came from the environment rather than printing it. `--demo --reset-superadmin-password` gets no substitution at all: `demo1234` is printed in the user documentation, and writing it onto the instance owner's account is the one thing the fallback must never do, so a reset with no `REZEPTE_ADMIN_PASSWORD` is `ErrAdminPasswordRequired` whether `--demo` is there or not. The same pair is repeated once more, deliberately, in `docs/user/scripts/demo-user.ts`, which is where the build-time tools that drive a demo instance read it from.

**On the demo credentials the household has two more members, and they wrote some of the samples.** `demo.AddMembers` creates `demo.Members`, `mila` and `jonas`, as plain users in the seed's locale with passwords by the [development-credential](/conventions/dev-credentials) rule (`mila1234`, `jonas1234`), before the seed, and renames the admin. All three get display names from the pantry in the seed's language (`displayNames`): Dattel Dill, Mila Majoran and Jonas Zimt in German, Damson Dill, Mila Marjoram and Jonas Cinnamon in English, the fallback for any other language. The names read as made up, so nobody takes the demo's people for real accounts, and none equals its login name, so every surface that prints both - the account menu's head, the You sheet, the people list - shows them apart and one that prints the wrong field is caught; each keeps its username's initial, so the author circles and colors are what they were. `AddMembers` hands the members to `Seed`, which creates the samples in `memberRecipes` as theirs, photos included: Jonas wrote samples 1 and 8, Mila 2 and 10, and Mila locked sample 2 (`lockedSample`, `edit_policy` `locked`, see [Editing rights](/features/editing-rights)). That way the admin meets recipes that are not their own - ones they can mark tasty, an author's name that is somebody else's, a lock line - and neither sample 0 nor Macaroni Cheese (6), which the user docs photograph as the admin's, changes hands. `demo.SeedMembers` then marks samples tasty on the members' behalf through `recipe.Service.SetTasty`, from `memberMarks`: the first sample, the overview's top card, gets both marks, four more one each, and no member marks a sample they wrote. It reads the recipe ids from `Summary.RecipeIDs`, which `Seed` fills in sample order, and the members from `Summary.Members`. `seedDemo` in `main.go` calls both only when `useDemoDefaults` substituted the published credentials: the members' passwords are as public as `demo1234`, and an operator who set `REZEPTE_ADMIN_PASSWORD` gets no accounts they did not ask for. It also gives the admin and each member public links of their own (`adminShares`, `memberShares`: one for the admin, two per member, none to the first sample, which the user docs photograph and whose pictures would otherwise carry the admin's marker). Creating a link needs public sharing on, so it switches sharing on as the owner, sets the lifetimes to a week by default and a month at most, creates the links through `share.Service.Create`, and switches sharing off again: the demo starts like every instance, with sharing off and the links paused, and turning it on is part of what one tries out. It needs the admin to be the instance owner, since only the owner switches sharing; under another admin the members come without links. It follows the seed - `AddMembers` creates nobody on an instance that already holds recipes - and a member name somebody already holds is left to them, recipes, marks and links included. Last it issues the admin three API tokens (`sampleTokens`): one running and used yesterday, one without an expiry, one expired - each through `auth.TokenService` with its clock set back to when the token was issued, and authenticated once at its last-use time, so the token service writes those dates itself; the names follow the admin's language. The [API tokens](/features/api-tokens) page then shows its key tags, lifetime bars and stamp from the first start; the `token-mcp` screenshot removes only the token it creates. The user docs' sharing screenshots (`docs/user/screenshots/sharing.spec.ts`) switch sharing on for their own pictures and off again, since the screenshot run shares one instance. Features that show one member's doing to another, [tasty marks](/features/tasty) first, are on screen from the first start that way, in the running demo as in the user docs' screenshots.

**A third member, `demo.Invited` (`noah`), is never signed in.** `AddMembers` creates it alongside `Members` with no password, so the people list shows an account nobody has claimed yet, exactly what an admin sees before somebody has used their invitation. It is named from the pantry like the others, Noah Nutmeg in English and Noah Nelke in German. `SeedMembers` issues it an open setup link with `auth.Service.IssueSetupLink`, as the instance owner - the same operation "Add account" uses, and `ReplaceSetupLink`'s upsert keeps a second issue harmless. The admin (`demo.AdminUser`, named by `nameAdmin`) and `Members` also get a confirmed sample email (`SetProfile` then `MarkEmailVerified`, `<username>@example.com`), so forgot password works in the demo, the people list shows the confirmed envelope, and the admin's prefills the mail card's test mail. Changing an address in a profile shows the unconfirmed state, and Mailpit catches the confirmation mail. `noah` gets none: an invited person's address is what the admin types when sending the link.

**Both sample sets carry AI-generated photos, embedded in the binary.** `service/internal/demo/photos/<locale>/<slug>/<n>.jpg` is embedded with `go:embed`; `photosFor` finds a sample's set by its slug (`recipe.Slugify` of the title) under any locale directory and reads `1.jpg`, `2.jpg`, … until the first missing number. `Seed` uploads them in that order through `image.Service.Upload`, so the first becomes the cover and each becomes the usual three variants (see [Images](/features/images)). Every upload moves the recipe's `updated_at`; `Seed` writes each sample and its uploads under one clock (below), so the uploads land on the creation time and no sample carries a "Last edited" line in its colophon, which would otherwise come and go between seeds with the second the last upload ends in. `TestSeedUploadsEmbeddedPhotos` checks every sample for it. Nine samples of each set have three photos — cover, a close-up or served shot, and a preparation or cooking step. The three least photogenic have none and keep the card's own `PlaceholderTile`, so both states of a recipe card stay visible: Leek and Potato Soup, Coronation Chicken Sandwiches and Bangers and Mash in English, Linseneintopf, Kartoffelsalat and Frikadellen in German. `TestEveryPhotoSetBelongsToASample` fails when a set's slug matches no sample of its locale or its files are not numbered without gaps, because a renamed sample would otherwise lose its photos silently.

**The embedded photos are derived, the originals live in Git LFS.** `assets/demo-photos/<locale>/<slug>/` holds each photo exactly as the image generator returned it (2400 × 1792 JPEG), tracked by Git LFS through `.gitattributes`, with a `prompts.md` beside them that records the generator, model and settings and the prompt of every photo, so an adjusted photo can be made with the same settings. `.lfsconfig` excludes the folder from every clone, CI included; `mise run demo-photos` first runs `demo-photos:pull` to fetch it, then `service/cmd/demo-photos` scales each original to at most 1600 px (Catmull-Rom, JPEG quality 82, no metadata) and rewrites `service/internal/demo/photos`, dropping sets that left the originals. Its output depends only on the originals, so a rerun changes no byte and a reseed uploads identical files. The 54 photos add about 14 MB to the binary.

**Two of the three demo people have a picture, made of their ingredient.** `demo.SeedAvatars` runs from `seedDemo` in `main.go` whenever the demo starts with the published credentials, after `SeedMembers`, and gives the accounts in `avatarUsers` - `demo` and `mila` - their picture through `avatar.Service.Set`, the path the API takes, with the centered crop. `jonas` has none on purpose: the demo then shows the color-and-initial fallback, and a manual test has an account to set a picture on. His picture is embedded all the same, so giving him one is adding his name to `avatarUsers`. An account that does not exist or already has a picture is left alone, so a second start changes nothing and a picture someone set by hand survives. It runs on every such start, not only after a fresh seed, so a demo database created before the pictures existed gets them too; the price is that a demo picture someone removed returns on the next start. The pictures are illustrated creatures made of each person's ingredient: `assets/demo-avatars/seed/<username>.jpg` holds the originals, `assets/demo-avatars/herbs/` the ingredient alone as an alternative, both tracked by Git LFS, and `assets/demo-avatars/prompts.md` records the generator, settings and every prompt. Unlike the photos, the avatars are fetched by an ordinary clone. `mise run demo-avatars` scales the originals to 640 px through `service/cmd/demo-photos -max 640` into `service/internal/demo/avatars`, which is embedded; the service renders its own 320 px file from that.

**A set without any photos gets placeholders drawn in Go.** `Seed` checks whether any sample of the chosen set has photos; only when none has does it fall back to `demo.Placeholder` for the first `imagedRecipes` (nine) samples, which is what a language with sample recipes of its own but no photos gets; `TestSeedFallsBackToPlaceholders` covers it by swapping the embedded photos for an empty file system. `service/internal/demo/placeholder.go` renders a 1200×900 image: a warm surface tint for the background, a 320 px-radius disc of that tint lightened halfway to white for the plate, and the recipe title's first rune, upper-cased (or `?` for an empty title), drawn in the embedded Go Bold face at 400 px and 72 DPI in the primary brown, positioned by its ink box rather than its advance box so narrow and wide letters both sit centered. The result is JPEG at quality 85. The tints are three warm surface colors from the design system, picked by `index % 3`, and every full rotation steps one shade darker — samples landing on the same base tint that also share an initial, of which the sample set has several, still get distinguishable tiles. Colors themselves belong to [Design system](/architecture/design-system). A placeholder depends on nothing but the index and the title, so it too is byte-identical across reseeds.

**The instance itself comes from one task, `//:demo`.** `mise run demo` starts the binary on the worktree's demo port and keeps it up until Ctrl-C; `mise run demo -- <cmd>` runs one command against it and stops it afterwards, which is how the screenshot and OpenAPI tasks get an instance they own. `mise/tasks/demo.sh` refuses to start when the port is already taken — a stranger's instance answering `/healthz` first would silently be screenshotted or scraped instead — creates a `mktemp -d` directory unless `REZEPTE_DATA_DIR` names one (a directory it did not create is never removed, and demo mode does not reseed a populated one), clears `REZEPTE_ADMIN_USER` and `REZEPTE_ADMIN_PASSWORD` out of the environment with `env -u` so an exported password cannot displace the credentials the callers log in with, polls `/healthz` until it answers, and removes both the process and its own directory from a trap. The port guard and the `/healthz` wait live in `mise/lib/instance.sh`, shared with `//:e2e`, which starts the same binary without `--demo` ([Toolchain](/architecture/toolchain)).

**With the test OIDC provider up, the demo signs in through it too.** `demo.sh` calls `rzp_oidc_env` (the same helper `//:e2e` uses) unless the caller already set `REZEPTE_OIDC_ISSUER` itself; when Dex is running it configures the instance against it (`Dex`) and prints which Dex user goes with which demo account. Dex's static users are named after the demo household on purpose (`demo@`, `mila@`, `jonas@example.com`, password `<name>1234`). Whenever OIDC is configured at all - Dex running, or the screenshot and OpenAPI tasks' own placeholder issuer - `demo.SeedMembers` pre-links jonas to the identity Dex issues for a user named `jonas` on its local connector, so the people list and his profile show "Signs in with …" from the first start with no one connecting an account by hand, and `jonas@example.com` / `jonas1234` signs in through a running test Dex right away. `service/internal/demo/identity.go`'s `dexSubject` hand-encodes that identity's `sub` claim (Dex's own protobuf-then-base64url encoding, checked against a live Dex rather than trusted blind) so the linked subject matches what Dex actually presents. demo and mila are left to connect their own Dex account from their profile, the ordinary way. The screenshot and OpenAPI tasks' placeholder issuer answers nothing, so jonas's line there is cosmetic only - the pictures stay the same whether or not Dex happens to be running - and `demo.sh` leaves a caller's own issuer alone. See [Test OIDC sign-in](/howtos/test-oidc).

**With Mailpit up, the demo sends its mail into it, configured in the database.** `demo.sh` asks `rzp_mailpit_up` (`mise/lib/instance.sh`) and, when Mailpit answers and `RZP_DEMO_MAIL` is not `off`, signs in as the demo owner after the health check and `PUT`s the Mailpit server to `/api/v1/settings/mail` (security `none`, from `rezepte@example.com`), but only while the instance's mail source is still `none`. The step is best-effort: if a call fails the demo prints "demo: mail not configured" and keeps running without mail. It never sets `REZEPTE_SMTP_*`, because the environment would lock the mail card the demo exists to click through. It sets `REZEPTE_PUBLIC_URL` to the demo's own URL unless the caller did, with or without Mailpit, since a mailed link has to be absolute and without one the mail card shows only a hint: without Mailpit the card is open to a server entered by hand, and an unreachable one shows its error. "Setup link" on `noah` then asks for an address and "Send link" sends it, and the mail lands in Mailpit's inbox, whose URL the startup prints. The screenshot and OpenAPI tasks set `RZP_DEMO_MAIL=off`: the pictures show the unconfigured card whether or not Mailpit runs, and the specs that need a configured one configure it themselves. See [Email](/features/email).

**The comments have a conversation going.** `SeedMembers` ends with `seedComments`, which gives the overview the new-comments dot on samples 0, 1 and 3; what it writes and why is in [Recipe comments](/features/recipe-comments).

**The screenshot tasks fix the demo's clock.** The samples, their comments and the admin's tokens are dated from the moment of seeding, so a recipe's "Added by … on" line, the comments' day separators ("Today", "Yesterday", a weekday) and the tokens' lifetime bars would move with the day a picture is taken. `demo.sh` passes `RZP_DEMO_NOW`, an RFC 3339 instant, to the binary as `--demo-now`, and `seedDemo` hands that instant to `Seed` in place of `time.Now()`, and `Seed` passes it on to `SeedMembers` as `Summary.Now`, which dates the comments and the admin's API tokens from it; without it, as in a plain `mise run demo`, all of them are dated from now. `Seed` stamps each sample and its photo uploads a minute before the next through `SetClock` on the `recipe.Service` and `image.Service` it writes with, the first a week (`sampleAge`) before the instant, older than any sample comment, so no comment predates its recipe and the overview's order rests on distinct `updated_at` values rather than on a tie. The `//docs/user` screenshot tasks set it to the instant `FIXED_TIME` in `docs/user/screenshots/helpers.ts` freezes the browser clock at, so both clocks agree. Their `prepare` also answers `PUT /api/v1/recipes/{id}/comments/seen` itself: the specs share one instance in a fixed order, and a detail shot that marked a recipe's comments seen would take the dot off its card in every later overview shot.

## Why it is this way

Seeding through the domain services into the configured directory keeps the flag useful for more than screenshots: pointed at a real data directory it is the fastest way to get a running instance with something in it, and the recipes it writes go down the same path an API client's would.

The fixtures are Go code rather than a file beside the binary, so demo mode has no external data dependency, works offline and cannot be run against a fixture that drifted from what the tests use.

Placeholders showed the layout but not what the app is for: a cookbook sells itself through its pictures, and the screenshots in the user documentation are the first thing a visitor sees. The photos are embedded rather than fetched because `--demo` has to run wherever the binary runs, offline included, and a seed that downloads could fail or change between runs. They are scaled to 1600 px because that is the largest variant the gallery shows; the full 2400 px originals would have quadrupled the size the binary grows by.

Keeping the untouched originals in the repository means a new size, crop or quality is a rerun of `mise run demo-photos`, not a new round of generation, which costs money and never returns the same picture twice. Git LFS keeps those 150 MB out of every clone's history, and the fetch exclude keeps them out of every checkout that does not regenerate photos.

Rendering the placeholders in Go keeps the one dependency demo mode must not have out of the fallback too: a browser at seed time. A deterministic function of an index and a title is stable across reseeds by construction rather than by care.

## Rejected

- **A temporary data directory built into the flag, plus a fixture file for the users.** The domain services already create the instance owner, and seeding into the configured directory is the more useful of the two behaviors; a script that wants a throwaway instance can make and delete a directory in three lines.
- **Downloading the photos at seed time.** The instance would need the network and a stable host for the pictures, and a reseed could get different bytes.
- **Embedding the originals as they are.** About 150 MB of binary for pixels the gallery never shows; the 1600 px copies look the same in the app.
- **Photos for a set chosen per sample in code.** The slug of a folder already names its sample; a list in Go would be a second place to keep in step.
- **Giving all three members a picture.** The demo and the user docs' screenshots would never show the fallback, and a manual test would have to remove a picture before it could set one.
- **Playwright-rendered HTML placeholders.** They need a working browser at seed time, which is exactly the dependency the flag cannot carry.
- **Seeding through the API from a script.** The fixtures would have to be reimplemented in TypeScript, and the result would be useless for manual testing, which wants the binary alone.

## Limits

- Only the English and German sets have photos. A new set gets placeholders unless photos are generated for it the same way.
- The photos are AI-generated, not pictures of the recipes as written; the originals carry the generator's C2PA provenance data, the embedded copies do not.
- The flag fills an empty instance; it does not reset a populated one. Starting over means removing the data directory first.
- The demo credentials are public — in this repository and in the binary — so an instance reachable beyond the household must set `REZEPTE_ADMIN_PASSWORD` of its own, whether or not it is seeded.
