Several household members share one recipe collection. Accounts are created, re-roled, reset and removed in the UI; only the first admin comes from the environment. [HTTP API](/architecture/api) owns the endpoints, their bodies and their status codes; [Data model](/architecture/data-model) owns the `users` and `sessions` tables.

## How it works

**A login form, and argon2id underneath it.** `frontend/src/routes/login/+page.svelte` posts username and password to the login operation; `user.Service.Authenticate` trims the username the way `Create` trims it and runs `VerifyPassword`. `HashPassword` in `service/internal/user/password.go` produces a PHC string (`$argon2id$…`) with 64 MiB of memory, one iteration, four lanes, a 16-byte salt and a 32-byte key. `VerifyPassword` reads those parameters back out of the stored hash and bounds each of them — at most 1 GiB, 16 iterations, 32 lanes — so a tampered row cannot make one login attempt allocate a gigabyte. An unknown username is still charged one argon2 evaluation, against a `dummyHash` computed once per process, so timing does not separate "no such user" from "wrong password".

**The token lives in the cookie, its digest in the table.** `Login` in `service/internal/auth/service.go` draws 32 random bytes, encodes them with `base64.RawURLEncoding` and stores only the SHA-256 of that string as the session id, so a database leak yields no usable session. The token goes back as the `rezepte_session` cookie: `HttpOnly`, `Path=/`, `SameSite=Lax`, and `Secure` when `REZEPTE_SECURE_COOKIES` is set. `SessionTTL` is 30 days and slides — `Authenticate` resets it to a full 30 days once less than `SessionTTL - renewAfter` is left, with `renewAfter` at 24 hours, so an active session is written back at most once a day. The renewal is reported back as `Verified.Renewed`, and both callers re-issue the cookie with the fresh expiry so the browser's copy never falls behind the row. A session found past its expiry is deleted on the spot; `DeleteExpired` also runs once at startup and `SweepLoop` every 24 hours after that.

**One middleware seam.** `auth.Middleware` authenticates exactly those operations that declare `Security: auth.SessionSecurity`; an operation without `Security` is public. It is installed through `httpserver.WithAPIMiddleware`, and `httpserver.New` applies every `Option` before it returns — so there is no window in which an operation could be registered ahead of it. That chain is the seam where a bearer-token authenticator and an OIDC one are added: further middleware beside this one, not a list iterated inside a single authenticator. Routes that are not huma operations take plain `func(http.Handler) http.Handler` middleware from `service/internal/auth/require.go` instead, with the same authentication and the same renewal re-issue: the image files are wrapped in `auth.RequireSession`, the contract routes in `auth.RequireSessionOrLogin`.

**CSRF is `SameSite=Lax` plus an origin check.** `checkOrigin` in `service/internal/httpserver/origin.go` refuses a `POST`, `PUT`, `PATCH` or `DELETE` under `/api/` whose `Origin` header names a host other than the request's. A request that carries no `Origin` passes: that is a non-browser client, which the cookie's `SameSite` does not constrain either. [HTTP API](/architecture/api) has the response body.

**Two roles, compared in the handler.** `user.RoleAdmin` and `user.RoleUser` are the whole set. `requireAdmin` in `service/internal/userapi/handler.go` pulls the session's user out of the request context, answers `401` when there is none and `403` `admin role required` when the role is not `admin`; all four user operations call it first. There is no permission table and no per-resource rule — the `role` field on the session's user is the entire authorization model.

**User management is its own package because of the import direction.** `auth` imports `user`, and the user handlers need `auth.UserFrom` and `auth.SessionSecurity`. Registering them from `user` would close the cycle, so they live in `userapi` instead.

**A member may change their own password.** That is the one user write a non-admin can do, and it sits next to `me` rather than on the admin resource. `user.Service.ChangePassword` verifies the current password before storing the new one; a mismatch is `user.ErrWrongPassword`, which the handler turns into a `422` located at `body.currentPassword`.

**Every password change revokes sessions, and the two kinds differ only in what they keep.** Both go through `auth.Service.DeleteUserSessionsExcept`. The own change passes the calling cookie's token, so the browser making the change stays signed in and every other device is signed out. The admin reset passes an empty token, which keeps nothing: a reset means the old credential is forgotten or compromised.

**The user table has two guards.** `user.Service.Delete` refuses `actorID == id` with `ErrSelfDelete`. `guardLastAdmin` counts admins with `CountAdmins` and returns `ErrLastAdmin` when at most one is left; it runs when an admin is deleted and when an admin is demoted. The self-delete refusal is a plain comparison before any transaction opens; `guardLastAdmin` runs inside the write transaction `db.Tx` opens, which takes its write lock at `BEGIN` because of the connection DSN [Data model](/architecture/data-model) lists, so the count cannot be raced by a concurrent demotion or delete. Deleting a user also reassigns the recipes they created to the acting admin, through `ReassignRecipes` in the same transaction; their sessions go with the row (see [Data model](/architecture/data-model)).

**The contract routes sit behind a session too.** `isSpecRoute` in `service/internal/httpserver/api.go` matches `/api/v1/docs`, everything under the `/api/v1/openapi` prefix and everything under `/api/v1/schemas/`. huma hangs those off the mux itself rather than registering them as operations, so `auth.Middleware` never sees them; `httpserver.WithSpecGuard` wraps them in front of the mux instead, and `service/cmd/rezepte/main.go` supplies `auth.RequireSessionOrLogin`. Any role is enough — reading the contract is not an administrative act. A `Server` built without the option serves them openly, so the package itself stays unopinionated. Matching by prefix rather than by an explicit list costs one rule: no operation may ever be registered at a path under those prefixes.

**A browser is redirected, everything else gets a `401`.** `RequireSessionOrLogin` differs from `RequireSession` only in how it denies. `navigatingBrowser` accepts a `GET` whose `Accept` contains `text/html` — someone typing the address — and that gets a `303` to `/login?next=<escaped request URI>`; a bare `*/*`, which is what `fetch` and curl send, does not count, and neither does any other method, so those keep the `401` problem body. The SPA closes the loop: `safeNext` in `frontend/src/lib/api/auth.ts` resolves `next` against a fixed fake origin and falls back to `/` for anything that leaves that origin or points at `/login` again, and `isAppPath` routes a target under `/api/` through a full page load, because `goto` is client-side routing and the Scalar page is not a SvelteKit route. `isSignedOut` in `frontend/src/lib/api/client.ts` lets a form skip its own error toast for the `401` the client already turned into that redirect.

## Why it is this way

An own login form gives the two things an HTTP Basic prompt cannot: a logout, and a place to manage users from.

Two roles at household scale keep authorization a field comparison. `requireAdmin`, the self-delete refusal and the last-admin count are the whole of it; there is nothing to configure, and a third role or a per-resource rule would be a design change rather than a row in a table.

The contract document describes the surface of the running deployment, down to the admin endpoints — a fingerprint of that instance, which is more than a published spec gives away, and a self-hosted instance on the internet should give a stranger nothing. Deriving the protection from a prefix rather than from six literal paths means an upgrade that adds a fifth flavour of the document is covered before anyone notices it exists.

The redirect-versus-`401` split is load-bearing rather than cosmetic. `docs/user/scripts/fetch-openapi.ts` decides by `res.ok`, so a redirect it followed to a `200` login page would look like success and write that page into `openapi.json`. Scalar's own fetch of the document asks for JSON and keeps the `401` as well.

## Rejected

- **HTTP Basic Auth.** No logout, and no user management.
- **A JWT in local storage.** Readable by any XSS, and with no server-side record there is nothing to revoke when a password changes.
- **A permission table or per-resource ACLs.** A schema and a lookup in place of one field comparison, for two roles and a handful of accounts.
- **Soft-deleting users.** Nothing in the schema references a user except their recipes and their sessions; reassigning the first and cascading the second beats a status column every query has to filter on.
- **Admin-only contract routes.** The contract is not admin-owned, and a logged-in member already knows the API from using the frontend.
- **Disabling the contract routes in production.** That removes the docs page from the operator who has the most use for it, instead of protecting it.
- **Reimplementing huma's Scalar page and schema handler behind the guard.** Its CSP and SRI pin would have to be rebuilt, for no gain over wrapping the handlers huma already registers.

## Limits

- The admin reset endpoint does not special-case an admin calling it on their own id: it ends every session of that user, their own included. The UI hides the action on the admin's own row and routes self-service through the own-password change, but the endpoint itself does not.
- The first start needs `REZEPTE_ADMIN_PASSWORD` while the `users` table is empty — `EnsureInitialAdmin` returns `ErrAdminPasswordRequired` without it, and the service does not come up. `REZEPTE_ADMIN_USER` names that account and defaults to `admin`. Once any user exists `EnsureInitialAdmin` is a no-op and neither variable creates anything. Both values are taken after the substitution `--demo` performs (see [Demo mode](/features/demo-mode)), so a demo run without `REZEPTE_ADMIN_PASSWORD` supplies both credentials itself: nothing is required of the environment, and a `REZEPTE_ADMIN_USER` set there is discarded before anything reads it.
