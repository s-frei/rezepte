Several people in a household share one recipe collection. Accounts are created, re-roled, reset and removed in the UI; only the instance owner comes from the environment. Every account carries a display name and a palette color on top of its login name, which together are how the UI names and marks a person; [Design system](/architecture/design-system) owns the tokens the color resolves to. The served OpenAPI document holds the endpoints, their bodies and their status codes ([HTTP API](/architecture/api)); [Data model](/architecture/data-model) owns the `users` and `sessions` tables. The `/switch` screen is [Who's cooking?](/features/user-switch); this page owns the device cookie underneath it.

<Callout type="warn" title="Traps">

- **Ask the role, never compare it.** A bare comparison against `RoleAdmin` (or `role === 'admin'` in the SPA) excludes the owner and is always a bug ([Roles and rank](#roles-and-rank)).
- **huma reads no `cookie:` tag from an embedded struct whose type is unexported.** The fields stay empty without an error; logout silently ended no session that way ([Several people on one device](#several-people-on-one-device)).
- **Cookies ignore the port.** Two instances on one hostname share `rezepte_session` and `rezepte_accounts` and sign each other out ([Login and sessions](#login-and-sessions)).
- **`Authenticate` renews; `Peek` does not.** Reading a session through `Authenticate` to show it keeps it alive and fakes activity ([Several people on one device](#several-people-on-one-device)).
- **A deleted user's sessions cascade away**, so the switch asks `users.ByID` before `Authenticate`, or a deleted person answers `409` instead of `404`.
- **A forged-signature test that changes the last base64 character proves nothing half the time**: those bits are padding `base64.RawURLEncoding` ignores; change one further in.
- **Never hash inside the write transaction.** `BEGIN IMMEDIATE` holds the write lock, so an argon2id run inside it blocks every other writer ([Roles and rank](#roles-and-rank)).
- **No operation may be registered under `/api/v1/docs`, `/api/v1/openapi` or `/api/v1/schemas/`**: the contract-route guard matches by prefix ([Packages and the contract routes](#packages-and-the-contract-routes)).
- **Every sign-in ends in a full page load (`location.assign`)**, never `goto`: SvelteKit's `goto` rejects a path without a client route and the form showed it as a failed sign-in.
- **The phone login's focus must happen inside the tap**, hence `flushSync()` before `focus()` ([The login form](#the-login-form)).
- **The login form on the cover is `display: none`, never just hidden**, or iOS autofills a form nobody sees ([The login form](#the-login-form)).
- **A keyboard-height stickiness test whose viewport stays too flat for the plate passes with the stickiness removed**; grow it to a height where the plate fits again ([The login form](#the-login-form)).

</Callout>

## How it works

### Login and sessions

**A login form, and argon2id underneath it.** `frontend/src/routes/login/+page.svelte` posts username and password to the login operation; `user.Service.Authenticate` trims the username the way `Create` trims it and runs `VerifyPassword`. `HashPassword` in `service/internal/user/password.go` produces a PHC string (`$argon2id$…`) with the `argon*` constants there. `VerifyPassword` reads the parameters back out of the stored hash and bounds each by the `maxArgon*` constants, so a tampered row cannot make one login attempt allocate a gigabyte. An unknown username is still charged one argon2 evaluation, against a `dummyHash` computed once per process, so timing does not separate "no such user" from "wrong password".

**Signing out says once who left.** `signOut` (`frontend/src/lib/sign-out.ts`) hands the login page the leaving person's display name and color as navigation state (`page.state.signedOut`), and the form opens with "Signed out: Mila" beside her initial on her color - a shared kitchen tablet passing from one person to the next. Navigation state is not restored on a fresh load, so a reload drops it, and nothing reaches the URL or storage. The username stays empty, and the mark never shows a photo: the login page is public ([Design system](/architecture/design-system#user-colors)).

**A name that keeps failing is locked.** `auth.Service.Login` asks the throttle in `service/internal/auth/throttle.go` before it touches the password.

- It counts attempts per username, folded the way the `users` column compares it: trimmed like `Authenticate` trims it, ASCII letters lowercased and every other letter left alone, which is what `COLLATE NOCASE` does.
- `freeAttempts` are free, the last of them arms `firstLock`, and every attempt after a lock has run out doubles it, up to `maxLock`. A locked name gets `*auth.ThrottledError` at once, which the handler turns into `429` with `Retry-After` in whole seconds, rounded up; the SPA shows `login_throttled`.
- A successful login forgets the name, and so does `forgetAfter` without attempts, swept on the same tick as expired sessions.

**Argon2 runs a few at a time.** `deriveKey` in `service/internal/user/password.go` runs at most `maxConcurrentArgon` derivations at once - logins, password changes and new hashes alike - and lets at most `maxQueuedArgon` more wait for a slot. A waiter whose request context ends gives up its place. A caller that finds the queue full gets `user.ErrBusy`, which `auth.BusyError` turns into `503` with `Retry-After: 1` on every operation that hashes or checks a password. `auth.DeclareRetryAfter` puts that header into the OpenAPI document too, because huma writes error responses from an operation's `Errors` list without headers.

**The token lives in the cookie, its digest in the table.** `Login` in `service/internal/auth/service.go` draws 32 random bytes, encodes them with `base64.RawURLEncoding` and stores only the SHA-256 of that string as the session id, so a database leak yields no usable session. The token goes back as the `rezepte_session` cookie: `HttpOnly`, `Path=/`, `SameSite=Lax`, and `Secure` when `REZEPTE_SECURE_COOKIES` is set. Cookies ignore the port, so two instances on one hostname share it and sign each other out ([Work in a worktree](/howtos/work-in-a-worktree)).

**Sessions slide, renewed at most once a day.** `Authenticate` resets a session to a full `SessionTTL` once less than `SessionTTL - renewAfter` is left. The renewal is reported as `Verified.Renewed`, and both callers re-issue the cookie with the fresh expiry so the browser's copy never falls behind the row. A session found past its expiry is deleted on the spot; `DeleteExpired` also runs once at startup and `SweepLoop` every 24 hours after that.

**One middleware, two authenticators.** `auth.Middleware` authenticates every operation that declares `Security` — `auth.SessionSecurity` for session-only operations, `auth.Protected(scopes...)` for the ones an API token may also reach, `auth.TokenOnly(scopes...)` for one no session may reach; an operation without `Security` is public. It is installed through `httpserver.Options.APIMiddleware`, and `httpserver.New` applies every `Option` before it returns, so no operation can be registered ahead of it. A request carrying an `Authorization: Bearer` header is decided by a branch inside `Middleware` alone, with no fallback to the cookie; [API tokens](/features/api-tokens) owns its outcomes. The contract routes are the only routes that are not operations and still need authentication ([Packages and the contract routes](#packages-and-the-contract-routes)).

**CSRF is `SameSite=Lax` plus an origin check.** `checkOrigin` in `service/internal/httpserver/origin.go` refuses a `POST`, `PUT`, `PATCH` or `DELETE` under `/api/`, and a request of any method to `/mcp`, whose `Origin` header names a host other than the request's (or cannot be parsed).

- `/mcp` is covered whatever the method because the MCP Streamable HTTP transport requires every server to validate `Origin` and answer a present, invalid one with `403`.
- A request that carries no `Origin` passes: that is a non-browser client, which the cookie's `SameSite` does not constrain either.
- `POST /api/v1/unsubscribe/one-click` passes from any origin: a mail client posts it from its own, and its signed token alone authorizes it, never a cookie ([Notifications](/features/notifications)).

### Several people on one device

**Every account on a device holds an ordinary session, and a second cookie lists them all.** The active account is `rezepte_session` as always. `rezepte_accounts` (`service/internal/auth/device.go`) holds every account on the device, the active one first with the same token: `HttpOnly`, `SameSite=Lax`, `Secure` per `REZEPTE_SECURE_COOKIES`, `Path=/api/v1/auth`, Max-Age 400 days, re-issued on every write. Its value is entries `userID.token.sig` joined by `~`, in the order the people were last active: the active one and up to `maxDeviceAccounts` others, the longest-unused dropped first. The active entry is there so a person never leaves the device by accident: the browser drops `rezepte_session` once it runs out, and the entry still names them, shown as expired.

**An entry is signed, and bound to its session's owner.** `sig` is a `sign.Signer` token (`auth.NewDevice`, label `rezepte device account`, the instance key from `settings.Service.LinkPreviewKey`) over `userID.token`, so an entry names a person even after its session is gone, and only one this server wrote: `Device.Parse` drops anything malformed, signed under another key, or with its user ID or token swapped. Two instances on one hostname share the cookie, and each drops the other's entries, which it did not sign. The owner binding is defense in depth, since only a holder of the instance key can sign an entry: `TestEntryBoundToItsSessionsOwner` signs `{anna, sam's token}` with the test key to prove both the switch and the list refuse it, and `TestParseDropsForgedEntries` changes a character short of the last (see Traps). Because these are plain sessions, everything that ends sessions keeps working on them: deleting a user, a password change, an admin reset, `--reset-superadmin-password`.

**Every sign-in hands over.** Password login, redeeming a setup link, a switch, and an identity provider's login and setup flows all end in `Device.SignInCookies`, which sets the session and locale cookies beside the accounts cookie `Device.SignedIn` writes: the new person goes first with the new token, and when the request carries a valid session of someone else, that person follows with that token (`auth.Handover`); everyone else keeps their place.

- A token that drops out of the cookie is ended (`endDropped`, also on logout and remove): the cookie was its only way back to the device, so nobody could use or end it anymore. That is the active person's own older token when they sign in again, and whatever the cap cuts; a token the new cookie still holds is never ended (`TestSignInAgainEndsTheOlderSession`, `TestSignedInEndsWhatTheCapDrops`, `TestLogoutEndsWhatTheCapDrops`).
- An invalid or missing current session ends nobody's entry: whoever it belonged to stays with the token written when they became active.
- The SPA sends no flag for "add a person"; a sign-in on top of a valid session is that. The provider's `link` intent changes no session and hands nothing over.
- `oidc` asks the provider for `prompt=select_account` when the start request carries a valid session or an accounts cookie with any validly signed entry (the cookie's path covers `/api/v1/auth/oidc/*`), so a provider that remembers someone on the device still offers its account picker - also after a sign-out left nobody active. A session that cannot be read there is logged at debug and counts as none.

**Three public operations on the list** (`service/internal/auth/device_handler.go`, `RegisterDevice`): `list-device-accounts`, `switch-account` and `remove-device-account`.

- The list leaves out the active session's user (still kept in the cookie), so without a valid session it lists everyone; it drops users that no longer exist and any entry whose token belongs to someone else (`Peek` names another user), and rewrites the cookie when anything was dropped.
- A switch is `404` for no entry, a deleted user or a token that authenticates as anyone but the entry's user, and `409` when the entry's session no longer authenticates; the entry stays, and the SPA sends the person to the login with their username. Otherwise the entry's token becomes the session cookie, the current valid session goes into the list, and the answer is login's.
- Removing an entry ends its session (`Logout`) and drops it; the account stays. Removing the active account is `409`: that is signing out. With nobody active, any entry can be removed.
- An input that needs more than the two cookies (login, switch, remove) names both cookie fields itself instead of embedding `logoutInput` (see Traps); the list takes `logoutInput` as it is.

**Signing out keeps the person on the device.** `logout` ends the session; when anyone else is in the list, the person who left stays first in it with their dead token, so the switcher shows them as signed out. That entry is written only from the session cookie that authenticated the request (`SessionIDFrom` equals the cookie's hash), never from anything else. On a full device the leaver goes first and the cap drops the longest-unused other, ending that session. Alone, the accounts cookie is expired with the session and locale cookies.

**Expiry is read, never used.** `auth.Service.Peek` reads the session row and answers whether it is valid, whose it is and `LastSeen`, which is `expires_at - SessionTTL`: the session's start or last renewal, so it lags real use by up to a day. It never renews, never writes `last_active_at` and never deletes an expired row. Only a switch authenticates the chosen token the normal way. The list's `lastSeenAt` is the zero time for an entry whose row is gone (ended, or swept after expiry); such an entry is always `expired`, and the switcher shows it as "sign in again", never with a day.

### Roles and rank

**Three ranked roles, compared in one file.** `user.RoleUser`, `user.RoleAdmin` and `user.RoleSuperadmin` are the whole set, in ascending rank. The superadmin is the instance owner and is an admin.

- **Ask the role, never compare it.** `Role.IsAdmin` and `Role.IsSuperadmin` in `service/internal/user/service.go` are the only way to ask what a role carries. The SPA's answer is `isAdminRole` in `frontend/src/lib/roles.ts`, because `role === 'admin'` locks the owner out of every admin surface. `roleLabel` (the only place a role becomes label text) and `roleRank` (the people list's order) sit in that module too.
- **`requireAdmin`** in `service/internal/userapi/handler.go` answers `401` without an authenticated user and `403` `admin role required` when `IsAdmin` is false. Every user management operation calls it first; update and delete pass the caller it returns into the service.
- **Everything finer lives in `service/internal/user/permission.go` and nowhere else.** `GuardTarget` says who may act on whom and, applied to a role instead of a row, who may hand out which role. The create path uses that second form, since it has a requested role but no target row.
- **The whole rule:** an admin manages plain users; anything touching an admin or the superadmin belongs to the superadmin; and the superadmin can be neither deleted nor demoted by anyone, themselves included. There is no permission table. Recipes carry the one per-resource rule, which [Editing rights](/features/editing-rights) owns.
- **A token acts as its issuer's account**, so the rank applies underneath its scopes: a `users:write` token issued by an admin who is not the owner cannot hand out `admin` any more than that admin can. [API tokens](/features/api-tokens) owns how a token re-reads its issuer.

**The matrix, once, so it need not be re-derived.** Rows are the caller, columns the target; a cell says what the API answers. Creation has no target row, so it is `GuardTarget` alone: an admin may ask for `user`, only the owner may ask for `admin`, and `superadmin` is refused by huma's `enum:"admin,user"` with `422` before a handler runs.

| Caller | Target: a member | Target: an admin | Target: the owner |
|---|---|---|---|
| member | `403` `admin role required`, from `requireAdmin` before rank is consulted | same | same |
| admin | delete, reset, a setup link, setting the email address and the public-sharing switch; a role change and a profile write are each `403` `superadmin role required` | `403` `superadmin role required` | `409` `the superadmin cannot be modified` |
| the owner | delete, reset, re-role, rename, recolor, set the email address and the public-sharing switch | delete, reset, re-role, rename, recolor, set the email address and the public-sharing switch | `409` `the superadmin cannot be modified` for delete, reset, setting the email address, re-role and the public-sharing switch; a profile write lands |

- The profile write is the one column that never reads the target's rank: `GuardProfileEdit` asks only whether the caller is the owner, so the owner reaches every row including their own, and everybody else is `403` `superadmin role required` whoever they aim at. The people list still hides it on the caller's own row: the profile page is the one place a person renames themselves.
- Nobody deletes their own account (`409` `cannot delete yourself`, checked before the transaction opens), and nobody resets their own password through the admin path — an admin aiming at their own row is aiming at an admin.
- `docs/user/content/(guide)/guide/users.mdx` states the same matrix as what a person sees in the row, since an action the caller may not take is never rendered.

**The rank guard runs inside the write transaction.**

- `user.Service.Delete` refuses `actor.ID == id` with `ErrSelfDelete`, a plain comparison before any transaction opens. Everything else is `GuardTarget`, which `SetRole`, `Delete` and `SetPassword` run on the row they have just read, inside the write transaction `db.Tx` opens. The lock is taken at `BEGIN` (the DSN in [Data model](/architecture/data-model)), so a concurrent promotion cannot slip the target out from under a passed check. `SetRole` runs `GuardTarget` a second time, on the role it is about to write.
- `SetPassword` hashes before opening the transaction: holding the `BEGIN IMMEDIATE` lock for an argon2id run would block every other writer for the length of it.
- Each refusal carries one status code. `ErrSuperadminProtected` is `409` `the superadmin cannot be modified`, a fact about the instance that holds for every caller, in the register `ErrSelfDelete` uses; `ErrSuperadminRequired` is `403` `superadmin role required`, which is about who is asking.
- Two SQLite triggers, `users_superadmin_undeletable` and `users_superadmin_role_locked`, refuse the delete and the demotion underneath the Go layer, for a raw query or a code path that forgets to ask; [Data model](/architecture/data-model) owns them.

**Deleting a user hands their recipes to the acting admin.** `ReassignRecipes` moves the recipes they created **or last edited** to the acting admin (the token's issuer when the call carried a bearer token, since `requireAdmin` reads whichever account the credential belongs to), in the same transaction. `created_by` and `updated_by` both reference `users` with no `ON DELETE` clause, so a recipe somebody else wrote but this user last touched would otherwise hold the delete on its foreign key. `edit_policy` stays as it is, so each recipe keeps its [editing rights](/features/editing-rights) under its new author. Their [comments](/features/recipe-comments) are not reassigned: `author_id` is `ON DELETE SET NULL`, so they stay and read "Former member", since words a person wrote must not become the admin's; their watermarks go. Their sessions go with the row (see [Data model](/architecture/data-model)).

**The bootstrap account is the owner, and only a shell resets it.** `EnsureSuperadmin` runs as the process starts and has three answers:

- an empty instance gets the account `REZEPTE_ADMIN_USER` names, created with `RoleSuperadmin` through `Create`, so it picks up the same profile defaults as every other account: its display name is its login name, and its color is `amber`, which is what the least-used rule yields on an empty table (every count zero, the tie going to palette order);
- an instance that already has an owner is left alone;
- a populated `users` table with no owner is `ErrNoSuperadmin`, which stops the service from coming up rather than let it serve an instance nobody owns.

`superadmin` is never an assignable role — `POST /users` and `PATCH /users/{id}` declare `enum:"admin,user"` — and the owner's password is theirs alone: the admin reset refuses that target for every caller, the owner included, and self-service goes through `ChangePassword`. The one way back from a forgotten owner password is outside the application: `rezepte --reset-superadmin-password` takes the new password from `REZEPTE_ADMIN_PASSWORD`, writes it to the owner, ends every session of that account, mails a password notice to the owner's confirmed address ([Email](/features/email)) and returns without starting the server. Reaching it needs shell access to the host, which is the operator by definition.

### Profile: name, color, picture, address

**Every account carries a display name and a color.** `display_name` is what the UI prints wherever it names somebody and `color` is the palette token that marks them; neither is an identity and neither is unique - `username` stays the only thing that identifies an account.

- `user.Create` is the single writer of a user row, so it owns both defaults: an empty display name becomes the trimmed username, and an empty color becomes the least-used color of the palette, ties broken by palette order (`leastUsed` in `service/internal/user/profile.go`, over the counts `ColorUsage` groups out of the table). Least-used rather than first-free because duplicates are allowed: the two only part company once every color is held, and spreading a household across the palette is the property worth keeping.
- `normalizeDisplayName` trims, falls back to the username when nothing printable is left, refuses more than 64 **runes** and refuses a control character - so the column is never empty and no client invents a fallback of its own.
- `ParseColor` accepts the palette exactly as written, with no trimming and no case folding: the API declares the closed set as an `enum`, so anything else is a client error rather than a typo to repair.
- Self-service is `PATCH /api/v1/auth/me/profile`, which every role may use on its own row; the color picker names who else wears a color from `GET /api/v1/people`, which every session may read anyway, so there is no separate count of colors. Writing somebody **else's** profile is the owner's alone: `user.GuardProfileEdit` in `service/internal/user/permission.go`, checked in `update-user` before anything is written, so a body that mixes a rename with a password reset changes neither.

**The own profile page is one card** (`routes/settings/+page.svelte`). `ProfileHead` with `editable` carries photo, name and the `ColorPicker`, whose pick is the save: debounced and sequenced, so a run of arrow keys sends one request and a late answer never overwrites a newer pick. Its sign-in row's "Connect" is a real form post to `/auth/oidc/start` with `intent=link` (a `fetch` would not follow the redirect), and "Disconnect" is off without a password; the service answers `409` anyway.

**Every account may carry a picture.** `users.avatar_id` names it, `NULL` means none, and a circle without one is the color and initial.

- The account sets and removes its own through `PUT`/`DELETE /api/v1/auth/me/avatar`; the owner does both for any account through `/api/v1/users/{id}/avatar`, the rule `user.GuardProfileEdit` applies to the rest of a profile.
- `service/internal/avatar` stores one square JPEG per account at `<REZEPTE_DATA_DIR>/avatars/<user id>/<avatar id>.jpg`, rendered by package image ([Images](/features/images) owns the pixels), with a fresh `avatar_id` per upload, so a changed picture is a changed URL and the file is cached for a year.
- `Service.Set` renders the file first, swaps the row in a transaction, and removes the previous file only once the row names the new one; a failed swap removes the new file. The row never names a missing file, and a failure leaves the old picture in place. `Remove` clears the column and deletes the file, and removing a picture that is not there is not an error. `delete-user` calls `RemoveAll` after the row is gone.
- Every session, and a token with `users:read`, may read the files.

**An account may carry an email address, and it is profile data, not an identity.** `email` is not unique and plays no part in signing in.

- It is set through the same `PATCH /api/v1/auth/me/profile` as name and color; `ParseEmail` in `service/internal/user/email.go` accepts only a bare address (no display name, no angle brackets) and treats `""` as "none".
- `email_verified` is true when an identity provider vouched for the address through its own `email_verified` claim ([OIDC](/features/oidc)), when a setup link mailed to it was redeemed, or when its confirmation link was opened ([Email](/features/email)). Typing a new address clears it; the same address in other letters is the same mailbox, so `nextEmail` keeps the stored spelling and the mark and nothing is mailed.
- `(*user.Service).SetEmailIfEmpty` is the other writer: it fills the column only while it is empty, so a provider's address becomes the account's own on the first sign-in through it and is left alone afterwards - a typed address always outranks a provider's.
- `userapi.UserAccount` (`GET /api/v1/users`, admins only) carries `email` and `emailVerified`, and `list-users` alone fills `lastActiveAt` (when the person last signed in or used a session or an API token, up to an hour late; `null` when never; [Data model](/architecture/data-model) owns when it is written); `PersonEntry`, the people list every account reads, carries none of the three, so a member never sees another member's address or activity.
- An admin writes another account's address through `PATCH /api/v1/users/{id}` (`email`) under `user.GuardTarget`, like a reset: `(*user.Service).SetEmail` runs `GuardTarget` inside the write transaction, and a new address clears `email_verified`. That write is session-only - a token gets `422` at `body.email` - since an address decides where a credential is mailed. The person page sends `email` alone, so a plain admin never trips the owner-only profile write.
- Creating an account with an address needs only `GuardTarget`, and a token may do it: a token-created account carries a password, so no setup link goes to that address.

**An account carries whether it may share publicly.** `users.can_share_publicly` is an admin's per-person switch, on by default (`canSharePublicly` in `UserAccount`), under `GuardTarget` like a reset; the owner's own row always answers `409`, since the owner's control is the household-wide switch. One rank rule for the role change, the reset and this switch is what lets `update-user` take them in one body without one landing while another is refused; an admin aiming at their own row is aiming at an admin, so nobody re-grants themselves a right another admin withdrew. In the SPA, `rowPermissions` grants `toggleSharing` exactly where it grants `manageAccount`. [Public shares](/features/public-shares) owns what withdrawing does to existing links.

### The people list

**Every account sees who takes part.** `GET /api/v1/people` (`list-people`, in `userapi`) answers any session with every account as a `PersonEntry` and nothing else; it is the one operation in the package that does not call `requireAdmin`.

- `latestRecipes` is up to four recipes the person created, newest **created** first (the card shows what someone added), in one query for every person (`LatestRecipesByCreator`, a `ROW_NUMBER()` window per `created_by`), with no visibility filter because every signed-in account reads every recipe. `lastRecipeTitle` on `GET /users` (newest changed) stays for API compatibility; nothing in the SPA reads it.
- The recipe and list counts are public on purpose: how many shopping lists someone has is household knowledge, what is on them is not, and the page says so (`users_lists_privacy`).
- `TestPeopleHidesAccountDetails` pins its key set field by field, so a field added to the struct has to be added to the test on purpose, and `TestPeopleNeedsTheUsersReadScope` holds tokens to `users:read`.
- The frontend type is `PersonEntry` in `frontend/src/lib/api/users.ts` too, because `Person` in `frontend/src/lib/api/recipes.ts` is the roleless person a recipe names, and two exports called `Person` would be one wrong import apart.

**One page for every rank.** Settings → People (`frontend/src/routes/settings/users/+page.svelte`; the path says `users` because accounts are managed there) reads `/people` for every viewer; admins also read `GET /users` for what only they may see (address, setup state, `canSharePublicly`, `createdAt`, `lastActiveAt`).

- The page keeps the `/people` entries as its list and merges every PATCH answer into them (`replace`), because a `UserAccount` carries no counts and a swapped-in one would drop the card to "No shopping list".
- Where a card leads is decided per card by `rowPermissions` in `frontend/src/lib/settings/row-permissions.ts` and `canOpenPerson` in `frontend/src/lib/settings/person-page.ts`. `rowPermissions` asks the viewer's rank first, because the page is open to every account, then mirrors `permission.go`.
- The list acts on nobody: every action on an account lives on that account's page. It keeps only "Add account" with `CreateUserDialog` and the setup-link result that follows it. "Add account" is off while the list loads, because the form preselects the least worn color from the people it is handed.

**The people list decides its own order.** `ListUsers` orders by `username COLLATE unicode` ([Data model](/architecture/data-model#storage)), but the page shows display names grouped by role, so it orders on the client: `groupPeople` in `frontend/src/lib/settings/people-groups.ts` makes one group per role somebody holds, in `roleRank` order, and orders each group by display name with an `Intl.Collator` over Paraglide's `getLocale()`. The order must stay total: a collator tie falls through to a code-point comparison, then to the username (`compareUsernames`), then to the id. `numeric: true` calls "user2" and "user02" equal, and a stable sort would then keep whatever order the rows arrived in, so a row would move between loads.

**What a card says and where it leads.** Every viewer gets the same card per person (`PersonTile.svelte`), and the whole card is one `<a>`: to `/settings/users/{username}` when `canOpenPerson(rowPermissions(...))` holds, to `/settings` on the own card. A card the viewer may not open is a plain `div`, and its circle opens the person card; a link never holds the circle's button, because interactive content inside an `<a>` is invalid. The card has no other controls and nothing unfolds.

- The address's state, the setup state ("Setup link open until", "Not set up yet", `Signs in with {name}`) and the last activity are admin-only: they come from the admin-only `GET /users`, and a member never learns anyone's address, whether it is confirmed, or when someone was last active. `lastActive` in `frontend/src/lib/settings/last-active.ts` turns `lastActiveAt` into its text and `state`; a dormant account is marked with an attention tone, never `destructive`.
- Recipes always come before lists, here and on the person page's Overview.
- **Wide and narrow are the card's width, not the viewport's**: the `li` is an `@container`, so the settings card at a tablet viewport is a phone-wide card.
- `settings.test.ts` pins that the card is one link with no buttons, the cover count, "No recipes yet", the own card's link to `/settings`, the owner's card having no link for a plain admin, and that a member's list has no link but the own card; `person-page.test.ts` pins the activity text and `data-activity`.

### The person page

`/settings/users/[username]` (`frontend/src/routes/settings/users/[username]/+page.svelte`) is every account action for one person, in the profile page's look: `ProfileHead`, then `SettingsGroup`s of `SettingsRow`s. The username is the URL because it is never renamed.

- **Who sees it.** The page loads `listPeople()` (plus `listUsers()`, `getOidc()` and `getSettings()` for an admin) and asks `personPageTarget`: the own username goes to `/settings`, anyone the viewer may not act on to `/settings/users` (`replaceState`), an unknown username shows an `EmptyState` with a way back. There is no read-only person page. The page re-loads when only the username changes, since SvelteKit keeps the component; `loadSeq` names the newest load, and the effect's cleanup retires the one in flight, so an answer for a person already left, or for a page already gone, neither lands nor redirects.
- **Groups follow `rowPermissions`.** The head is `editable` under `editProfile` (the owner's alone); Account (email, password reset, setup link, disconnect) under `manageAccount`; Role under `changeRole`; "May share publicly" under `toggleSharing`; Overview for every viewer. A refused rename or address goes through the page's `refused()`, which names the rank rule instead of the own profile's generic line. `ResetPasswordDialog`'s `onreset` patches `hasPassword: true`, so the setup row stops saying "Not set up yet".
- **One tap, one Undo.** A color or a role takes effect at once, and its toast carries "Undo", which sends the previous value back through the same path; a run of color picks is debounced into one request and one toast.
- The row buttons keep their short visible word and carry the person in their accessible name (`person_email_change_aria`, `person_reset_aria`, `person_setup_link_create_aria`), since every person page has the same three.
- **Focus.** A dialog returns focus to its opener ([Accessibility](/conventions/svelte#accessibility)), and some openers are gone when it closes: "Create link" becomes "Manage" once a link is open, and the disconnect row leaves with the identity, so the page then focuses the setup-link control (`focusSetupControl`). "Revoke" swaps "Manage" back to "Create link", so `revokeLink()` focuses it after the reload. The mail step closes a tick before the result opens: flipped in one update, both dialogs stayed open. `person-page.test.ts`, `mail.test.ts` and `oidc.test.ts` pin all three.

**Three words, three things.** *User* and *account* name the login and its management: `/api/v1/users`, the `users:*` scopes, "Add account". *Person* and *people* name who takes part in the household: `/api/v1/people`, the `Person` a recipe's `createdBy` carries, the "People" tab. *Member* names one role, `user`, and nothing else. The German catalog draws the same line ("Benutzer" for the account, "Mitglied" for the role), so no label in either language can be read as both.

### Setup links, reset links and `/welcome`

**Setup links instead of handed-over passwords.** Creating a user with no `password` (`POST /api/v1/users`, `createInput.Body.Password` is `omitempty`) stores an empty `password_hash` and issues a setup link in the same response.

- `auth.Service.IssueSetupLink` draws 32 random bytes the way a session token is drawn, stores only `hashToken` of it in `setup_links` (`0010_setup_links.sql`), and returns the raw token once.
- `setup_links` holds one row per account (`setup_links_user_idx` is unique on `user_id`), so `ReplaceSetupLink`'s `ON CONFLICT (user_id) DO UPDATE` is the whole of "issuing another replaces it": there is never a second open link, and the old token stops resolving the moment a new one is stored.
- `auth.SetupPath` puts the token in the URL fragment, `"/welcome#" + token`: a fragment never leaves the browser, so it reaches neither a server log nor a `Referer` header. A link lives `auth.SetupLinkTTL` and is swept by `DeleteExpired` with expired sessions.
- Issuing a link is the same act as a password reset and follows the same rank rule: `user.GuardTarget`, called from `IssueSetupLink` and from `RevokeSetupLink`. A revoke deletes the row if one exists and is not an error when none does.
- Every setup operation is session-only (`auth.SessionSecurity`): issuing a credential is not a thing a `users:write` token should do unattended.
- A token cannot create a user with an empty `password` either, since redeeming a setup link takes the admin UI's dialog, which a token cannot show: `create-user` answers `422` at `body.password`, deciding "bearer caller" with `auth.ViaToken(ctx)`, a context flag only `auth.Middleware`'s bearer branch sets.
- `GET /api/v1/users` calls `sessions.OpenSetupLinks` once per request and folds `setupLinkExpiresAt` into each row with an open link, so the list needs no request per row; `hasPassword` rides on every row, and `auth.UserResponse` carries it too.

**Redeeming is the public half, and spends a link exactly once.**

- `POST /api/v1/auth/setup/inspect` (`PeekSetupLink`) answers a token with the username, display name and color to greet, without spending it, and for a setup link issued for someone else `inviter`, the issuer's (`setup_links.created_by`) display name and color; a reset, a link the account issued for itself and an issuer that cannot be read carry none (`TestInspectSetupLinkNamesTheInviter`). Never a picture id: whoever holds the link has no session.
- `POST /api/v1/auth/setup/password` (`RedeemWithPassword`) hashes the new password **before** touching the link, so a full argon2 queue (`user.ErrBusy` → `503`) leaves the link open for a retry. It then runs one transaction: the delete-returning consume (`consumeWith`, the one place both `ConsumeSetupLinkByHash` and `RedeemWithPassword` map a spent or unknown token to `ErrNoSetupLink`), the password write, and `DeleteUserSessionsExcept` with an empty keep-token, since an invite is not assumed to be the person's only browser. After the commit, `afterConsume` sends the password notice (or, for a setup link redeemed through OIDC that linked a new identity to an account that could sign in already, the sign-in method notice) or hands the accepted invitation on ([Email](/features/email)).
- A concurrent second redemption finds no row left to delete, so of two requests racing on one link exactly one sets a password (`TestRedeemSetupLinkOnlyOnce`, under `-race`).
- Unknown, expired and used all answer the same `ErrNoSetupLink` → `404`, so a probe learns nothing about which case it hit.
- Success signs the account in through `StartSession`, the call `Login` uses, so accepting an invite and being signed in are one step.

**A forgotten password is reset through a link of its own.** A reset link is a `setup_links` row with `purpose = 'reset'` (`auth.PurposeReset`), issued by `IssueResetLink` for `ResetLinkTTL` with `created_by` the account itself.

- It replaces an older or expired reset link, never an open setup link an admin handed out: `ReplaceSetupLink`'s upsert updates no row then, `issueLink` answers `errSetupLinkOpen`, and the request mails nothing.
- Changing the address or the password closes it: the trigger `users_change_closes_reset_link` deletes the account's `purpose = 'reset'` row on every write of `email` (case folded) or `password_hash`, whichever code path makes it, and leaves a setup link alone.
- The people list's "setup link open" line (`ListOpenSetupLinks`) counts only `purpose = 'setup'`, so a member's own reset request never shows there.
- It opens `/welcome` in reset mode, which names the account, offers no identity provider button and ends every other session when the password is saved. `PeekSetupLinkByHash`, the OIDC flow's peek, refuses a reset link, so a hand-made `intent=setup` post can never attach an identity to the account.
- The owner is never reached by it. Two cooldowns sit next to the login throttle, one on reset mails and one on confirmation mails per account; [Email](/features/email) owns who gets what.

**Issuing a link in the UI.** "Add account" (`CreateUserDialog.svelte`) defaults to "Send a setup link"; a link-mode create opens `SetupLinkDialog.svelte` with the token, which leads with where it was mailed when it was ([Email](/features/email)) and always shows the link itself as the fallback. The person page's setup-link row opens the same dialog at any later point and replaces whatever link was open; with mail on it first asks in `SendSetupLinkDialog.svelte` whether to mail the link or only show it.

**`/welcome` is where a link lands.** `frontend/src/routes/welcome/+page.svelte` reads the token from `location.hash` once, on mount, and immediately removes it from the address bar with `history.replaceState` - whether or not the form is ever finished - so an abandoned invite never sits as a live token in browser history.

- It passes `history.state` on, SvelteKit's entry for the page: with `null` a back onto `/welcome` changed only the address and left the previous page on screen (`back onto a setup link shows its page again`). `/confirm-email` clears its token the same way.
- It calls `inspectSetupLink` to greet the person and `redeemSetupLink` on submit. For a setup link (not a reset) it names the inviter and shows "This is how the others see you" (`welcome_seen_as`): the person's mark, name and color as the account was created. Both marks get no `avatarId` - the person has no picture yet; `an invited person sets their own password through the setup link` in `e2e/setup-links.test.ts` checks that no `/avatars/` image shows.
- A `404` from either call is the only case that shows "This link no longer works"; any other inspect failure offers a retry, since the token stays in the page's memory.
- `/welcome` is exempt from the root layout's login redirect, so a browser already signed in as another account shows a notice naming both, and finishing the link replaces that session.

### Passwords

**A member may change their own password.** That and the own profile are the two user writes a non-admin can do, and both sit next to `me` rather than on the admin resource. `user.Service.ChangePassword` verifies the current password before storing the new one; a mismatch is `user.ErrWrongPassword`, located at `body.currentPassword`.

**An account may have no password.** `password_hash` is `''`, not `NULL` - a bare `TEXT NOT NULL` needs no migration to add the state, and every reader already treats the column as a string.

- `user.Create` stores the empty hash whenever `CreateParams.Password` is empty, except for the superadmin: `Create` refuses `RoleSuperadmin` without a password (`ErrAdminPasswordRequired`), so the instance's own way back in always has one.
- `Authenticate` treats an empty hash exactly like a wrong password and still runs one `VerifyPassword` against `dummyHash`, so neither timing nor response tells a caller a name exists with no password to guess.
- `ChangePassword` skips the current-password check while there is none: the caller's own session is proof enough, so `PATCH /api/v1/auth/me` accepts a body with no `currentPassword`. Once a password is set, the next change demands it like any other.

**Every password change revokes sessions, and the two kinds differ only in what they keep.** Both go through `auth.Service.DeleteUserSessionsExcept`. The own change passes the calling cookie's token, so the browser making the change stays signed in and every other device is signed out. The admin reset passes an empty token, which keeps nothing: a reset means the old credential is forgotten or compromised.

**Every password field is written for a password manager.** A manager fills and saves by `autocomplete` alone.

- The login form marks its fields `username` and `current-password`; every field that sets a password is `new-password`, which also makes a browser offer a generated one. The login's username field turns off `autocapitalize` and `spellcheck`, because a phone keyboard that capitalizes `sam` to `Sam` fails the login.
- `PasswordDialog.svelte` has no visible username, so it carries a hidden, read-only `autocomplete="username"` field holding the caller's own: without it a manager cannot tell which account the password belongs to and saves a second entry. The two admin dialogs stay without one on purpose, because the password they set belongs to somebody else.
- From `lg` the login's first field carries `autofocus`, as the attribute, not a `focus()` call on mount ([Accessibility](/conventions/svelte#accessibility)). Below `lg` nothing is focused on arrival; the cover's tap focuses.

**A new password is rated while it is typed, and only rated.** `PasswordStrength.svelte` sits under the field in every form that sets a password - the own change, "Add account", the admin reset and the welcome page - all of which render `NewPasswordFields.svelte` (new password, rating, repeat). `estimateStrength` in `frontend/src/lib/settings/password-strength.ts` runs `@zxcvbn-ts/core` with `@zxcvbn-ts/language-common`, both behind a dynamic `import()`, so the roughly 230 KB gzipped reach a browser only when somebody types into one of those fields. It passes the account's username and display name, whole and word by word, plus `rezepte` and `recipes`, so `anna1990` is weak for Anna and nobody else. The rating is a polite live region, announced after a pause in typing. Its line is reserved from the first character: a line that grew when the rating arrived pushed the save button down under a click, and e2e tests lost their click on a busy runner. Nothing is blocked: the length rule the API enforces is the only rule a password must pass.

**Every form that sets a password takes it twice and states the minimum.** `validateNewPassword` in `frontend/src/lib/settings/password.ts` checks the pair before anything is sent; the API never sees the second copy. The new-password field's hint is the same message the too-short error uses, so a failed save turns the hint red in place instead of adding a line.

### The login form

**On a phone the login opens on a cover, and the form waits in a sheet.** Below `lg` the page is `AuthScene` with `frame="cover"`: a cover with "Sign in" (and the provider's button) that needs no keyboard, and the one `<form>` in a sheet that opens over it as a modal dialog ([Design system](/architecture/design-system#app-shell) owns the scene and its motion). The cover's tap sets `open`, calls `flushSync()` and focuses the first empty field, all inside the tap ([User activation](/conventions/svelte#user-activation)): without `flushSync()` Svelte would apply `open` in a microtask, after the activation is gone, and no keyboard would come up; `e2e/auth.test.ts` clicks and reads `document.activeElement` in one synchronous `evaluate` to hold that. The sheet closes on a tap on the plate, Escape, the grip (`pullToClose`, shared with `SheetHandle`) and Android's Back through a `CloseWatcher` that exists only while it is open; meanwhile the plate's view (`[data-auth-view]`) is `inert`, not the plate itself, since an inert plate takes no hits and the closing tap would land on `main`.

- **The form stays in the DOM**, `display: none` on the cover so iOS does not autofill a hidden form, and is never re-created, so a password manager sees stable fields.
- **`MediaQuery('width >= 64rem')` is the exact complement of `AuthScene`'s `width < 64rem`**, so no fractional width shows neither the form nor the cover's button.
- **Below `lg`, Enter in the username moves focus to the password** instead of submitting, except while an IME composes (`isComposing`); from `lg` it submits.
- **The frame is `overflow: clip`, not `hidden`**: a field scrolled into view (`reveal`) while the sheet is still below would scroll a `hidden` frame and shift the plate.
- **A test of the keyboard-height stickiness must start from a viewport too flat for the plate and grow to one where it fits**: from a height that stays too flat anyway, it passes with the stickiness taken out (`e2e/auth.test.ts`).

**The login answers in motion, and success is a full page load.** A refused sign-in (401) shakes the card, marks both fields and selects the password; a 429 or a failed request shows its message without marking a field. A second press while the request is out is ignored in `submit`, since the busy button is not disabled. Success ends as a switch does ([Who's cooking?](/features/user-switch#motion)) - only once the request has answered, so a refused sign-in never shows a greeting: the sheet or card grows into `HelloSplash`, `markArrival` stores the person's color, and the page makes a full load of `safeNext(next)`, so nothing of the previous person survives. The add mode (`?add=1`) does the same; under reduced motion there is only the load, and a provider sign-in is the server's redirect and shows neither. The provider button and "Forgot password" come from `login/+page.ts`, which waits briefly for both lookups so the card does not grow under the fields a frame after it appears; a slower answer still fills them in, a failed one leaves them out.

### Packages and the contract routes

**User management and token management are their own packages because of the import direction.** `auth` imports `user`, and both the user handlers and the token handlers need `auth.UserFrom` and `auth.SessionSecurity` or `auth.Protected`. Registering either from `user`, or from `auth` itself, would close the cycle, so they live in `userapi` and `tokenapi`.

**The contract routes require a session or a token.** `isSpecRoute` in `service/internal/httpserver/api.go` matches `/api/v1/docs`, everything under the `/api/v1/openapi` prefix and everything under `/api/v1/schemas/`. huma hangs those off the mux rather than registering them as operations, so `auth.Middleware` never sees them; `httpserver.Options.SpecGuard` wraps them in front of the mux instead, and `service/cmd/rezepte/main.go` supplies `auth.RequireAuthOrLogin` from `service/internal/auth/require.go` - plain `func(http.Handler) http.Handler` middleware with the same session authentication and renewal re-issue. Any role is enough, and a valid API token of any scope opens them too, since `RequireAuthOrLogin` checks no scope. A `Server` built without the option serves them openly, so the package stays unopinionated. Matching by prefix costs one rule: no operation may ever be registered at a path under those prefixes.

**A browser is redirected, everything else gets a `401`.** A bearer request is never redirected: a bad token gets a plain `401`, because a login page means nothing to a client that authenticates with a header. For a session, `navigatingBrowser` accepts a `GET` whose `Accept` contains `text/html` and answers it with `303` to `/login?next=<escaped request URI>`; a bare `*/*`, which `fetch` and curl send, does not count, and neither does any other method, so those keep the `401` problem body.

**The SPA closes the loop.** `safeNext` in `frontend/src/lib/api/auth.ts` resolves `next` against a fixed fake origin and falls back to `/` for anything that leaves it or points at `/login` again. Every successful sign-in - the login, the add mode, the setup-link redeem, and the identity provider's server redirects - ends in a full page load (`location.assign`) of that target, so nothing of the person before stays in memory. That also reaches targets without a client route, such as the Scalar page under `/api/`, which `goto` rejects (`e2e/auth.test.ts`, `a sign-in towards a page that does not exist lands on its 404`). Where a signed-out moment goes is decided once, by `signedOutTarget(next?)` in `frontend/src/lib/device-accounts.ts`; [Who's cooking?](/features/user-switch#ways-in-and-out) owns its callers. `POST /auth/logout` is left out of the client's `401` redirect, so `signOut` makes the one navigation, and `isSignedOut` lets a form skip its own error toast for the `401` the client already turned into that redirect.

## Why it is this way

An own login form gives the two things an HTTP Basic prompt cannot: a logout, and a place to manage users from.

**`golang.org/x/crypto/argon2` hashes the passwords** because the standard library has no memory-hard password hash; argon2id is the current recommendation, and the Go team's own implementation is the one to trust with it.

### The throttle and the argon2 cap

- The throttle keys on the username alone, because behind a reverse proxy the only address Rezepte sees is the proxy's, and reading `X-Forwarded-For` safely takes a list of trusted proxies an operator can get wrong without anything telling them.
- An attempt counts when it begins, not when its password turns out wrong: counted afterwards, a burst of parallel requests would all pass the check before the first failure landed.
- Unknown names are counted exactly like real ones, so a `429` never tells anyone which accounts exist; a full argon2 queue is reported for an unknown name exactly as for a real one, for the same reason, and `dummyHash` derives its one key outside the queue so that it can never fail.
- Counting unknown names is why the map is capped (`throttleCapacity`) rather than limited to names that exist. When it is full, idle names go first, then the least recently seen name that still has free attempts, and a name that has used them only when every tracked name has: evicting a locked name hands it its free attempts back, and entries are made before the argon2 queue, so a flood of fresh names must not be able to reach one.
- The lock sits on the name, not on the password check, which keeps a locked attempt free: no query, no argon2.
- The concurrency cap covers what the lock cannot, many different names at once. It bounds memory, the resource an argon2 flood exhausts, and the queue bound keeps waiting bounded too: a caller turned away learns it at once, instead of every login, a household member's included, waiting behind whatever an attacker has queued.

### Rank

Renaming somebody is not administration, which is why the profile write has a guard of its own instead of reusing `GuardTarget`. `GuardTarget` lets an admin act on a member, and that is the right rule for a role change or a password reset: those keep the instance usable, and any admin has to be able to perform them without waiting for the owner. Deciding what another adult in the household is called has nothing operational in it, so it stays with the account that owns the instance. Folding it into `GuardTarget` would have handed it to every admin as a side effect of a rule written about something else.

Authorization at household scale stays a comparison of two fields, the actor's rank and the target's. `requireAdmin`, the self-delete refusal and the two pure functions in `permission.go` are the whole of it. The one configurable rule in the instance is the household lock on recipes, which [Editing rights](/features/editing-rights) owns.

The rank is what makes `admin` a role that is handed out and taken back. Without an account that outranks every other, any admin can delete, demote or reset the person who installed the instance, and a rule that only keeps the admin count from reaching zero protects nobody from that: it still leaves every admin able to remove every other. An account that can be neither deleted nor demoted always counts as an admin, and the admins below it are delegated rather than protected.

### The contract routes

The contract document describes the surface of the running deployment, down to the admin endpoints — a fingerprint of that instance, which is more than a published spec gives away, and a self-hosted instance on the internet should give a stranger nothing. Deriving the protection from a prefix rather than from literal paths means a new flavor of the document is covered before anyone notices it exists.

The redirect-versus-`401` split is load-bearing rather than cosmetic. `docs/user/scripts/fetch-openapi.ts` decides by `res.ok`, so a redirect it followed to a `200` login page would look like success and write that page into `openapi.json`. Scalar's own fetch of the document asks for JSON and keeps the `401` as well.

### People, pictures and devices

Who takes part is not a secret inside a household, and hiding it would make the list of people a privilege: a member would see only the accounts that have written a recipe, and could not tell who may change their recipes or reset their password. `/people` is its own operation rather than a looser `/users` because the two answer different questions to different audiences - who is here, for everyone, and which account to manage, for admins - and one shape per operation keeps both contracts exact. Opening the list shows every login name, including accounts that have written nothing; the authors' names were already visible through `/authors` and `?author=`, and the login throttle keys on the name precisely so that knowing one buys nothing.

The browser picks the crop and the service cuts it. The dialog sends the original and three fractions, and package image is the only code that touches pixels, so the UI, an API client and an MCP tool reach one pixel path with one set of limits, one orientation rule and the same decode slots as a recipe photo. A client that cropped would have to be trusted to send a well-formed square, and a second client would have to implement the same thing.

The device operations are public, not `SessionSecurity`: the switcher has to work with nobody active, after a sign-out with others on the device or once the active session ran out. Their credential is the accounts cookie itself, whose entries only this server signs and each of which carries a real session token; switching to an entry is using that token, and `checkOrigin` covers the `POST` and `DELETE`. The cookie's narrow path keeps it off every other request. Listing reads expiry through `Peek` rather than `Authenticate` because the latter renews: it would keep every session on the device alive for as long as anyone opened the switcher, and make the admin's "last active" claim activity nobody had.

## Rejected

- **A table of devices and their accounts.** A migration, a device id to issue and expire, and rows to sweep, for what a signed cookie already holds; the sessions the entries point to are rows anyway.
- **Listing every account of the instance on the switcher.** Anyone at the tablet could become anyone, the owner included; only people who signed in on the device appear.
- **Sortable columns on the people list.** Grouping by role already gives the one order worth choosing, and names are ordered inside each group; a household of a handful of accounts gains nothing from reversing it, and a sort head is a second control over the same job that a phone has no room for.
- **Opening `/api/v1/users` to every account and trimming the body by rank.** One operation with two shapes: fields would turn optional in the OpenAPI document for every client, and each caller would learn from the data which shape it got.
- **Growing `/api/v1/authors` into the people list.** It is a facet of the recipe list - who wrote how many - under the `recipes:read` scope; accounts without a recipe and roles have nothing to do with filtering recipes.
- **Limiting logins per client IP, or counting failures after the password check.** See [The throttle and the argon2 cap](#the-throttle-and-the-argon2-cap): behind a proxy a per-IP limit locks the household out together unless a trusted-proxy list, which fails silently in both directions, is right; counted afterwards, parallel requests all pass.
- **HTTP Basic Auth.** No logout, and no user management.
- **A JWT in local storage.** Readable by any XSS, and with no server-side record there is nothing to revoke when a password changes.
- **A permission table or per-resource ACLs.** A schema and a lookup in place of two field comparisons, for three ranked roles and a handful of accounts.
- **A flag beside the role, such as `is_owner`.** Two columns holding one fact, and a `role` field that does not state the whole truth about an account: every reader has to fetch both and every writer has to keep them agreeing.
- **A separate `instance` table pointing at the owner.** Every test that builds a user service would seed a second table, for a guarantee the partial unique index and the two triggers already give.
- **A unique color per account.** A unique index on `color` caps the household at the palette's size and turns the next person into a schema problem, and it makes picking a color a race rather than a preference - the swatch somebody was about to choose disappears under them. The picker marks a color another account already holds and lets it be chosen anyway, which is the whole of the constraint worth having.
- **A free color value rather than a palette token.** A hex string arrives as a background with no foreground to go with it, so the capital inside the circle has whatever contrast the person happened to land on, and one value cannot serve both themes. A closed set keeps the measured pairs in `frontend/src/app.css` and lets the API refuse everything else with an `enum` before a handler runs.
- **Soft-deleting users.** Little in the schema references a user beyond the recipes they wrote or edited, their comments and their sessions; reassigning the first, orphaning the second and cascading the rest beats a status column every query has to filter on.
- **Email as a login name or match key.** Nothing verifies a typed address, and a provider's address can be re-registered; `(iss, sub)` is the only link.
- **Restricting the contract routes further — to admins, or off entirely in production.** The contract is not admin-owned, and a logged-in member already knows the API from using the frontend; switching the docs page off takes it from the operator who has the most use for it instead of protecting it. A session of any role is the line.
- **zxcvbn's German and English language packs.** They add names, common words and Wikipedia vocabulary, and a megabyte gzipped on top of what the leaked-password list costs; that list already catches most of what a household actually types.
- **Rating in the service.** No bundle cost, but a request per pause in typing and a Go port of zxcvbn that nobody maintains, against a standard-library-first service.
- **Refusing a weak password in the form.** A rule only the browser enforces is one API call away from not existing; a real refusal belongs in the service, next to the length rule.
- **Cropping on a canvas in the browser.** The upload would be a pre-cut bitmap: the service could not enforce a minimum, API and MCP clients would have to reimplement the crop, and a second pixel path would sit beside package image. The browser only reports the square it shows.
- **A two-step upload with a server-rendered preview.** A draft file to store and expire, and a second request before anything changes, for a preview the dialog already draws from the file in memory.
- **A crop library.** The math is a handful of pure functions in `frontend/src/lib/user/crop.ts` with their own tests, where a library would bring its own pointer handling and styling against the design system.
- **A throttle on setup-link redemption.** A 256-bit token cannot be guessed.
- **The token in the path.** It would land in proxy logs and Referer headers.

## Limits

- No account can use the admin reset on itself, and that falls out of the rank rule rather than being a case of its own: an admin's own row is an admin target, which only the owner may touch, and the owner's row is refused for every caller including the owner. Self-service is the profile page's own-password change, which verifies the current password and keeps the calling browser signed in - unless the account has none yet, in which case there is nothing to verify and the call sets one outright. The reset still ends every session of the account it is used on.
- The first start needs `REZEPTE_ADMIN_PASSWORD` while the `users` table is empty (`ErrAdminPasswordRequired`, and the service does not come up); `REZEPTE_ADMIN_USER` defaults to `admin`. Both are read after the substitution `--demo` performs ([Demo mode](/features/demo-mode)), so a demo run supplies both itself and discards a `REZEPTE_ADMIN_USER` from the environment.
- Whoever knows a username can keep that account locked by failing on purpose, for at most `maxLock` after their last attempt — accepted, because the alternative keys need client addresses Rezepte cannot see behind a proxy. The owner is not exempt. Sessions already signed in are untouched, and `rezepte --reset-superadmin-password` does not go through the throttle.
- Because an attempt counts when it begins, several correct logins for one name started at the same moment count against each other, and past the free attempts they are refused with `429`. People do not sign in that way; a script sharing one account across parallel workers would have to.
- The own-password change is not throttled. It takes a session of that account already, so it is no way in for someone who has none, and its argon2 evaluations sit in the same queue as every other.
- The throttle lives in memory: a restart forgets every lock, and it counts per process, which is all a single-binary SQLite deployment runs. A locked name is evicted only once `throttleCapacity` names are tracked and every one of them has used its free attempts.
- A flood of logins that keeps the argon2 queue full turns everybody else away with `503` for as long as it lasts: the cap trades availability for bounded memory, and a household member retries.
- Switching needs no password: whoever holds the device holds every session on it, by the owner's decision. Removing a person or changing their password is what takes them off.
- Ownership cannot be handed over: the bootstrap account is the owner for the life of the instance, no endpoint promotes a second one, and a forgotten owner password has no reset inside the application, not even by mail - only `rezepte --reset-superadmin-password` from a shell. Giving up that account means giving up the instance.
