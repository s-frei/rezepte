---
title: "0014: Warm theme for the user docs"
description: The user docs wear the frontend palette; docs/memory stays neutral
---

**Status:** accepted · 2026-09-18

## Context

`docs/user/` shipped with the stock Fumadocs `neutral` preset: cool greys, a near-black primary, system fonts. The pages it renders are about a warm, cream-coloured app, and once `<Screenshot>` starts serving generated PNGs, every page shows the app's palette inside a grey frame. End users meet the docs before they meet the app, so the docs are where the product's look is introduced.

Fumadocs turned out to be a good host for this: it reads every colour from a `--color-fd-*` variable and hardcodes none - not in `css/generated/*`, not in `css/lib/base.css`, not in the typography plugin. The `shadcn.css` preset it ships does exactly this remapping for another design system.

## Decision

- `docs/user/` uses the "Warm & handmade" palette from [ADR 0007](/decisions/0007-visual-direction-warm-handmade): the 17 `--color-fd-*` tokens are mapped onto the Rezepte values in `docs/user/app/global.css`, Karla is the body face, Literata the heading face, IBM Plex Mono the code face.
- **`docs/memory/` stays neutral.** It is an agent tool, not a product surface; the visual difference says at a glance which of the two sites is being read.
- The values are **copied, not imported**. Crossing the app boundary would contradict [ADR 0005](/decisions/0005-fumadocs-as-agent-memory), and a shared file would have to carry both dark-mode mechanics - the frontend switches on `data-theme`, Fumadocs' next-themes on a `.dark` class.
- Two values deliberately differ from the app, both carrying far more body-sized reading text here (sidebar, table of contents, page descriptions) than they do there (meta lines, chips).
- `fd-primary`: the app's `#b45309` measures 4.32:1 on `#f4ede2`, below AA for body text; the docs use `#9a4707` at 5.51:1.
- `fd-muted-foreground`: the app's value was `#7d6d5c` (4.29:1, below AA) when this decision was taken and has since been raised to `#756554` (4.82:1, commit `951d071`), which clears AA. The docs keep `#6f6152` at 5.15:1 for the extra margin, because the token carries far more reading text here than it does in the app.
- Callout colours are earthy rather than the Tailwind 500 shades Fumadocs ships: `info` `#4f6d74`, `warning` `#b45309`, `error` `#a3321f`, `success` `#5c8a45`, `idea` `#a8761c`. Five distinguishable hues, each above 3:1 on the callout surface so the icons stay perceivable. `success` is the app's sage darkened, which measures 2.41:1 on cream and would otherwise be invisible.
- `fd-accent` is the deeper paper tone `#eadfcd`, not the app's `accent`. In Fumadocs `accent` is the hover and active surface; in the app it is a decorative chip. The paper tone is the one value that stays visible on both substrates, since the sidebar sits on `card` and the navbar and table of contents on `background`.
- Code highlighting uses `vitesse-light` / `vitesse-dark` instead of the `github-*` default, whose cool greys clash with warm paper.

## Consequences

- Changing a colour in `frontend/src/app.css` does not change the docs. Both places have to be edited, and the docs values have to be re-checked for contrast because their background carries body text.
- `docs/user/app/global.css` imports `fumadocs-ui/css/lib/default-colors.css` rather than `neutral.css`. The latter carries a `.dark #nd-sidebar` rule whose id selector outweighs any `.dark` override.
- The overrides live in plain `:root` and `.dark` blocks, not in `@theme`. Unlayered declarations beat Tailwind's `@layer theme`, so they win regardless of import order.
- Setting `themes` in `rehypeCodeOptions` replaces the Fumadocs default wholesale, so `defaultColor: false` has to be repeated - without it Shiki emits fixed colours instead of the `--shiki-light` / `--shiki-dark` variables that dark mode reads.
- Three Fontsource dependencies were added to `docs/user/`, all OFL-1.1 like the two the frontend already carries.
- Tailwind v4 compiles `@theme` shadow values into each utility class as a literal `--tw-shadow` declaration, not a live `var(--shadow-*)` reference (confirmed against the built CSS). A runtime `.dark` override of `--shadow-sm`/`--shadow-md`/`--shadow-lg`/`--shadow-2xl` therefore has no effect - unlike the colour and radius tokens, which utilities do reference live. The next person theming a shadow per mode should budget for this before losing an afternoon to it.

<Accordions type="single">
  <Accordion title="Alternatives considered">

    - **A shared `tokens.css` imported by both apps:** one source of truth, but it breaks the independence of the two builds ([ADR 0005](/decisions/0005-fumadocs-as-agent-memory)) and would have to declare its dark values under both `:root[data-theme='dark']` and `.dark`. Rejected as too much structure for twenty values.
    - **Taking the app's contrast values unchanged:** maximum fidelity, but sidebar, table of contents and page descriptions would sit below AA. Rejected; the hue difference is invisible, the contrast difference is not.
    - **Callouts in palette colours only:** `info` as brown, `warning` as primary. Fully closed, but info, warning and error would all land in the brown-orange-red family and only the icon would tell them apart.
    - **Theming `docs/memory/` the same way:** rejected. The neutral look marks it as internal.
    - **Also adopting the app's radii and shadows:** deferred. Fumadocs leans on `rounded-lg` and `rounded-xl`, which the app's scale roughly doubles; small controls such as badges and the search field would come close to pills. Worth a separate look with screenshots.
