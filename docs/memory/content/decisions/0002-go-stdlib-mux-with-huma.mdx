---
title: "0002: Go stdlib router with huma for the API"
description: net/http ServeMux plus huma for typed handlers, validation and OpenAPI
---

**Status:** accepted · 2026-09-17

## Context

The API must be clean, idiomatic Go and later become a documented public REST API. The maintainer is new to Go and wants to learn the standard library, but does not want to reinvent validation or OpenAPI generation.

## Decision

- Routing: `net/http.ServeMux` with method patterns (`GET /api/v1/recipes/{id}`), no third-party router.
- API layer: `github.com/danielgtaylor/huma/v2` via the `humago` adapter. Handlers are typed functions `func(ctx, *Input) (*Output, error)`; huma validates input, produces OpenAPI 3.1 at `/api/v1/openapi.json` and a Scalar UI at `/api/v1/docs`, and renders errors as RFC 9457 problem+json.
- Everything else comes from the standard library: `log/slog`, `encoding/json`, `embed`, `database/sql`, `signal.NotifyContext`.
- Dependencies are allowed when they are the established solution and replace real work (huma, sqlc, goose, argon2, x/image).

## Consequences

- Every endpoint is documented for free, which the roadmap (public API, MCP server) relies on.
- Handlers have request/response structs that double as API contract; keep them in the feature package next to the service.
- huma shapes handler signatures; feature code must not reach for `http.ResponseWriter` inside operations.
- The Scalar docs UI at `/api/v1/docs` loads its JS bundle from jsdelivr at runtime (huma's default `DocsRendererScalar`); acceptable for an admin-facing docs page, to be revisited if offline use matters.

<Accordions type="single">
  <Accordion title="Alternatives considered">

    - Plain stdlib without huma: less to learn, but validation and OpenAPI would be hand-written later.
    - chi/echo/gin: unnecessary since Go 1.22 patterns cover routing.
    - Spec-first (oapi-codegen, ogen): generates handlers from a hand-written spec; code-first fits a small team better.

  </Accordion>
</Accordions>
