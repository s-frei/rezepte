---
title: Update the memory
description: Which page owns which fact, and how to change it
---

The memory holds one page per thing that exists. Updating it is therefore not writing a new entry: it is finding the page that owns the fact and rewriting the sentence that is now wrong.

## What belongs here

This memory describes **the repository, not the machine and not the day**.

**Write the present.** Every page says what is true now. When something changes, rewrite the sentence - do not append a correction, do not leave the old claim standing beside the new one, and do not add a date. Git holds what the page said before, and a page that reads as a changelog has stopped being memory. There is one document per thing that exists, never one per event, so the number of pages follows the size of the system rather than the age of the project. Reasoning moves with its subject: why a thing is shaped the way it is, and which alternatives were weighed and refused, live on that thing's page under `## Why it is this way` and `## Rejected`.

**Write the constraint, not the event.** "macOS binds port 5000 system-wide to the AirPlay receiver, which answers every request with 403" is durable: it explains the choice and stops anyone picking 5000 again. "We moved off 5000 on 2026-09-18" is the same fact with a shelf life, and git already records it. So: no dates, no "originally", no "used to", no "for now", no "Phase 2", no "no longer, since", no "not built yet". If a sentence only makes sense to someone who knows what the repository looked like before, rewrite it as the constraint that outlived it. Where a concrete incident is what makes a rule credible, keep it to one sentence and lead with the rule.

**One fact, one owner.** A value written in two places will rot in one of them. Ports, paths, task names and commands are named where they belong and linked from everywhere else - for ports that means `mise run ports`, never a copied number or table. A list a source file already holds - routes, icons, color values, environment variables - is pointed at, not copied.

**Never record one machine's setup.** No absolute paths, usernames, hostnames, or "on the development machine" quirks: this repository is meant to be readable by anyone, on any machine, and it may become public. A workaround that is true only of one laptop belongs in that developer's own notes. Ports named here are the project's own defaults (offset 0), not a fact about anyone's setup.

**Write down what the next agent would rediscover.** A trap you hit, the way a change finally got tested, a gate that passed when it should have failed: if the next agent would have to find it again, it goes into the page that owns it, in the commit that taught it. An agent's private memory is invisible to every other agent and to every other developer; keep only what is about one person and how they like to work there.

**Write for an agent that greps.** Nobody reads the memory end to end. Lead each paragraph with its rule, keep one idea per paragraph, and leave out what the code already shows - the pixel sizes and class lists of a component, the fields of a generated schema.

## How to change it

<Steps>
  <Step>

    ### Find the page that owns the fact
    A user-visible capability is a page under [Features](/features/recipes). The shape of the system - packages, tables, endpoints, tokens, the toolchain, the documentation sites - is a page under [Architecture](/architecture/overview). How to do a recurring task is a [how-to](/howtos). How to write code is a page under [Conventions](/conventions/go).

    If the fact has no page and the thing it describes exists, create the page. If two pages would both take the sentence, one of them owns the subject and the other links to it: a value written twice rots in one of the copies.

    **What earns a page under `features/`.** A capability earns one when it carries facts no component file states: a contract with the service - an endpoint, a table, files on disk - a rule that has to hold across several places such as the scaling arithmetic, a storage key or an upload limit, or an alternative a competent agent would still propose and that was refused for a reason. Those are what the four sections further down are fillable with.

    A capability whose facts are exhausted by how it looks and how its component is written already has an owner: a row or a bullet in [Design system](/architecture/design-system) for the first, a rule in [Svelte conventions](/conventions/svelte) for the second. The command palette, theme switching, the recipe editor and the tag filter are owned that way, and giving one of them a page would split its facts rather than collect them. So ask what a reader who has to change the thing must know that the code does not already say, and write it where that answer already lives.

  </Step>
  <Step>

    ### A new feature page carries the four sections
    In this order, and the audit enforces both their presence and their order:

    ```markdown
    ---
    title: The capability
    description: One line naming what it does
    ---

    A paragraph saying what a user can do and which packages hold it.

    ## How it works

    ## Why it is this way

    ## Rejected

    ## Limits
    ```

    `How it works` is the present-tense description. `Why it is this way` carries the reasoning: why this shape and not another. `Rejected` names the options that were weighed and not taken. `Limits` names what the thing deliberately does not do. Add the page to `docs/memory/content/features/meta.json` in the same change, so navigation never names a page that has no file. A new how-to goes into `docs/memory/content/howtos/meta.json` and gets a `<Card>` in `howtos/index.mdx`; the memory audit fails while either is missing.

  </Step>
  <Step>

    ### Keep a rejected option only while someone might still propose it
    A `## Rejected` entry earns its place by stopping an agent from suggesting the same discarded option again. Delete one that has become unthinkable. A section that only grows is the thing this structure replaced.

  </Step>
  <Step>

    ### Delete the page when the thing is gone
    One document per thing that exists. The number of pages follows the size of the system, not the age of the project, so removing a capability removes its page and the links into it in the same change.

  </Step>
  <Step>

    ### Run the gate
    `mise run check` must pass before the commit; `mise run //docs/memory:check` is the fast loop while writing. `docs/memory/scripts/memory-audit.ts` is the part that reads the prose: it fails when a `mise run` task name does not exist, when a repository path in backticks does not exist, when a link into the memory resolves to no page, when a `features/` page is missing one of its four sections or carries them out of order, when a sentence names one machine's setup, and when a sentence describes an event instead of a constraint.

    It cannot tell whether a sentence is true, only whether the things it names still exist. Everything else rests on the rules above.

  </Step>
</Steps>
