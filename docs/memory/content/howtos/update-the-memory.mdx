This page is the one place that says how the memory is written. Its rules are project-neutral; only the last section, [In this repository](#in-this-repository), names Rezepte's paths and tools. To give another project the same memory, copy this page and `docs/memory/scripts/memory-audit.ts`, then rewrite that last section and the config block at the top of the script; the phrasing lists below the block are project-neutral.

<Callout type="warn" title="Before you commit a memory change">

- The fact sits on the page that owns it; every other page links there instead of repeating it.
- It says what is true now: no dates, no "used to", no "for now", no correction appended beside the old claim.
- Each paragraph leads with its rule and holds one idea; none runs past 300 words.
- A section past about 1,000 words is split with `###` subheadings.
- A trap - something that breaks the build, loses data or fails silently - is a one-line bullet in the page's `Traps` Callout near the top.
- Nothing the code already shows: no pixel sizes, class lists or copied lists of routes, keys or fields.
- No machine's setup: no absolute paths, usernames, hostnames or one laptop's quirks.
- The audit passes ([Run the gate](#run-the-gate)).

</Callout>

## The shape

The memory holds **one page per thing that exists, never one per event**. Updating it means finding the page that owns the fact and rewriting the sentence that is now wrong, so the number of pages follows the size of the system, not the age of the project.

| Section | Holds | One page per |
| --- | --- | --- |
| Index | What the project is, a routing table from "your task touches" to the pages to read, a map of the top-level folders | - |
| Architecture | The shape of the system: packages, tables, endpoints, tokens, the toolchain, the docs sites | part of the system |
| Features | What a user can do, how it works, why, what was refused, what it does not do | user-visible capability with facts beyond its look |
| Conventions | How to write code and commits: rules for a whole class of files | language or concern |
| How-tos | Step-by-step guides for work that recurs | recurring task |

The agent's entry file (`AGENTS.md`) lists only the hard rules, each with a `→` to the page that explains it, and sends every agent to the index first.

### A feature page carries four sections

The four `##` sections in this order, which the audit enforces (it does not check the Callout):

```markdown
---
title: The capability
description: One line naming what it does
---

A paragraph saying what a user can do and which packages hold it.

<Callout type="warn" title="Traps">
- One line per trap, linking down to the detail.
</Callout>

## How it works

### One subheading per part

## Why it is this way

## Rejected

## Limits
```

- **How it works** is the present-tense description, split into `###` parts once it grows past a screen.
- **Why it is this way** is the reasoning: why this shape and not another.
- **Rejected** names options that were weighed and not taken. Keep an entry only while a competent agent might still propose it; delete one that has become unthinkable.
- **Limits** names what the thing deliberately does not do.

The `Traps` Callout is there only when the page has traps; a page without them leaves it out.

### What earns a page under features

A capability earns one when it carries facts no component file states: a contract with the service (an endpoint, a table, files on disk), a rule that has to hold across several places (a storage key, an upload limit, shared arithmetic), or a refused alternative someone would still propose.

A capability whose facts are exhausted by how it looks and how its component is written already has an owner: a row in the design-system page or a rule in a conventions page. Giving it a page would split its facts rather than collect them. Rezepte's command palette, theme switching, recipe editor and tag filter are owned that way.

## Writing rules

### What to write

- **Write the present.** Every page says what is true now. When something changes, rewrite the sentence; git holds what it said before.
- **Write the constraint, not the event.** "macOS binds port 5000 to the AirPlay receiver, which answers every request with 403" is durable; "we moved off 5000 last September" has a shelf life. So no dates, no "originally", "used to", "for now", "Phase 2", "not built yet". Where an incident makes a rule credible, keep it to one clause after the rule.
- **One fact, one owner.** A value written in two places rots in one of them. Ports, paths, task names and commands are named where they belong and linked from everywhere else. A list a source file already holds - routes, icons, colors, environment variables - is pointed at, not copied.
- **A rule for a class goes to the class.** A learning that holds for every sheet, every dialog, every e2e test or every migration belongs to that class's owner: a section of an architecture page, a conventions page or a how-to. The feature page where you met it keeps what is specific to the feature and links to the rule. A paragraph past 300 words, or the same trap on two feature pages, is the sign a class rule is hiding there.
- **Write down what the next agent would rediscover.** A trap you hit, the way a change finally got tested, a gate that passed when it should have failed: it goes into the owning page in the commit that taught it. An agent's private memory is invisible to every other agent; keep only what is about one person and how they like to work.
- **Never record one machine's setup.** No absolute paths, usernames, hostnames or "on the development machine" quirks; the repository is meant to be readable by anyone. Ports are named by their variable and the project's default, not by one checkout's offset.

### How to write it

Nobody reads the memory end to end. Agents grep, land mid-page and read a screen.

- **Lead each paragraph with its rule**, then the reason. One idea per paragraph, at most 300 words.
- **Make the important things look important.** Traps go in the `Traps` Callout at the top, each one line. Bold marks the one sentence of a paragraph that is its rule, never decoration. A hard rule from the entry file gets a `Callout` on its owning how-to.
- **Use structure where the content has it.** A list in prose is a bulleted list; values side by side are a table; a sequence is `<Steps>`. Headings are the table of contents, so a long section gets `###` subheadings named after what they hold.
- **Leave out what the code shows.** A component's pixel sizes, class lists, animation timings and the fields of a generated schema live in the code. Write what a reader who has to change the thing must know that the code does not say: the contract, the rule across places, the trap, the reason.
- **Link, do not retell.** Name the owning page with a link, with an anchor when the fact sits in one section.

## How to change it

<Steps>
  <Step>

    ### Find the page that owns the fact
    A user-visible capability is a page under Features, the system's shape a page under Architecture, a recurring task a how-to, how to write code a page under Conventions. If the fact holds for a whole class, its owner is the class's page, not the feature's. If two pages would both take the sentence, one owns the subject and the other links to it. If the thing exists and has no page, create one.

  </Step>
  <Step>

    ### Rewrite, do not append
    Change the sentence that is now wrong. Remove what is gone: a capability that is removed takes its page and the links into it with it, in the same change.

  </Step>
  <Step>

    ### Register a new page
    Add it to its folder's navigation, and a how-to also to the how-to index and, when an agent would look for it by task, to the routing table on the index ([In this repository](#in-this-repository) names the files).

  </Step>
  <Step>

    ### Run the gate
    The audit reads the prose for what can be checked mechanically ([In this repository](#in-this-repository) lists every check). It cannot tell whether a sentence is true, only whether the things it names exist and whether the page keeps the form above; everything else rests on these rules.

  </Step>
</Steps>

## In this repository

- **Entry file:** `AGENTS.md`, with `CLAUDE.md` a symlink to it, so Claude Code and every tool that looks for `AGENTS.md` read the same file. Edit `AGENTS.md`; never replace the symlink with a copy.
- **Pages:** `docs/memory/content/`, a Fumadocs site. Each folder's `meta.json` lists its pages in navigation order; the how-to index is `docs/memory/content/howtos/index.mdx`, one `<Card>` per how-to with the page's `description` as its text.
- **Gate:** `mise run //docs/memory:check` is the fast loop while writing; `mise run check` runs it with everything else before a commit.
- **Audit:** `docs/memory/scripts/memory-audit.ts` fails when
  - a `mise run` task does not exist, or a backticked path under `service/`, `frontend/`, `docs/`, `mise/`, `assets/` or `.github/` (or `mise.toml`, `AGENTS.md`, `CLAUDE.md`) is neither tracked nor an unignored new file - write paths from the repository root so they are checked;
  - a link into the memory, or its `#anchor`, resolves to nothing;
  - a page is missing from its folder's `meta.json`, or `meta.json` names a page that has no file;
  - a how-to has no `<Card>`, or its card text differs from the page's `description`;
  - a `features/` page lacks one of its four sections or orders them differently;
  - a paragraph or list item runs past 300 words, or a `##` section past 1,000 words has no `###`;
  - a sentence names one machine's setup or describes an event instead of a constraint (this page is exempt, since it quotes what it forbids).

  Ports are not checked: every port in the memory is a default named beside its variable or a `mise run ports` pointer.
