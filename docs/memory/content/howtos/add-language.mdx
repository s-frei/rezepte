<Callout type="info">

  This is for adding a whole **language**. Adding a *string* to the languages that already exist is [Add a translation](/howtos/add-translation).

</Callout>

A language is two files: its code in `service/internal/i18n/locales.json` and its catalogue in `frontend/messages/`. Everything else reads that list - see [Languages](/features/languages) for how. The user docs carry the contributor's version of these steps in `docs/user/content/contributing/add-a-language.mdx`; keep the two in step.

<Steps>
  <Step>

    ### Add the code
    Append it to `locales` in `service/internal/i18n/locales.json`, leaving `baseLocale` alone. The order is the order the picker shows.

    ```json
    {
    	"baseLocale": "en",
    	"locales": ["en", "de", "fr"]
    }
    ```

    The Go service embeds this file, and `frontend/vite.config.ts` generates Paraglide's `project.inlang/settings.json` from it on the next dev, build or test run.

  </Step>
  <Step>

    ### Translate the catalogue
    Copy `frontend/messages/en.json` to `frontend/messages/<locale>.json` and translate every value, keeping every key and every `{param}` placeholder exactly as it stands. The catalogues are peers, not a source and its translations: `mise run check` fails while any of them is missing a key the others have (`frontend/scripts/message-parity.ts`), and while a listed locale has no catalogue at all (`service/internal/i18n/i18n_test.go`).

    Do not add a key for the language's own name. The picker gets those from `Intl.DisplayNames`.

  </Step>
  <Step>

    ### Regenerate the API reference
    `docs/user/content/api/reference.mdx` is generated from the OpenAPI document, whose `locale` enum now has one more value. Run `mise run //docs/user:openapi` and commit the result; CI regenerates it and fails on a difference.

  </Step>
  <Step>

    ### Sample recipes, if you want them
    This step is optional. Without it, a demo instance in the new language seeds the English recipes: `recipe.Samples` falls back to `user.BaseLocale`'s set when `recipes.<locale>.json` is missing.

    To give the language its own set, add `service/internal/recipe/testdata/recipes.<locale>.json` with twelve recipes, matching the key set of the files beside it. They are their own recipes, not translations - the demo shows what someone in that language would actually cook. Twelve matters: `imagedRecipes` in `service/internal/demo/seed.go` gives the first nine a placeholder photo and leaves three showing tiles. `Samples` finds the file by name, so there is no Go change.

  </Step>
  <Step>

    ### Run the gate
    `mise run check` covers the catalogues, the Go suite and the frontend. Then `RZP_DEMO_LOCALE=<locale> mise run demo` starts an instance in the new language to look at. `mise/tasks/demo.sh` prefers `RZP_DEMO_LOCALE` over `REZEPTE_LOCALE`, so this works even when a `mise.local.toml` sets `REZEPTE_LOCALE`, whose config env would win over one given on the command line.

  </Step>
</Steps>

## What you do not have to touch

Each of these follows `locales.json`, and editing it would be the bug rather than the fix.

| | Follows |
| --- | --- |
| `user.Locales`, `user.BaseLocale`, `ParseLocale` | `service/internal/i18n`, which embeds the file |
| The database | Nothing: `users.locale` has no `CHECK`, so there is no migration |
| Paraglide's `project.inlang/settings.json` | Generated by `frontend/scripts/inlang-settings.ts`, and gitignored |
| The API's `enum` for `locale` | `user.Locales`, via `Locale.Schema` (huma `SchemaProvider`) |
| `REZEPTE_LOCALE` validation | `user.ParseLocale` in `service/internal/config` |
| The frontend's `Locale` type | Paraglide's generated type, re-exported by `frontend/src/lib/api/auth.ts` |
| The picker's entries and their names | Paraglide's `locales` plus `Intl.DisplayNames`, in `frontend/src/lib/i18n/languages.ts` |
| Which sample recipes the demo seeds | The filename, matched by `//go:embed testdata/recipes.*.json`, else English |

## Worth deciding, not inherited

**The picker is a select** (`frontend/src/lib/components/settings/LanguageControl.svelte`), and it lists every language with its endonym beside it - "German · Deutsch" - so somebody who cannot read the current interface can still find their own language. That holds at any number of entries.

**The two Playwright suites run in fixed languages**, and a third language does not change that: `frontend/e2e/` is pinned to German by `REZEPTE_LOCALE=de` in `mise/tasks/e2e.sh`, and `docs/user/screenshots/` is pinned to English by the `env` of its tasks in `docs/user/mise.toml`. Covering a new language end to end means deciding which of those it belongs in, or leaving it to the unit tests - see [Add a screenshot](/howtos/add-screenshot).
