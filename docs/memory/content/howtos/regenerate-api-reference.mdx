<Callout type="warn" title="Hard rule">

  Never hand-edit anything in `docs/user/content/api/reference/`. It is generated; any manual change is overwritten by the next regeneration.

</Callout>

## What the task does

```bash
mise run //docs/user:openapi
```

1. Builds the Go binary (`//service:build`).
2. `mise run demo --` starts it with `--demo` on `:8070` (offset 0; `mise run ports` for this worktree) against a throwaway data directory and waits for `/healthz`.
3. `docs/user/scripts/fetch-openapi.ts` logs in as the demo admin (`docs/user/scripts/demo-user.ts`, shared with the screenshot specs), fetches `/api/v1/openapi.json` from that instance with the session cookie and writes `docs/user/public/openapi.json`. The login step is not optional: the document sits behind the session (see [Users and authentication](/features/users-and-auth)), which is also why this task needs a demo instance rather than any running server - it has to be one whose credentials we know.
4. `docs/user/scripts/generate-api.ts` reads `docs/user/public/openapi.json` (no running server needed for this step) and hands it to `generateFiles` from `fumadocs-openapi`, which writes `content/api/reference/`: one page per operation in a folder per tag, a card page per folder, one over all of them, and the `meta.json` files that order them.
5. `//:demo` stops the binary and deletes the data directory.

Run it whenever an endpoint, parameter or schema changes - see [Keep the user docs in step with the UI](/howtos/update-user-docs). CI runs the same task and then `git diff --exit-code`, so a forgotten regeneration fails the build, not just a review.

## A new tag still needs a declaration

`groupBy: 'tag'` groups by the tags an operation carries, so an undeclared tag does produce a folder — but a shabby one: the raw tag name as its title, no description on its card, and a position after every declared tag, since the declaration order in `apiTags` (`service/internal/httpserver/api.go`) is what `beforeWrite` restores onto the top-level `meta.json`.

`TestEveryTagIsDeclared` in `service/internal/httpserver/wiring_test.go` fails on both halves of the mistake: a tag an operation uses but the document does not declare, and a declaration no operation uses (which would generate an empty folder). The fix is to add the tag with its description where the others live. That order is also the order the Scalar page at `/api/v1/docs` presents.

## Changing how it renders

`docs/user/scripts/generate-api.ts` configures the generator; `docs/user/components/api-page.tsx` configures the renderer. Between them:

- **`per` / `groupBy`** - `'operation'` foldered by `'tag'`, so the sidebar lists the endpoints themselves. `per: 'tag'` would collapse each tag into one long page and the sidebar back to six entries.
- **`includeDescription`** - deliberately `false`, which keeps the description in the page frontmatter instead of moving it into the body. Every other page on the site carries its description there, and it is where `<DocsDescription>`, the search index and `/llms.txt` read it.
- **`index`** - the card pages: one per tag folder, one over all of them. Without the per-folder ones a tag is a bare navigation node, `/api/reference/recipes` is a 404 and the breadcrumb above an operation leads nowhere.
- **`beforeWrite`** - does three things `generateFiles` has no option for: retitles each page with its route (the summary moves to the description), prepends `index` to every generated `meta.json`, and puts the top-level one back into tag-declaration order.
- **`playground`** - off, and [Documentation sites](/architecture/docs) says why it has to be.

After any change there, run the task and read the diff in `docs/user/content/api/reference/` before committing.

`SCREENSHOT_BASE_URL` also affects this task: `fetch-openapi.ts` reads it (default `http://localhost:8070`) to find the running instance - see [Add a screenshot](/howtos/add-screenshot) for when to override it.
