---
title: Keep the user docs in step with the UI
description: What to edit and regenerate when a UI or API change lands
---

<Callout type="warn" title="Hard rule">

  A UI or API change is not done until the affected page under `docs/user/content/` reflects it. See [Testing](/conventions/testing).

</Callout>

<Steps>
  <Step>

    ### Edit the affected page
    Find the page under `docs/user/content/` (`(hosting)/getting-started/`, `(guide)/guide/`, `(hosting)/operations/`, `(guide)/contributing/`, `api/index.mdx`, `api/tokens.mdx`, or `(releases)/roadmap.mdx`) and update its prose. Never edit anything in `content/api/reference/` by hand - see [Regenerate the API reference](/howtos/regenerate-api-reference).

  </Step>
  <Step>

    ### Regenerate screenshots, where Chromium runs
    ```bash
    mise run //docs/user:screenshots -- --grep <names>   # the tests that show the changed page
    mise run //docs/user:screenshots                     # all of them
    ```
    To find the names, grep the specs for the route: `grep -n "/settings/users" docs/user/screenshots/*.spec.ts` gives the tests that open it. `--grep` is a Playwright pattern and matches part of a name, so `login` also catches `first-login`.

    The task rewrites the matching PNGs under `docs/user/public/screenshots/` against a `rezepte --demo` of its own on `:8080` (`RZP_SCREENSHOTS_PORT`; offset 0, `mise run ports` for this worktree's number), which runs beside `mise run demo`. If Chromium does not start on your machine, leave the existing PNGs untouched and say so in the commit message - see [Documentation sites](/architecture/docs). `mise run //docs/user:screenshots:check` reports drift (compares without updating) when you want to know whether the committed PNGs are stale without regenerating them. A green check does not prove them current: it passes anything under `maxDiffPixelRatio` (1%), and a word added beside a heading on a 1440x900 page stays below that. After a UI change, regenerate every screenshot that shows the changed page rather than trusting the check. The task then repaints the README images (`assets/readme/`) and the hero scenes (`docs/user/public/heroes/`) from the new PNGs, so those can change in the same run.

  </Step>
  <Step>

    ### Regenerate the API reference when the contract changed
    ```bash
    mise run //docs/user:openapi
    ```
    Run this whenever an endpoint, parameter or schema changed - see [Regenerate the API reference](/howtos/regenerate-api-reference) for what the task does.

  </Step>
  <Step>

    ### Review changed PNGs
    Read the changed files under `docs/user/public/screenshots/`, `docs/user/public/heroes/` and `assets/readme/` with the Read tool (agents: this is how you check a screenshot - never a browser extension, see [Verify UI with Playwright](/howtos/verify-ui)) and compare against the design system before committing. The screenshot suite retries a test once (the reason is in `docs/user/playwright.config.ts`) and loses one more often while another worktree's e2e runs, so a PNG can change for no reason of yours - read each diff rather than committing the batch.

  </Step>
  <Step>

    ### Commit docs with the feature
    Stage the changed content page, any regenerated PNGs and everything the reference regenerated under `content/api/reference/` in the same commit as the code change, not a separate docs commit.

  </Step>
</Steps>

<Callout type="info">

  CI checks only the API reference (`mise run //docs/user:openapi` then a diff check) - never the screenshots, because font rendering differs between macOS and Linux. A stale screenshot is caught by review, not by CI.

</Callout>
