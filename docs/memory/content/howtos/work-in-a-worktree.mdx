---
title: Work in a worktree
description: One worktree per feature, one port offset per worktree
---

<Callout type="warn" title="Hard rule">

  Feature work happens in a worktree created with `mise run worktree:new <name>`. Never hand-edit a port; `mise run ports` shows the map. See [Toolchain](/architecture/toolchain).

</Callout>

<Steps>
  <Step>

    ### Create the worktree

    ```bash
    mise run worktree:new <name>
    ```

    Creates `.claude/worktrees/<name>`, branched off `develop` as `feat/<name>`, and assigns it the lowest port offset not already in use by another live worktree (1-9). The offset is written to that worktree's `mise.local.toml`, under `[vars]`, and printed along with the rest of the port map. `cd` into the new directory and work there.

    Run from inside a Herdr pane (`HERDR_ENV=1`), it also opens the worktree as a Herdr workspace labeled `<name>`, linked to the repository's own, without moving focus. With `--move`, the pane that ran the task - usually the agent asked to open the worktree - moves into that workspace in place of the fresh shell, and focus follows it; the agent still has to `cd` into the worktree itself. Without Herdr this step is skipped, and a Herdr failure only warns, because the worktree is already there.

    An optional second argument names the branch; without it the branch is `feat/<name>`. `release:start` uses it for `release/vX.Y.Z` (see [Release](/howtos/release)).

  </Step>
  <Step>

    ### Read the port map

    ```bash
    mise run ports
    ```

    Prints this worktree's offset and every port derived from it. Run it whenever you need a number for a browser tab, a `curl`, or another tool that needs one spelled out.

    | Service | Port at offset 0 |
    |---|---|
    | Go API (`RZP_BACKEND_PORT`) | 8060 |
    | Vite dev server (`RZP_FRONTEND_PORT`) | 9060 |
    | Demo instance (`RZP_DEMO_PORT`) | 8070 |
    | E2E instance (`RZP_E2E_PORT`) | 8050 |
    | Docs screenshot and OpenAPI instance (`RZP_SCREENSHOTS_PORT`) | 8080 |
    | Docs memory (`RZP_DOCS_MEMORY_PORT`) | 4000 |
    | Docs user (`RZP_DOCS_USER_PORT`) | 4001 |

    A worktree at offset *n* adds `n * 100` to each. The main checkout is always offset 0 and keeps exactly these numbers.

    Every instance a task starts for itself has a port of its own, so `mise run e2e` and `mise run //docs/user:screenshots` run while `mise run dev` and `mise run demo` stay up.

  </Step>
  <Step>

    ### Never commit `mise.local.toml`

    It is gitignored on purpose - it is where the offset lives, and it must stay local to the worktree. `.gitignore` covers it at every depth, so never force-add it with `git add -f`. If one slips into a commit anyway, `git rm --cached mise.local.toml` and keep it untracked.

  </Step>
  <Step>

    ### Hand the maintainer a demo

    Once a feature is done, or has reached a solid state worth trying, start a demo instance from the worktree and hand over its address before asking whether to merge:

    ```bash
    mise run demo
    ```

    Run it in the background, wait for `/healthz`, and give the URL from `mise run ports` (the demo line) together with the login `demo` / `demo1234` ([Demo mode](/features/demo-mode)). Green tests are not the hand-over: the maintainer clicks through the change on real data before it lands.

    Set the instance up so the change can be tried at once, not after a round of clicking to reach it:

    - **Data every demo should show belongs in the seed, not in the hand-over.** A feature that needs examples - recipes in some state, marks, links, tokens - gets them from the demo seed as part of the feature ([Demo mode](/features/demo-mode)), so every demo, screenshot run and later hand-over has them too. The hand-over only adds what the seed deliberately leaves out: a household switch the demo starts with off, like every instance does (public sharing, link previews, locked recipes), turned on with `PATCH /api/v1/settings`.
    - **Drive it through the HTTP API**, logged in with the same credentials the maintainer gets ([HTTP API](/architecture/api)): switch settings, create or look up the objects the change acts on (a public link, a token, a recipe in the state that shows the change), and read them back once to confirm the setup took - a public link that answers, a setting that reads back on.
    - **Pick the viewpoint the change is about.** When it shows one person's doing to another - a tasty mark, a lock, a member without a right - hand over the member's login too (`mila` / `mila1234`, `jonas` / `jonas1234`), or the public URL to open in a private window when it is what a stranger sees.
    - **Hand over direct links** to every page that shows the change, the account for each, and what to try; not only the root URL.

    A restarted demo starts fresh, so the setup is redone after every restart, including the ones that pick up a fix.

  </Step>
  <Step>

    ### Tidy the history, then merge

    Before the branch lands, give its history the shape you want to read later: one commit per finished change, no fixup trail. See [Commits](/conventions/commits). Squash while the branch is still yours - after the merge it is final.

  </Step>
  <Step>

    ### Clean up when the feature is done

    ```bash
    mise run worktree:remove <name>
    ```

    Removes the worktree with `git worktree remove`, then the whole directory, then the branch - but only once it is merged into `develop`; an unmerged branch is kept and named. It never passes `--force`: a worktree holding changes or untracked files you created makes git refuse and list them, and the decision stays yours. `mise.local.toml` is gitignored, so it never blocks the removal.

    Inside Herdr, it asks before closing the worktree's Herdr workspace, because closing it takes its panes with it. Run without a terminal - by an agent, or through a `!` command in Claude Code - it cannot ask, so it leaves the workspace open and prints the `herdr workspace close` command instead. `--close` is the explicit yes that works everywhere. An agent passes it only when the maintainer asked for the workspace to go.

    There is no separate offset registry to update. The live worktrees *are* the register - `worktree:new` finds a free offset by reading `mise.local.toml` out of each one still on disk, so removing the worktree frees its offset immediately, and nothing can go stale.

    IntelliJ writes `.idea/` back into a worktree it still had open after the worktree is gone. `worktree:new` treats a directory holding nothing but `.idea/` as that residue and clears it, so the name can be reused.

  </Step>
  <Step>

    ### The ceiling is nine

    Offsets run 1-9; the main checkout holds 0. A tenth simultaneous worktree has nowhere to go, and `worktree:new` fails with the list of who holds what rather than guessing. Remove one first.

  </Step>
</Steps>

## If you use the native `git worktree` tool directly

`mise run worktree:new` is the supported path because it names `develop` explicitly as the base branch and assigns the offset for you. The harness's own worktree tool defaults to `origin/main` (the release branch, far behind `develop`) unless `.claude/settings.json` sets `worktree.baseRef` to `head` - and even then, `head` is only correct when you happen to be standing on `develop` already. If you create a worktree any other way, check the base yourself, then run `mise run worktree:new` without a name from inside it: it creates nothing and only writes that worktree's `mise.local.toml` with the lowest free offset. It refuses in the main checkout, which keeps offset 0, and in a worktree that already has a `mise.local.toml`.
