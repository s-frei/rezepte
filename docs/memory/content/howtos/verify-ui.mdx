Run `mise run ports` for this worktree's number, see [Work in a worktree](/howtos/work-in-a-worktree). Traces and screenshots of failures land in `frontend/test-results/`.

    **A request missing from the run's output may still have arrived.** The instance logs at `info`, and the request log writes 2xx and 3xx at `debug`, so a request that succeeded leaves no line at all. To see every request, run `REZEPTE_LOG_LEVEL=debug mise run e2e`; the trace of the failing test holds the browser's side.

    **Run it from the repository root.** Inside `frontend/`, `mise run e2e` resolves to `//frontend:e2e`, which starts no instance and points the suite at the dev server's port, so every test fails on `page.goto` with `ERR_CONNECTION_REFUSED` - that is the task, not your change.

    The task refuses to start when the port is taken, and aborts if the binary dies while binding - otherwise a stranger's instance answers `/healthz` and every test that logs in fails against *their* data.

    ### Writing a test

    **Add a test per user-facing flow you touch**, in the `frontend/e2e/<area>.test.ts` file for its area. A change that sends mail runs the suite with `mise run mail:up` first ([Mail](#mail)).

    **Log in with the `login` helper from `frontend/e2e/helpers.ts`.** With the account's development password it posts `/api/v1/auth/login` through `page.request`, which shares the browser context's cookie jar, so the session cookie the response sets signs the page in; then it opens `/` and returns once `main` renders. That skips the form, the sheet and the full load after it, which halves the suite's time. `auth.test.ts` and `smoke.test.ts` drive the form itself. Any other password, or a refused right one, goes through the form and returns right after the click, so a test that expects an error reads it on the page; that path waits, on success, until the next page's `main` renders.

    **"Too many failed attempts" on the right password is a race between workers, never a lock worth testing.** The throttle counts an attempt when it begins, so the workers of one run signing `admin` in together lock the name until the first of them succeeds. Both paths of `login` retry a sign-in the throttle refused on the right password (`429`, or the message on the form).

    **A new file runs on both projects; add it to the `mobile` project's `testIgnore` (`frontend/playwright.config.ts`) when it has no phone path.** Files that never ask `isMobile` or `project.name`, or that set their own viewport, would only run the same steps again at 412px, and that second pass was half the suite's time. Take a listed file off the list the moment it grows a phone path, or its phone branch never runs.

    **To find what is slow, sum durations per test from the JSON reporter:** `PLAYWRIGHT_JSON_OUTPUT_NAME=<file> mise run e2e --reporter=json`, then `.results[].duration` per test, file and project. A test far above the median of about 2s is usually a fake clock ticking through minutes (`page.clock.runFor`, see [Cook timers](/features/cook-timers)) or an `expect` inside a loop: each call carries Playwright's bookkeeping, and one per pair of 300 cards took 40s where one `expect` on the collected failures takes none.

    ### Races on a slow runner

    **Wait for the state; never read the page once right after an action.** CI runs four workers on four cores, so the browser is slow there in a way a laptop never is: `expect(await count()).toBe(1)` reads the layout before the click has landed, where `await expect.poll(count).toBe(1)` waits for it. To catch one before CI does, run it under load: `mise run e2e <file> -g <name> --repeat-each=40 --workers=14`, and read `error-context.md` in `frontend/test-results/` of a failed repeat, which shows the page the test saw.

    The races a slow runner has turned up, each of them in the test or the page and none in the runner:

    - A helper that branches on what the page looks like right after a click: `openNewRecipe` asked whether the bottom nav was there, while an empty overview's own "New recipe" link had already taken it to the editor.
    - A helper that returns before what it started has finished: `signOut` now returns once the app has reached `/login`, since the app's logout still running under the next `login` landed a test on `/login` right after signing in.
    - A click on a button that something loading late pushes away: the password meter's label, which arrives 250 ms after typing, holds its line from the start.
    - A drop on a spot that itself moves the page (see the edge trap in [Images](/features/images)).
    - A step that takes longer than the 5s an `expect` waits by default (300 recipe cards in phone WebKit).

    Fonts are not one of them: the app ships Karla and Literata, so the Playwright image's fonts (its `sans-serif` is WenQuanYi Zen Hei) against the runner's DejaVu change nothing.

    **To reproduce CI locally, run the `mcr.microsoft.com/playwright` image in Docker with `--workers 4` and the CPU capped** (`docker update --cpus 1.2 <container>`). Two things make a Docker run lie: Playwright's `workers: '100%'` counts the host's cores even under `--cpuset-cpus`, and that many browsers in a Docker VM's memory get the binary OOM-killed, which reads as `ECONNREFUSED` and timeouts in every test after it.

    ### Traps of the whole suite

    **After a click that navigates, wait for the new page's heading before checking anything.** Otherwise the check can pass against the page still on screen: the overview card showed the same counts the list page was meant to show, so the test was green without looking at the list, and red when the list won the race and showed them three times. Sharding mostly hides this; it shows when the whole suite runs at once.

    **An instance-wide setting flipped in one file leaks into every test beside it**, because files run in parallel against one instance. Each setting has one owning spec file; [Testing](/conventions/testing#instance-wide-settings) lists them and how a test that flips one guards itself.

## Widths that matter

| Width | Stands for | Why it is in the list |
| --- | --- | --- |
| 320px | iPhone SE (1st gen) | The floor. Nothing may overflow here. |
| **360px** | **The default phone** | **Verify here.** A phone with display size or text scaling raised lands at 360-375px, and most Android phones report 360px. |
| 375px | iPhone SE 2/3, 13 mini | Second-narrowest common phone. |
| 390px | iPhone 13/14/15 | What agents reach for by default - and it is too forgiving. |
| 412px | Pixel 7 | What the repo's own Playwright projects use, so a green e2e run says nothing about 360px. |
| 1440px | Desktop | The `md:` branch of every component. |

A layout that only ever gets checked at 390px hides real bugs: a content-sized `inline-flex` row of 297px fits there with 5px to spare, so every screenshot looks right, and pushes out of its card at 360px. Sweep the widths whenever a row of controls looks tight.

## Look at it in German, with long content

English is the short language. German labels run longer, and a row that fits in English can squeeze a column next to it down to nothing while e2e, the English screenshots and a review all pass. So every UI change is also looked at in German before it is called done: `RZP_DEMO_LOCALE=de mise run demo` starts the demo with German accounts and sample recipes ([Demo mode](/features/demo-mode)).

Check it at 360px, with the longest realistic value of whatever the change adds - a long title, a long time phrase, a long name - and in cook mode at its largest type size. When a row runs out of room, that is a design question to raise, not something to squeeze until it fits.

Layout variants are compared on the real page too: inject each one into the running demo with `page.evaluate` in a [probe](#running-a-probe) and screenshot it at 1280px, 360px and 320px. A mockup built by hand misses the app's own type and spacing, and with them the phone breakage the comparison is for.

## Scrollbars are hidden in screenshots

Playwright starts Chromium with `--hide-scrollbars`, so no probe screenshot shows a scrollbar, and a macOS headless run shows only thin overlay ones even without that flag. A scrollbar that takes room - Windows, or macOS set to always show them - is what runs square over a rounded popup's border when the element that scrolls is not the one that rounds. For anything that scrolls inside a rounded frame, launch with `ignoreDefaultArgs: ['--hide-scrollbars']` and force a wide one in the page: `* { scrollbar-color: auto !important; scrollbar-width: auto !important } ::-webkit-scrollbar { width: 15px; background: red }` (the app's own `scrollbar-color` otherwise wins over `::-webkit-scrollbar`). The fix that holds: the frame clips (`overflow-hidden` with its radius), and the body inside it scrolls.

## A test that has never run is not a test

Run a suite the moment you write it. A test that has never executed is not evidence of anything - it asserts against the UI its author imagined, and the first real run is where you find out. When a locator and the app disagree, establish which of the two is wrong before "fixing" either; a green suite bought by loosening a locator tests nothing.

Two locator facts this repo will otherwise cost you twice: the user menu is a Bits UI dropdown of `menuitem`s on desktop and a sheet of real buttons on phones (`signOut` in `e2e/helpers.ts` knows the difference, and returns once the app has reached `/login`), and the select trigger is a plain `<button>` with an aria-label, not a `combobox`. A username filtered with `getByRole('listitem')` also matches a svelte-sonner toast, which renders as an `li` too.

## Check the empty state, not just the seeded one

The demo data is the *comfortable* case. Seeded ingredient groups carry short names, so their name field shows a short value and looks fine; a **new** group's field falls back to its placeholder, "Name this group…", which needs 140px, and only an empty state shows whether its row leaves it that much.

So exercise the states the fixture does not cover:

- **Empty / just created:** placeholders instead of values, a list with one entry, a form with nothing filled in.
- **One versus many:** singular labels ("1 ingredient", not "1 ingredients"), the last row of a list, a list with a single item where an action is disabled.
- **Long content:** a recipe title that wraps, a group name that fills the field.

A placeholder is invisible to the usual truncation check, because `scrollWidth` measures the *value*, not the placeholder. Measure it against the rendered font instead:

```ts
const cs = getComputedStyle(input);
const ctx = document.createElement('canvas').getContext('2d')!;
ctx.font = `${cs.fontStyle} ${cs.fontWeight} ${cs.fontSize} ${cs.fontFamily}`;
const fits = input.getBoundingClientRect().width >= ctx.measureText(input.placeholder).width;
```

## Measure, do not eyeball

A screenshot shows *that* something looks off, never *why*, and it cannot tell 4px of overlap from a rendering artifact. Drive the page with a throwaway Playwright script and assert on geometry - the numbers are the evidence, and they survive being pasted into a commit message:

```ts
// scratch probe, run through `mise run demo` (demo/demo1234 on :8070 by default, RZP_DEMO_PORT)
const info = await page.evaluate(() => {
	const el = document.querySelector('[role="radiogroup"]')!;
	const box = el.closest('section')!;           // the container it must fit inside
	const cs = getComputedStyle(box);
	const inner = box.getBoundingClientRect().right - parseFloat(cs.paddingRight);
	return {
		overflow: Math.round(el.getBoundingClientRect().right - inner),   // > 0 means it sticks out
		pageScroll: document.documentElement.scrollWidth,                 // > innerWidth means the page scrolls sideways
		clipped: [...el.querySelectorAll('span')]
			.filter((s) => s.scrollWidth > s.clientWidth + 1)
			.map((s) => s.textContent)                                    // truncated labels
	};
});
```

Three assertions catch most layout bugs:

- **Fits its container:** `element.right <= container.right - paddingRight`. Compare against the parent's content box, never against the viewport - an element can sit inside the screen and still break out of its card.
- **No sideways scroll:** `document.documentElement.scrollWidth <= window.innerWidth`.
- **Nothing truncated:** `scrollWidth <= clientWidth` on every text node that matters.

For stacking bugs (something hidden behind a fixed bar), `document.elementFromPoint(x, y)` names the element that actually paints there, and `getComputedStyle` gives you `zIndex`, `position` and `backdropFilter` of both sides.

## What Playwright cannot do

Headless Chromium lacks a few things the app depends on, and each has a stand-in. A test that ignores the gap passes for the wrong reason.

- **No software keyboard.** Shrink the viewport to the keyboard's height to stand in for it (`frontend/e2e/auth-sheet.test.ts`). Check a field against its scroll container's box, never with `toBeInViewport`: it counts an element clipped by its scroller as in view. Scroll the container away from the field before the resize, because focusing alone scrolls a field into view natively. Allow about 1px in a geometry check, since Chromium rounds the scroll offset `scrollIntoView` sets to whole pixels.
- **A mouse is not a finger.** A mouse pointer ignores `touch-action`, so a swipe or drag test sends real touches through CDP `Input.dispatchTouchEvent` and runs on the mobile project only. Long-press needs `Input.synthesizeTapGesture` with a `duration` (`longPress` in `frontend/e2e/helpers.ts`); touch events alone never trigger it, and it only fires on Chromium on macOS ([Images](/features/images)).
- **Time is `page.clock`.** Install it before the first navigation, then move it with `runFor` or `fastForward` ([Cook timers](/features/cook-timers)).
- **No push service and no permission prompt.** Headless Chromium reports `Notification.permission` as `denied` even with the permission granted and has no `PushManager` subscription, so a test that needs push stubs both with `page.addInitScript` (`frontend/e2e/cook-timers.test.ts`, `frontend/e2e/install.test.ts`).
- **One instance serves every file.** Files run in parallel against it, so an instance-wide setting that one file flips leaks into the others ([Instance-wide settings](/conventions/testing#instance-wide-settings) lists each setting's owning file).
- **Content that arrives late moves what is under the pointer.** A click on a control that a late label, image or list pushes away lands on the moved element, so the page reserves the space from the first frame (the end-to-end tab lists the races it caused).

## Mail
A change that sends mail is verified against Mailpit, not against a mocked sender. `docker-compose.test.yaml` runs a pinned Mailpit that accepts any login; `mise run mail:up` and `mail:down` start and stop only it, and its SMTP and inbox ports follow the worktree's offset ([Toolchain](/architecture/toolchain)). The inbox is a browser tab at the URL `mail:up` prints, where the HTML part and the plain-text part can be looked at side by side.

- **e2e:** `mise run e2e` hands the suite `MAILPIT_URL` and `MAILPIT_SMTP_PORT`; `frontend/e2e/mail.test.ts` configures mail through the UI, reads the delivered messages through `frontend/e2e/mailpit.ts`, and skips without Mailpit, the way the OIDC specs skip without Dex. A green run without Mailpit proves nothing about mail. Mail settings are instance-wide and the suite runs its files in parallel, while `mode: 'serial'` orders tests only within one file, so a flow that needs a mail sent goes into `mail.test.ts` rather than a file of its own: a second file writing the settings would race the test there that points mail at a dead port, both ways, and a "no mail arrived" check could pass for the wrong reason. Another spec that needs a state of the mail settings answers `GET /api/v1/settings` with `page.route` instead of writing them.
- **Demo:** when `rzp_mailpit_up` (`mise/lib/instance.sh`) finds Mailpit and `RZP_DEMO_MAIL` is not `off`, `mise/tasks/demo.sh` signs in as the demo owner after the health check and `PUT`s Mailpit to `/api/v1/settings/mail` (security `none`, from `rezepte@example.com`), only while the instance's mail source is still `none`, and prints the inbox URL; a setup link mailed to `noah`, the demo's invited member, lands there. It is best-effort: a failed call prints "demo: mail not configured" and the demo runs without mail. It never sets `REZEPTE_SMTP_*`, because the environment would lock the mail card the demo exists to click through ([Email](/features/email)).
- **Public URL:** `demo.sh` sets `REZEPTE_PUBLIC_URL` to the demo's own URL unless the caller did, with or without Mailpit, since a mailed link has to be absolute; without Mailpit the card stays open to a server entered by hand, and an unreachable one shows its error.
- **Preview:** `mise run //service:mail-preview` renders every sample mail, in English and German, into an ignored `out` folder and prints the path of its index page; open it to see a letter's HTML and text without a send. A new mail needs a `mail.Samples` entry, or `TestEveryTemplateHasASample` fails.
- **Screenshots:** the screenshot and OpenAPI tasks set `RZP_DEMO_MAIL=off`, so the pictures show the unconfigured card whether or not Mailpit runs; the specs that need a configured one configure it themselves.

## Motion, frame by frame

A screenshot after an animation says nothing about the animation, and one taken during it lands wherever the clock happened to be. Stop the clock instead: CDP's `Animation.setPlaybackRate` with `0` holds every CSS transition, CSS animation, Web Animation (Svelte's `transition:` and `animate:` run as those) and view transition at its first frame as it starts. Run the action, list `document.getAnimations()` (each one's target, `getComputedTiming()` delay, duration and easing), then for each point of the run set every animation's `currentTime` after `pause()` and take a screenshot; lay the frames side by side to read them as one strip. `finish()` them and put the rate back to `1` afterwards.

```ts
const cdp = await page.context().newCDPSession(page);
await cdp.send('Animation.enable');
await cdp.send('Animation.setPlaybackRate', { playbackRate: 0 });
await page.locator('#overview-filters').click();
for (const t of [0, 40, 80, 120, 200]) {
	await page.evaluate((t) => document.getAnimations().forEach((a) => (a.pause(), (a.currentTime = t))), t);
	await page.screenshot({ path: `test-results/filters-${t}.png` });
}
```

- Look at the first frame and the last: a first frame that already shows the end state, or a last one that is not the resting layout, is a jump the eye sees.
- Run it twice, with `reducedMotion: 'no-preference'` and `'reduce'` on the context. Under `reduce` the list should come back empty for anything that moves.
- A hover left over from the click (the card under the pointer) shows up in the list too; read the targets, not just the count.
- One theme change per page: after a frozen theme circle is finished, its `::view-transition-group(root)` stays behind, `data-theme-transition` is never removed and the `html` takes every later click. To look at a control's own motion without the circle, delete `Document.prototype.startViewTransition` first; `setTheme` then recolors at once.
- Creating an API token through its dialog crashes Chromium's renderer whenever the playback rate is below 1 (0 and 0.05 both), with or without the new row's motion; make the token through the API and freeze the clock for the revoke instead.
- A Svelte transition driven by `tick` instead of `css` (the editor's `reveal`) stops when its animation is paused, so a frozen clock shows it stuck at its first frame. Slow the clock instead (`playbackRate: 0.05`) and take screenshots in real time.
- A Svelte `in:` transition with a `delay` runs the delay as an animation of its own and starts the real one only after it, so a frozen clock never shows it (the login's error line): slow the clock for it too.
- Freeze the clock only once the setup has settled: typing into a form right before the action leaves its focus transitions running (a floating label halfway up), and the frozen first frame shows them as if the action had caused them.
- Frames of a refused sign-in (the login's error line): each failed attempt counts toward the login throttle, so fail with a fresh unknown name every time.
- A request held open with `page.route` (to see "Saving …") is not canceled by `unrouteAll`: the held save went on to the instance and created the recipe. Keep the `Route` and `abort()` it before unrouting.
- A probe that must not change the demo's data blocks every non-GET `/api` request with `page.route` except `/api/v1/auth/`, and creates its context with `serviceWorkers: 'block'`: the app's service worker (built in the demo and the e2e binary) fetches on the page's behalf, and those requests pass `page.route` by, so a save went through to the instance.

## Running a probe

The root `demo` task with a command after `--` starts the built binary with demo data on `:8070` by default (`RZP_DEMO_PORT`; login `demo` / `demo1234`, twelve recipes with images), runs the command against it and stops it afterwards - the fastest way to a realistic page:

```bash
cd frontend
mise run //:demo -- bun run test-results/probe.ts
```

`//:demo` is that task's full name: the call runs in `frontend/`, where the probe has to run, and there a bare `demo` is not found. A probe that needs a signed-in page at phone width:

```ts
// frontend/test-results/probe.ts
import { chromium } from '@playwright/test';
const browser = await chromium.launch();
const context = await browser.newContext({ baseURL: `http://localhost:${process.env.RZP_DEMO_PORT}`, viewport: { width: 360, height: 780 } });
const page = await context.newPage();
// signs in the way `login` in frontend/e2e/helpers.ts does: page.request shares the context's cookies
await page.request.post('/api/v1/auth/login', { data: { username: 'demo', password: 'demo1234' } });
await page.goto('/');
await page.getByRole('main').waitFor();
await page.screenshot({ path: 'test-results/probe-360.png' });
await browser.close();
```

The probe lives in `frontend/test-results/`, which is git-ignored: a script outside `frontend/` cannot import `playwright`, because Bun resolves packages from the script's own directory. The command runs where it was typed, with the instance at `http://localhost:${process.env.RZP_DEMO_PORT}`. Playwright empties `frontend/test-results/` at the start of every `mise run e2e`, probes and their screenshots included, so keep the probe's source elsewhere and copy it in before a run.

Without a command, `mise run demo` keeps that instance up until Ctrl-C, which is what you want when you are clicking through it yourself rather than driving it. Both forms build the binary first through the task's `depends`, and `REZEPTE_DATA_DIR=<dir> mise run demo` keeps its recipes across restarts instead of seeding a throwaway directory.

Two traps worth knowing:

- Every `mise run e2e` empties `frontend/test-results/` before it runs - Playwright clears its output directory - and takes every probe and screenshot in it along. Anything there that has to outlive the next test run (a mockup someone approved, a probe to run again) gets copied somewhere else first.
- Both `mise run e2e` and `mise run demo` refuse to start on a busy port. Without that guard a stale process answers `/healthz` instead, and every test that logs in fails with "That username or password is wrong." while the ones that do not log in pass. That failure shape means the port, not your change: check `lsof -nP -iTCP:<port> -sTCP:LISTEN`, with the port from `mise run ports`.

## Handing a running demo to the owner

Whenever an instance is left running for the owner to look at - after a change, at a checkpoint, after a restart - the message ends with this block, in the owner's language, never with the URL or the login inside a sentence. It is the one part of the message they act on, so it has to be findable at a glance and complete without the prose around it:

```markdown
### Demo

| | |
|---|---|
| **URL** | http://localhost:8170 |
| **Login** | `demo` / `demo1234` |
| **Other accounts** | `mila` / `mila1234`, `jonas` / `jonas1234` |
| **Build** | `edef0152` on `feat/overview-tiles` |
| **Data** | 29 recipes, tasty marks from mila and jonas |
| **Runs** | in the background until you say stop |

**Look at:**
1. `/` at 360px, a card without a photo: the initials sit on the star's axis.
2. Hover a three-line title on desktop: the wave is whole under the last line.
```

- **URL** is the port from `mise run ports`, clickable, with the path when one page is meant.
- **Build** is the commit the binary was built from, and says "uncommitted" when it carries changes not yet committed - a demo started before the last edit shows the old code.
- **Data** names what was seeded beyond the twelve sample recipes, so the owner knows which cases the instance can show; a restart of `mise run demo` without `REZEPTE_DATA_DIR` starts from the twelve again.
- **Look at** lists the concrete checks, each a page or width and what should be true there - not "have a look". Leave it out only when nothing changed since the last handover.
- After every restart the block comes again, even if only the build changed.
