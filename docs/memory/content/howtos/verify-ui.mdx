## Widths that matter

| Width | Stands for | Why it is in the list |
| --- | --- | --- |
| 320px | iPhone SE (1st gen) | The floor. Nothing may overflow here. |
| **360px** | **The default phone** | **Verify here.** A phone with display size or text scaling raised lands at 360-375px, and most Android phones report 360px. |
| 375px | iPhone SE 2/3, 13 mini | Second-narrowest common phone. |
| 390px | iPhone 13/14/15 | What agents reach for by default - and it is too forgiving. |
| 412px | Pixel 7 | What the repo's own Playwright projects use, so a green e2e run says nothing about 360px. |
| 1440px | Desktop | The `md:` branch of every component. |

A layout that only ever gets checked at 390px hides real bugs: a content-sized `inline-flex` row of 297px fits there with 5px to spare, so every screenshot looks right, and pushes out of its card at 360px. Sweep the widths whenever a row of controls looks tight.

## A test that has never run is not a test

Run a suite the moment you write it. A test that has never executed is not evidence of anything - it asserts against the UI its author imagined, and the first real run is where you find out. When a locator and the app disagree, establish which of the two is wrong before "fixing" either; a green suite bought by loosening a locator tests nothing.

Two locator facts this repo will otherwise cost you twice: the user menu is a Bits UI dropdown of `menuitem`s on desktop and a sheet of real buttons on phones (`signOut` in `e2e/helpers.ts` knows the difference), and the select trigger is a plain `<button>` with an aria-label, not a `combobox`. A username filtered with `getByRole('listitem')` also matches a svelte-sonner toast, which renders as an `li` too.

## Check the empty state, not just the seeded one

The demo data is the *comfortable* case. Seeded ingredient groups carry short names, so their name field shows a short value and looks fine; a **new** group's field falls back to its placeholder, "Name this group…", which needs 140px, and only an empty state shows whether its row leaves it that much.

So exercise the states the fixture does not cover:

- **Empty / just created:** placeholders instead of values, a list with one entry, a form with nothing filled in.
- **One versus many:** singular labels ("1 ingredient", not "1 ingredients"), the last row of a list, a list with a single item where an action is disabled.
- **Long content:** a recipe title that wraps, a group name that fills the field.

A placeholder is invisible to the usual truncation check, because `scrollWidth` measures the *value*, not the placeholder. Measure it against the rendered font instead:

```ts
const cs = getComputedStyle(input);
const ctx = document.createElement('canvas').getContext('2d')!;
ctx.font = `${cs.fontStyle} ${cs.fontWeight} ${cs.fontSize} ${cs.fontFamily}`;
const fits = input.getBoundingClientRect().width >= ctx.measureText(input.placeholder).width;
```

## Measure, do not eyeball

A screenshot shows *that* something looks off, never *why*, and it cannot tell 4px of overlap from a rendering artifact. Drive the page with a throwaway Playwright script and assert on geometry - the numbers are the evidence, and they survive being pasted into a commit message:

```ts
// scratch probe, run through `mise run demo` (demo/demo1234 on :8070 by default)
const info = await page.evaluate(() => {
	const el = document.querySelector('[role="radiogroup"]')!;
	const box = el.closest('section')!;           // the container it must fit inside
	const cs = getComputedStyle(box);
	const inner = box.getBoundingClientRect().right - parseFloat(cs.paddingRight);
	return {
		overflow: Math.round(el.getBoundingClientRect().right - inner),   // > 0 means it sticks out
		pageScroll: document.documentElement.scrollWidth,                 // > innerWidth means the page scrolls sideways
		clipped: [...el.querySelectorAll('span')]
			.filter((s) => s.scrollWidth > s.clientWidth + 1)
			.map((s) => s.textContent)                                    // truncated labels
	};
});
```

Three assertions catch most layout bugs:

- **Fits its container:** `element.right <= container.right - paddingRight`. Compare against the parent's content box, never against the viewport - an element can sit inside the screen and still break out of its card.
- **No sideways scroll:** `document.documentElement.scrollWidth <= window.innerWidth`.
- **Nothing truncated:** `scrollWidth <= clientWidth` on every text node that matters.

For stacking bugs (something hidden behind a fixed bar), `document.elementFromPoint(x, y)` names the element that actually paints there, and `getComputedStyle` gives you `zIndex`, `position` and `backdropFilter` of both sides.

## Running a probe

`mise run demo -- <command>` starts the built binary with demo data on `:8070` by default (login `demo` / `demo1234`, twelve recipes with images), runs the command against it and stops it afterwards - the fastest way to a realistic page:

```bash
mise run demo -- bun run /tmp/probe.ts
```

Without a command, `mise run demo` keeps that instance up until Ctrl-C, which is what you want when you are clicking through it yourself rather than driving it. Both forms build the binary first through the task's `depends`, and `REZEPTE_DATA_DIR=<dir> mise run demo` keeps its recipes across restarts instead of seeding a throwaway directory.

Two traps worth knowing:

- Both `mise run e2e` and `mise run demo` refuse to start on a busy port. Without that guard a stale process answers `/healthz` instead, and every test that logs in fails with "That username or password is wrong." while the ones that do not log in pass. That failure shape means the port, not your change: check `lsof -nP -iTCP:<port> -sTCP:LISTEN`, with the port from `mise run ports`.
- A locked screen does not stop Chromium. If a run does nothing, look at the port before the browser.
