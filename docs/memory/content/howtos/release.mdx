---
title: Release
description: Maintainer-only checklist for cutting a release
---

<Callout type="warn" title="Maintainer only">

  Agents never merge to `main`, push, tag or open pull requests on their own (see [Commits and branches](/conventions/commits)). This how-to is for the maintainer running the steps by hand, or for an agent explicitly asked to walk through them one at a time with confirmation before anything irreversible.

</Callout>

<Steps>
  <Step>

    ### Gate `develop`
    ```bash
    mise run check && mise run build
    ```
    Run on `develop`, both green.

  </Step>
  <Step>

    ### Update the docs
    Update [Roadmap](/roadmap) for anything the release finishes or starts, and any `docs/user/` page the release changes user-visible behaviour for. Commit on `develop` like any other docs change.

  </Step>
  <Step>

    ### Only after changing the release workflow: dispatch a test run

    Not an every-release step. Run it before the first release, and whenever this release changed `.github/workflows/release.yml` — it has to happen before the merge, because a dispatch runs the workflow as it exists on the ref it is started from, so the branch carrying the change is the only place the change can be tested.

    Run the workflow from the Actions tab, selecting that branch and one of the two offered image tags (`dev` or `edge`). It publishes the image under that one tag and creates no GitHub release, so the build, the push and the multi-architecture step are exercised without spending a version number. A dispatch from a tag is rejected by the job's first step - see [Releases](/architecture/releases).

  </Step>
  <Step>

    ### First release only: make the package public

    A GHCR package does not inherit the repository's visibility: it is created private by the first push to it, and every anonymous `docker pull` fails with an authentication error until it is set public once, under the repository's Packages settings.

    Do it as soon as the package exists - which is the moment the dispatch above first pushes - and before the release is announced. Left until after the tag push, the documented quick start is broken for everyone between the release going out and the setting being changed.

  </Step>
  <Step>

    ### Merge into `main`
    ```bash
    git checkout main
    git merge --ff-only develop
    ```
    Fast-forward only - `main` never gets its own merge commits or direct commits (see [Commits and branches](/conventions/commits)).

  </Step>
  <Step>

    ### Push `main` and wait for CI
    ```bash
    git push origin main
    ```
    This push also triggers `.github/workflows/pages.yml`, which CI calls once its gate is green; it rebuilds `docs/user/` and publishes it to `https://s-frei.github.io/rezepte` - see [Documentation sites](/architecture/docs). There is no separate opt-in: every push to `main` republishes the docs site. A documentation fix between releases needs none of this: dispatch the `Pages` workflow from `main` or `develop` instead.

    Waiting for that run before tagging is a convenience, not a safety net: `.github/workflows/release.yml` runs the same gate itself and publishes nothing if it fails. Pushing the tag straight after the branch only means two gate runs on the same commit.

  </Step>
  <Step>

    ### Tag and push the tag
    ```bash
    git tag vX.Y.Z
    git push origin vX.Y.Z
    ```

  </Step>
  <Step>

    ### Let CI publish
    The tag push above starts `.github/workflows/release.yml`, which builds and pushes `ghcr.io/s-frei/rezepte` for `linux/amd64` and `linux/arm64` and attaches the platform binaries to the GitHub release — see [Releases](/architecture/releases). Nothing is built by hand.

    If the `binaries` job fails after `release:publish` has started, the GitHub release already exists and re-running the job fails with "release already exists". Delete the release first (`gh release delete vX.Y.Z`) and then re-run; the tag and the pushed image can stay as they are.

  </Step>
  <Step>

    ### Back up before deploying
    Back up the existing deployment's data directory before rolling out the new image - see the user docs' `operations/data-and-backup` page (`docs/user/content/operations/data-and-backup.mdx`).

  </Step>
</Steps>

<Callout type="info">

  Nothing else is bumped: no version file is maintained yet, and the huma API version in `internal/httpserver/api.go` (currently `0.1.0`) stays as-is until the API is public.

</Callout>
