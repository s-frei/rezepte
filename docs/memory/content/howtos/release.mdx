<Callout type="warn" title="Maintainer only">

  Agents never merge to `main`, push, tag or open pull requests on their own (see [Commits and branches](/conventions/commits)). This how-to is for the maintainer running the steps by hand, or for an agent explicitly asked to walk through them one at a time with confirmation before anything irreversible.

</Callout>

<Steps>
  <Step>

    ### Only after changing the release workflow: dispatch a test run

    Not an every-release step. Run it before the first release, and whenever this release changed `.github/workflows/release.yml` — a dispatch runs the workflow as it exists on the ref it is started from, so the branch carrying the change is the only place the change can be tested. Pick `dev` or `edge` as the image tag; nothing else is published. See [Releases](/architecture/releases).

  </Step>
  <Step>

    ### First release only: make the package public

    A GHCR package is created private by its first push, and every anonymous `docker pull` fails until it is set public once, under the repository's Packages settings. Do it as soon as the dispatch above has created the package, before the release is announced.

  </Step>
  <Step>

    ### Start the release
    ```bash
    mise run release:start
    ```
    In the main checkout, on a clean `develop`. It prints how many breaking, `feat` and other commits came since the last release and names the breaking ones, suggests the version (breaking → major, `feat` → minor, else patch; `v1.0.0` without a tag; after a release candidate the release it previews, unless what landed since needs a bigger step) and asks; pass a version (`mise run release:start v1.2.0`) to skip the question; a version smaller than the suggestion gets a warning, not a refusal, because a `!` commit may break nothing anyone runs. `--dry-run` shows the suggestion, the branch and worktree it would open and the draft page, and creates nothing. It opens `release/vX.Y.Z` in its own worktree, installs its dependencies, and drafts `docs/user/content/changelog/<version>.mdx`.

  </Step>
  <Step>

    ### Write the release notes

    In the release worktree, turn the draft into the page - usually an agent does, following [Write release notes](/howtos/write-release-notes), and the maintainer reads the result. Update [Roadmap](/roadmap) and any `docs/user/` page the release changes. Commit: `docs(changelog): write the vX.Y.Z release notes`.

  </Step>
  <Step>

    ### Finish the release
    ```bash
    mise run release:finish
    ```
    In the release worktree. It refuses a page that still has the draft marker, `FILL IN`, a missing field, or no upgrade notice despite breaking commits; stops if `develop` moved on meanwhile (`git rebase develop` in the release worktree, then run it again), if the tag already exists, if a local `main` is diverged or checked out in a worktree, or if `origin/develop` or `origin/main` has commits the release lacks - before the gate and once more after it; runs `mise run check`; fast-forwards `develop`, then `main`; tags `main` with an annotated `vX.Y.Z`; removes the worktree and the branch. All of it is local. `mise run release:finish --dry-run` runs every check except `mise run check`, then lists the exact git commands it would run and the push; it exits 0 only when the release is ready. If a step fails in a real run, the message lists what already happened and the remaining commands, quoted so they can be pasted.

  </Step>
  <Step>

    ### Push
    ```bash
    git push --atomic origin develop main vX.Y.Z
    ```
    `--atomic` pushes all three or none: without it a rejected `develop` would still let `main` and the tag through, and the tag alone starts the release. The `main` push publishes the docs (CI, then `.github/workflows/pages.yml`). The tag starts `.github/workflows/release.yml`: gate, image, binaries, and the GitHub release, whose body `release:publish` builds from the changelog page once that page is live.

    If the `binaries` job fails after `release:publish` has started, the GitHub release already exists and re-running fails with "release already exists": `gh release delete vX.Y.Z`, then re-run. If it timed out waiting for the docs, re-run it once the Pages run is green.

    The local gate is `mise run check`; CI also builds and runs the end-to-end tests. A failure only CI finds leaves a pushed tag that published nothing, and the fix costs a new patch version. The careful path, for a release that touches the build: push `develop` and `main` first, wait for CI, then push the tag.

  </Step>
  <Step>

    ### Back up before deploying
    Back up the existing deployment's data directory before rolling out the new image — see the user docs' `operations/data-and-backup` page (`docs/user/content/operations/data-and-backup.mdx`).

  </Step>
</Steps>
