---
title: Add a database migration
description: Sequential goose migrations, embedded and applied at startup
---

<Callout type="warn" title="A released migration is never edited">

  Every tagged release, a release candidate included, has installed databases behind it. goose records each migration's version in those databases and never runs it again, so a column, an index or a table added to a migration that already shipped never reaches them: the next binary starts against a schema that lacks it. Every schema change is therefore a new, additive migration with a working `Down`.

</Callout>

<Steps>
  <Step>

    ### Create the file
    `service/internal/db/migrations/NNNN_short_name.sql` with the next four-digit number. Never reuse or renumber.

  </Step>
  <Step>

    ### Write Up and Down
    ```sql title="0003_example.sql"
    -- +goose Up
    ALTER TABLE users ADD COLUMN display_name TEXT;

    -- +goose Down
    ALTER TABLE users DROP COLUMN display_name;
    ```
    Wrap statements containing semicolons (triggers) in `-- +goose StatementBegin` / `-- +goose StatementEnd`.

  </Step>
  <Step>

    ### Regenerate sqlc
    sqlc reads the migrations as schema: `mise run //service:generate`.

  </Step>
  <Step>

    ### Test
    `dbtest.Open(t)` applies every migration, so existing tests cover it. Add a test if the migration transforms data.

  </Step>
</Steps>

<Callout type="warn">

  Migrations run automatically when the binary starts. A failing migration stops the service; test locally with `mise run //service:dev` before committing.

</Callout>
