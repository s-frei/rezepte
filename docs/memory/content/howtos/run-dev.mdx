---
title: Run the app locally
description: Dev servers, builds and the check gate
---

<Steps>
  <Step>

    ### Install tools and dependencies
    ```bash
    mise trust && mise install && mise run setup
    ```

  </Step>
  <Step>

    ### Start the dev servers
    ```bash
    mise run dev
    ```
    Go API on `http://localhost:8060` (restarts on `.go` changes), SvelteKit on `http://localhost:9060` (proxies `/api` and `/images` to Go, so the browser sees one origin and the API's origin check still matches) - both by default; run `mise run ports` to see the numbers for this worktree, see [Work in a worktree](/howtos/work-in-a-worktree).

    Log in as `admin` / `admin1234` at `http://localhost:9060/login` (or the frontend port `mise run ports` gives this worktree); the task prints the pair as it starts. `REZEPTE_ADMIN_PASSWORD` has no default in the binary - an empty `users` table without it is `ErrAdminPasswordRequired` and the service refuses to start, see [Users and auth](/features/users-and-auth) - so `//service:dev` defaults it to the username with `1234` appended, like every bootstrapped account here ([Development credentials](/conventions/dev-credentials)); a value set in the environment still wins. That password creates the instance owner on the very first start and is read again only by `rezepte --reset-superadmin-password`.

    For an instance that already has recipes in it, `mise run demo` starts the built binary with the twelve samples on the demo port and keeps it up until Ctrl-C (`demo` / `demo1234`) - no dev server, no HMR, but nothing to fill in either ([Demo mode](/features/demo-mode)).

    Uploads land in `$REZEPTE_DATA_DIR/images/<recipeId>/` (default `./data/images/`, git-ignored with the database, see [Architecture overview](/architecture/overview)); delete that directory together with `rezepte.db` when resetting local data.

  </Step>
  <Step>

    ### Run the docs
    ```bash
    mise run docs
    ```
    `mise run docs` starts the memory site on `http://localhost:4000` and the user docs on `http://localhost:4001/rezepte` by default - run `mise run ports` for this worktree's numbers, see [Work in a worktree](/howtos/work-in-a-worktree). The base path on the user docs is set unconditionally so dev matches production - see [Documentation sites](/architecture/docs). Both sites listen on `0.0.0.0` and both `next.config.mjs` files pass this machine's own IPv4 addresses as `allowedDevOrigins`, so a phone on the same network can open them: without that, Next answers the HTML but 403s every `/_next/*` chunk, and the page renders once and never hydrates.

  </Step>
  <Step>

    ### Try the app with sample data
    ```bash
    cd service && REZEPTE_DATA_DIR=$(mktemp -d) mise exec -- go run ./cmd/rezepte --demo
    ```
    (or the built binary, `./bin/rezepte --demo`, from a temporary `REZEPTE_DATA_DIR`). Seeds twelve sample recipes with placeholder photos and, with no `REZEPTE_ADMIN_PASSWORD` set, a `demo` / `demo1234` admin - log in at `http://localhost:8060`. Unlike `mise run dev` above, this runs the binary directly without setting `REZEPTE_ADDR`, so it always binds `:8060` regardless of this worktree's offset. See [Demo mode](/features/demo-mode).

  </Step>
  <Step>

    ### Build the production binary
    ```bash
    mise run build
    ./service/bin/rezepte
    ```
    The frontend is built into `service/internal/web/dist` and embedded.

  </Step>
  <Step>

    ### Run the gate
    ```bash
    mise run check
    ```

  </Step>
</Steps>

<Callout type="info">

  Use `mise tasks --all` to list every task, including package-local ones like `//service:test`.

</Callout>

## Known issues

<Callout type="warn">

  - If `bunx playwright install chromium` times out downloading, run it once from a normal terminal. `mise run setup` is idempotent and will pick up the cached browser on the next run.
  - A stale process holding the port is what makes an e2e run look broken rather than blocked: the binary cannot bind, the other app answers `/healthz`, and every test that logs in fails with "Benutzername oder Passwort ist falsch" while the rest pass. The task pre-checks the port and says so; `mise run ports` gives this worktree's numbers.
  - The screenshot suite is flaky by nature - `docs/user/playwright.config.ts` retries once because a run tends to lose a single, different test to a 30s timeout, and running it alongside another worktree's e2e makes that more likely. Read the diff before committing regenerated PNGs. The placeholder frames [Documentation sites](/architecture/docs) describes are for environments without a working Chromium, such as CI.

</Callout>
