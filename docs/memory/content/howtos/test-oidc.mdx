---
title: Test OIDC sign-in
description: Running the OIDC login feature against Dex, the test identity provider
---

[OIDC login](/features/oidc) needs a real identity provider to sign in against - no unit test can stand in for the browser leaving Rezepte, authenticating elsewhere, and coming back. Dex (`ghcr.io/dexidp/dex`) fills that role locally: a self-hosted provider that starts from a static config in seconds and needs no account of its own.

## Start it

```bash
mise run oidc:up
```

`mise/tasks/oidc/up.sh` renders `mise/oidc/dex.yaml.tmpl` into `.oidc/dex.yaml` (gitignored, regenerated every run) with this worktree's ports substituted in, then starts `docker-compose.test.yaml`. It prints the configuration Rezepte needs:

```
oidc:up: issuer http://localhost:$RZP_DEX_PORT/dex - Dex: sign in as demo@, mila@ or jonas@example.com, password <name>1234
  REZEPTE_PUBLIC_URL=http://localhost:$RZP_BACKEND_PORT REZEPTE_OIDC_ISSUER=http://localhost:$RZP_DEX_PORT/dex REZEPTE_OIDC_CLIENT_ID=rezepte REZEPTE_OIDC_CLIENT_SECRET=rezepte-test-secret REZEPTE_OIDC_NAME=Dex
```

Start `mise run dev` with that line to sign in against Dex by hand with the Sign-in card locked to the environment, or save the same issuer, client ID and secret in Settings → Sign-in to keep the card editable. `mise run e2e` and `mise run demo` need neither: they clear any exported `REZEPTE_OIDC_*` and save Dex themselves (below). `mise run oidc:down` stops it. Both tasks touch only Dex, never Mailpit ([Email](/features/email)).

Four accounts are seeded, passwords by the [development-credential](/conventions/dev-credentials) rule:

- `demo@example.com` / `demo1234`, `mila@example.com` / `mila1234` and `jonas@example.com` / `jonas1234` match, name for name, the accounts [demo mode](/features/demo-mode) seeds, so linking one to the matching demo account is the obvious thing to try by hand.
- `gast@example.com` / `gast1234` has no demo account behind it, for the not-connected and setup-link cases.
- Their Dex subjects are fixed (`userID: demo`, `mila`, `jonas`, `gast`), so a re-rendered config never changes who they are.
- In the demo, demo and mila connect by hand: sign in at Dex from the demo account's profile. jonas is pre-linked by the seed at the issuer `--demo-oidc-issuer` names, so `jonas@example.com` / `jonas1234` signs in right away ([Demo mode](/features/demo-mode) owns how).
- The e2e suite splits the accounts so its two Dex files never race for one identity: `frontend/e2e/oidc.test.ts` (desktop project) signs in as mila and gast, `frontend/e2e/oidc-mobile.test.ts` (mobile project) as jonas. The e2e instance is not a demo, so nothing is pre-linked there.

## Automatic pickup

`mise run e2e` and `mise run demo` both ask `rzp_dex_up` (`mise/lib/instance.sh`) whether Dex answers its discovery document and, when it does, save Dex as the provider through `PUT /api/v1/settings/sign-in` after `/healthz` (`rzp_oidc_configure`, as the owner: `admin` for e2e, `demo` for the demo) - `Dex` as the provider name. Neither ever sets `REZEPTE_OIDC_*`, which would lock the Sign-in card; both always set `REZEPTE_PUBLIC_URL`. e2e fails when Dex answers but saving it does not; the demo carries on without it. Without Dex running nothing is saved, and `frontend/e2e/oidc.test.ts` skips itself (it asks `GET /api/v1/auth/oidc` in a `beforeEach` and calls `test.skip` when `enabled` is false). Nothing has to be told which case it is in:

```bash
mise run oidc:up && mise run e2e     # OIDC specs run
mise run oidc:down && mise run e2e   # OIDC specs skip, the rest is unaffected
```

With Dex up, `mise run demo` prints which Dex user goes with which demo account. `RZP_DEMO_OIDC` picks the demo's provider: `dex` (the default, when Dex answers), `stub` or `off`. The user-docs screenshot tasks set `stub`: `demo.sh` starts `mise/lib/stub-issuer.ts`, a `Bun.serve` on a free port that answers only discovery, passes its origin as `--demo-oidc-issuer` and saves it with an empty name, so every screenshot shows the same neutral "Continue with single sign-on" and jonas's "Signs in with …" line whether or not Dex happens to be running. Nothing behind the stub signs anyone in.

The stub's port is random, so the issuer on the Sign-in page would change every run, and the redirect URI there follows the worktree's port offset. The `sign-in-card` screenshot (`docs/user/screenshots/settings.spec.ts`) therefore rewrites both texts to fixed addresses in the DOM before the shot, rather than giving the stub a port from the map: any port tied to the offset would still differ between worktrees and fail `screenshots:check` in one of them. A screenshot that shows the issuer or the redirect URI must do the same.

## Once a release

Dex proves the protocol, not every provider's quirks. Before a release, sign in with a real Google account by hand once - `docs/memory/content/features/oidc.mdx` names the exact routes and cookies the flow uses.

## Why it is this way

A container rather than a fake HTTP server in Go: `service/internal/oidc` already depends on `go-oidc` doing real discovery and JWKS verification against whatever issuer is configured (the environment or Settings → Sign-in), and a hand-rolled stand-in would test that package against a shape no real provider has. Dex speaks the protocol for real, for the cost of a container most contributors already have.

Static passwords with fixed subjects, not a database migration or an admin API call: the four accounts exist the moment the container is up, and a subject that never changes means a test asserting on `(iss, sub)` never has to look one up first.
