title: Releases
description: How a version tag becomes a published image and a set of binaries
---

Rezepte ships two artifacts from one commit: a multi-architecture image at `ghcr.io/s-frei/rezepte` and a self-contained binary per platform attached to the GitHub release. Both are produced by `.github/workflows/release.yml`, which has two entry points. A pushed three-part version tag (`v[0-9]*.[0-9]*.[0-9]*`) — the shape `docker/metadata-action` can translate, so a `v1.0` never reaches a build that would fail at push with no image tag — builds and publishes both artifacts. A manual `workflow_dispatch` run publishes only the image, under one of the two throwaway tags the `image_tag` choice offers — `dev` or `edge` — and creates no release; it exists to exercise the pipeline — the build, the push, the multi-architecture step — without spending a version number, which matters because the workflow otherwise cannot be run before it matters: the first tag push would be its first execution. A dispatch has to be started from a branch, and the `image` job's first step fails the run when it was started from a tag: rebuilding a released tag would republish that version at a new digest with no release behind it. Which branch is free, deliberately — dispatching from the branch that carries a change to `release.yml` is the only way to test that change, and the run then publishes that branch's build under `dev` or `edge`. Nothing else publishes: a push to `main`, to `develop` or to any other branch produces no image and no release on its own, and only a version tag produces a version.

Both entry points run the gate first. `release.yml` calls `.github/workflows/check.yml` as its first job and `image` carries `needs: check`, so a tag whose commit fails the gate publishes nothing at all — no image, no release, nothing to retract. That costs a second full gate run on a commit CI has usually just checked, and it is worth it because the two failures are not comparable: a flaky gate on this path leaves a tag that can be deleted and re-pushed with nobody outside the repository the wiser, while an ungated tag puts a broken build on GHCR under `latest`, where the recovery is a burnt version number and a package nobody can un-pull. The gate also guards a manual dispatch, unconditionally: making it conditional needs an `always()` expression on `image` to let a skipped `check` through, and a dispatch happens rarely enough that the wait costs less than that expression costs to keep correct.

## From tag to artifacts

The git tag carries the `v` prefix and the image tags do not. `docker/metadata-action` performs that translation: a non-prerelease tag such as `v1.4.2` yields `1.4.2`, `1.4` and `latest`, while a prerelease tag such as `v1.5.0-rc1` yields only `1.5.0-rc1` — no bare `1.5` and no `latest`, because `latest` pointing at a release candidate would be worse than no `latest` at all. There is no version file: the tag is the only place a version is written.

A `workflow_dispatch` run has no git tag to translate, so the `type=semver` patterns produce nothing — which holds because the guard step keeps a dispatch off a tag ref in the first place; from a branch there is no version for them to read. A `type=raw` rule keyed on the dispatch's `image_tag` input takes over, producing that one tag and nothing else. Two things keep a dispatch away from `:latest`, which is what the README and the user docs tell people to pull: the `flavor` input forces `latest=false` rather than leaving `latest=auto` to decide, and `image_tag` is a `type: choice` of `dev` and `edge`, so the raw rule cannot be handed the literal string `latest` either — `flavor` suppresses only the automatic one. `enable` on the raw rule and the override on `flavor` both key off `github.event_name == 'workflow_dispatch'`, so a tag push is unaffected: the raw rule stays disabled and `latest=auto` still governs it.

The `image` job builds `linux/amd64` and `linux/arm64` from one Dockerfile without emulation. The two build stages pin to `$BUILDPLATFORM` and the Go build takes its target from `ARG TARGETARCH`, which works because `modernc.org/sqlite` is pure Go and the build is already `CGO_ENABLED=0`. The frontend stage is platform independent and BuildKit runs it once for both.

The `binaries` job needs the `image` job, so the two run in sequence rather than in parallel: the release binaries are only built once the image has pushed successfully. It also carries `if: github.event_name == 'push'`, so a `workflow_dispatch` run skips it entirely — there is no tag for `release:publish` to attach a release to, and it would either fail or invent a release for a ref nobody tagged. It runs three tasks and nothing else — `//frontend:install:deps`, `release:binaries`, `release:publish`.

`mise run release:binaries` (`mise/tasks/release/binaries.sh`) builds the SPA once through its `depends`, then cross-compiles `linux/amd64`, `linux/arm64`, `darwin/arm64` and `darwin/amd64` by calling `//service:build:only` with `GOOS` and `GOARCH` set. That split is why `//service:build` and `//service:build:only` both exist: the compiler flags stay written once, in `service/mise.toml`, and the frontend is not rebuilt four times. Output is `dist/`, holding only the archives and `checksums.txt`; `service/bin/rezepte` is removed afterwards, because the last cross-compile would otherwise leave a binary for a foreign platform at the path `mise run build` owns.

`mise run release:publish` (`mise/tasks/release/publish.sh`) creates the GitHub release from `dist/`, with the body `release:notes` builds from the release's changelog page (see [Versions and the changelog](#versions-and-the-changelog)). It refuses an empty `dist/`, and it passes `--prerelease` when the tag contains a hyphen, so a `v1.5.0-rc1` does not become `/releases/latest` while the image job is withholding `:latest` from the same tag.

The frontend install in this job is `//frontend:install:deps`, not `//frontend:install`: the job runs no browser test, and it runs after the image has already been pushed, so a Playwright download failing there would leave a tag with a published image and no release at all.

macOS binaries are cross-compiled and unsigned. The user documentation says so, because Gatekeeper blocks the first launch.

The version reaches the binary the same way regardless of how it was built: `-ldflags "-X main.version=..."`. `service/mise.toml` sets it from `REZEPTE_VERSION` (falling back to `git describe --tags --always` with the `v` stripped), and the image sets it from the `REZEPTE_VERSION` build arg, which the `image` job wires from `steps.meta.outputs.version` — the tag's version on a push, and the dispatch's `image_tag` input on a dispatch, since the raw rule is then the only tag `docker/metadata-action` has to derive a version from. Either way it is read back through `rezepte --version` and the `/healthz` endpoint.

## Versions and the changelog

Tags are the only record of versions; there is no version file. `mise/lib/release/version.ts` reads the last `v*.*.*` tag and the commit subjects since it and suggests the next version: a subject with `!` before its colon bumps major, a `feat` bumps minor, anything else patch. After a prerelease tag the suggestion is the release it previews, even with no commits since, which is how a candidate gets promoted. The suggestion counts from the nearest tag, but a release's page and its upgrade check count from the last release (`classificationBase`): a `v2.0.0` after `v2.0.0-rc1` still lists, and still demands the upgrade notice for, a breaking change that shipped in the candidate. The first release is `v1.0.0`. The API version in `service/internal/httpserver/api.go` (`0.1.0`) is deliberately not tied to it and stays until the API is public.

Every release has one page in the user docs, `docs/user/content/changelog/<version>.mdx`, listed newest first in `changelog/meta.json`. It is plain MDX with two extra frontmatter fields the docs schema knows: `date`, shown under the description, and `upgrade`, rendered by `page.tsx` as a **Before you upgrade** callout and prepended to the page's Markdown export so the LLM view keeps it. The page is written once, at release time, from a draft `release:start` generates; `release:finish` refuses to tag an unfinished page (`mise/lib/release/changelog.ts` holds the checks, `bun test` covers them through `mise run test:release`).

The GitHub release body is not written separately. `release:notes` builds it from the page's frontmatter — the upgrade notice, the description and two links, one to the page and one to its Markdown for LLMs — and `release:publish` passes it to `gh release create --notes-file`. Because the body links the page, `release:publish` first polls the page URL (every 30 seconds, at most 20 minutes): the `main` push publishes the docs through CI and Pages at the same time as the tag runs this workflow, and a release that links a page that is not there yet would be the first thing everyone sees. Waiting in the task keeps both workflows as they are; on timeout nothing is created and the job is re-run.

`release:start` and `release:finish` follow git flow's release-branch model without its tool: `release/vX.Y.Z` lives in its own worktree (`worktree:new` with a branch argument), and finishing fast-forwards `develop` and then `main` (`git fetch . develop:main`, so `main` never needs a checkout) instead of merging, which keeps `main` linear. `release:finish` checks before it runs the gate, and again right after it, that `develop` has not moved on, that the tag is free, that a local `main` is neither diverged nor checked out in any worktree (`mainBlocker`), and that the release contains everything on `origin/develop` and `origin/main` (`remoteBlocker`). A failure at `git fetch . develop:main` or at the tag would leave `develop` carrying a release that `main` and the tag do not, and a push that `origin` rejects in part would publish a tag without its branches — which is also why the printed push is `git push --atomic`. Neither task pushes. The git steps of `release:finish` are a list (`mise/lib/release/steps.ts`) that a real run executes and `--dry-run` prints, so the preview cannot drift from what runs; `release:start --dry-run` stops before `worktree:new` and prints the draft instead.

## The build context is an allowlist

`.dockerignore` starts with `*` and re-includes the individual files and directories the build reads. Docker matches these patterns against full paths, so a path can be re-included under an excluded parent — which is what makes an allowlist expressible at all.

## Building and running locally

`mise run docker:build` builds the image for the current machine only, with the version stamped the same way `//service:build:only` stamps it — `REZEPTE_VERSION`, or `git describe --tags --always` with the `v` stripped when that variable is unset. `mise run docker:demo` then runs that image on the worktree's demo port with `docker run --rm`, so every run seeds a fresh database. It exists to exercise the *image* — distroless, the nonroot UID, the entrypoint, the version stamp — which the rest of the demo tooling cannot, because `mise run demo` and the screenshot tasks run the binary directly.

`docker-compose.yaml` is not part of that path. It is the users' file: rendered into the documentation, validated by `mise run docker:compose:check` (which CI runs), and nothing else. The demo does not run through it: a demo overlay has to replace every key the base service defines, so it would prove nothing about the file it layers over while costing an override file, an anonymous-volume teardown and a second place to keep the file list.

**The documentation renders that file rather than copying it.** Both getting-started pages carry `<include lang="yaml">…/docker-compose.yaml#compose</include>`, so there is one copy of the YAML and no way for a page to drift from what Rezepte is run with. The include reaches outside the documentation app, which works because `docs/user/next.config.mjs` sets Turbopack's `root` to the repository root: the plugin reads the file itself, but registers it with the bundler, and a narrower root makes the bundler reject it. The same setting stops Turbopack searching above the repository for a root. The `#compose` region — `# #region compose` markers in the file — keeps the repository-facing header comment out of what users see.

**The OCI labels are split by who wins, not by what changes.** A `--label` on the build command overrides a Dockerfile `LABEL`, and `docker/build-push-action` passes everything `docker/metadata-action` emits — which includes `title`, `description` and `url` as well as `version`, `revision` and `created`. Anything the action produces would therefore be overridden on exactly the published images and survive only on locally built ones, so the curated `title`, `description` and `url` are set through the action's `labels:` input in the workflow. The Dockerfile keeps `source`, `documentation` and `licenses`: `documentation` because the action has no equivalent, `source` and `licenses` because repeating them costs nothing and makes an image built locally or in CI still say where it came from — GHCR links a package to its repository through `source`.

**The image declares its own healthcheck, and the binary is what runs it.** `HEALTHCHECK` in the Dockerfile calls `/rezepte --healthcheck`, which reads `REZEPTE_ADDR`, probes that instance's `/healthz` over the loopback interface and exits non-zero when it does not answer. The indirection is forced: the runtime image is distroless, so there is no shell and no `curl` for a healthcheck to call, and the only executable in the container is the binary itself. The flag returns before the data directory or the database is touched, because it runs as a second process beside the one that owns them. `--start-period` is 30s, covering the first start, where migrations and demo seeding run before the server answers. Anyone who runs the image gets this, `docker-compose.yaml` included, which is why that file carries no `healthcheck` block of its own.

**`docker-compose.yaml` orders service keys `image`, `restart`, `volumes`, `environment`, `ports`:** what runs and how it behaves over time, then the service from the inside out. It is a file strangers copy, so the order is the one that answers their questions in the order they ask them. The multi-platform build stays CI's job: it is one `docker buildx build --platform linux/amd64,linux/arm64 .` and a local task would only be a second place to keep that platform list correct. The Dockerfile stays at the repository root, not under `service/`, because the build context has to be the repository root — `service/` alone would not see `frontend/`.

## Why it is this way

**An allowlist names what the build reads; a denylist would have to name everything it must not read, forever.** `.claude/worktrees/` holds a full repository copy per worktree, and any directory like it — a cache, a scratch tree, an editor's state directory — is exactly the kind of path a denylist maintainer has no reason to think of before it exists. An allowlist carries no such blind spot: a path that is not listed is never read, whatever it is called and whenever it appears. The cost is symmetric and deliberate: a genuinely new build input must be added by hand, so a missing one breaks the build loudly instead of an unwanted one shipping quietly.

**The tag is the trigger, so publishing stays deliberate.** A push to `main` is not automatically a release; the maintainer decides by tagging, and the gate then decides whether that tag ships. This also keeps the image tags derivable from one source, with no version file to drift from it.

**Packaging lives in mise tasks, not in the workflow.** [GitHub Actions conventions](/conventions/github-actions) requires it, and the effect is that the whole release is reproducible locally: `mise run release:binaries` builds exactly what CI uploads, and `mise run release:publish` is the same command CI runs to create the release.

## Rejected

- **Docker Hub.** Costs an account, stored credentials and anonymous pull rate limits for users. GHCR authenticates with the workflow's own token.
- **Publishing `develop` as `:edge` on every push.** No identified consumer, and a second moving tag to reason about. `edge` survives as one of the two tags a manual dispatch may publish under, which is a different thing: it moves only when someone dispatches a run.
- **QEMU for arm64.** `docker/setup-qemu-action` plus emulated builds is the usual recipe and is far slower than cross-compiling a language that cross-compiles for free.
- **Extracting the release binaries from the image build** with an export stage. One source of truth for the build flags, but it cannot produce the macOS binaries, so the task is needed regardless and the extraction only adds a second mechanism.
- **A build matrix for the binaries.** Four runners each rebuilding the same platform-independent SPA, plus artifact upload and download to reassemble the release.
- **Coarse allowlist entries** — `!frontend` and `!service` whole. Survives a new config file, but a new cache directory inside those trees re-enters the context silently, which is the same blind spot one level down.

## Limits

- GHCR packages do not inherit repository visibility. The first push creates a private package and every anonymous pull fails until the maintainer sets it public once; [Release](/howtos/release) carries the step.
- `/healthz` reports the version without authentication, which lets anyone who can reach the instance match it to known vulnerabilities — accepted deliberately, because it is also what makes the version readable without shell access.
