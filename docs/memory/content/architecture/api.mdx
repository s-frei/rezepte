Base path `/api/v1`. OpenAPI 3.1 at `/api/v1/openapi.json`, interactive docs at `/api/v1/docs`.

## Version

The API has no version of its own. `info.version` in the served document is the build version - the one `-X main.version` stamps into the binary, `rezepte --version` prints and `/healthz` reports (see [Releases](/architecture/releases)): `httpserver.New` sets it from `WithVersion` once the options have run, and a build without it says `"dev"` in both places. So there is nothing to bump by hand; the release tag is the one place a version is written. `/api/v1` in the path is a different thing, the compatibility line: it changes only if the API ever has to serve two incompatible shapes side by side.

The committed copy, `docs/user/public/openapi.json`, cannot carry the build version: between releases that is `git describe --tags --always`, which changes with every commit, and CI regenerates the document and runs `git diff --exit-code` (see [Regenerate the API reference](/howtos/regenerate-api-reference)). It carries the version of the release it is published with instead:

- `docs/user/scripts/fetch-openapi.ts` keeps the committed `info.version` when it regenerates (`openapi-version.ts`).
- `release:start` stamps the release's version into it on the release branch, and `release:finish` refuses a release whose document says anything else (`mise/lib/release/openapi.ts`).
- The user docs are published from `main`, which only ever holds release commits, so the published reference always names the release it describes.

## Interactive docs

`/api/v1/docs` is Scalar, rendered by huma from the same OpenAPI document, and it wears the app's colors. Its sidebar names each operation by its route (`operationTitleSource: "path"`) rather than by its summary, which is both what the generated reference in `docs/user/` does and what keeps the entries to one line each.

- `service/internal/httpserver/scalar_theme.css` maps the design tokens in `frontend/src/app.css` onto Scalar's `--scalar-*` variables; it is embedded into the binary and handed to Scalar as `customCss`, because huma renders the page itself and its CSP permits inline styles only. The values are copied rather than imported, so `scalar_theme_test.go` reads `app.css` and fails on any color in `scalar_theme.css` that is not one of its `--color-*` tokens.
- Only the colors are ours. Typography and layout stay Scalar's, and so do the six semantic colors for HTTP methods and status codes - the app's palette is warm and narrow, and would leave GET, POST and DELETE hard to tell apart. Webfonts are out of reach in any case: huma's CSP declares no `font-src`.
- `DocsRendererConfig` turns off the API client (`hideClientButton`) and the assistant (`agent.disabled`), both of which lead away from the contract and into Scalar's product; `hideModels` drops the schema list. The page keeps its own light/dark choice rather than following the app's, because huma leaves no room for a script that could read it.

The document also declares its tags, in `apiTags` in `service/internal/httpserver/api.go`. An operation's own `Tags` field names a tag but does not declare it, and both consumers need the declaration: the Scalar page titles and describes its sections from it, and the generated reference in `docs/user/` takes each folder's title, description and position from it, falling back to a bare tag name for one it does not find. `TestEveryTagIsDeclared` fails on a tag used without a declaration and on a declaration nothing uses; the order they are declared in is the order both renderings present.

The app points at the Scalar page rather than duplicating it: Settings → API carries a card for every signed-in member ([API tokens](/features/api-tokens)). The version it shows comes from `/healthz`, the same number as `info.version` and the one place an operator can read it without signing in.

## Authentication

Two authenticators, declared as two OpenAPI security schemes (`session`, `token`) via `httpserver.WithSecuritySchemes(auth.SecuritySchemes())`; the Scalar page at `/api/v1/docs` therefore carries an Authorize control for both. See [API tokens](/features/api-tokens) for the token half.

<Tabs items={['Cookie session', 'API token', 'Public']}>
  <Tab value="Cookie session">

    Operations with `Security: auth.SessionSecurity` require the `rezepte_session` cookie. The middleware resolves it to a `user.User` available via `auth.UserFrom(ctx)`. Missing or expired sessions yield `401`.

  </Tab>
  <Tab value="API token">

    Operations with `Security: auth.Protected(scopes...)` also accept `Authorization: Bearer <token>` carrying every listed scope, resolved to the same `user.User` via `auth.UserFrom(ctx)`. A missing scheme, an invalid token or a missing scope are covered in [API tokens](/features/api-tokens).

  </Tab>
  <Tab value="Public">

    Operations without `Security` are public: login, `GET /healthz`, the setup-link, password-reset, email-confirmation and OIDC entry points under `/api/v1/auth`, `GET /api/v1/public/shares/{token}`, `GET /public-images/…` (see [Public shares](/features/public-shares)) and `GET /link-preview/…` (see [Link previews](/features/link-previews)) - the last two outside `/api/v1` and deliberately without authentication, since the stranger or the crawler behind either has no session to carry. Living outside `/api/v1` says nothing about security: `GET /images/…` and `GET /avatars/…` declare `auth.Protected` like any other operation, and `/mcp` declares `auth.TokenOnly`, so it never accepts a session cookie - only a bearer token carrying `recipes:read` reaches it at all (see [MCP](/features/mcp)).

  </Tab>
</Tabs>

The contract routes under `/api/v1/` - the Scalar docs page, the OpenAPI document and the schema registry - are not public either: they require a session of any role or a valid API token of any scope, enforced in front of the mux rather than by `auth.Middleware`, which only ever sees huma operations. [Users and auth](/features/users-and-auth) owns that guard, the prefix rule it derives from and the redirect-versus-`401` split it applies to a browser.

The two steps of the OIDC flow answer a browser navigation with a `303`, never JSON, so they are `*huma.StreamResponse` operations whose stream hands the request to `(*oidc.Login).start` and `.callback`, which write the redirect and their cookies themselves. Start is a mutating request under `/api/`, so `checkOrigin` refuses a cross-origin form post exactly as it refuses a cross-origin `fetch`; the callback is a `GET`, which the provider reaches as a top-level navigation. [OIDC](/features/oidc) owns the flow.

Read the committed copy, `docs/user/public/openapi.json`, or the reference generated from it in `docs/user/content/api/reference/`, one folder per tag. ### Rules the document does not show

- **A `GET` cannot live under `/recipes/{id}/…`.** `GET /recipes/by-slug/{slug}` claims that prefix in `net/http.ServeMux`, and a second three-segment `GET` there is equally specific, which the mux has no tiebreaker for ([Public shares](/features/public-shares)). `POST` and `PUT` there do not collide. Hence `POST /recipes/{id}/share-link` (also because each call signs a new token), `GET /comments?recipeId=` and `GET /shares/by-recipe/{recipeId}`.
- **A bearer header on a session-only operation is `403`, not `401`.** `auth.Middleware`'s bearer branch answers `403` `API tokens cannot use this operation` before it checks the token's validity at all, while the same route answers `401` to a request with no credential ([API tokens](/features/api-tokens)).
- **An admin-only operation tells a member's token from a member's session.** A non-admin session gets `403` `admin role required` from `requireAdmin`; a token whose owner is not an admin never reaches it, because the bearer branch treats a demoted owner as an invalid credential and answers `401` `api token invalid or expired`. Rank then binds a token exactly as it binds a session; [Users and authentication](/features/users-and-auth) owns the matrix.
- **`PATCH /users/{id}` takes several fields in one body.** Every field is optional and at least one is required (`422` `nothing to change`, as on `PATCH /auth/me/profile`). Every value is validated, and the owner-only profile check runs, before the first write, so a refusal writes nothing; they are then applied in the order role, `canSharePublicly`, `email`, profile, password.
- **A username is trimmed** on create and on login, so a whitespace-only one is a `422` at `body.username`.
- **The token list is instance-wide.** `GET /tokens` returns every token in the table to every admin, including one whose issuer has since been demoted and which therefore no longer authenticates.
- **`GET /recipes`'s `sort` is an `enum`.** Any other value is a `422` on `query.sort`; absent or empty (`?sort=`) takes the `updated` default before validation runs. `page` and `limit` outside their bounds are `422`s from huma too: the clamping in `List` ([Recipes and search](/features/recipes)) only serves in-process callers, which an HTTP request never reaches with such a value.
- **Recipe input arrays are never `null`.** huma makes every Go slice nullable unless the field says `nullable:"false"`, and a `null` would pass `minItems` and replace what is stored with nothing. So `tags`, `ingredientGroups`, `steps` and each group's `ingredients` carry `nullable:"false"` on `recipe.Input` (`internal/recipe/recipe.go`): `null` is a `422` and "none" is `[]`. `references` and `times` stay nullable, since REST keeps them optional.
- **`recipe.Input` requires every field but `sourceName` and `editPolicy`.** A script on an API token or an MCP client that does not know `sourceName` must keep working, so it is optional and absent is the same as `null`. An absent `editPolicy` keeps the stored one ([Editing rights](/features/editing-rights)).
- **Recipe validation beyond the schema is located exactly.** A reference that cannot be resolved is a `422` at `body.steps[i].references[j].<field>` ([Ingredient references](/features/ingredient-references)), a step time at `body.steps[i].times[j].<field>` ([Step times](/features/step-times)), an import error at its path inside the zip ([Import and export](/features/import-export)).
- **huma cannot mark a `$ref` nullable.** An optional object field is absent rather than `null` - `Comment.author` for a former member, `Share.createdBy` outside an admin's list.
- **Upload size is enforced by middleware, not by huma.** `Operation.MaxBodyBytes` is not applied to multipart bodies, so `LimitUpload` answers `413` on a declared `Content-Length` above the upload limit before the body is read; a chunked or lying client is cut off mid-parse by `http.MaxBytesReader` and surfaces as a `422` on `body` ([Images](/features/images)). The zip import avoids multipart and streams to a temp file under its own cap.
- **File routes check ids before building a path.** `/images/…` and `/avatars/…` run every id through `image.IsID`, the UUID alphabet, so no component escapes its directory, and anything that is not an existing file is `404` ([Images](/features/images)).
- **A person on the wire is joined, not copied.** `createdBy`, `updatedBy` and `tastyBy` on a recipe are people (`{id, username, displayName, color, avatarId}`) joined from `users` on every read, so a rename reaches every card at once ([Recipes and search](/features/recipes)). Everywhere the API means a login name the key says `username`; `displayName` is only ever the name shown. `avatarId` rides on every person-shaped body a 20 px circle or larger draws from; `/authors` and a share's creator feed 12 to 16 px color dots and carry none. The client builds the file URL from `id` and `avatarId`; the API carries no paths.
- **No parameter names whose mark it is.** Favorites, tasty marks, comment watermarks and `Card.favorite` come from the session alone ([Favorites](/features/favorites)).

## CSRF

Cookies are `SameSite=Lax`, and a cross-origin write under `/api/` - or any cross-origin request to `/mcp` - is refused on top of that - [Users and auth](/features/users-and-auth) owns the rule and what passes it. The refusal is a `403` `application/problem+json` body: `{"title":"Forbidden","status":403,"detail":"origin not allowed"}`.

## Errors

RFC 9457 `application/problem+json`:
```json
{ "title": "Unprocessable Entity", "status": 422, "detail": "validation failed",
  "errors": [{ "location": "body.username", "message": "expected length >= 1" }] }
```
The frontend maps this to `ApiError` in `src/lib/api/client.ts`. A `401` from any call - except the login call itself, except `GET /auth/me`, and except while already on `/login` - clears the SPA's session state and redirects to `/login?next=<original path>` so the user lands back where they were after signing in again. `GET /auth/me` is excluded (mutating calls such as `PATCH /auth/me` still redirect) because its only caller is the root `+layout.ts` guard, which already redirects via SvelteKit's `redirect()` on a `401`; calling `goto()` from the client as well would race that in-flight navigation.

The login operation also answers `429` with a `Retry-After` header when the username is locked after too many attempts, and every operation that hashes or checks a password answers `503` with `Retry-After: 1` when too many password checks are already running or waiting; [Users and auth](/features/users-and-auth) owns both rules.

## Why it is this way

Routing is `net/http.ServeMux` with method patterns (`GET /api/v1/recipes/{id}`). The standard library matches on method and path parameters, which is all the routing this API does, so there is no third-party router to learn or to keep current.

huma sits on top of that mux through the `humago` adapter, configured once in `service/internal/httpserver/api.go`, and it is there because it replaces work rather than wrapping it: handlers are typed `func(ctx, *Input) (*Output, error)`, the input validation comes from struct tags, the OpenAPI 3.1 document and the Scalar page are generated from the registered operations, and errors are rendered as RFC 9457 problem documents. The [token-authenticated REST API](/features/api-tokens) and the [MCP server](/features/mcp) both start from that document, so every operation is described the moment it exists instead of being documented afterwards. Adding a dependency at all follows [Go conventions](/conventions/go).

The typed shape is also a layering rule. The input and output structs *are* the contract, so they live in the feature package beside the service that fills them (`service/internal/recipe/handler.go`) rather than in a shared transport package.

**Every route a client, a crawler or an agent calls is a huma operation**, so the document lists all of them and cannot drift from the mux.

- That includes the ones that write bytes: an operation answering a file returns a `*huma.StreamResponse` whose body reaches the `http.ResponseWriter` through `humago.Unwrap` - `image.JPEG` (`service/internal/image/file.go`) for the four JPEG routes, the export's zip, `/mcp` handing the request to the SDK's handler - and declares its `200` by hand in `Responses`, since a stream has no schema to infer (`image.JPEGResponses`).
- Only two kinds of route stay on the mux: the SPA shell and its assets, which are not API, and the contract routes huma hangs there itself.
- A public operation's `404` is `httpserver.PublicNotFound`, huma's problem body without the `$schema` link a stranger could not follow.

## Rejected

- **An API version bumped separately from the application.** A second number nobody keeps in step: it would have to be raised by hand on every API change, and a breaking change is already marked by the commit convention and announced by the release that ships it ([Commits and branches](/conventions/commits)).
- **Writing the build version into the committed document.** Every commit would change it and fail CI's regenerate-and-diff check. Stripping `info.version` instead is not open either: OpenAPI requires it.
- **Plain stdlib without huma.** Nothing to learn beyond `net/http`, but the validation and the OpenAPI document would have to be hand-written, and both are load-bearing for the roadmap rather than decoration.
- **chi, echo or gin.** A router in place of the one already in the standard library; method patterns cover what this API asks of routing.
- **Spec-first generation (oapi-codegen, ogen).** Handlers generated from a hand-written specification. Code-first keeps the contract in the same file as the code that serves it, which is fewer places to keep honest.
- **Route tables on this page.** A copy of every route, field and status code that nothing checks against the generated document drifts from it; the document is the list, and the feature pages hold the reasons.

## Limits

- The Scalar page at `/api/v1/docs` fetches its JavaScript bundle from `unpkg.com` at runtime - huma's `DocsRendererScalar` pins the version and an SRI hash, and the CSP allows that one origin - so the page needs outbound internet access to render. The OpenAPI document itself is served from the binary and works offline.
