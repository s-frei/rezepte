Base path `/api/v1`. OpenAPI 3.1 at `/api/v1/openapi.json`, interactive docs at `/api/v1/docs`.

## Interactive docs

`/api/v1/docs` is Scalar, rendered by huma from the same OpenAPI document, and it wears the app's colours. `service/internal/httpserver/scalar_theme.css` maps the design tokens in `frontend/src/app.css` onto Scalar's `--scalar-*` variables; it is embedded into the binary and handed to Scalar as `customCss`, because huma renders the page itself and its CSP permits inline styles only. The values are copied rather than imported, so `scalar_theme_test.go` reads `app.css` and fails on any colour there that is no longer one of its tokens.

Only the colours are ours. Typography and layout stay Scalar's, and so do the six semantic colours for HTTP methods and status codes - the app's palette is warm and narrow, and would leave GET, POST and DELETE hard to tell apart. Webfonts are out of reach in any case: huma's CSP declares no `font-src`.

Two of Scalar's own features are off in `DocsRendererConfig`, both of which lead away from the contract and into Scalar's product: the API client (`hideClientButton`) and the assistant (`agent.disabled`). `hideModels` drops the schema list. The page keeps its own light/dark choice rather than following the app's, because huma leaves no room for a script that could read it.

The app points at that page rather than duplicating it: Settings → API carries a card - open to every signed-in member, see [API tokens](/features/api-tokens) - with the base URL to copy, the endpoint and area counts read off the OpenAPI document, and links to `/api/v1/docs` and the document itself. The version beside them comes from `/healthz`, not from the document's `info.version`, which stays the fixed `"0.1.0"` of `huma.DefaultConfig`. Stamping the build version into the document would break a gate rather than improve it: the build version is `git describe --tags --always`, so it changes with every commit, while `docs/user/public/openapi.json` and the generated pages under `content/api/reference/` are checked in and CI regenerates both and runs `git diff --exit-code` (see [Regenerate the API reference](/howtos/regenerate-api-reference)). `/healthz` already publishes that number without authentication and is the one place an operator can read what is running, so the card asks it there.

## Authentication

The document also declares its tags, in `apiTags` in `service/internal/httpserver/api.go`. An operation's own `Tags` field names a tag but does not declare it, and both consumers need the declaration: the Scalar page titles and describes its sections from it, and the generated reference in `docs/user/` takes each folder's title, description and position from it, falling back to a bare tag name for one it does not find. `TestEveryTagIsDeclared` fails on a tag used without a declaration and on a declaration nothing uses; the order they are declared in is the order both renderings present.

Two authenticators, declared as two OpenAPI security schemes (`session`, `token`) via `httpserver.WithSecuritySchemes(auth.SecuritySchemes())`; the Scalar page at `/api/v1/docs` therefore carries an Authorize control for both. See [API tokens](/features/api-tokens) for the token half.

<Tabs items={['Cookie session', 'API token', 'Public']}>
  <Tab value="Cookie session">

    Operations with `Security: auth.SessionSecurity` require the `rezepte_session` cookie. The middleware resolves it to a `user.User` available via `auth.UserFrom(ctx)`. Missing or expired sessions yield `401`.

  </Tab>
  <Tab value="API token">

    Operations with `Security: auth.Protected(scopes...)` also accept `Authorization: Bearer <token>` carrying every listed scope, resolved to the same `user.User` via `auth.UserFrom(ctx)`. A missing scheme, an invalid token or a missing scope are covered in [API tokens](/features/api-tokens).

  </Tab>
  <Tab value="Public">

    Operations without `Security` are public. Today: `POST /api/v1/auth/login`, `GET /healthz`. `GET /images/…` is not one of them, even though it lives outside `/api/v1` - it is a plain mux route wrapped in `auth.RequireAuth`, so viewing a photo still requires a session or a token carrying `recipes:read`.

  </Tab>
</Tabs>

| Operation | Path | Notes |
|---|---|---|
| login | `POST /auth/login` | body `{username, password}`; sets cookie; returns the user |
| logout | `POST /auth/logout` | 204, clears the cookie |
| me | `GET /auth/me` | `{id, username, displayName, role, color}` |
| change-own-password | `PATCH /auth/me` | body `{currentPassword, password}`; 204; wrong `currentPassword` → `422` at `body.currentPassword`; ends every other session of the caller (see [Users and authentication](/features/users-and-auth)) |
| update-own-profile | `PATCH /auth/me/profile` | body `{displayName?, color?}`, at least one of them (`422` `nothing to change` otherwise); returns the user. Its own path rather than `PATCH /auth/me`, which is the password change and demands the current password - a rename has nothing to do with it. Every role may use it, on its own row only; an empty `displayName` falls back to the login name, a name over 64 runes is `422` at `body.displayName`, and a colour outside the `enum` is huma's own `422` before the handler runs |
| list-color-usage | `GET /auth/me/colors` | `{items: [{color, count}]}`, every palette colour in palette order, zeros included. Counts, never names: the picker has to mark a colour as taken, and a plain member may not list users. It sits under `/auth/me` because it describes what the caller may choose for themselves |

The contract routes under `/api/v1/` - the Scalar docs page, the OpenAPI document and the schema registry - are not public either: they require a session of any role or a valid API token of any scope, enforced in front of the mux rather than by `auth.Middleware`, which only ever sees huma operations. [Users and auth](/features/users-and-auth) owns that guard, the prefix rule it derives from and the redirect-versus-`401` split it applies to a browser.

## API tokens (admin only)

Every operation below requires an admin session; no API token can reach `/api/v1/tokens`, including one carrying `users:write` (see [API tokens](/features/api-tokens)).

| Operation | Path | Notes |
|---|---|---|
| list | `GET /tokens` | instance-wide: every token in the table, including one whose owner has since been demoted, with owner |
| create | `POST /tokens` | `201`, body `{name, scopes, expiresInDays}`; response carries the raw token once, never again; `422` on an unknown scope or an empty `scopes` |
| revoke | `DELETE /tokens/{id}` | `204`; `404` for an unknown id |

## Users (admin only)

Every operation below requires the admin role — the instance owner counts as one — whether the caller authenticates with a session or an API token carrying the matching `users:read`/`users:write` scope. A non-admin session gets `403` `admin role required` from `requireAdmin`; a token whose owner is not an admin never reaches `requireAdmin` at all - `auth.Middleware`'s bearer branch treats a demoted owner as an invalid credential rather than a forbidden caller, and answers `401` `api token invalid or expired` before authorization is ever checked (see [Users and authentication](/features/users-and-auth)). `username` is 1-64 chars and is trimmed on create and login (whitespace-only names are rejected with `422` at `body.username`), `password` is 8-128 chars on both create and reset.

Rank decides the rest, and it shows up as two status codes on every operation that names a target: `403` `superadmin role required` when an admin who is not the owner aims at an admin or asks for the `admin` role, and `409` `the superadmin cannot be modified` when the target is the owner, whoever is asking. `role` reads back as `superadmin`, `admin` or `user`; create and update declare `enum:"admin,user"`, so `superadmin` in a request body is a `422` from huma before any handler runs. Rank applies to the account a credential belongs to, so it binds a token exactly as it binds a session: a `users:write` token issued by an admin who is not the owner cannot hand out the `admin` role either.

| Operation | Path | Notes |
|---|---|---|
| list | `GET /users` | `{items: [{id, username, displayName, role, color, createdAt}]}`, ordered by username |
| create | `POST /users` | `201`, body `{username, password, role, displayName?, color?}`; `409` `username already taken`; `403` `superadmin role required` when an admin who is not the owner asks for `role: "admin"`. An omitted or empty `displayName` becomes the trimmed username and an omitted `color` becomes the least-used colour of the palette, both decided by `user.Create` (see [Users and authentication](/features/users-and-auth)) |
| update role | `PATCH /users/{id}` | body `{role}`; `404`; `403` `superadmin role required`; `409` `the superadmin cannot be modified` |
| update profile | `PATCH /users/{id}` | body `{displayName?, color?}`; `404`; `403` `superadmin role required` for every caller but the instance owner, whoever the target is - renaming somebody is not administration, so it does not follow the rank rule the rest of this table does. The check runs before any write, so a body that mixes a rename with a password reset changes neither |
| reset password | `PATCH /users/{id}` | body `{password}`; `404`; `403` / `409` as above; ends every session of that user. No caller can use it on their own row: an admin's own row is an admin target and the owner's row is refused for everyone, so self-service is the profile page's `PATCH /auth/me` |
| delete | `DELETE /users/{id}` | `204`; `409` `cannot delete yourself` or `the superadmin cannot be modified`; `403` `superadmin role required`; `404`; reassigns the recipes the user created to the acting admin instead of deleting or orphaning them |

Every field of `PATCH /users/{id}` is optional and at least one is required (`422` `nothing to change` otherwise). One request may carry several of them; they are applied role first, then profile, then password.

## Recipes and tags

| Operation | Path | Notes |
|---|---|---|
| list/search | `GET /recipes` | query params below; `404` never - an empty result is a normal page |
| get by id | `GET /recipes/{id}` | `404` |
| get by slug | `GET /recipes/by-slug/{slug}` | `404` |
| create | `POST /recipes` | `201`, body is the recipe input |
| update | `PUT /recipes/{id}` | full replace of title, description and every child (groups, ingredients, steps, tags); `404` |
| delete | `DELETE /recipes/{id}` | `204`; also prunes tags left with no recipes |
| set favourite | `PUT /recipes/{id}/favourite` | `204`; `404` for an unknown recipe; idempotent - starring twice is not an error |
| clear favourite | `DELETE /recipes/{id}/favourite` | `204`; never `404` - clearing a star that was not set is not an error |
| list tags | `GET /tags` | `{items: [{name, count}]}`, most used first; always exactly the tags currently in use (see [Recipes and search](/features/recipes)) |
| list authors | `GET /authors` | `{items: [{name, displayName, color, count}]}`, most recipes first; the people who wrote at least one recipe. `name` is the username, because that is what `?author=` matches; `displayName` and `color` are what the facet chip shows. Readable by any signed-in member, unlike `/users` above: no roles, no ids and no accounts without recipes (see [Recipes and search](/features/recipes)) |

`GET /recipes` query parameters:

| Param | Notes |
|---|---|
| `q` | full-text search across title, description, ingredient names and tags (max 100 chars); prefix-matched, umlaut/ASCII-insensitive - see [Recipes and search](/features/recipes) |
| `tags` | comma-separated tag names, trimmed and lower-cased before matching; no length limit of its own, unlike the `tags` of a recipe body below; restricts to recipes carrying **all** of them (AND, not OR). Normalised and de-duplicated server-side and capped at 20 entries after deduplication - see [Recipes and search](/features/recipes) |
| `maxMinutes` | 0-1440; keeps recipes whose prep and cook minutes sum to at least 1 and at most this bound, so a recipe with neither time set is excluded while the bound is active. `0` is off - see [Recipes and search](/features/recipes) |
| `favourites` | `true` restricts the page to the caller's own favourites - see [Favourites](/features/favourites) |
| `author` | a username (max 50 chars); restricts the page to the recipes that person wrote. Matched exactly against `users.username` and not against the display name, so a filter link survives a rename; an unknown name yields an empty page rather than dropping the filter - see [Recipes and search](/features/recipes) |
| `sort` | `updated`, `created` or `title`, declared as an `enum`, so any other value is a `422` on `query.sort`; absent or empty (`?sort=`) takes the `updated` default before validation runs |
| `page` | 1-based, defaults to 1 |
| `limit` | defaults to 24, clamped to `[1, 100]` |

Every parameter above combines with AND when more than one is set.

`Recipe` and `Card` both carry `createdByName`, `createdByColor`, `updatedByName` and `updatedByColor` beside the two user ids: the display name and the palette token of the author and of the last editor, joined from `users` on every read rather than copied onto the recipe, so a rename or a recolour reaches every card at once. They are on the response because user management is admin-only and a member could resolve neither an id nor a colour themselves (see [Recipes and search](/features/recipes)).

Whose favourites either favourite operation touches, and whose star a listed card reports, comes from the session alone - no path, query or body parameter names a user (see [Favourites](/features/favourites)). `Card.favourite` is filled on every list; `Recipe.favourite` only by the two get operations.

Validation summary for the recipe input body (`Input` in `internal/recipe/recipe.go`): `title` 1-200 chars, `description` ≤ 2000 chars, `servings` 1-99, `prepMinutes`/`cookMinutes` 0-1440 or `null`, `sourceUrl` ≤ 500 chars or `null` (must be a URI), `tags` ≤ 20 entries of 1-40 chars each, `ingredientGroups` 1-20 groups of ≤ 100 ingredients each (ingredient `name` 1-120 chars, `unit` ≤ 20 chars or `null`, `note` ≤ 200 chars or `null`, `quantity` ≥ 0 or `null`), `steps` ≤ 50 entries of 1-2000 chars each. Violations come back as the standard `422` problem body below.

## Images

See [Images](/features/images) for why each upload becomes three server-rendered JPEG variants and how the cover works.

| Operation | Path | Notes |
|---|---|---|
| upload | `POST /recipes/{id}/images` | multipart, one part named `file`; JPEG/PNG/WebP, ≤ 10 MiB; `201`, body is the new image; first upload on a recipe becomes its cover |
| delete | `DELETE /recipes/{id}/images/{imageId}` | `204`; if the cover was deleted, the next image by position is promoted, or the cover is cleared |
| reorder | `PUT /recipes/{id}/images/order` | body `{imageIds}` - every image id of the recipe, in the new order; response `OrderResult` (`{items: [...]}`), the images in their new order |
| set cover | `PUT /recipes/{id}/cover` | body `{imageId}`; `204`; `404` unless the image belongs to the recipe |
| serve a variant | `GET /images/{recipeId}/{imageId}/{thumb\|detail\|original}.jpg` | not under `/api/v1`, not a huma operation - a plain mux route behind `auth.RequireAuth`, reachable by a session of any role or a token carrying `recipes:read`; `Content-Type: image/jpeg`, `Cache-Control: private, max-age=31536000, immutable`; `404` for anything else (unknown recipe/image/variant, wrong extension) |

Upload-specific error statuses, on top of the standard ones below:

| Status | When | Detail |
|---|---|---|
| `404` | recipe or image id does not exist | "recipe or image not found" |
| `413` | declared `Content-Length` above 10 MiB | "upload larger than 10 MiB" - answered by the `limitUpload` middleware before the body is read, since huma's `MaxBodyBytes` is not enforced on multipart bodies (see [Images](/features/images)). A chunked or lying client is instead cut off mid-parse by `http.MaxBytesReader` and surfaces as a `422` on `body` |
| `415` | the real image format (sniffed from bytes, not the declared `Content-Type`) is not JPEG, PNG or WebP | "unsupported image format" |
| `422` | the multipart part is declared with a `Content-Type` outside `image/jpeg,image/png,image/webp` (huma's form validation, before the handler runs), sides outside 64-12000 px, more than 60 megapixels, decode failure, the recipe already has 20 images, or (reorder) `imageIds` does not name every image of the recipe exactly once | "image must be 64-12000 px per side" / "image has more than 60 megapixels" / "recipe has 20 images" / "imageIds must list every image exactly once" |

`Image` is `{id, width, height, position}`; a recipe's `images` array is ordered by `position` and its `coverImageId` is one of those ids or `null`. The first upload onto a coverless recipe becomes the cover. Every image mutation (upload, delete, reorder, set-cover) touches the recipe's `updatedAt`. Rationale and limits: [Images](/features/images).

## CSRF

Cookies are `SameSite=Lax`, and a cross-origin write under `/api/` is refused on top of that - [Users and auth](/features/users-and-auth) owns the rule and what passes it. The refusal is a `403` `application/problem+json` body: `{"title":"Forbidden","status":403,"detail":"origin not allowed"}`.

## Errors

RFC 9457 `application/problem+json`:
```json
{ "title": "Unprocessable Entity", "status": 422, "detail": "validation failed",
  "errors": [{ "location": "body.username", "message": "expected length >= 1" }] }
```
The frontend maps this to `ApiError` in `src/lib/api/client.ts`. A `401` from any call - except the login call itself, except `GET /auth/me`, and except while already on `/login` - clears the SPA's session state and redirects to `/login?next=<original path>` so the user lands back where they were after signing in again. `GET /auth/me` is excluded (mutating calls such as `PATCH /auth/me` still redirect) because its only caller is the root `+layout.ts` guard, which already redirects via SvelteKit's `redirect()` on a `401`; calling `goto()` from the client as well would race that in-flight navigation.

## Why it is this way

Routing is `net/http.ServeMux` with method patterns (`GET /api/v1/recipes/{id}`). The standard library matches on method and path parameters, which is all the routing this API does, so there is no third-party router to learn or to keep current.

huma sits on top of that mux through the `humago` adapter, configured once in `service/internal/httpserver/api.go`, and it is there because it replaces work rather than wrapping it: handlers are typed `func(ctx, *Input) (*Output, error)`, the input validation comes from struct tags, the OpenAPI 3.1 document and the Scalar page are generated from the registered operations, and errors are rendered as RFC 9457 problem documents. The roadmap's public REST API and its MCP server both start from that document, so every operation is described the moment it exists instead of being documented afterwards. Adding a dependency at all follows [Go conventions](/conventions/go).

The typed shape is also a layering rule. The input and output structs *are* the contract, so they live in the feature package beside the service that fills them (`service/internal/recipe/handler.go`) rather than in a shared transport package, and feature code inside an operation never touches `http.ResponseWriter`. Anything that has to write bytes itself leaves the operation set and becomes a plain mux route instead - which is exactly what the image files are (`service/internal/image/file.go`).

## Rejected

- **Plain stdlib without huma.** Nothing to learn beyond `net/http`, but the validation and the OpenAPI document would have to be hand-written, and both are load-bearing for the roadmap rather than decoration.
- **chi, echo or gin.** A router in place of the one already in the standard library; method patterns cover what this API asks of routing.
- **Spec-first generation (oapi-codegen, ogen).** Handlers generated from a hand-written specification. Code-first keeps the contract in the same file as the code that serves it, which is fewer places to keep honest.

## Limits

- The Scalar page at `/api/v1/docs` fetches its JavaScript bundle from `unpkg.com` at runtime - huma's `DocsRendererScalar` pins the version and an SRI hash, and the CSP allows that one origin - so the page needs outbound internet access to render. The OpenAPI document itself is served from the binary and works offline.
