<Callout type="info">

  `frontend/src/app.css` owns every value: colors, radii, shadows and type sizes are Tailwind v4 `@theme` tokens there, and components use only the generated utility classes. This page owns what each token is **for**, the rules components follow, and the traps behind them. Look a value up in `app.css`; never copy one into a component. The only values written here are the user docs' contrast deltas, which depend on them.

</Callout>

<Callout type="warn" title="Traps">

- The display face is `'Literata Variable'`; written `Literata`, every heading silently renders in Georgia ([Implementation notes](#implementation-notes)).
- `@theme` shadows are baked into their utilities: the dark blocks' `--shadow-*: none` does nothing ([Implementation notes](#implementation-notes)).
- The dark tokens are declared twice in `app.css`; a change to one block only leaves the other theme path wrong ([Implementation notes](#implementation-notes)).
- Tailwind cannot compose `bg-user-${color}`; the user palette is written in three places ([User colors](#user-colors)).
- There is no tailwind-merge: a caller's class and a component's class of the same property are decided by CSS source order ([Primitives](#primitives-in-frontendsrclibcomponentsui)).
- Svelte's `transition:`, `animate:flip` and smooth scrolling ignore `prefers-reduced-motion`; every duration has to ask ([Interaction rules](#interaction-rules)).
- A component's view-transition keyframes must be `@keyframes -global-name`, or the animation silently matches nothing; an unscoped root rule switches off every later page cross-fade ([View transitions](#view-transitions)).
- A `1fr` grid track stops at its min-content and pushes its rigid neighbor out of the box, in a width band no Playwright project checks ([Rules](#grids-and-rows)).
- A hit-area inset counts from the padding box, so a border takes from it; measure hits, never add up classes ([Rules](#targets-and-controls)).
- `touch-action` combines only up to the nearest scroll container: a value on a gesture's element alone does nothing inside a scroller, and the browser cancels the pointer ([Scrolling](#scrolling)).
- Sonner's styles are unlayered and beat the utilities; its classes need Tailwind's `!` ([Components](#patterns-in-feature-components)).

</Callout>

## Color tokens

Every color token is redefined for dark mode (see [Implementation notes](#implementation-notes)) except the ones marked theme-independent.

| Token | Role |
|---|---|
| `background` | page ground; the track of a segmented control or the servings stepper; bottom sheets |
| `surface` | cards, dialogs, cook mode's page |
| `surface-elevated` | inputs, and anything raised inside a `surface` dialog or panel |
| `border` | 1px borders and dashed separators |
| `popover` / `popover-border` | lists and menus that open over fields or the page: `Select`, the tag and unit suggestions, the user menu. Equal to `surface-elevated` and `border` in light, where the shadow sets them apart; a step lighter in dark, where the shadow does not read |
| `text` / `text-muted` | body text / secondary text and labels |
| `primary` / `primary-foreground` | primary buttons, links, focus outlines, group headings |
| `accent` / `accent-foreground` | display tag chips, step numbers, accent buttons. **Never a success state**: amber reads as a warning |
| `destructive` / `destructive-foreground` / `destructive-soft` | delete actions, error text and banners. `destructive` text has to clear 4.5:1 on `destructive-soft` (the quiet Delete pill) and on `surface-elevated` in both themes |
| `success-soft` / `success-foreground` | success banners and messages, always with a check icon (`CircleCheckIcon`, see [Icons that answer](#icons-that-answer)). Success is green, never `accent` |
| `success` | small success marks: a status dot, the strong end of the password meter |
| `inverse` / `inverse-foreground` / `inverse-muted` | something laid over the page that has to invert with the theme: toasts, active filter chips, the author popover |
| `skeleton` | loading placeholders |
| `handle` | drop slots, inactive icons, scrollbar thumbs, unchecked round checkboxes |
| `tint-1` / `tint-2` / `tint-3` | placeholder tiles for a recipe without a photo |
| `lightbox` / `lightbox-foreground` / `lightbox-primary` | the lightbox, and marks set on a photo. Theme-independent: it sits behind a photo, not behind the page. `lightbox-primary` is the dark theme's primary, the light one's is below 3:1 on it |
| `overlay` | the scrim behind dialogs and sheets. Black in dark: the light theme's brown left a `background` sheet and a `surface` dialog the same tone as the page around them |
| `scene-ink` / `scene-muted` | text set on a painting (the wordmark and its line on the kitchen scene). Theme-independent: it sits on the painting's cream |

A new color means a new token in `app.css` (both dark blocks included), never a hex value in markup.

## Time color

`--color-time-foreground` marks a duration in a step's text, solid when stored and dotted when suggested (`.time-link`, `.time-proposal` in `frontend/src/app.css`). Its values equal `user-teal`'s foreground on purpose and stay a separate token: `user-teal` belongs to people and may be retuned without touching times. See [Step times](/features/step-times).

## User colors

A second, closed palette: one pair per color, `--color-user-<name>` and `--color-user-<name>-foreground`, redefined in the dark blocks like everything else. **It marks a person and nothing else.** Where it appears:

- **Large, only at a person's own places:** `ProfileHead`, `PersonCard` and `AuthorBand`.
- **Elsewhere at most a small mark (`PersonMark`, `lg` at most), one person per row:** a card's authors, the people list, the "Added by" chip, the colophon, a shopping row's adder or ticker - never both in one row.
- **Beyond the app's pages, always a small circle beside the name:** a push's icon (`avatar.Service.Mark`, [Notifications](/features/notifications)), the mail circle (`mail.Circle`, [Email](/features/email)), `/welcome` and a public page's "Shared by" ribbon ([Public shares](/features/public-shares)).
- **The own app, tinted for whoever is signed in:** the top bar's avatar (`PersonMark ringed`), the overview running head's dotted leader (`userLeaderClass`, the `-foreground` tone dimmed so it does not outweigh the section name), the focused comment composer, shopping mode's head ([Shopping lists](/features/shopping-lists)) and the browser's bar (`theme-color`, never on a sign-in page or a public share, see [Installable app](/features/installable-app)). Nothing that acts: buttons, links and focus stay `primary`.
- **A ring around a photo**, from `md` up: the photo, a gap, a ring in the person's color, so a picture still says whose color it is. The ring takes the pair's `-foreground` tone on `background` and `surface`, the base tone on `inverse`. Initials under `md` get none: the circle already is the color, and at that size a ring ate the face.

The rules:

- **Color only answers "who in the household".** Never state, time, priority, kind or ownership: those keep the main palette. A token's or shared link's card keeps a neutral edge though it has an issuer; the issuer is their mark and name.
- **Color is never the only signal.** Every circle keeps the face or the initial, and the name stands beside it or is the control's accessible name (the mark `aria-hidden`); the picker marks the chosen swatch with a check, not a ring alone.
- **Where a stranger can look, initial on color, never a photo.** A public share page, the sign-in pages, `/welcome` (whoever holds the link has no session yet) and the mails that leave the household or reach an unconfirmed address get the initial on its color: the APIs behind them carry no `avatarId`. `/avatars/...` answers only a session or token (`get-avatar-file` is `auth.Protected`). The one exception is a public share's "Shared by" ribbon while the owner's "Name who shared it" switch is on, from the share-scoped `/public-images/{token}/sharer.jpg` ([Public shares](/features/public-shares)); `public-shares.test.ts` checks that a share page renders no `/avatars/` image and no picture at all with the switch off.
- **Each color carries its own foreground.** The author circle's initial needs 4.5:1 against its own background, and no single ink holds that across eight hues in two themes. The tones stay muted and warm so a grid of cards reads as cards, not as a status board.
- **The palette is written in three places; adding or renaming a color edits all three.** `user.Colors` in `service/internal/user/profile.go` owns the order, `frontend/src/app.css` what each name looks like, and `USER_COLOR_CLASSES` in `frontend/src/lib/user/color.ts` the class pair, since Tailwind cannot compose `bg-user-${color}` at runtime. The API's `enum` is the tie-breaker: a color outside it is a `422`, and a frontend that meets one anyway renders `bg-accent` rather than a circle with no background.
- **Color names are read only through `userColorLabel`** in `frontend/src/lib/user/color-label.ts`: the `user_color_*` keys must each be called by name for Paraglide, so the table lives there once.

## Typography

- UI and body: `font-sans` = Karla, weights 400/500/600/700.
- Numbers: `tabular-nums` everywhere (`body` sets it); fractions as Unicode (½ ¼ ¾ ⅓ ⅔) or “1 ½”.

## Radii and shadows

- **Radii** run `rounded-pill` (buttons, chips, search, stepper, segmented control, bottom nav) down through `rounded-4xl`, `3xl`, `2xl`, `xl`, `lg`, `md` and `sm` from cards to list options; avatars and icon buttons are circles. Five fall outside the scale and are named for their one caller: `rounded-toast`, `rounded-dock` (the floating phone nav), `rounded-word` (a highlight behind one word in running text), `rounded-time` (the cook-mode time chip, in em so it keeps its shape at every type size) and `rounded-index-card` (the cards on "Who's cooking?", whose view transition starts from it).
- **Shadows** are warm and brown-based: `shadow-card`, `shadow-lift` (anything hovered or picked up), `shadow-cover`, `shadow-dialog` (dialogs and floating lists), `shadow-sheet`, `shadow-cta` (mobile primary CTA), and `drop-shadow-lift` for a shape with holes cut out (the pass-on ticket's notches), which a box-shadow would lose. The dark blocks' `none` for three of them has no effect - see below.

## Implementation notes

**The display face is `'Literata Variable'`, not `'Literata'`.** `@fontsource-variable/literata` declares that family name and CSS matches family names exactly, so both stylesheets lead with `--font-display: 'Literata Variable', Literata, Georgia, serif`. Written without `Variable`, the stack matches no `@font-face` and every heading, recipe title, step number and the wordmark renders in Georgia; nothing looks broken, since a serif falls back to a serif. Only a measurement catches it: `document.fonts.load("64px 'Literata Variable'")` first (a face stays `unloaded` until asked for), then compare the rendered width with the same text in Georgia. Keep `frontend/src/app.css` and `docs/user/app/global.css` in sync; each declares the stack for itself. Literata runs wider than Georgia, which is why card titles clamp to two lines on phones and three on desktop.

**A `@theme` shadow cannot be re-themed per mode.** Tailwind v4 compiles an `@theme` shadow into each utility as a literal `--tw-shadow` value, where a color utility keeps a live `var(--color-*)`. So the `--shadow-card`/`--shadow-cover`/`--shadow-cta: none` declarations in the dark blocks of `frontend/src/app.css` set properties no rule reads, and those shadows render in dark exactly as in light. A shadow that has to differ per mode needs a `dark:` utility on the element; `docs/user/app/global.css` declares no dark shadow override for the same reason.

**Theme switching.** `data-theme` on `<html>` is absent when the choice is "system"; an explicit choice sets it to `light` or `dark` and is stored in `localStorage` under `rezepte-theme`. There is no `data-theme="system"`: "system" is the attribute's absence, applied before paint by an inline script in `app.html` that mirrors `#lib/theme.ts`.

- **The dark tokens are declared twice** - under `:root[data-theme='dark']` and inside `@media (prefers-color-scheme: dark) { :root:not([data-theme='light']) { ... } }` - because CSS cannot share one block between a plain selector and a media query. Keep both in sync by hand.
- **The `dark:` variant is redefined** with `@custom-variant dark` to follow the same rule, so a component using `dark:` respects an explicit `light` choice under a dark system preference.
- **`--image-squiggle` is repeated in both dark blocks**, because an SVG in `url()` cannot read a custom property and spells the primary color out.

## Rules that keep layouts from breaking

Each of these comes from a bug that shipped. Verify them at 360px and 200% text - see [Verify UI with Playwright](/howtos/verify-ui); a check that walks the DOM is a [probe](/howtos/verify-ui#running-a-probe).

### Targets and controls

- **An action is never bare text.** Text with a click handler and no padding is a 20px-tall target; give it a padded pill, even where it reads like a link.
- **A control's hover is `hover-tint`, never `hover:brightness-*`.** The utility in `frontend/src/app.css` veils the control in its own `currentColor`, so a light button darkens and a dark one lightens in both themes with no color per variant; `brightness` barely moved the dark theme's buttons. `hover:bg-*` and `hover:text-*` are for ghost and text controls only.
- **Actions in dense rows are 44px tall on phones** (`h-11`) and drop to the table's density on desktop (`md:h-8`); elsewhere the floor is `Button`'s own height. A small control reaches 44px through an absolute span or `::after` (`-inset-*`), which counts from the padding box, so a border takes from the hit; measure it with `elementFromPoint` around the center rather than adding up classes.
- **A hit area that overhangs inside running text grows only vertically** (`after:-inset-y-*`, never `-inset-x-*`): a sideways overhang widens the line past its column on a narrow phone. The cook step's time chip (`StepText.svelte`, [Cook timers](/features/cook-timers)) is the case.
- **A card that carries its own controls is a stretched link.** The anchor holds the title and grows an `::after` over the card; the star and the author initials are its siblings, since a `<button>` inside an `<a>` is invalid and a focus trap. The wrapper is an `<article>` labeled by the title, and hover and focus hang off it via `card-hover` (`:has(a:hover)`) and `has-[a:focus-visible]`, so the effect covers the card but answers to the link alone.
- **A button never breaks into two lines.** Add `whitespace-nowrap`, and when the row is too narrow give the button its own full-width line (`w-full md:w-auto`).
- **A filter has one home, and is shown where it acts.** The tags are not in the filter panel: two controls for one filter left no way to tell which one the grid answers. What the panel sets stands on the page as chips (`ActiveFilters`) that only open the panel or drop their filter, and the "Filters" button carries no count, since the chips already say it.

### Text and wrapping

- **A title that identifies something wraps, it does not truncate.** `line-clamp-3` for recipe card titles, since a cut-off name is a card nobody recognizes; `truncate` stays right for secondary lines and a title inside a fixed-height bar.
- **Long words wrap inside their box, at 200% text too.** Prose that names something is `wrap-break-word hyphens-auto`, which hyphenates by `<html lang>` (the account's locale) and still breaks a word with no hyphenation point; a value that is not prose (an address, a URL) is `wrap-break-word`, or `wrap-anywhere` where its min-content must shrink, which splits a closing „…" off its word. `hyphenate-limit-chars` is `12 4 4` where a long word is the exception (recipe title, cook step), `12 6 6` for ingredient names and `6 3 3` only where ordinary words outrun the box (card titles, `NoteEmptyState`); never `overflow-wrap: break-word` beside a float, which broke "Noch" mid-letter.
- **Sizes that grow with the text are `rem` or `em`, container thresholds `rem`.** Android's font size grows px text alone, so a px box keeps its size while its text doubles.
- **A field has to be able to show its own placeholder.** Give it the full line (`w-full md:flex-1`) and let the meta items wrap under it, or a new group opens with its own prompt cut off.
- **What a field shares its line with follows the length of its value, not its kind.** The source name and URL each own a full-width line; the servings and two times, three short numbers, share a row.

### Grids and rows

- **A `1fr` grid track stops at its own min-content, so the rigid track beside it is what overflows.** Give the *rigid* track a `minmax(0, …)` and let it yield; on the flexible one it only moves the overflow inside the column. On the recipe page a long title word pushed the cover past the edge in a band between both Playwright projects' viewports, so the suite stayed green.
- **A field that shares a row needs `min-w-0` on the item in the row**, not on the input: a flex item's minimum is its min-content, and an `<input>` contributes its `size="20"` default even when it carries `min-w-0` itself.
- **Rows with several fields align on one baseline** (`items-center`), and a status hint belongs under its action, not beside it.
- **Separators go between entries, never after the last one:** `last:border-b-0`.
- **A component that can sit in boxes of different widths decides by container query, not by screen breakpoint.** `@container` plus `@min-[…]:` measures the box it lives in, where `md:` guesses from the device. The container needs a definite inline size: a content-sized one, or one in an `items-center` column, measures 0 and everything under the query takes its narrowest form.

### Scrolling

- **Scrollbars are themed once, globally.** `app.css` gives every scroll box a thin `handle` thumb in `@layer base`, so no component carries a scrollbar class and a utility still wins (`[scrollbar-width:none]`, `[scrollbar-gutter:stable]` on lists whose rows must not shift). A dialog does not reserve the gutter. `FilterPanel` alone draws its own thumb, because iOS and macOS show the system bar only while the list moves and nothing said that more waited below.
- **A rounded box never scrolls itself.** The browser draws the scrollbar straight through the rounded corners, so the rounded box is a clipping frame with padding and a plain child scrolls; the padding has to clear the corner's curve where the scroller starts. Every `BaseDialog` is built this way except with `bleed`, which puts all padding on the scroller so content reaches the rounded edge. A scroll box also clips focus rings at its edge, so whatever sits flush with it needs the ring's width inside.
- **`touch-action` combines only up to the nearest scroll container.** An element that handles a gesture itself (a swipe) carries its `touch-pan-*` on every scroll box between it and that element too; otherwise the scroller's default lets the browser take the pan and cancel the pointer. Cook mode's step `section` is the case ([Cooking](/features/cooking#keyboard-pointer-and-motion)), and only the mobile project's real touches show it.
- **Two scroll containers inside each other are a guessing game.** The same flick moves one or the other depending on where it lands; a section that wants its own scrollbar inside a dialog belongs somewhere else.

### Bars, menus and stacking

- **On desktop a page's own actions go in its rail, not in a bar over its content.** A sticky bar over a scrolling form hides a band of what is being read; the section rail is empty for the content's whole height. The editor's rail stacks its actions primary on top, with the status line under them so its appearing never moves a button under the pointer. Phones keep their own top bar ([App shell](#app-shell)).
- **A bar that floats over content is the width of its column, never the shell's**, and its sticky offset matches the padding under it, or it detaches from the viewport edge at the page's end.
- **A menu or popover never runs past the window.** `app.css` caps every `[data-dropdown-menu-content]`, `[data-popover-content]` and `[data-select-content]` at `100vw - 2rem` in the base layer, so a caller's `max-w-*` still wins: on a phone a wider menu grew the layout viewport, the fixed bar reflowed, and the tap opened the photo behind it. The same rule drops the ring around a menu a tap has focused.
- **Round controls stay round when squeezed.** `IconButton` and menu triggers are `shrink-0`; where a bar has no room at 200% text they shrink as circles (`aspect-square`, `h-auto`).
- **Stacking:** dialogs and the lightbox own `z-50`, the mobile header `z-40`. A floating menu that has to clear a fixed bar needs a `z-50` of its own (Bits UI copies the content's computed z-index onto its floating wrapper) and a `sideOffset` that clears the whole bar, not just its trigger.

## Interaction rules

- **A card's actions sit at its end.** Buttons in a card, a note or a dialog follow `DialogActions`: content-sized at the end from `md`, the full line and at least 44px tall below it.
- **Hover only where hover is real.** Tailwind v4's `hover:` sits under `@media (hover: hover)`, and hand-written hover CSS (`hover-tint`, `card-hover`) does the same, so a tap never leaves a hover stuck. A control revealed on hover stays visible on touch; a pointer-only hint is `pointer-fine:`. Bits UI's `Tooltip` ignores touch, so it only repeats a name the control already has; an explanation is a `Popover` on a wide screen and a `BottomSheet` on a phone.
- **Buttons point.** `app.css` restores `cursor: pointer` on `button:not(:disabled)` and `[role="button"]`, which Tailwind v4 dropped from its preflight; disabled buttons keep the default cursor. The rule sits in `@layer base`: unlayered, it beat every `cursor-*` class and a drag handle lost `grab`.
- **Search is debounced 250ms** (`SearchBar.svelte`); **skeletons show only past 300ms** of loading.
- **Tag filters are multi-select and mirrored into the URL query.**
- **The time filter snaps up to its scale.** It is a bound in minutes on fixed stops defined in `#lib/recipe/time-filter`, and `query.ts` rounds `maxMinutes` up onto them on the way in: rounded down, it would drop recipes the caller asked to see, and a value between stops would leave the slider naming another bound than the grid answers.
- **Ingredient checks are visual only**, kept per session in `sessionStorage` under `rezepte:checked-ingredients` (`#lib/recipe/checked.svelte.ts`).
- **Servings persist per recipe** in `localStorage` under `rezepte-servings:<recipeId>`; [Cooking](/features/cooking) owns the bounds, the rounding, and cook mode's keys, swipe, motion and wake lock.
- **Editor keys:** `beforeunload` prompt when dirty; Enter (`enterkeyhint="next"`) walks an ingredient row - name, amount, unit - and from the unit or the note adds the next row; a unit picked from its list with Enter takes that Enter (`defaultPrevented`). Backspace in an empty row deletes it.
- **Form errors come from a save, never while typing, and leave as soon as someone types in their field.** `withoutErrors` in `#lib/form-errors` drops them; the editor's fields name their errors with `data-error-key` and one `oninput` on the form clears them. An error whose cause a button changes (unlinking, deleting a step) never fires `input`, so the editor shows `currentErrors` (`#lib/recipe/form`): the last save's errors re-checked against the live form. The section marks read the same set.
- **Respect `prefers-reduced-motion`: nothing travels, scales, turns or pulses, and the state still changes.** Nothing in Svelte does this on its own - `transition:`, `animate:flip`, svelte-dnd-action's `flipDurationMs` and `scrollIntoView({ behavior: 'smooth' })` all move regardless - so every duration is `$derived(prefersReducedMotion.current ? 0 : n)` (`svelte/motion`), every smooth scroll asks the same, and a moving utility carries `motion-reduce:transition-none` or `motion-safe:`. A color or opacity transition on hover may stay. Check it with a frozen clock under `reducedMotion: 'reduce'` ([Verify UI](/howtos/verify-ui#motion-frame-by-frame)): `document.getAnimations()` lists nothing after the action.

### View transitions

The grid, page and theme changes and the user switch's pick ([Motion in feature components](#motion-in-feature-components)) share these rules.

- **Scope it to what changes, never to `<html>`.** `element.startViewTransition` on the changing wrapper, falling back to `document.startViewTransition`: only Chromium has the element method, and Safari threw on `<html>`'s, which only the WebKit e2e projects catch. A transition swallows every click inside its scope while it runs, so a document-wide one lost a second tag picked right after the first. Chromium holds a scoped transition's scope at its old size, so a change that keeps the reader's place in a growing page runs document-wide. Delete `Element.prototype.startViewTransition` in an init script to see Safari's path in Chromium.
- **Name every fixed layer, and lift it.** A fixed element is part of the page's picture unless it carries a `view-transition-name` (`top-bar`, `bottom-nav`, `timers`), and named groups stack in their own order: the bars' groups get `z-index: 2`, a dialog or menu open over a document-wide glide is named `layer-<n>` (`z-index: 1`), or the cards slide across them. A named layer also paints over unnamed labels above it, so the settings nav's pill glides by a FLIP of its own.
- **No animation frame runs while an update is pending**, so an update callback that waits (a fetched card, a `decode()`) polls with timers.
- **Root rules hang off an attribute set only for that transition** (`html[data-page-transition]`, `[data-theme-transition]`, `[data-switching]`): a component's styles stay loaded after it is left, and an unscoped root rule switched off every later page change's cross-fade. A glide does not start while another's attribute is set.
- **A component's keyframes for the pseudo-elements are `@keyframes -global-name`, referenced as `name`**: written `-global-` in `animation`, the name silently matches nothing.

## Sheets

**"Phone" has two definitions.** A layout asks the width ("below `md`" on this page, `lg` for the sign-in scene, `desk:` for the recipe card). Whether a spot opens a sheet or a card at the pointer asks `phone` (`#lib/ui/phone.svelte.ts`: a coarse pointer, and a small window): a narrow window with a mouse has no taps, and a phone on its side is no roomier with the keyboard up.

**Every dialog except the lightbox leaves the page's scroll alone; on a touch screen `app.css` locks it.** `BaseDialog`, `BottomSheet`, `CommandPalette`, `FilterPanel` and the menus pass `preventScroll={false}`, because Bits UI's lock takes the scrollbar away and the page jumps sideways. On a coarse pointer `app.css` sets `overflow: hidden` on the root while any `aria-modal='true'` element is open, since a swipe on the overlay or past the end of a sheet's list scrolled the page behind it, and a touch screen's scrollbar takes no room. The mobile e2e test "the page stays put under an open sheet" covers it. The lightbox keeps Bits UI's lock; [Images](/features/images) owns why and how it sizes itself around the gutter. A new dialog passes `preventScroll={false}` too.

**The keyboard shrinks the layout on Android, only the visual viewport on iOS.** `interactive-widget=resizes-content` in `app.html`'s viewport meta makes Chromium shrink the layout, so every `fixed` or `100dvh` box ends at the keyboard; without it a bottom toolbar left a gap and focus fired transient `visualViewport.offsetTop` jumps. iOS ignores the key, so a box that must end at the keyboard follows `followVisibleArea` (`#lib/visible-area.ts`), which measures against a zero-width fixed probe rather than `innerHeight`, reads no keyboard unless a text field has focus, and reads 0 on Android.

**A sheet never restructures while typing.** Its header, gaps and padding stay the same whatever the keyboard's height: Gboard adds a number row in a password field, and a sheet that compacted for it flickered between two fields. A collapse is decided as the keyboard opens and held while a field has focus.

**A sheet taller than its room scrolls inside** (`max-height`, `overscroll-behavior: contain`, the body `min-h-0 flex-1`), and on `focusin` and every change of the visible area the focused field scrolls into view within it (`block: 'nearest'`). Its foot pads itself, since `env(safe-area-inset-bottom)` is 0 (see the bottom nav under [App shell](#app-shell)). A form whose button must stay reachable puts it after the body, at the sheet's foot (the recipe and list imports).

**`BottomSheet` rests on the keyboard.** It follows `followVisibleArea` with a zero-width probe, since a `fixed` sheet measures from the layout viewport the iOS keyboard does not shrink; without it the sheet sat behind the keyboard or, once the page under it had scrolled, floated with a gap above it. Lifted by `area.bottom` on iOS, it rounds all its corners and caps its height to the visible area.

**A field never scrolls inside a scrolling sheet.** Two scrollers in one another move whichever the finger lands on, so the import fields in a sheet grow with their text (`field-sizing-content`, at least their rows) and only the sheet's body scrolls; empty, they are as tall as their example placeholder, so neither scrolls. `BottomSheet` then does not scroll a focused field taller than the body into view, which would align its top and hide the caret; the browser keeps the caret in view.

**A sheet that scrolls always shows its thumb.** The caller marks the scrolling body `data-sheet-body`; while it overflows, `BottomSheet` draws a `handle` thumb over its right edge (`data-sheet-thumb`), and `app.css` hides the body's own scrollbar and gives it `overscroll-behavior: contain`. A phone shows a scrollbar only during a swipe, and a sheet cut off by the screen's edge read as broken. The thumb is kept by a `ResizeObserver` and a `MutationObserver`, since content that unfolds changes the height to scroll without resizing the body.

**Motion starts from what is drawn.** A move with the keyboard runs from the drawn position (FLIP), and one still running is taken over, never restarted: Chrome fires a burst of resizes while its keyboard slides.

**A sheet about a spot on the page keeps the spot in sight.** `spotlight` leaves it out of the dim through a clip-path hole, which leaves the hit test too (a tap there closes the sheet unless the caller answers it first), cut flat at a clipping box and at the bars marked `data-covers-top`, whose edge `coveredTop()` reads. `revealAbove` scrolls the spot's last line clear of the sheet, never its first under those bars, padding the page or the subject's scroll box until the sheet closes; call it again once the keyboard has gone.

**Focus.** Opening focuses the grip unless typing is the point (the palette's field). Closing returns focus to the opener unless that is a text field, which would raise the keyboard: then a stable neighbor takes it.

## Components

Every component wraps a Bits UI primitive where one exists and is styled by hand. The code carries the measurements; what follows is what each one is for and the rule a change could break.

### Primitives in `frontend/src/lib/components/ui/`

**Buttons and fields**

- **`Button`** (`Button.Root`, or an `<a>` with `href`) - variants primary, secondary, accent, ghost, quiet (a settings row's control), destructive, destructive-quiet (a danger row's pill). **Focus-visible everywhere is a `primary` outline, text fields included**; only `Input`'s `floating` field keeps its own ring. `busy` marks a request still out with `aria-busy`, never `disabled`, which dimmed the one thing working; the caller ignores a second press.
- **`IconButton`** - a circle named by `label`. Its default `bg-surface` steps aside when the caller passes a `bg-*` class: there is no tailwind-merge, so CSS source order would otherwise decide.
- **`ShareButton`** - the one share button of a page's head; its glyph is nudged left because the icon's ink sits right of its box.
- **`Input` / `Textarea`** - the field rules:
  - `counter` counts **code points**, not `.length`, so it agrees with the server's rune limit; it is `aria-hidden` and at the limit goes semibold, never `destructive`: a full field is valid.
  - `required` puts a `RequiredMark` **beside** the `<label>`, so the label stays the field's name for `getByLabel`, password managers and autofill, and sets `aria-required`, never native `required`, whose browser bubble preempts the form's error. The mark turns to a check once "satisfied", which is "not blank" unless the field passes `satisfied` (`servingsValid`, `hasNamedIngredient` in `#lib/recipe/form`), so a check never stands on a value the save would reject. Only forms that mix required and optional fields mark anything.
  - `floating` is the sign-in pages' field (inside `AuthScene` only). `:-webkit-autofill` has a rule of its own, since one unknown pseudo-class drops a whole selector list. An `aria-invalid` field traces its outline in `destructive`, its `stroke-dasharray` gap longer than the path, or `pathLength` rounding leaves a red sliver at rest. Every move waits for `data-ready` ([Sign-in scene](#sign-in-scene)).
  - `prefix` is measured, not a fixed inset, because its length is the reader's language's.
- **Read-only value** (a pattern) - a value someone cannot change sits in a `bg-background` block sized to its content, never to the column, so it is not mistaken for a field.
- **`Select`** - `variant` sets the shape; the caller sets the background, one step above its ground. The list is never narrower than its trigger (`--bits-floating-anchor-width`); `align="end"` is for a trigger at a `SettingsRow`'s end. Where a value cannot change there is no pill.
- **`UnitInput`** (own combobox, in `editor/`) - its list looks like `Select`'s.
- **`TagInput`** (own combobox, in `editor/`) - chips in a field. Enter or a comma takes the highlighted row (`preferred` from `tagSuggestions`: the first match, creating only when nothing matches). **A tag goes on only by a choice** (`tagToCommit`): Tab, a tap elsewhere, closing the keyboard and Save commit nothing and leave the text in the field. Only a real pointer move moves the highlight. The listbox is `tabindex="-1"`: Chromium makes a scrolling box a Tab stop, and Tab into it closed the list and dropped focus to `<body>`.
- **`TagChip`** - with `onclick` a filter chip (`aria-pressed`), without one a display chip on `accent`; the label truncates so the chip never leaves its row. `ariaLabel` names a chip by what a tap does and drops `aria-pressed`: a chip that only removes is a button, not a toggle.
- **`Switch`** - a setting that takes effect when flipped; a checkbox marks an item in a list. It reports `role="switch"`, so Playwright's `check()` does not drive it: click and read `aria-checked`.
- **`Checkbox`** - the square form checkbox; the ingredient list draws a round one on the same primitive. Its tick draws only when clicked ([Icons that answer](#icons-that-answer)).
- **`Slider`** - `value` is a **position** on a fixed scale; the caller maps it. `role="slider"` sits on the thumb, so `aria-label`/`aria-valuetext` go there. A filter refetches from `oncommit`.
- **`SegmentedControl`** (own radiogroup) - a choice of a few; `track="surface"` is the bolder track for a choice a whole sheet hangs on. `disabled` is `aria-disabled`, so the checked segment stays focusable. Labels never truncate: the track wraps, and the checked pill is measured from the checked button, gliding only on a pick. `size="sm"` is every `SettingsRow` control's height.
- **`AccessLadder`** (own radiogroup) - levels where each includes the ones below (a token's access); a sentence under it says what the chosen step allows.

**Dialogs and sheets**

- **`BaseDialog`** - the centered dialog, capped to the viewport and scrolling inside so a tall form keeps title and buttons. A dialog that scrolls on a desktop is the signal for `wide`. `dismissible={false}` keeps the token reveal open on Escape; `bleed` lets a side panel reach the rounded edge. `ConfirmDialog` is a `BaseDialog` with ghost Cancel and a primary or destructive confirm.
- **`DialogActions`** - every dialog's buttons: they wrap instead of squeezing, never break a label, fill their line below `md` and sit at the end from `md`.
- **`BottomSheet`** - the phone's one sheet, on `background` in both themes (the dark `overlay` sets it apart), its grip the close button. The filter panel draws the same sheet itself below `md`. Every sheet follows [Sheets](#sheets).
- **`SheetHandle`** - the grip: a tap, a long enough pull or a flick closes the sheet, and the click ending a pull is swallowed. The e2e tests "…closes when its handle is pulled down" must measure the handle after the sheet's rise, or the press lands in the text.
- **`CommandPalette`** - near the top on desktop, a sheet on the keyboard below `md`. A navigation closes it only if it was open when the navigation began (`beforeNavigate`): one opened with ⌘K during a page change was meant for the new page.
- **`Lightbox`** - `lightbox` tokens, no overlay; Escape is Bits UI's, arrows and swipe the component's. It alone keeps Bits UI's scroll lock ([Sheets](#sheets)).

**States and people**

- **`Skeleton`** - pulse and color only; size and radius come from the caller.
- **`EmptyState`** - the italic "R" circle, title, sentence and actions; every empty state but two.
- **`NoteEmptyState`** - the empty page that explains itself, for the two a person meets first: the overview on an empty instance and the shopping lists with none. A mascot pose beside a taped note whose steps are an `ol`; on a phone the painting shares the note's grid cell so it sits the same on both pages. It keeps `data-empty`, which the overview's glide names.
- **`LifetimeBar`**, **`Stamp`** - how much of a token's or link's life has passed, and a stamp for what happened to it; both decoration, so the caller says it in words.
- **`PersonMark`** (own, not Bits UI `Avatar`) - every circle that stands for a person: color pair and initial, their picture over it. The top bar's is `ringed`. The photo ring is an `outline` with `outline-offset` (`userRingClass`), so the gap shows whatever ground it sits on and does not fight a caller's `ring-*`; it is clipped by an `overflow` ancestor, so keep a ringed mark clear of a scroll box's edge. Marks set in a line of text are sized in `em`, so they grow with 200% text. In the "Shared by" ribbon it is `strong` (the pair turned over), or the initial melts into the ribbon.
- **`PersonDot`** - a person as a dot where no picture travels (a link's creator, a token's issuer), and every color dot under 20px, where a face is a smudge.
- **`PersonCard`** - one person: a `Popover` on a wide screen, a `BottomSheet` below `md`; it inherits its surface's text color, so it reads on `inverse`, `surface` and a sheet. Roles and counts come from one cache, `frontend/src/lib/user/people.svelte.ts`, refreshed only by a reload.
- **`FaceStack`** - overlapping `PersonMark`s for who the sentence beside it names, "+N" beyond `slots`; `aria-hidden`. The overlap stays small enough that every initial stays whole.

### Patterns in feature components

**Overview**

- **`AccountCard`** (in `switch/`) - the index card of "Who's cooking?"; [Who's cooking?](/features/user-switch#motion) owns its motion.
- **`RecipeCard`** - a stretched link ([Rules](#targets-and-controls)). Its desktop look hangs off `desk:`, not `md:`, so a phone with one card per row gets it too ([Recipes and search](/features/recipes)). **Its corners are concentric: corner radius = mark radius + gap**, so star and initials share the corners' centers. The total time is a `text-label` line, never a pill, so the longest allowed time fits unrounded; text-card title colors must keep 4.5:1 (3:1 for the large title).
- **`AuthorInitials`** - a card's author circles, opening a `Popover` anchored to the card on `inverse` (on `surface` it dissolved into the card), a `BottomSheet` below `md`. The "Added by" filter travels as the username, so a link survives a rename.
- **Overview search** (`SearchBar.svelte`) - a combobox in the `TagInput` pattern, set like a cookbook index. It is a multi-select listbox: `aria-selected` on chosen tags and the highlight by `aria-activedescendant`, because VoiceOver does not announce `aria-checked` on an option.
- **`ActiveFilters`** - the panel's filters as chips, each a label that opens the panel and a × that drops it. On a phone it leads with a non-default order, since the sort control is out of sight, and folds into one bar once it needs a second line, measured from an inert `w-max` twin of the row (inside the zero-width wrapper the chips capped themselves at 0). "All ×" (`clearFilters`) leaves the order and search text, which the bar does not show; the panel's `resetFilters` clears the text too - two functions, since an `onclick` handler receives the event as its first argument. A control that removes itself hands focus to what took its place; the last hands it to `focusfallback`, never the search field, whose focus opens suggestions.
- **Overview running head** (`frontend/src/routes/+page.svelte`) - "Recipes", `ResultCount` and the date, set like a cookbook page's head; the section name is `aria-hidden`, since it repeats the navigation.
- **`AuthorBand`** (in `recipe/`) - heads the overview while `?author=` names a known person. On a phone it replaces the person's chip and carries its ×; from md the chip keeps the ×: one way to drop a filter per screen. It is copied from `ProfileHead`'s band rather than shared, since the two differ in every measure.

**People and settings**

- **People list** (`PeopleList`, `PersonTile`) - one group per role; each person a card and an `@container`, display name over login name (what an admin types). A card the viewer may open is one link named by the person; it has no controls, since the person page holds them.
- **Settings rows** (`SettingsGroup`, `SettingsRow`, in `settings/`) - icon tile, label over value, one quiet control. **Every row has the same shape, danger rows too:** no whole-row button, and in `tone="danger"` only the `destructive-quiet` button reacts, named by the row's label. `tone="attention"` marks a fact worth a second look without reading as an error. Values never truncate and the control never wraps its label; short of room, the control takes its own line.
- **`ProfileHead`** - a band in the person's color with the photo on its edge, an inline rename and the color picker; the caller's `onrename` toasts, not the head. The camera badge (`AvatarControl`) opens a menu with a photo and the file picker without one, and puts focus back on the new badge after a swap.
- **`ColorPicker`** (`RadioGroup`, in `settings/`) - swatches in a container query, under them who else wears the chosen color (`#lib/user/holders.ts`) as the group's `aria-describedby`. **Never a disabled state: duplicates are allowed.** On the profile and person pages picking **is** the save.
- **`RecipeColophon`** - "Added by …", and "Last edited by …" only when `hasBeenEdited` (`#lib/recipe/authorship.ts`); each person opens their `PersonCard`. The sentence is translated whole and split at placeholders, so each language keeps its order.
- **`SourceCredit`** - the "Adapted from" line, credited as a cookbook would; it wraps and exists only when there is something to credit ([Recipes](/features/recipes)).

**Editor, cooking and shell**

- **Step links** (`StepLinks.svelte`) - [Ingredient references](/features/ingredient-references) owns them; image tiles (`ImagesSection.svelte`) - [Images](/features/images), their overlay always visible on touch.
- **Save bar** (`SaveBar.svelte`) - both labels share one grid cell and the dirty dot's wrapper is always rendered, so nothing moves Save.
- **`ServingsStepper`** - the bound buttons stay enabled and announce `aria-disabled`: a truly disabled button drops keyboard focus the moment it is pressed at the bound.
- **Cook timers** (`frontend/src/lib/components/timer/`) - [Cook timers](/features/cook-timers) owns the behavior. The dock wears `user-teal` with `time-foreground`, the times' own teal, and turns `primary` while ringing.
- **Toast** (svelte-sonner, in `frontend/src/routes/+layout.svelte`) - `bg-inverse`, `rounded-toast`. Sonner's styles are unlayered and beat the utilities, so its classes carry Tailwind's `!`.
- **Drag handle** - Lucide `grip-vertical` in `text-handle`.

### Motion in feature components

Every entry obeys reduced motion ([Interaction rules](#interaction-rules)); timings live in the code. Motion answers an action and never plays on load.

- **Grid change** - a new card size, filter or order glides the cards through a view transition; a leaving card fades out before a joining one fades in, so a slot never shows two titles. "Load more", search while typing and the first list go without ([Recipes and search](/features/recipes)).
- **Page change** - `pageTransition` in `#lib/page-transition.ts`, from the root layout's `onNavigate`, runs every route change as a view transition: old page out before new page in, the `top-bar` swapped at once, a card's photo becoming the detail cover (`recipe-cover`). **A navigation that starts while a transition still holds the previous one waits for it and goes without (`held`)**, because SvelteKit renders a held navigation once its `onNavigate` promise resolves and only then drops it as superseded ([sveltejs/kit#17492](https://github.com/sveltejs/kit/issues/17492); `held` can go once the installed SvelteKit includes the fix, [sveltejs/kit#17302](https://github.com/sveltejs/kit/pull/17302)); `back while the recipe still opens shows the list` in `frontend/e2e/recipes.test.ts` holds that gap open. A same-route query change, reduced motion and a touch screen's back go without, except the app's own back buttons, which call `back` from the same module.
- **Settings navigation** - no page transition between settings pages, a change of tab; the current pill glides by its own FLIP (`pill` in `SettingsLayout`), measured in `beforeNavigate` while the old page is still laid out.
- **Theme change** - `setTheme` opens the new colors as a circle from the focused control with `mix-blend-mode: normal` (crossed over, light and dark met in grey) and every other `view-transition-name` off (`html[data-theme-transition] *`).
- **Arrival** - after a switch or sign-in the card or sheet grows into `HelloSplash`, the page reloads under `html[data-arrival]::after`, and the root layout closes it into the person's avatar; [Who's cooking?](/features/user-switch#motion) owns it.
- **Card hover** - `card-hover` lifts and tips a recipe card, every card the same way and arriving timed apart from leaving, or a pointer crossing a row reads as a seesaw. The title's wave (`squiggle`) lives on a transparent `aria-hidden` copy of the title, since the three-line clamp leaves no room for it. `ListCard` is the link itself, so plain `hover:` and no `hover-tint`, whose veil greyed the paper.
- **Tag row** (`TagFilter`) - a picked tag glides to the front with `animate:flip`. `measure()` assigns `folded` only when the set of names changes: a fresh array of the same names re-ran the keyed each and flip had nothing to move.
- **Active filter chips** - no `out:`, because `keepFocus` hands focus on once the removed button is out of the document.
- **Settings lists** - only the viewer's own add or remove slides: `rowMotion()` in `#lib/settings/row-motion.svelte.ts` turns the duration on for that one change. Rows are spaced by margins, not `gap`, which jumped at the end of a slide, and carry no `animate:flip`, which takes a leaving row out of the flow.
- **Editor lists** (`#lib/components/editor/motion.ts`) - only ids in `fresh` open (`reveal`) and removals fold (`collapse`); loaded rows and svelte-dnd-action's shadow are simply there. The traps:
  - **Removal is not an `out:`.** Under `animate:flip` Svelte pins a leaving item `position: absolute` and rows slid through it; `collapse` animates the height and the caller splices after, focus moving to the neighbor first.
  - **No flip while a row is added**, since Svelte measures it with the new row at full height; its duration is 0 while `fresh` is not empty.
  - **The height is read every frame**, since a step's parts mount after the reveal starts; a tick-driven transition stops under a paused clock, so check it in slow motion ([Verify UI](/howtos/verify-ui#motion-frame-by-frame)).
  - **`overflow: clip`, not `hidden`**, which is a scroll container and scrolled a focused step's top row away.
  - **The last item takes its neighbor's gap along** in a `space-y-*` list, or the list jumps.
- **Saved** (`EditorBar`, `SaveBar`) - once the save and its uploads went through, `RecipeForm` sets `saved` and the button turns green at once (amber tweened to green passes through olive). It waits `SAVED_PAUSE` before `goto` with the editor `inert` and `handleSave` returning on `saved`, so nothing is typed or sent twice. To see its frames, pause the button's own animations, not the page's.
- **Editor chips** - a tag chip does not flip when one goes: the field after it reflows at once and sliding chips ran over its placeholder.
- **Detail page and cook mode** - owned by [Cooking](/features/cooking), [Images](/features/images), [Recipe comments](/features/recipe-comments), [Tasty](/features/tasty) and [Cook timers](/features/cook-timers). Cook-step text and countdown digits stay still; a mark taken back snaps.

## App shell

### Sign-in scene

**Login and `/welcome`** (and `/forgot-password`, `/confirm-email`) share the kitchen scene of `AuthScene.svelte` ([Logo](#logo)): from `lg` the scene covers the window with the form on its right; below `lg` it is a plate above a text page, where the "Sign in" heading stays for screen readers only. The pages pass only the wordmark's line and the card's contents, so scene, card motion and frame cannot drift apart.

- **`frame` makes `main` a fixed frame below `lg`**, following the visible area's insets, with `<html>` not scrolling while it is mounted: `"sheet"` on `/forgot-password` and `/welcome`, `"cover"` on the login; `/confirm-email` and `/unsubscribe` pass none and scroll as any page. It follows the [sheet rules](#sheets).
- **In sheet state the text page is the sheet** (`main[data-sheet]`), lying over the plate, with no grip and no close: the sheet is the page. With `frame="cover"` the paper is a cover until `open`, and the form opens as the page's dialog ([Users and auth](/features/users-and-auth#the-login-form)).
- **The plate gives way first; too flat for the mascot it collapses** (`data-flat`) and the sheet's heading becomes a small header with the mascot cutout. `measure()` decides from the frame and the sheet's contents, never `scrollHeight` or the plate, or a collapsed plate would stay collapsed; `flat` is sticky while typing. A paused animation counts as running, so a test holding a frame starts no new move.
- **Playwright raises no keyboard:** `e2e/auth-sheet.test.ts` shrinks the viewport and checks the field against the sheet's box, since `toBeInViewport` counts a field the sheet clips as in view.
- **Nothing moves as the page opens:** `data-ready` comes with the first key or pointer press. Fields are `Input`'s `floating` ones, the submit a `busy` `Button`; the login's success hands over in **Arrival** ([Motion](#motion-in-feature-components)).

### Desktop top bar

**`TopBar.svelte` holds the home tab, the breadcrumb, the places, the page's actions and `UserMenu.svelte`.** A page fills the breadcrumb and actions through `shell` in `#lib/shell.svelte.ts` and resets them in its effect's cleanup. Without a page's own actions the bar makes something new where the places say you are: "New recipe" and the recipe import, on the lists "New list" and the list import, as the phone's New sheet does.

- **The home link is a tab hanging from the top edge**, `surface` in both themes, holding the mascot and the wordmark ([Wordmark and lockups](#wordmark-and-lockups)); a cream lockup box was the one light block on a dark page. Below `lg` it holds the mascot alone.
- **The places (Recipes, Shopping lists) are marked from `navPlace`, like the phone's bar**, and show only where `navPlace` is not `null`. The row is a `1fr auto 1fr` grid with `minmax(0,1fr)` sides, so the places sit in the exact middle at every width.
- **"New recipe" (or "New list") turns into a circle only while its label does not fit**: `fitLabel` measures the track, since the label's width is the language's and a fixed breakpoint cut one language or wasted room in another. `e2e/top-bar.test.ts` sweeps the widths in both languages for the exact middle, no overlap and both shapes. Where the places are, the breadcrumb shows only from `lg`.
- **The user menu sits on the `popover` tokens**, since `surface` merged into the overview's chips in dark. Its order is Settings, Appearance, a rule, Sign out, so focus opens on navigation and the destructive action stands apart; Appearance's segments are `DropdownMenu.RadioItem`s with `closeOnSelect={false}`, so the menu's arrow keys reach them and it stays open while the page recolors.

### Phone bottom nav

**`BottomNav.svelte` is one bar: Recipes, Shopping lists, Search (the command palette), You (the You sheet), and New at its end.** New opens `NewSheet` with two ways to something new where you are: writing or importing a recipe, or on the lists (`lists`) starting or importing a list. **Icons only, no printed word**, so no language can squeeze it and the four places are equal slots everywhere; the names are the accessible names. You is a line icon, not the person's circle, so the bar reads as one set.

- **The current place is one `bg-accent` pill, moved by slot.** An open Search or You sheet takes it and gives it back on close. `aria-current="page"` marks the page; on settings You carries `aria-current="true"`, since it opens a sheet rather than being the page.
- **The bar floats at the top of a page and docks past `DOCK_AT`** (`docked` in `frontend/src/lib/components/shell/nav-scroll.ts`). **It always has the docked size and floating is that bar scaled and lifted**, so the move animates only transforms, radius, border color and shadow: animating `left`, `right`, `bottom` and `height` lays the page out every frame and stutters on an iPhone. `rounded-dock`, not `rounded-pill`, because 9999px cannot ease into a small radius. It is `bg-surface` with a hairline, which carries the edge in dark where shadows vanish.
- **It steps aside while a text field outside a dialog has focus** (`isField` in `frontend/src/lib/components/shell/typing.ts`), so the keyboard never puts it over the field.
- **It publishes `docked` and `still` in `bottomNav`** (`#lib/shell.svelte.ts`); the timer player above it reads both to stay with it, and nothing else writes it.
- **A tap on Recipes while on the overview scrolls to the top** and keeps search and filters; only a tap at the top goes to `/` and starts over.
- **`env(safe-area-inset-bottom)` stays 0**, because `app.html` has no `viewport-fit=cover`: `cover` reaches every page and would push the landscape desktop layout under the notch. `main` keeps room for the bar (`AppShell`).

**The You sheet** (`YouSheet.svelte`) is the phone's account menu: the person and the theme `SegmentedControl` in one `bg-surface` card (which its `bg-background` track needs), the settings links in the settings navigation's groups, then Sign out in `destructive`. The theme sits in both account menus and on the profile page because it is switched now and then, not set once.

### Phone screens and their bars

**One bar per phone screen, and only where something is current.** `NAV_PLACES` in `#lib/shell.svelte.ts` maps every page route to `recipes`, `you` or `null`, and `navPlace(routeId, hasError)` is what `AppShell` renders the nav from, so a bar with nothing marked cannot appear. The detail page and both editors own the screen with their own top bar; so do an unmatched path and any page with `page.error` set, where `+error.svelte` offers the way back. `shell.test.ts` globs every `+page.svelte` and fails when a route is missing from the table, so a new route has to decide.

**Those action bars sit at the top.** The bottom is the software keyboard's, and a bar there covers what a cook is reading. They carry at most one control per side plus a title, so nothing truncates. **The detail page's header starts transparent over the cover** and is `pointer-events-none` there, so taps reach the gallery, fading in once the cover has scrolled past.

**A phone navigates a page's parts with a running head and a contents sheet**, as a cookbook does: the head says where you are, the contents page takes you anywhere else, and it holds five sections or fifteen the same way. Both live in `#lib/components/nav/`, take generic `ContentsEntry` items and are `md:hidden`; desktop keeps its rails.

- **`RunningHead`** heads pages (settings): one sticky select-like button named like "Profile, open contents"; its name wraps rather than truncating.
- **`ContentsSheet`** is a `BottomSheet` set as a contents page: one row per entry, a dotted leader, and on the right what a book prints as the page number, truncating before the name ever does. Actions that are not entries follow under a rule.
- **`EditorBar`** (`#lib/components/editor/`) is the editor's head: cancel, the current section with reading progress, save; it opens the same sheet. While it shows, the page's `scroll-padding-top` is its height, so a focused field scrolls out from under it, and the section spy's band (`PINNED`) starts under it. A picked section keeps the head until the reader scrolls again (`stillPinned` in `#lib/recipe/section-spy.ts`), or a short recipe scrolled to its end handed it to the next section.

### Settings navigation

**Settings groups its pages in every nav** - the desktop sidebar, its contents sheet and the You sheet: "For you" and "Household", each under a `GroupHeading` (`#lib/components/nav/`), Sign out under a plain rule. A member sees both groups too, so the shape does not change with the role. The heading is smaller than the rows and never `primary`, or it read as one more entry. The list lives once, `settingsPages(role)` in `#lib/settings/pages.ts`, with each page's icon; `byGroup` in `#lib/components/nav/contents.ts` turns it into the runs all three draw, each a `role="group"` named by its heading.

**The current entry is the bottom nav's pill everywhere:** `bg-accent` with `text-accent-foreground`, in the settings sidebar and in every contents sheet. One idiom for "you are here" across the app.

## Icons (Lucide)

Every icon is a per-icon import from `@lucide/svelte/icons/<name>`; the imports are the list of icons in use (`grep -rho '@lucide/svelte/icons/[a-z0-9-]*' frontend/src | sort -u`). **Before adding one, reuse the icon that already stands for the same action elsewhere** - `ellipsis` for a row's menu, `circle-alert` for an error, `chef-hat` for cooking mode. A Lucide icon that has to animate is redrawn as a component in `src/lib/components/icons/` (see below).

### Icons that answer

Five icons move, each its own component in `frontend/src/lib/components/icons/` with Lucide's paths and plain CSS: `HeartIcon` beats when a recipe is marked tasty, `StarIcon` turns when it becomes a favorite, `CopyIcon` draws a check once a copy has landed, `SendIcon` flies out when a test mail goes out, and `CircleCheckIcon` draws itself when a success message appears. `Checkbox`'s tick is drawn inline, Lucide's check with its path reversed so it draws from the short stroke; Bits UI's `onCheckedChange` sets the cue, so a box mounted checked never draws. Every other icon stays still Lucide.

**Motion here is an answer to an action, never decoration.** The caller plays an icon through its `play()` export (`bind:this`) the moment the thing happened, so nothing moves on hover, on load or when a mark is taken back. `CopyIcon` plays only when the copy succeeded, which is why `copyText` resolves to whether the text reached the clipboard. `CircleCheckIcon` needs no call because its message mounts on success; a message that stays mounted keys the icon on its result. Under reduced motion the state still changes. The icons are `aria-hidden`; the button carries the name.

## Logo

The logo is a mascot: a well-used hardcover cookbook that waves with one hand and holds a wooden spoon in the other, a sage-green ribbon bookmark swooshing out of its pages, painted in vintage-cookbook gouache. Its face is friendly with a hint of mischief and grown-up rather than cute: no blush, no sparkle in the eyes. It says what Rezepte is, the household's cookbook, and belongs to the same family as the demo accounts' ingredient creatures without being one of them: the people are the ingredients, the book is what holds them.

The master is the painting itself, `assets/brand/mascot/rezepte-mascot-original.jpg` exactly as generated, and `rezepte-mascot.png`, the same picture cut out of its cream ground and trimmed. Both are in Git LFS; `prompts.md` beside them records the generator, its settings and the prompts, so a variant (a pose for an empty state) can be generated as an edit of the same figure.

**Wherever there is room, the painting is used as it is, never redrawn**: a vector copy lost the brush texture and with it the warmth, and simplified small versions lost the character. The one exception is the favicon, `assets/brand/icon/rezepte-book.svg`: the book alone, upright, without face or limbs, as a flat vector. At 16 px the figure turns into a brown smudge, while the book with its green ribbon still reads.

### Wordmark and lockups

The wordmark is "Rezepte" in Literata Bold at its display optical size, as one outlined path in the ink (`assets/brand/lockups/rezepte-wordmark.svg`). Bold, because the Medium weight looked thin beside the painted figure.

**Mascot and wordmark always share one rounded cream box with a hairline edge** - the mascot's own ground and the app's light border. The box carries its ground with it, like a label on a cover, so a lockup looks the same in both themes and there are no `-dark` or `-mono` files; without the hairline the box would dissolve into the app's cream background. The app's desktop top bar is the one exception: there mascot and wordmark sit on the bar's `surface` tab ([Desktop top bar](#desktop-top-bar)), the wordmark as a mask in `accent-foreground`.

| File | Composition | Used for |
|---|---|---|
| `rezepte-lockup-horizontal.svg` | mascot left of the wordmark | the public share page's header and its share card, the docs navigation |
| `rezepte-mascot.webp` | the mascot alone | the app's top bar, the credit bar on the public share page |
| `rezepte-mascot-not-found.webp`, `rezepte-mascot-error.webp` | a pose on the app's background | the error page |
| `rezepte-mascot-shopping.webp`, `rezepte-mascot-first-recipe.webp` | the basket pose and the opening-cover pose on the app's background | `NoteEmptyState` on the shopping lists and the recipe overview |
| `rezepte-mascot-switch.webp` | the chef's-hat pose, cut out like the master | the header of "Who's cooking?" |

The SVG embeds the mascot as a WebP data URI, so it is one self-contained file an `<img>` can load on GitHub, the docs site and in the app alike. **It is generated, never edited by hand.** Never recolor a lockup, set the mascot without its box on a busy picture, stretch it, or redraw the figure as a vector.

**The wordmark stands without the box only on the kitchen scene** of `frontend/src/lib/components/auth/AuthScene.svelte`, and there it is the one piece of the logo that may change color: `scene-ink` on the painting, `accent-foreground` on the narrow text page, where the ink would vanish in dark. `AuthScene` sets it as a CSS mask over that color rather than an `<img>`, so the file itself stays in the ink.

**Below `lg` the plate frames the painting on the mascot, never on the picture's middle**: the mascot stands whole and centered, or the painting is not shown at all - never a letterboxed stamp, whose bars read as brown frames. The mascot's place in `rezepte-kitchen.webp` (its ratio, center and extent, its feet as `--figure-foot`) lives once, as custom properties in `AuthScene`'s style block; a new painting changes them there and in the figure box of `frontend/e2e/logo.test.ts`, which holds the mascot clear of the view at the phone widths and checks it against the sheet in sheet state. A view too flat for the whole figure (12/5, `FLAT`) hides the painting: by container query on a page without a frame, by `measure()` in the frame, where it fades out rather than vanishing, since a container query hid it a frame before the fade could run. From `lg` the image covers the window.

### Icons and preview

`mise run //frontend:brand:export` writes everything from the masters (it needs the LFS files, so pull them first if a clone skipped them):

- into `assets/brand/lockups/`: the lockups, `rezepte-kitchen.webp` for the login screen, the [error page](#error-page) and empty-state poses, and the cut-out poses (`CUTOUTS` in `brand-export.ts`), resized from their own cut-out `.png` master (the ImageMagick command is in `assets/brand/mascot/prompts.md`);
- into `frontend/static/`: the favicon (`favicon.svg`, the book file itself, and `favicon.ico` through `@vite-pwa/assets-generator`), the home screen icons (`apple-touch-icon.png`, `icon-192.png`, `icon-512.png`, and `icon-maskable-512.png` inside Android's safe zone), `manifest.webmanifest` (the base locale) and one `manifest.<locale>.webmanifest` for every other locale in `service/internal/i18n/locales.json`, and `og.png`;
- `assets/brand/social-preview.png`, the same picture as `og.png`, mascot and wordmark edge to edge so a platform that crops keeps both.

"Add to home screen" shows the painting, not the book: a home screen icon is large enough for the figure to read. The Go service serves the instance locale's manifest at `/manifest.webmanifest` (`ManifestHandler`, `no-cache` so installed apps pick up changed shortcuts); what it declares belongs to [Installable app](/features/installable-app).

**`//frontend:brand:check`, part of `check`, never reads the masters, since CI does not fetch LFS.** It holds the committed outputs to their shape - the wordmark one path in the ink, each lockup a cream box with the hairline and exactly one embedded WebP, the favicon identical to the book, the manifests to what `manifest(locale)` writes, the rasters to their sizes and ground - but not to their pixels, because sharp may encode differently on another platform. `frontend/scripts/brand-palette.ts` is the one list of these colors; the ink is also the `scene-ink` token and light `accent-foreground`.

In the app, `#lib/components/brand/Lockup.svelte` loads a lockup as an `<img>` through the `$brand` alias (`../assets/brand`, a Vite `resolve.alias` in `vite.config.ts`, where the dev server is also allowed to serve the folder), so Vite fingerprints it. The top bar's home link carries the name through `aria-label` while picture and masked wordmark stay silent; the login's masked wordmark is a `role="img"` named by `aria-label`.

**Link-preview tags.** `app.html` carries the Open Graph and Twitter Card tags common link-preview crawlers read; a recipe link can carry its own ([Link previews](/features/link-previews) owns when).

- **The service makes their URLs absolute** each time it serves the app shell (`renderLinkPreview` in `service/internal/httpserver/spa.go`), since the build can write only paths and most crawlers drop a relative URL.
- **The host is the request's `Host`**, which the reverse proxy already passes for the Origin check, and the scheme is `https` when `REZEPTE_SECURE_COOKIES` is set, the connection is TLS or `X-Forwarded-Proto` says so, so an instance needs no setting for its public address.
- **`robots.txt` allows every crawler**, because Slack's, X's and LinkedIn's honor it.
- The GitHub repository's social preview is the same file, uploaded by hand, since GitHub does not read it from the tree.

**The user docs hold copies of the brand files**, because Next cannot import from outside `docs/user` at build time: the lockup in the navigation (`docs/user/components/lockup.tsx`), the tab and touch icons in `docs/user/app/` (a raster icon beside the SVG, since search results show a site's icon reliably only as a raster), and the social preview as `og:image` through `OG_IMAGES` in `docs/user/lib/shared.ts`. `mise run //docs/user:brand-assets` refreshes them, and `docs/user/scripts/brand-assets.test.ts`, part of that package's `check`, fails when one drifts.

The README's images in `assets/readme/` (the app icon, two framed screenshots) have their corners and borders baked in, since GitHub strips a README's CSS; `mise run //docs/user:readme-images` makes them, and `//docs/user:screenshots` runs it after regenerating the screenshots.

### Error page

`+error.svelte` shows the mascot in one of two poses, both edits of the master with their prompts in `assets/brand/mascot/prompts.md`: on a 404 the book leafs through its own pages with a shrug, on anything else it sits sooty beside a smoking saucepan with "Try again". **The poses are illustrations, not the logo**: they are not cut out (their smoke and page edges are the ground's color), and `brand:export` moves their ground onto the app's background (`PAGE` in `brand-palette.ts`, `reground` in `brand-export.ts`). `brand.test.ts` holds `PAGE` to `--color-background`, so a new background color cannot leave the poses on the old one. On "No connection" the page drops the way back, since the recipes would only fail again.

**The root load never fails, or SvelteKit shows only its bare built-in 500 page.** The likeliest error, an unreachable server, fails `me()` in the root `+layout.ts`. On a route, SvelteKit renders the error page by running the root load once more, so the load remembers its failure and lets that run pass; on an unmatched path the one run is already the error page's, so it passes at once (`route.id === null`). Both return `{ user: null, unreachable: true }`: `+layout.svelte` renders the page bare and `+error.svelte` shows the sooty pose even where the status says 404. `e2e/auth.test.ts` aborts `me()` on `/` and on an unknown path and checks that "Try again" recovers.

## The user docs wear the same palette

`docs/user/` maps the app's tokens onto Fumadocs' `--color-fd-*` variables in `docs/user/app/global.css`, and takes the app's radius scale and maps its shadows onto the four shadow steps Fumadocs uses; `docs/memory/` deliberately stays neutral. The values there are a **copy**, so a change in `frontend/src/app.css` has to be repeated; [Documentation sites](/architecture/docs) owns why the two apps share no file.

Three deltas are intentional and must survive any sync. The contrast figures are against the docs' light `background` and depend on these exact values:

| Docs token | Docs value | App value | Why |
|---|---|---|---|
| `fd-muted-foreground` | `#6f6152` | `text-muted` `#756554` | The docs' most-used token carries body text (sidebar, TOC, page descriptions); the app's value clears AA at 4.82:1, and the docs keep the extra margin (5.15:1) that much reading text needs. |
| `fd-primary` | `#9a4707` | `primary` `#b45309` | Marks the active navigation entry at body size, where the app value's 4.32:1 sits below AA; the docs value is 5.51:1. |
| `fd-accent` | the app's `skeleton` | `accent` | In Fumadocs `accent` is the hover surface, not a chip. The paper tone stays visible on both `card` (sidebar) and `background` (navbar, TOC). |

Dark mode needs no delta: the app's values already clear AA there.

Callouts use an earthy set of their own (`info`, `warning`, `error`, `success`, `idea`) rather than the palette alone, because `info` and `idea` have no counterpart in it. **Every callout color has to clear 3:1 on the callout surface**, `fd-card` - Fumadocs fills the callout icon with the color, so anything under that floor is an icon nobody can see, and a sixth color has to clear it too. `success` is the app's sage darkened for exactly that reason: the app's `success` measures 2.41:1 there. Code blocks use `vitesse-light` / `vitesse-dark` and IBM Plex Mono.

## Why it is this way

The direction is warm and calm so that the food is the loudest thing on the page: paper and cream grounds, a single burnt-orange accent, brown-based shadows instead of gray ones. It is also a phone-in-a-kitchen interface, which is what the pill shapes and the generous target sizes are for - one hand, a wet thumb, and a screen propped against something while a pan is on the hob.

The logo is a painted mascot rather than a drawn mark because a drawn mark with a face reads as generic clip art, and a friendly character only carries once it is painted in the same gouache as the demo avatars. Keeping the painting everywhere it fits, and only the favicon as a vector, follows from that: a simplified figure loses either the face or the warmth.

Both faces are self-hosted through Fontsource and imported from CSS (`frontend/src/app.css`), never fetched from a font service at runtime. A self-hosted app should not tell a third party who is reading which recipe, and a kitchen tablet on a LAN with no internet has to render the same as one online.

New UI takes its idea from the cookbook - a running head, a contents page, a credit line - and has to hold twice the entries it starts with. An element lifted from another part of the app into a new place fits only the case it was built for and breaks with the next entry.

Tokens are the only source of color, radius, shadow and font, which is what makes a palette change a single edit and a dark mode possible at all. A color written straight into a component is a color nothing can theme and nothing can find.

The user docs wear this palette because end users meet the docs before they meet the app: a gray manual wrapped around cream screenshots reads as two products. `docs/memory/` stays neutral for the mirror-image reason - the look is what tells a reader at a glance which of the two sites is open. The contrast deltas are not drift: the same token carries body-sized reading text in the docs and only meta lines and chips in the app, and text people actually read has AA as a floor.

## Rejected

- **A neutral, minimal direction.** Perfectly correct and completely forgettable; it would make this look like every other self-hosted tool.
- **Loading the fonts from Google Fonts.** A request per reader to a third party, and a fallback face on any instance without internet access.
- **A shared token file imported by both the app and the user docs.** One source of truth, but it breaks the independence of the two builds ([Documentation sites](/architecture/docs)) and would have to declare its dark values twice over, since the app switches on `data-theme` and Fumadocs on a `.dark` class.
- **Taking the app's contrast values unchanged in the docs.** Maximum fidelity, and the sidebar, table of contents and page descriptions land below AA. The hue difference is invisible; the contrast difference is not.
- **Callouts in palette colors only.** Fully closed, but `info`, `warning` and `error` would all sit in the same brown-orange-red family, with only the icon telling them apart.
- **`class="dark"` on `<html>`, the common Tailwind convention.** A boolean class has two states where the theme has three: explicit `light`, explicit `dark`, and the attribute's absence meaning "follow the system". `data-theme` carries all three, and it is what lets `:root:not([data-theme='light'])` keep an explicit `light` under a dark system preference.
- **Theming `docs/memory/` the same way.** The neutral look is what marks it as internal.
- **A vector trace of the mascot for the small sizes.** Traced flat, cropped to a bust, or with thicker outlines, it kept the pose but lost the charm, and at 24 px and below only the silhouette survives anyway.
- **A face on the favicon.** At 16 px it is two dark pixels; the book with its ribbon reads better.
- **A face in the phone's dock.** The dock's You keeps a line icon, so the bar reads as one set.
- **A sage or amber box, or a dark box in the dark theme.** Cream is the painting's own ground, so the box and the picture are one surface; a second color would frame the picture instead of holding it.
- **A drawn mark with a face**, such as a brush-painted onion with a sprout. It reads as clip art, and a face drawn in a few strokes looks either startled or smug.
- **The `@jis3r/icons` package (movingicons.dev) for animated icons.** It covers only part of the set in use, wraps every icon in a `<div role="img" aria-label>` that a screen reader announces inside an already labelled button (and that is invalid inside a `<button>`), starts on hover of the icon alone rather than the control, and ignores reduced motion. The five components that move are short enough to own.
- **Animating icons on hover.** On a phone there is no hover, and on a desktop every pass of the pointer sets an icon twitching without anything having happened.
- **Labels in the phone's bottom nav**, on the current item or under every icon. The current item's label made the pill change width between pages, a flexible label ("Einstellungen" on settings) did not fit at 360px, and any label left 1-3px at 320px in longer languages.
- **A docked tab bar from the start, with a label under each icon.** The most familiar shape and the most visible, and it read as a stock app rather than the cookbook; the floating bar that docks keeps the lightness at the top of a page.
- **A dark (`inverse`) or `accent`-tinted bar.** `inverse` turns into a bright cream band in dark mode, and an `accent` bar with a white current pill inverts the app's one "you are here" idiom.
- **A `primary` bar on the left edge for the current entry.** Quieter than the pill, but a second idiom for "you are here".
- **The bottom nav's pill for the editor's sections on a phone.** It reads as a part borrowed from elsewhere and has no room for one more section; the running head and the contents sheet hold any number.
- **A minimized bottom nav** of one icon and a chevron while scrolling. It was the least visible thing on the screen.
- **Book-culture words as visible copy**, such as "Ex libris" on the login. They mean nothing to most cooks; the login's words stay plain, and the wordmark always shows.
- **Inline SVG recolored by tokens.** A painting cannot follow a token, and the box makes a dark variant unnecessary.
