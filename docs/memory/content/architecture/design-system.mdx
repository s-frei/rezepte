<Callout type="info">

  `frontend/src/app.css` owns every value: colors, radii, shadows and type sizes are Tailwind v4 `@theme` tokens there, and components use only the generated utility classes. This page owns what each token is **for**, the rules components follow, and the traps behind them. Look a value up in `app.css`; never copy one into a component. The only values written here are the user docs' contrast deltas, which depend on them.

</Callout>

## Color tokens

Every color token is redefined for dark mode (see [Implementation notes](#implementation-notes)) except the ones marked theme-independent.

| Token | Role |
|---|---|
| `background` | page ground; the track of a segmented control or the servings stepper; bottom sheets |
| `surface` | cards, dialogs, cook mode's page |
| `surface-elevated` | inputs, and anything raised inside a `surface` dialog or panel |
| `border` | 1px borders and dashed separators |
| `popover` / `popover-border` | lists and menus that open over fields or the page: `Select`, the tag and unit suggestions, the user menu. Equal to `surface-elevated` and `border` in light, where the shadow sets them apart; a step lighter in dark, where the shadow does not read |
| `text` / `text-muted` | body text / secondary text and labels |
| `primary` / `primary-foreground` | primary buttons, links, focus outlines, group headings |
| `accent` / `accent-foreground` | display tag chips, step numbers, accent buttons. **Never a success state**: amber reads as a warning |
| `destructive` / `destructive-foreground` / `destructive-soft` | delete actions, error text and banners. `destructive` text has to clear 4.5:1 on `destructive-soft` (the quiet Delete pill) and on `surface-elevated` in both themes; the dark `#e5674f` gave 4.37:1 and 4.41:1, `#e86f58` gives 4.69:1 and 4.73:1 |
| `success-soft` / `success-foreground` | success banners and messages, always with a check icon (`CircleCheckIcon`, see [Icons that answer](#icons-that-answer)). Success is green, never `accent` |
| `success` | small success marks: a status dot, the strong end of the password meter |
| `inverse` / `inverse-foreground` / `inverse-muted` | something laid over the page that has to invert with the theme: toasts, active filter chips, the author popover |
| `skeleton` | loading placeholders |
| `handle` | drag handles, inactive icons, scrollbar thumbs, unchecked round checkboxes |
| `tint-1` / `tint-2` / `tint-3` | placeholder tiles for a recipe without a photo |
| `lightbox` / `lightbox-foreground` / `lightbox-primary` | the lightbox, and marks set on a photo. Theme-independent: it sits behind a photo, not behind the page. `lightbox-primary` is the dark theme's primary, the light one's is below 3:1 on it |
| `overlay` | the scrim behind dialogs and sheets. Black at 60% in dark: the light theme's brown at 40% left a `background` sheet and a `surface` dialog the same tone as the page around them |
| `scene-ink` / `scene-muted` | text set on a painting (the wordmark and its line on the kitchen scene). Theme-independent: it sits on the painting's cream |

A new color means a new token in `app.css` (both dark blocks included), never a hex value in markup.

## Time color

`--color-time-foreground` marks a duration in a step's text, solid when stored and dotted when suggested (`.time-link`, `.time-proposal` in `frontend/src/app.css`). Its values equal `user-teal`'s foreground on purpose and stay a separate token: `user-teal` belongs to people and may be retuned without touching times. See [Step times](/features/step-times).

## User colors

A second, closed palette: one pair per color, `--color-user-<name>` and `--color-user-<name>-foreground`, redefined in the dark blocks like everything else. It marks a person and nothing else. Where it appears:

- **Large, only at a person's own places:** the profile and person page head (`ProfileHead`), the person card (`PersonCard`, in the card's popover or sheet) and the author band over a grid narrowed to one person (`AuthorBand`).
- **Elsewhere at most a small mark (`PersonMark`, `lg` at most), one person per row:** the author circles on a card, the people list, the "Added by" filter chip, the recipe colophon's two people, a shopping row's adder (open rows) or ticker (done rows) - never both in one row.
- **The picker's swatches** show the colors themselves, each named (`userColorLabel`).
- **Beyond the app's pages, always a small circle, beside the name:** a push's icon (the person's face, rendered as a PNG by `avatar.Service.Mark`, see [Notifications](/features/notifications)), the mail circle (`mail.Circle`, see [Email](/features/email)), `/welcome`'s "This is how the others see you" (`PersonMark` `card`) and its inviter (`xs`), and a public page's "Shared by" ribbon (`ribbon`, the sharer's picture under the owner's switch, [Public shares](/features/public-shares)).
- **The own app, tinted for whoever is signed in:** the top bar's avatar (`PersonMark ringed`), the overview running head's dotted leader (`userLeaderClass`, the `-foreground` tone at 55%: full strength outweighed the section name, and amber and clay read as primary beside it), the comment composer, focused, in the writer's paper with their mark beside it, shopping mode's head (their small mark, `ringed` as in the top bar, see [Shopping lists](/features/shopping-lists)), the browser's bar (`theme-color` in the pair's base tone, see [Installable app](/features/installable-app); never on a sign-in page or a public share), and nothing that acts: buttons, links and focus stay `primary`.
- **A ring around a photo**, from `md` (32px) up: the photo, a gap, a ring in the person's color, so a picture still says whose color it is. `md` to `card` 2px gap and 2px ring (1.5px each blurred into one line on a 1x screen); `profile` and `band` 2.5px and 2px past their own 4px cut-out. The ring takes the pair's `-foreground` tone on `background` and `surface` in both themes, the base tone on `inverse` (the author popovers: `PersonCard inverse`), where the strong tone is the ground's own lightness. Initials and marks under `md` get none: the circle already is the color, and at 28px a ring ate the face.

The rules the owner accepted:

- **Public pages show no photo but the sharer's, under the owner's switch.** On a page a stranger can open - a public share, the sign-in pages - a person appears at most as their initial on their color (the login page's "Signed out: Mila"), with one exception: while the owner's "Name who shared it" switch is on, a public share's "Shared by" ribbon carries the sharer's picture, from the share-scoped `/public-images/{token}/sharer.jpg`, which answers only under that switch (see [Public shares](/features/public-shares)). `/avatars/...` answers only a session or token (`get-avatar-file` is `auth.Protected`), so no other photo would even load. `public-shares.test.ts` checks that a share page renders no `/avatars/` image, viewed signed in or not, and no picture at all with the switch off.
- **Color never alone.** Every colored thing carries the face or the initial, and the name stands beside it (or is the control's accessible name, the mark `aria-hidden`).
- **Color only answers "who in the household".** Never state, time, priority, kind or ownership: those keep the main palette. A token's or shared link's card keeps a neutral edge though it has an issuer; the issuer is their mark and name.
- **Where a stranger can look, initial on color, never a photo** - the sharer's picture under the owner's switch the one exception (above). A public share page, `/welcome` (whoever holds the link has no session yet) and the mails that leave the household or reach an address nobody confirmed (the setup mail, the invitation accepted mail) get the person's initial on their color and never their picture: the APIs behind them carry no `avatarId`, and the components get a person without one. A face goes only where a member of the household sees it: the app, a push to a member's device, the notification mails to a member's confirmed address.

- **Each color carries its own foreground.** The author circle is a 12px semibold capital, so it needs 4.5:1 against its own background, and no single ink holds that across eight hues in two themes. The tones stay muted and warm-leaning so a grid of cards reads as cards, not as a status board.
- **Color is never the only signal.** Every circle keeps the person's initial, the card's popover and the recipe colophon spell both names out, a shopping row says "by Jonas" after the mark, the people list prints display and login name, and the picker marks the chosen swatch with a check inside it, not a ring alone.
- **The palette is written in three places; adding or renaming a color edits all three.** `user.Colors` in `service/internal/user/profile.go` owns the order, `frontend/src/app.css` what each name looks like, and `USER_COLOR_CLASSES` in `frontend/src/lib/user/color.ts` the class pair - Tailwind cannot compose `bg-user-${color}` at runtime, so every pair is spelled out. The API's `enum` is the tie-breaker: a color outside it is a `422` before a handler runs, and a frontend that meets one anyway renders `bg-accent` rather than a circle with no background.
- Each language's color names are `user_color_*` in `frontend/messages/en.json` and `de.json`, read only through `userColorLabel` in `frontend/src/lib/user/color-label.ts` (Paraglide needs every key called by name, so the table lives there once): the picker labels its swatches with it, and the color toast on a person names the new color.

## Typography

- Display and headings: `font-display` = Literata (variable, optical size), weights 400/500/600, italic 500 for ingredient-group headings and placeholder initials. The family name is a trap - see [Implementation notes](#implementation-notes).
- UI and body: `font-sans` = Karla, weights 400/500/600/700.
- Numbers: `tabular-nums` everywhere (`body` sets it); fractions as Unicode (½ ¼ ¾ ⅓ ⅔) or “1 ½”.

| Class | Used for |

## Radii and shadows

- Radii: `rounded-pill` (buttons, chips, search, stepper, segmented control, bottom nav), `rounded-4xl` (28px, desktop cards), `rounded-3xl` (dialogs, cover image, sheet tops, mobile cards), `rounded-2xl` (desktop card photos, section containers, every floating panel), `rounded-xl` (mobile card photos), `rounded-lg` (image in a card, the editor's cover tile and its add tile while there is no photo), `rounded-md` (inputs, thumbnails, the editor's other photo tiles and add tile), `rounded-sm` (editor row inputs, list options). Four fall outside the scale and are named for their one caller: `rounded-toast`, `rounded-dock` (the floating phone nav), `rounded-word`, the highlight behind a single word in running text, where `rounded-sm` already reads as a button sitting in the sentence, and `rounded-time`, the cook-mode time chip, which is meant to read as one and is in em so it keeps its shape at every type size. Avatars and icon buttons are circles.
- Shadows, warm and brown-based: `shadow-card`, `shadow-lift` (a hovered recipe card, a photo lifted by the sortable), `shadow-cover`, `shadow-dialog` (dialogs and floating lists), `shadow-sheet`, `shadow-cta` (mobile primary CTA). The dark blocks' `none` for three of them has no effect - see below.

## Implementation notes

**The display face is `'Literata Variable'`, not `'Literata'`.** `@fontsource-variable/literata` declares that family name and CSS matches family names exactly, so both stylesheets lead with `--font-display: 'Literata Variable', Literata, Georgia, serif`; plain `Literata` stays behind it only for a system install. Write the family without `Variable` and the stack matches no `@font-face` at all: every heading, recipe title, step number and the wordmark would render in Georgia. Nothing would look broken - a serif falls back to a serif - and measuring the rendered width is the only way to catch it:

```
appStack 825.9  === georgia 825.9              ← the fallback face
appStack 884.8  === 'Literata Variable' 884.8  ← the declared face
```

Verify with `document.fonts.load("64px 'Literata Variable'")` **before** measuring; a registered face stays `unloaded` until something asks for it, and a width taken in that moment is the fallback's. Keep `frontend/src/app.css` and `docs/user/app/global.css` in sync: each declares the stack for itself, and only a measurement tells you that one of them is wrong. Literata runs ~7% wider than Georgia, which is why the card titles clamp to two lines on phones and three on desktop.

**A `@theme` shadow cannot be re-themed per mode.** Tailwind v4 compiles an `@theme` shadow value into each utility class as a literal `--tw-shadow` declaration instead of a live reference: the built CSS carries `.shadow-card{--tw-shadow:0 1px 2px …}`, where `.bg-surface` carries `background-color:var(--color-surface)`. Color and radius tokens are therefore live and shadow tokens are not, so the `--shadow-card`/`--shadow-cover`/`--shadow-cta: none` declarations in the dark blocks of `frontend/src/app.css` set custom properties no rule reads, and those shadows render in dark mode exactly as in light. A shadow that really has to differ per mode needs a `dark:` utility on the element. The same mechanism is why `docs/user/app/global.css` declares no dark shadow override at all.

**Theme switching.** `data-theme` on `<html>` is absent when the choice is "system"; an explicit choice sets it to `light` or `dark` and is stored in `localStorage` under `rezepte-theme`. There is no `data-theme="system"`: "system" is the attribute's absence, applied before paint by an inline script in `app.html` that mirrors `#lib/theme.ts`.

- **The dark tokens are declared twice** - under `:root[data-theme='dark']` and inside `@media (prefers-color-scheme: dark) { :root:not([data-theme='light']) { ... } }` - because CSS cannot share one declaration block between a plain selector and a media query. Keep both in sync by hand.
- **The `dark:` variant is redefined** with `@custom-variant dark` to follow the same rule instead of bare `prefers-color-scheme`, so a component using `dark:` respects an explicit `light` choice under a dark system preference.
- **`--image-squiggle` is repeated in both dark blocks**, because an SVG in `url()` cannot read a custom property and spells the primary color out.

## Rules that keep layouts from breaking

Each of these comes from a bug that shipped. Verify them at 360px - see [Verify UI with Playwright](/howtos/verify-ui).

- **An action is never bare text.** "Delete" in the people list was a 50×20 target and "Remove" in the ingredient editor 59×20 - text with a click handler and no padding. Give them a padded pill, even where they read like links.
- **A control's hover is `hover-tint`, never `hover:brightness-*`.** The utility in `frontend/src/app.css` lays a 14% veil of the control's own `currentColor` over its background (a `background-image`, so shadow and radius stay), under `@media (hover: hover)` and not on `:disabled`: a light button darkens, a dark one lightens, in both themes, with no color per variant. `brightness` darkened the dark theme's dark buttons by a few levels nobody saw. `Button`, `IconButton` and every hand-built control use it; a hover that changes the control's own colors (`hover:bg-*`, `hover:text-*`) is for ghost and text controls only.
- **Actions inside dense rows are 44px tall on phones** (`h-11`) and drop to the table's density on desktop (`md:h-8`). Elsewhere the floor is the `Button` component's own 40px.
- **A card that carries its own controls is a stretched link.** The anchor holds the title and grows an `::after` over the whole card; the star and the author initials are siblings of it, not content inside it. A `<button>` inside an `<a>` is invalid HTML and a focus trap, and wrapping the card in the anchor is what forces that choice. The wrapper is an `<article>` labeled by the title, so the card still has a name once the anchor no longer spans it, and hover and focus hang off the wrapper via `card-hover` (the `@custom-variant` in `app.css`: `:has(a:hover)` inside `@media (hover: hover)`) / `has-[a:focus-visible]` — an effect then covers the whole card while still answering to the link alone, leaving it at rest when the pointer is on a control, and a tap on a phone never leaves a card stuck in its hover state.
- **A title that identifies something wraps, it does not truncate.** `line-clamp-3` beats `truncate` for recipe card titles - a cut-off name is a card you cannot recognize. `truncate` stays right for secondary lines (tag lists, breadcrumbs) and for a title inside a fixed-height bar.
- **A button never breaks into two lines.** Add `whitespace-nowrap`, and when the row is too narrow give the button its own full-width line (`w-full md:w-auto`) instead. The people list's add button next to its heading needed 306px inside a 302px card and wrapped into an oddly tall pill.
- **Rows with several fields align on one baseline** (`items-center`), and a status hint belongs under its action, not beside it. In the member table "Delete" sat right-aligned above a left-aligned hint, with the name vertically centered against neither.
- **A field has to be able to show its own placeholder.** "Name this group…" needs 140px; sharing its row with a count and a remove button left it 90px on a 360px screen, so a new group opened with its own prompt cut off. Give the field the full line (`w-full md:flex-1`) and let the meta items wrap underneath.
- **What a field shares its line with follows the length of its value, not the kind of field it is.** The editor's source name and source URL, the form's longest values, each own a full-width line under the description, because a quarter of the card is not enough to tell two recipes from the same site apart; the servings and the two times, three two-digit numbers, share a row.
- **A `1fr` grid track stops at its own min-content, so the rigid track beside it is what overflows.** `1fr` carries an implicit `min-width: auto`: once the flexible column has shrunk to its longest unbreakable word it gives nothing more, and a fixed neighbor pushes the row past the container. On the recipe page the title's longest word at 52px floored the text column at 335px, and the 420px cover beside it then hung over the edge between 768px and ~858px - a band that falls between both Playwright projects' viewports, so the suite stayed green. Give the *rigid* track a `minmax(0, …)` and let it yield; putting the `minmax(0, …)` on the flexible one only moves the overflow inside the column, where the word leaves its box instead.
- **A filter has one home, and is shown where it acts.** The tags are not in the filter panel: a second list of the same names there would be two controls for one filter, with no way to tell from either which one the grid answers. They are found through the search's suggestions and, on desktop, the row under it; both read the one `tags` state and mark the chosen ones alike (a check, a pressed chip). What the panel sets stands on the page as light chips (`ActiveFilters`) that only open the panel or drop their filter, so the panel stays the one place a value is changed. The "Filters" button carries no count: every active filter already stands as a chip, and a number beside them counted something else (the tags too) than the folded bar did.
- **Scrollbars are themed once, globally.** `app.css` gives every scroll box a thin `handle`-colored thumb on no track in `@layer base` (`scrollbar-color` on `:root`, which inherits; `scrollbar-width` on `*`, which does not), so no component carries a scrollbar class. It stays in the base layer so a utility still wins: the image gallery hides its bar with `[scrollbar-width:none]`, and the export and import lists add `[scrollbar-gutter:stable]` so their rows do not shift when the bar appears. A dialog does not reserve the gutter, since its content would sit off-center whenever it fits. The filter panel is the one place that draws its own: its body may be cut off between two sections on a phone, and iOS, like macOS by default, shows the system's bar only while the list moves, so nothing said that the sort order waited below. `FilterPanel` hides the system's bar there and draws a `handle` thumb on a faint track in the panel's padding, kept in view whenever there is more to scroll and following the scroll; a resize or a section appearing (the authors, once loaded) re-measures it.
- **A rounded box never scrolls itself.** The browser draws the scrollbar straight along the scroller's edge, through its rounded corners, so it sits in a square box while the left side is round. The rounded box is a frame that clips (`overflow-hidden`) and carries padding; a plain child inside it scrolls. The padding has to clear the corner's curve where the scroller starts: at depth `d` a radius `r` reaches `r - sqrt(r² - (r - d)²)` in, so 8px down a 20px radius is 3.3px, which a 6px side padding clears (`px-1.5 py-2`, `SearchBar`'s list). Built this way: the share dialog's chip field and suggestions (`InvitePicker`), the tag and unit suggestions (`TagInput`, `UnitInput`), the add-to-list ingredients (`AddToListDialog`), the timer panel and dock (`TimerIndicator`, `TimerDock`, whose inner box is `md:contents` so the rows still wrap on a computer, and whose head stays outside the scroll), and every `BaseDialog` (`px-1.5 py-3` on the box, the rest of its 20px, 28px from `md`, on the scroller). A probe finds an offender: for each scroller, walk up to the first ancestor with a radius and compare the scroller's right inset with the curve at its top inset; run Chromium with `ignoreDefaultArgs: ['--hide-scrollbars']`, or headless screenshots show no bar at all. A scroll box also clips focus rings at its edge: whatever sits flush with the scroller needs the ring's 4px inside it (the chip field's `py-1`), or it moves out of the scroll (the dock's head).
- **Two scroll containers inside each other are a guessing game.** A flick 200px from the top moved the tag list, the same flick 200px lower moved the panel body, and nothing on screen said which. A section long enough to want its own scrollbar inside a dialog is long enough to belong somewhere else.
- **A field that shares a row needs `min-w-0` to shrink.** A flex item's automatic minimum size is its min-content width, and an `<input>` contributes its `size="20"` default (166px at the body font) to that even when the input itself carries `min-w-0`. The search bar bottomed out at 226px and pushed the 88px filter button 46px past the right edge at 320px. The fix belongs on the item in the row, not on the input inside it.
- **Separators go between entries, never after the last one:** `last:border-b-0`.
- **A component that can sit in boxes of different widths decides by container query, not by screen breakpoint.** `@container` on the component plus `@min-[280px]:` on what has to fit measures the box it actually lives in; `md:` measures the device and guesses. The theme `SegmentedControl` hides its icons this way, the color picker switches to one row the same way.
- **On desktop a page's own actions go in its rail, not in a bar over its content.** Anything sticky above a scrolling form hides a band of exactly what is being read - the editor's save bar covered 64px of the step the cook was looking at. Where a page has a section rail, that rail is 200px wide and empty for the content's whole height, which makes it the one place a control costs nothing. The editor's rail is a single sticky block: nav entries, a rule, then the stacked actions with the primary on top. 200px cannot hold two pills side by side, and a status line goes under the buttons so that its appearing never pushes them down under the pointer. (Phones keep their own top bar - see **One bar per phone screen** below.)
- **A bar that does float over content is the width of the column it belongs to, never the shell's.** The editor's save bar spanned all 1280px of the app shell while the form is a 720px column, so "Save" sat 240px to the right of the last field it saves. Its sticky offset also has to match the padding underneath it: at `bottom-0` inside a `main` that carries `md:pb-8`, it detached from the viewport edge at the end of the page and hung 32px above it, where `bottom-8` would have made the floating and the resting position identical.
- **A menu or popover never runs past the window.** At 200% text a `w-52` menu is 416px, and on a 360px phone the page grew under it; a phone's layout viewport grows with the page, so the recipe page's fixed bar reflowed and moved the "…" out from under the finger, and the tap's click opened the photo behind it. `app.css` caps every `[data-dropdown-menu-content]`, `[data-popover-content]` and `[data-select-content]` at `100vw - 2rem` in the base layer, so a caller's own `max-w-*` still wins; the same rule drops the browser's ring around a menu a tap has focused (the keyboard lands on an item).
- **The recipe page's phone bar keeps its circles round at 200% text.** `IconButton` and the menu trigger are `shrink-0`, so a squeezed row never makes ovals; the bar itself has no room for three 80px circles, so there they shrink as circles (`aspect-square`, `h-auto`) and its insets stop at 40px and 20px. The detail page's one column below 840px is `minmax(0,1fr)` and the steps/comments tabs wrap: an implicit track grew to the tab row's 439px.
- **Stacking:** dialogs and the lightbox own `z-50`, the mobile header `z-40`. A floating menu that has to clear a fixed bar needs both a `z-50` of its own (Bits UI copies the content's computed z-index onto its floating wrapper, which is otherwise `auto`) and enough `sideOffset` to clear the whole bar, not just its 40px trigger.

## Interaction rules

- **A card's actions sit at its end.** Inside a card, a note or a dialog the buttons follow `DialogActions`: content-sized at the end from `md`, the full line and at least 44px tall below it. A lone button at a card's start read as stray beside text that ended on the right.
- **Buttons point.** `app.css` restores `cursor: pointer` on `button:not(:disabled)` and `[role="button"]`, which Tailwind v4 dropped from its preflight in favor of the browser default. Without it every button reads as non-clickable while links still point. Disabled buttons keep the default cursor, so an unavailable control stays legible as unavailable.
- Search is debounced 250ms (`SearchBar.svelte`); skeletons show only when loading takes longer than 300ms.
- Tag filters are multi-select and mirrored into the URL query.
- The time filter is a bound in minutes on a fixed scale of stops (15/30/45/60/90/120/180/240 and "no bound"), defined in `#lib/recipe/time-filter`. `query.ts` snaps `maxMinutes` to that scale on the way in, rounding up — a bound rounded down would drop recipes the caller asked to see, and a URL that named a value between stops would leave the slider's label naming a different bound than the grid answers.
- Ingredient checks are visual only, kept per session in `sessionStorage` under `rezepte:checked-ingredients` (`#lib/recipe/checked.svelte.ts`).
- Servings persist per recipe in `localStorage` under `rezepte-servings:<recipeId>`; [Cooking](/features/cooking) owns the bounds, the rounding, and cook mode's keys, swipe, motion and wake lock.
- Editor: `beforeunload` prompt when dirty; Enter adds an ingredient row, Backspace in an empty row deletes it.
- Form errors come from a save, never while typing, and a field's error leaves as soon as someone types in that field: it answered the last save and no longer describes what is there. `withoutErrors` in `#lib/form-errors` drops them; the editor's fields name the errors they own with `data-error-key` and one `oninput` on the form clears them.
- Theme: `data-theme` on `<html>`, persisted as `rezepte-theme` - see [Implementation notes](#implementation-notes).
- Respect `prefers-reduced-motion`: under it nothing travels, scales, turns or pulses, and the state still changes. Nothing in Svelte does this on its own - `transition:`, `animate:flip`, svelte-dnd-action's `flipDurationMs` and `scrollIntoView({ behavior: 'smooth' })` all move regardless - so every duration is `$derived(prefersReducedMotion.current ? 0 : n)` (`svelte/motion`), every smooth scroll asks the same, and a moving utility (`transition-transform`, `animate-*`) carries `motion-reduce:transition-none` or `motion-safe:`. A color or opacity `transition` on hover may stay. To check it, freeze the page's clock (see [Verify UI](/howtos/verify-ui#motion-frame-by-frame)) under `reducedMotion: 'reduce'`: `document.getAnimations()` should list nothing after the action.

## Components

Every component wraps a Bits UI primitive where one exists and is styled by hand. The source comments carry the measurements; what follows is what each one is for and the rule a change could break.

### Primitives in `frontend/src/lib/components/ui/`

- **`Button`** (`Button.Root`, or an `<a>` with `href`) - variants primary, secondary, accent, ghost, quiet (a `bg-background` pill without a border, the control at a settings row's end), destructive, destructive-quiet (`bg-destructive-soft` with `destructive` text, the quiet pill of a danger row: the person page's Delete); `sm` sits inside a field, `lg` is the mobile primary CTA. Focus-visible everywhere in the app is a 2px `primary` outline at offset 2, text fields (`Input`, `Textarea`) included: their 1px border turning `primary` alone was too faint to find in a dialog. Only `Input`'s `floating` field keeps its own soft ring. `busy` is a request still out: the button keeps its full strength and its press (`aria-busy`, never `disabled`, which dimmed it to half while it was the one thing working), a sheen in the text color runs through it (`animate-sheen`) over a line filling along its foot towards 92% (`animate-progress`, 3s); the caller ignores the second press and changes the label. Reduced motion shows neither.
- **`IconButton`** (`Button.Root`) - a circle named by `label`. Its default `bg-surface` steps aside when the caller passes a `bg-*` class: there is no tailwind-merge, so CSS source order would otherwise decide.
- **`Input` / `Textarea`** (native, Bits `Label`) - the field rules:
  - `counter` counts **code points**, not `.length`, so it agrees with the server's rune limit. It stays hidden until three quarters of the limit with its padding reserved throughout, is `aria-hidden` (`maxlength` already tells a screen reader), and at the limit goes semibold, never `destructive` - a full field is valid.
  - `required` puts a `RequiredMark` star **beside** the `<label>`, not inside it, so the label stays the field's name for `getByLabel`, password managers and autofill, and a `primary` stroke in the left margin while the field is empty and error-free. The field carries `aria-required`, never native `required`, which would stop the submit with the browser's bubble instead of the form's own error. The stroke needs free space on its left, so it only goes on fields at their container's left edge; a group with no single field (the editor's ingredients) takes the star on its heading. Only forms that mix required and optional fields mark anything; the editor states "* Required field" once.
  - `floating` is the sign-in pages' field (inside `AuthScene` only): 58px, the label inside it, floating up (scaled 0.78) on focus, with a value, or autofilled - `:-webkit-autofill` in a rule of its own, since one unknown pseudo-class drops a whole selector list. It is still the `<label for>`, behind a `placeholder=" "` that `:placeholder-shown` needs. A field marked `aria-invalid` (from `error`, or passed straight through, as the login does for one message under two fields) has its outline traced in `destructive` from the top-left corner round (an SVG `rect` with `pathLength="100"`, 320ms; `rx` from `--radius-md` in CSS), its border turning as the trace closes, a second wrong field 60ms behind; refocused, its ring and label are red too. Only the way in moves, so typing takes the error away at once. Every move waits for `data-ready` on an ancestor (see Login under App shell), and reduced motion keeps none.
  - `prefix` (the source name's "Adapted from" / "Nach") is measured, not a fixed inset, because its length is the reader's language's; like `suffix` it is part of the field's meaning and is described with `aria-describedby`.
- **Read-only value** (a pattern, not a component) - a value someone reads but cannot change, such as the login name on the profile page, sits in a `rounded-md bg-background` block sized to its content, never to the column: a field always spans its column, so the block cannot be mistaken for one and no disabled input invites a click. `bg-background` because `surface-elevated` on a `surface` card is white on cream and disappears.
- **`Select`** (`Select`) - `variant` sets the shape only (`field` the height of `Input`, `pill` for a people row; an `h-*` class from the caller replaces the height, so a settings row's pill matches its 36px buttons); the caller sets the background, one step above its ground: `bg-surface-elevated` in a dialog or panel, `bg-surface` on the page. The list sits on the `popover` tokens, aligned to the start edge by default, kept 16px (the page gutter) off the viewport's edges by `collisionPadding`, and never narrower than its trigger (`--bits-floating-anchor-width`, not a fixed number). `align="end"` is for a trigger at a `SettingsRow`'s end (language, role): aligned on its start, a list wider than the pill grew rightward past the card. It opens in 120ms out of the trigger's side of it (`animate-drop`: fade and scale from 0.96 about bits-ui's `--bits-floating-transform-origin`, which follows a flip above) and closes at once; under reduced motion it only fades (`animate-appear`). Where a role cannot change there is no pill, since the group heading already names it.
- **`TagInput` / `UnitInput`** (own `role="combobox"` + `role="listbox"`, in `editor/`) - their lists look like `Select`'s.
- **`TagChip`** (own) - with `onclick` a filter chip (`aria-pressed`, active on `inverse`), without one a display chip on `accent`. `leading` puts a `PersonMark` into an "Added by" chip, `trailing` an icon after the label in place of the count (the phone's chosen tags carry their ×). The label truncates, so a long tag gives way before the chip leaves its row. `ariaLabel` names a chip by what a tap does and drops `aria-pressed`: a chip that only ever removes is a button, not a toggle.
- **`BaseDialog`** (`Dialog`) - the centered dialog. Capped at `100dvh - 2rem` and scrolling inside itself, so a form taller than a phone keeps its title and buttons reachable. 440px by default, `wide` 720px where content sits side by side (the add-account form's two columns, the pass-on card beside its actions): a dialog that scrolls on a desktop is the signal to go `wide`, a short one at 720px is mostly empty. `dismissible={false}` keeps the token reveal open on Escape. The content is `wrap-break-word` and its `h2` (every `Dialog.Title`) `hyphens-auto`: "Einrichtungslink" at 200% text scrolled the dialog sideways. Hyphenation stops at the title, since a button label never breaks. A dialog with two groups of fields heads each like the people list's groups. `ConfirmDialog` is a `BaseDialog` with ghost Cancel and a primary or destructive confirm. Every dialog's buttons sit in `DialogActions` (in `ui/`, the caller adds only the gap above or a hairline): they wrap instead of squeezing, never break their label, grow to fill their line and stand 44px tall below `md`, and sit content-sized at the end from `md`. On one fixed row, Cancel and "Send link" ran off a 320px phone's dialog at 200% text.
- **`BottomSheet`** (`Dialog`) - the phone's one sheet: rises from the bottom edge on `background`, its grip is the close button. It stays `background` in dark too (its contents lay `surface` panels on it); the dark `overlay` is what sets it apart from the page. The contents, You, New, person, author, share and import sheets all use it. The filter panel is a dialog on desktop and the same sheet on a phone, so it draws the grip and the `background` itself below `md`.
- **`SheetHandle`** - that grip, a 44px button with the 4px bar in its middle (the command palette's grip likewise): a tap closes the sheet, and so does pulling it down. The sheet follows the finger and closes once let go a quarter of its height down or flicked faster than 0.5 px/ms; short of that it springs back, and the click that ends the pull is swallowed so it does not close. It finds its sheet as the closest `role="dialog"`, and the sheet's own outro carries on from where the finger left it. The mobile e2e tests "…closes when its handle is pulled down" drive it with the mouse; measure the handle only after the sheet's rise has finished, or the press lands lower, in the text, and selects it.
- **`CommandPalette`** (`Command` in a `Dialog`) - a dialog near the top on desktop, a bottom sheet below `md` that the bottom nav's Search opens. On a phone opening focuses the field, not the grip, so the keyboard comes up, and the sheet's bottom follows `visualViewport`, measured against a zero-height fixed probe rather than `innerHeight` (Chrome for Android anchors fixed elements to a different box). Rows highlight in whichever of `surface` and `background` the container is not. "All results for …" hands the query to the overview as `/?q=`, offered only while there is something to hand over. A navigation closes it only if it was open when the navigation began (`beforeNavigate`): one opened with ⌘K while a page change was still under way was meant for the new page, and closing it in `afterNavigate` swallowed the key - the page transition made that window long enough for e2e under load to hit it.
- **`SegmentedControl`** (own `role="radiogroup"`, roving tabindex) - below `md` each segment's `::after` reaches over the track's 4px above and below, so a 36px segment hits on 44px. Its track is `bg-background`, so on a background-colored sheet it needs a `bg-surface` panel under it (the You sheet). `disabled` is `aria-disabled`: the checked segment stays focusable, clicks and arrow keys are dropped (a held group's kinds on Settings → Notifications). The `@container` is phones only, since from `md` it sits content-sized beside text in rows (and does not shrink there), where an inline-size container would measure 0; three or more segments hide their icons below 280px of it, two always show them. The checked look is one `aria-hidden` `bg-surface` pill behind the labels; on each segment the background blinked across. The segments differ in width (their labels, the icons from 280px of container width), so the pill is measured from the checked button's `offsetLeft`/`offsetWidth` rather than moved by a fraction like the bottom nav's, and only a pick glides it (`animate()` on `translate` and `width`, 300ms, `--ease-glide`): mount, a `value` changed from outside and every resize (a `ResizeObserver` on the group and the buttons) place it without motion, so a window resize never leaves it trailing. Instant under reduced motion. `size="sm"` (segments `h-7`, 36px with the track) is the one height of a `SettingsRow` control from `md`, where the row lifts it to 44px below; everywhere else it stays 44px. Labels never truncate: the track wraps, so segments that do not fit side by side (200% text on a phone) go onto a second line, and the pill is measured with `offsetTop`/`offsetHeight` too. The account menu's Appearance segments are equal squares, so their pill moves by its own width with a CSS transition, like the bottom nav's.
- **`AccessLadder`** (own `role="radiogroup"`, roving tabindex) - for levels where each includes the ones below (a token's access). Labels sit under the bars, which lets four fit a 320px phone where a segmented control cuts "Read & write" off; a sentence under it (`aria-describedby`) says what the chosen step allows.
- **`Switch`** (`Switch`) - a setting that takes effect when flipped; a checkbox marks an item in a list instead. The 28x16 track sits in a transparent button that is the hit area, 44px tall below `md` and 36px from it like a settings row's other controls, 8px wider on each side and given back by a negative margin; vertically it gives back all but a 22px line (`-my-[11px]`, `md:-my-[7px]`), so in a top-aligned row the track sits on its title's first line instead of 10px below it. The focus outline stays on the track. It reports `role="switch"`, so Playwright's `check()` does not drive it: click and read `aria-checked`. The thumb clicks into place on `--ease-spring` (200ms), at once under reduced motion.
- **`Checkbox`** (`Checkbox`) - the square form checkbox; the ingredient list draws its own round one on the same primitive. Its tick draws itself when the box is clicked (see [Icons that answer](#icons-that-answer)); a box that loads checked, or that "select all" checks, shows it at once.
- **`Slider`** (`Slider`) - `value` is a **position** on a fixed scale, not the quantity behind it; the caller maps position to meaning. `role="slider"` sits on the thumb, so `aria-label`/`aria-valuetext` go there, never on the root. `muted` when the setting is off; a filter refetches from `oncommit`, not per step.
- **`Skeleton`** - the pulse and color only; size and radius come from the caller.
- **`EmptyState`** - the italic "R" circle, a title, a sentence and actions.
- **`NoteEmptyState`** - an empty page that explains itself, for the two a person meets first: the recipe overview with no recipe on the instance and the shopping lists overview with no list. A mascot pose (`art`) on a small stack of pages, as on the error page, beside a taped note (`surface`, `rounded-t-md rounded-b-xl`, a strip of `accent` tape) whose title and steps read as the rows of a list: an `ol`, each step a line and a muted hint, the circles before them decoration (`aria-hidden`). The caller's actions sit at the note's end. Below `md` both pages look alike: the painting (41% of the note up to 128px, in px and % so larger text does not grow it; at 80px it went under on a phone, and a fixed 128px left "Einkaufsliste" no room beside it on a 320px phone) shares the note's grid cell and sits in its top end corner, 40px over its edge, so it lines up with the note whatever the page does - the two pages once placed it differently (one above the note, one absolutely in the page's corner) and it never sat the same. An empty float under it (`art-room`) keeps the title beside it, and a word that no longer fits there moves below it; the steps `clear` it, so they never start in a sliver beside the painting. The title is in `rem` and hyphenates only once the note is narrower than 12rem (an `@container` query, in `rem`, so it switches on as the text grows, not on a 320px phone at normal size, where "keine Ein-kaufsliste" broke for nothing), with `hyphenate-limit-chars: 6 3 3` as on the recipe cards, so "keine" never splits and a long word still may, and at 200% text "Einkaufsliste" hyphenates instead of running under the painting or off the note. `overflow-wrap: break-word` is not on it: beside the float it broke "Noch" into "Noc" and "h". Below `md` the whole is at most `max-w-md`, so a large phone's note does not stretch. The actions stay above the bottom nav at 360px on both pages (the overview's at 702px, just above it); at 320px the recipe overview scrolls to them. From `md` the two stand side by side, the picture narrower up to `lg` so its fanned pages keep clear of a tablet's gutter. On arrival the picture drops in and its pages fan out, the note is pressed on, its rows are written one after another (a `clip-path` from the left, 160ms apart) and the actions rise last; under reduced motion it is all simply there. It keeps `data-empty`, which the overview's glide names. The primary action carries `shadow-cta` and a `size-5` plus at `strokeWidth` 2.5 that turns a quarter on hover; a plus in a translucent disc read as muddy on the primary fill. Every other empty state stays an `EmptyState`.
- **`LifetimeBar`** - how much of a token's or shared link's life has passed; `aria-hidden`, so the caller states the dates in words.
- **`Stamp`** - a rubber stamp over a token or link row for what happened to it (`destructive` gone or paused, `caution` reversible); decoration only, the caller says it in words.
- **`PersonMark`** (own, not Bits UI `Avatar`) - the one component for every circle that stands for a person: their color pair and initial, their picture over it when the account has one. The top bar's own circle is `ringed`: the signed-in person's own color (their initial on it, or their photo) with a fine ring in the pair's `-foreground` tone, 1.5px past a 2px gap, whether it shows a photo or the initial - it is where the app says whose it is. The phone's dock keeps its person icon: the owner turned down a face there. The photo's ring is an `outline` with an `outline-offset` (`userRingClass`), not a `ring-offset` box shadow: the offset is transparent, so the gap is whatever ground the circle sits on and no caller has to name it, and an outline paints after a caller's `ring-*` cut-out instead of fighting it for `box-shadow`. Like a shadow it is clipped by any `overflow` ancestor, so a ringed mark keeps 4px clear of a scroll container's edge. Chrome floors outline widths to whole device pixels: the profile's 2.5px is 2px on a 1x screen. The `<img>` is `absolute inset-0` because the circle's `initial-centered` padding would cut an in-flow picture short; a failed load falls back to the initial. The picture's address is `avatarUrl(person)` (`/avatars/...`, a session's) unless the caller passes `src`, which the public share page does with the sharer's share-scoped address. The card's initials use `corner` (24px, 28px on the desktop card), the size its card corner gives, in px because the corner's geometry sets it; `xs` (20px) and `xs-plus` (24px), the marks that sit in a line of text (a shopping row, the colophon, a filter chip), are sized in `em` of their own 12px letter, so with text scaled to 200% (Android's font size, which grows px text and nothing else) circle and letter double together instead of the letter spilling out of a fixed circle; the author filter uses it at `xs` - in the panel, the chip under the search and the phone's folded bar - so a filter shows the person the way their cards do. `band` (52px, 60 from md, capped at 64/72px so 200% text does not make it the band's biggest thing) is the author band's photo. `ribbon` (40px, ringed like `md`) is the public page's "Shared by" ribbon: a 32px pill in the sharer's color pair right under the title block's source line, the author band's motif shrunk to one line so it closes the title block instead of opening a section, with the mark standing over both of its edges and cut out by the page's ground. There the mark is `strong` - `userColorClasses(color, true)`, the pair turned over with the `-foreground` tone as ground - because an initial in the ribbon's own base tone would melt into it; a photo covers that ground anyway, and its ring rather than the face lines up with the text column. Anything under 20px stays a color dot (`PersonDot`): a face at that size is a smudge, and a share's creator carries no `avatarId`.
- **`PersonDot`** - a person as a dot in their color beside their name in a chip, where no picture travels: a shared link's creator, an API token's issuer. It carries a 1.5px `text-muted` ring: a dark color sank into a dark chip and a light one into a light chip, and the ring keeps both visible on either. Every small color dot is this component, so they all read alike.
- **`PersonCard`** - one person: a `Popover` on a wide screen, a `BottomSheet` below `md`. It sets no color of its own and inherits its surface's text color, so one component reads on `inverse`, `surface` and a sheet. With no recipes the count stays and the link goes (it would lead to an empty filter); the link is a 44px block, and below 16rem of card (a phone's sheet at 200% text) the photo stands above the text; `onnavigate` lets a popover close when its link is followed. Roles and counts come from one cache, `frontend/src/lib/user/people.svelte.ts`, loaded once from `/people` and `/authors` and refreshed only by a page reload.
- **`Lightbox`** (`Dialog`, no overlay) - `lightbox` tokens; Escape is Bits UI's, arrows and swipe are the component's.

### Patterns in feature components

- **`RecipeCard`** - a stretched link (see the rules above). Its desktop look hangs off `desk:`, not `md:`: from `md` up, and on a phone that shows one card per row (see [Recipes and search](/features/recipes)). Wherever this page says "on a phone" for the card, it means a phone with two cards per row. The total time is a `text-label` line over the title, not a pill: the longest time the service allows ("47 Std 59 Min") fits a 320px phone's card that way, so it is never rounded. Without a time there is no time line: the overview is a masonry, so no line is reserved for a missing value. Its corners are concentric: a round mark in a rounded corner shares the corner's center, so corner radius = mark radius + gap. Card 28px (24 on a phone) = photo 20 (18) + 8 (6) inset; the 28px star sits 14px from the card edge, so its center is the photo corner's center; the initials (28px, 24 on a phone) share the center of the card's bottom-right corner, 14px (12) from both edges, so they sit on the star's axis. Their wrapper holds the 2px ring in a 2px padding, so the group is as tall as the pill beside it, and a negative margin moves it from the text's 16px (12) inset into the corner; it is bottom-aligned in the footer, so wrapped tags never lift it. The photo keeps its ratio, clamped to 4:5 through 16:9. Contrast on a text card: tags in `text`, the phone title in `accent-foreground`, the desktop title in `primary` (large text); each pair is at least 4.5:1, 3:1 for the large title. A title hyphenates (`hyphenate-limit-chars: 6 3 3`); a text card's larger title also breaks anywhere (`wrap-anywhere`) when a word still does not fit. On a phone the star is a 24px translucent disc on the photo's 18px corner (a 28px light one on a text card's 24px corner), its target grown to 44px by an `::after`; the footer gives the tags a line of their own, two lines on a photo card, and the tasty count's end cap shares the center of the card's bottom-left corner as the initials the bottom-right one's. From md the heart on a photo is 28px in its 20px corner. The tasty pill in a footer is as tall as the initials with their ring, 28px on a phone and 32px from md.
- **Grid change** - a new card size, and a new list for a filter or an order, glide the overview's cards to their new place through a view transition, 450ms on `--ease-glide` (sets off gently and settles without the spring's overshoot): a card that stays glides, one that leaves fades out in 80ms where it was and one that joins fades in after it (60ms late, 160ms), so a card leaving a slot and one arriving in it never show both titles at once. The empty state crosses over the same way. "Load more", the search while typing and the first list on page load go without; [Recipes and search](/features/recipes) owns how. A fixed element over the page needs a `view-transition-name` of its own, or the cards glide over it.
- **Tag row** (`TagFilter`) - a picked tag glides to the front with `animate:flip` (240ms) and the chips it overtakes make room; it passes over them (`z-10` on a chosen chip), not under. No outro, since the folded row clips and `measure()` has already dropped a chip that goes. `measure()` assigns `folded` only when the set of names changes: a fresh array of the same names, assigned in the same update as the pick, re-ran the keyed each, flip measured the chips where they already stood, and nothing moved.
- **Active filter chips** (`ActiveFilters`) - a new chip grows in (`in:scale` from 0.9, 160ms) and the rest make room with `animate:flip` (200ms), the panel's chips and the tags in one keyed list so a tag after a dropped chip glides up too. No `out:`: `keepFocus` hands the focus on once the removed button is out of the document, one task after the click. Svelte's transitions are local, so the chips standing when the row appears - a page load, the first filter - do not pop in.
- **Search suggestions** (`SearchBar`) - the list drops 4px into place and fades in over 140ms as it opens, and goes at once on close; under reduced motion it only fades.
- **Settings lists** (tokens, shared links, people) - a row the viewer added opens and one they revoked or deleted closes (`transition:slide`, 200ms, `cubicOut`), and the rows after it follow in the flow. `rowMotion()` in `#lib/settings/row-motion.svelte.ts` holds the duration: the page hands the add or remove to `play`, which sets 200ms, makes the change and drops back to 0 a frame later, so a load, a filter (the shared links' "everyone" reloads the list) and a role change that moves a person to another group swap rows at once. The rows read it as their `motion` prop. The token and link lists are spaced by the rows' `mb-3.5` and the list's `-mb-3.5`, not a `gap`: slide folds a row's margin with it, where a gap stayed until the row was gone and then jumped. No `animate:flip`: with an `animate:` Svelte takes a leaving row out of the flow (`position: absolute`) and the rows below would slide up over it. The last row going, or the first arriving, swaps the empty state at once, since the branch around the list changes. A deleted person's row is still in the document while it closes, so focus inside it counts as lost and moves to the card's heading.
- **Install banner** (`InstallBanner`) - × folds the note away (slide and fade, 240ms) and the overview closes up under it; an install or the phone leaving the breakpoint takes it at once, and it never arrives with motion.
- **Password meter** (`PasswordStrength`) - fades in with the first character (160ms); a new score colors the segments one after another from the left (200ms each, 40ms apart). Under reduced motion both are instant.
- **Card size switch** (`CardSizeControl`) - one `bg-accent` pill under the icons glides to the chosen one (240ms, `--ease-glide`), as in the bottom nav: the options are equal squares, so each step is a square plus the 2px gap. Instant under reduced motion.
- **Detail page and cook mode** - the ingredient strike and the servings answer ([Cooking](/features/cooking)), the cover and lightbox crossfade ([Images](/features/images)), the diary's entries ([Recipe comments](/features/recipe-comments)), your circle in the tasty stack ([Tasty](/features/tasty)), the timer player, dock and panels ([Cook timers](/features/cook-timers)), and the share sheet's preview, which fades in over 150ms when it arrives. Cook-step text and its size, countdown digits and anything on load stay still; a mark taken back snaps.
- **Card photo** (`RecipeCard`) - the photo's box holds the `skeleton` tint, and a photo that loads fades in over 200ms instead of popping in as the list scrolls; one the browser already holds (`complete` when the card mounts, a way back from the recipe) shows at once and never fades. Reduced motion shows it at once.
- **Sign-in** - `signIn` in `#lib/page-transition.ts`, taken by `pageTransition` for a `goto` from `/login` to the overview only (a `next` elsewhere, or `/welcome`'s sign-in, gets the page change): the card grows into the app, about 900ms. The old page names the card `sign-in-card` - from `lg` the card (`data-auth-card`), below it the text page (`data-auth-page`, square) - and writes its box and corner radius to `--sign-in-from`; the new page names the layout's tree `sign-in` (`data-app` in the root layout), and every other name inside it is cleared for the run (`html[data-sign-in] [data-app] *`), so the bottom nav and timers open with the app instead of floating over it; the two names are set inline with `important` to beat that rule. In app.css the `sign-in` group is a sheet clipped from the card's box to the window (405ms, slow start) turning from `surface` to `background`, the overview appears on it 90ms in (200ms), the card's picture lets go of its contents above it (144ms; `z-index: 1`, or the sheet would hide it at once), and the kitchen (`old(root)`) recedes to 0.94 and 40% over `surface`. The update waits for the overview's cards and its first eight photos (capped at 400ms, like the cover) so it never opens on an empty grid, and the overview's first list after it sets `data-arrival`: every card rises (`--rise` on `RecipeCard`), the first eight 40ms apart from 270ms, 360ms each, the rest with the eighth. The pseudo-elements show the new page live, so the rise plays through the transition and on after it. Under reduced motion only the pages fade through (80ms out, 160ms in after 60ms), after the same wait. Built on `document.startViewTransition` only: `Element.startViewTransition` broke Safari once. The address already reads `/` while the old page is captured, so a test that signs in and then touches the overview's DOM waits for the overview's heading, not for the URL - `document.querySelector('main')` otherwise finds the login's `<main>`, which goes a frame later.
- **Page change** - `pageTransition` in `#lib/page-transition.ts`, returned from `onNavigate` in the root layout, wraps every navigation between two routes in a view transition: the old page fades out in 80ms and the new one in after it (60ms late, 160ms), so the two never lie over each other - crossed over, both texts showed through one another. The desktop top bar is named `top-bar` and shows its new state at once (no old picture, no animation): faded with the page it went blank for two or three frames on every click and read as flicker, and crossed over on its own it showed "New recipe" through the recipe's "Cook mode". Its segments' 150ms color change is all that moves; the phone's bar stays put through its own `bottom-nav`. Measured with a CDP screencast (`Page.startScreencast`) over a click, the header band's contrast per frame: a page change that blanks it drops near zero. Between the overview and a recipe the card's photo becomes the detail cover and back (`recipe-cover`, 420ms on `--ease-glide`): both carry `data-cover` (the card's with the slug), only a rendered one on screen is named, and on the way back the update waits up to 400ms for the overview's fetched card and the picture's `decode()`, polled with timers because no animation frame runs while an update is pending. A change of the query on the same route, reduced motion, and a back or forward on a touch screen (whose swipe already slides the page) go without - except the app's own back buttons (detail, cook mode), which call `back` from the same module instead of `history.back()`: a tap draws no slide, and without the transition the overview flashed bare before its cards came. `the back button glides the cover home on a touch screen too` in `frontend/e2e/recipes.test.ts` counts the transitions. ## Icons (Lucide)

Every icon is a per-icon import from `@lucide/svelte/icons/<name>`; the imports are the list of icons in use (`grep -rho '@lucide/svelte/icons/[a-z0-9-]*' frontend/src | sort -u`). Before adding one, reuse the icon that already stands for the same action elsewhere - `ellipsis` for a row's menu, `circle-alert` for an error, `chef-hat` for cooking mode. A Lucide icon that has to animate is redrawn as a component in `src/lib/components/icons/` (see below).

### Icons that answer

Five icons move, each as its own component in `frontend/src/lib/components/icons/` with Lucide's paths and plain CSS: `HeartIcon` beats twice when a tap marks a recipe tasty, `StarIcon` turns a fifth and springs back when it becomes a favorite, `CopyIcon` slides its sheets together and draws a check once a copy has landed (back after 1.6s), `SendIcon` flies out at the top right and back in from the bottom left when a test mail goes out, and `CircleCheckIcon` draws itself when a success message appears. One more is drawn inline rather than as a component, because only its box uses it: `Checkbox`'s tick is Lucide's check with its path turned around, so it draws from the short stroke to the long one (200ms, `--ease-glide`) when the box is clicked - Bits UI's `onCheckedChange` sets the cue, so a box mounted checked never draws. Every other icon stays still Lucide.

Motion here is an answer to an action, never decoration: the caller plays an icon through its `play()` export (`bind:this`) at the moment the thing happened, so nothing moves on hover, on page load or when a mark is taken back. `CopyIcon` is played only when the copy succeeded, which is why `copyText` resolves to whether the text reached the clipboard. `CircleCheckIcon` needs no call because the message it sits in mounts on success; a message that stays mounted keys the icon on its result to draw it again. Under `prefers-reduced-motion` the state still changes - the heart fills, the check is there - it just does not travel. The icons are `aria-hidden` like the Lucide ones around them; the button carries the name.

## Logo

The logo is a mascot: a well-used hardcover cookbook that waves with one hand and holds a wooden spoon in the other, a sage-green ribbon bookmark swooshing out of its pages, painted in vintage-cookbook gouache. Its face is friendly with a hint of mischief and grown-up rather than cute: no blush, no sparkle in the eyes. It says what Rezepte is, the household's cookbook, and belongs to the same family as the demo accounts' ingredient creatures without being one of them: the people are the ingredients, the book is what holds them.

The master is the painting itself, `assets/brand/mascot/rezepte-mascot-original.jpg` exactly as generated, and `rezepte-mascot.png`, the same picture cut out of its cream ground and trimmed. Both are in Git LFS; `prompts.md` beside them records the generator, its settings and the prompts that led there, so a variant (a pose for an empty state, say) can be generated as an edit of the same figure.

Wherever there is room, the painting is used as it is, never redrawn: a vector copy lost the brush texture and with it the warmth, and simplified small versions lost the character. The one exception is the favicon, `assets/brand/icon/rezepte-book.svg`: the book alone, upright, without face, arms, legs or spoon, as a flat vector in seven colors. At 16 px the figure turns into a brown smudge, while the book with its green ribbon still reads.

### Error page

`+error.svelte` shows the mascot in one of two poses, both edits of the master with their prompts in `assets/brand/mascot/prompts.md`: on a 404 the book leafs through its own pages with a shrug ("This page isn't in the book", one button back to the recipes), on anything else it sits sooty beside a smoking saucepan ("Something went wrong", a primary "Try again" that reloads, and the way back). The poses are illustrations, not the logo, so they do not sit on the logo's ground: they are not cut out either - their smoke and page edges are the ground's color - and `brand:export` moves their ground onto the app's light background (`PAGE` in `brand-palette.ts`, `reground` in `brand-export.ts`; the generator paints each on a slightly different cream). The painting lies as a slightly turned card (`surface`, hairline, `shadow-lift`) on two pages fanned out under it, 240 px wide on a phone and 300 px from `md`, where the text stands beside it, left-aligned in a 25rem column (wide enough for both buttons in a row, narrow enough that the balanced heading leaves the pair centered). Above the heading a pill in the accent names the case: "Error 404" (any status, `error_code`), or "No connection" with a blinking dot when the server is unreachable, where the page drops the way back, since the recipes would only fail again.

The page answers a navigation, so it moves once as it opens (scoped keyframes in `+error.svelte`): the card drops in on `--ease-spring` while the pages fan out, the pill, heading, text and buttons rise after it 100ms apart, and after an error the card shakes once. The dot's blink is the only loop. Everything sits in `prefers-reduced-motion: no-preference`, so under reduce `document.getAnimations()` is empty. `brand.test.ts` holds `PAGE` to `--color-background`, so a new background color cannot leave the poses on the old one.

The likeliest error is the server being unreachable, and that fails `me()` in the root `+layout.ts`. A failed root load leaves SvelteKit only its bare built-in "500 Internal Error" page, so the load never fails where SvelteKit still has a page to render. On a route, SvelteKit renders the error page by running the root load once more, so the load remembers its failure and lets that run pass; on a path no route matches, the one run is already the error page's, so it passes at once (`route.id === null`). Both return `{ user: null, unreachable: true }`: `+layout.svelte` renders the page bare (no account, no nav), `+error.svelte` shows the sooty pose even where the status says 404, and centers itself in the window. `e2e/auth.test.ts` aborts `me()` on `/` and on an unknown path and checks that "Try again" recovers.

## The user docs wear the same palette

`docs/user/` maps the app's tokens onto Fumadocs' `--color-fd-*` variables in `docs/user/app/global.css`, and takes the app's radius scale and maps its shadows onto the four shadow steps Fumadocs uses; `docs/memory/` deliberately stays neutral. The values there are a **copy**, so a change in `frontend/src/app.css` has to be repeated; [Documentation sites](/architecture/docs) owns why the two apps share no file.

Three deltas are intentional and must survive any sync. The contrast figures are against the docs' light `background` and depend on these exact values:

| Docs token | Docs value | App value | Why |
|---|---|---|---|
| `fd-muted-foreground` | `#6f6152` | `text-muted` `#756554` | The docs' most-used token carries body text (sidebar, TOC, page descriptions); the app's value clears AA at 4.82:1, and the docs keep the extra margin (5.15:1) that much reading text needs. |
| `fd-primary` | `#9a4707` | `primary` `#b45309` | Marks the active navigation entry at body size, where the app value's 4.32:1 sits below AA; the docs value is 5.51:1. |
| `fd-accent` | the app's `skeleton` | `accent` | In Fumadocs `accent` is the hover surface, not a chip. The paper tone stays visible on both `card` (sidebar) and `background` (navbar, TOC). |

Dark mode needs no delta: the app's values already clear AA there.

Callouts use an earthy set of their own (`info`, `warning`, `error`, `success`, `idea`) rather than the palette alone, because `info` and `idea` have no counterpart in it. **Every callout color has to clear 3:1 on the callout surface**, `fd-card` - Fumadocs fills the callout icon with the color, so anything under that floor is an icon nobody can see, and a sixth color has to clear it too. `success` is the app's sage darkened for exactly that reason: the app's `success` measures 2.41:1 there. Code blocks use `vitesse-light` / `vitesse-dark` and IBM Plex Mono.

## Why it is this way

The direction is warm and calm so that the food is the loudest thing on the page: paper and cream grounds, a single burnt-orange accent, brown-based shadows instead of gray ones. It is also a phone-in-a-kitchen interface, which is what the pill shapes and the generous target sizes are for - one hand, a wet thumb, and a screen propped against something while a pan is on the hob.

The logo is a painted mascot rather than a drawn mark because a drawn mark with a face reads as generic clip art, and a friendly character only carries once it is painted in the same gouache as the demo avatars. Keeping the painting everywhere it fits, and only the favicon as a vector, follows from that: a simplified figure loses either the face or the warmth.

Both faces are self-hosted through Fontsource and imported from CSS (`frontend/src/app.css`), never fetched from a font service at runtime. A self-hosted app should not tell a third party who is reading which recipe, and a kitchen tablet on a LAN with no internet has to render the same as one online.

New UI takes its idea from the cookbook - a running head, a contents page, a credit line - and has to hold twice the entries it starts with. An element lifted from another part of the app into a new place fits only the case it was built for and breaks with the next entry.

Tokens are the only source of color, radius, shadow and font, which is what makes a palette change a single edit and a dark mode possible at all. A color written straight into a component is a color nothing can theme and nothing can find.

The user docs wear this palette because end users meet the docs before they meet the app: a gray manual wrapped around cream screenshots reads as two products. `docs/memory/` stays neutral for the mirror-image reason - the look is what tells a reader at a glance which of the two sites is open. The contrast deltas are not drift: the same token carries body-sized reading text in the docs and only meta lines and chips in the app, and text people actually read has AA as a floor.

## Rejected

- **A neutral, minimal direction.** Perfectly correct and completely forgettable; it would make this look like every other self-hosted tool.
- **Loading the fonts from Google Fonts.** A request per reader to a third party, and a fallback face on any instance without internet access.
- **A shared token file imported by both the app and the user docs.** One source of truth, but it breaks the independence of the two builds ([Documentation sites](/architecture/docs)) and would have to declare its dark values twice over, since the app switches on `data-theme` and Fumadocs on a `.dark` class.
- **Taking the app's contrast values unchanged in the docs.** Maximum fidelity, and the sidebar, table of contents and page descriptions land below AA. The hue difference is invisible; the contrast difference is not.
- **Callouts in palette colors only.** Fully closed, but `info`, `warning` and `error` would all sit in the same brown-orange-red family, with only the icon telling them apart.
- **`class="dark"` on `<html>`, the common Tailwind convention.** A boolean class has two states where the theme has three: explicit `light`, explicit `dark`, and the attribute's absence meaning "follow the system". `data-theme` carries all three, and it is what lets `:root:not([data-theme='light'])` keep an explicit `light` under a dark system preference.
- **Theming `docs/memory/` the same way.** The neutral look is what marks it as internal.
- **A vector trace of the mascot for the small sizes.** Traced flat, cropped to a bust, or with thicker outlines, it kept the pose but lost the charm, and at 24 px and below only the silhouette survives anyway.
- **A face on the favicon.** At 16 px it is two dark pixels; the book with its ribbon reads better.
- **A sage or amber box, or a dark box in the dark theme.** Cream is the painting's own ground, so the box and the picture are one surface; a second color would frame the picture instead of holding it.
- **A drawn mark with a face**, such as a brush-painted onion with a sprout. It reads as clip art, and a face drawn in a few strokes looks either startled or smug.
- **The `@jis3r/icons` package (movingicons.dev) for animated icons.** It covers only part of the set in use, wraps every icon in a `<div role="img" aria-label>` that a screen reader announces inside an already labelled button (and that is invalid inside a `<button>`), starts on hover of the icon alone rather than the control, and ignores reduced motion. The five components that move are short enough to own.
- **Animating icons on hover.** On a phone there is no hover, and on a desktop every pass of the pointer sets an icon twitching without anything having happened.
- **Labels in the phone's bottom nav**, on the current item or under every icon. The current item's label made the pill change width between pages, a flexible label ("Einstellungen" on settings) did not fit at 360px, and any label left 1-3px at 320px in longer languages.
- **A docked tab bar from the start, with a label under each icon.** The most familiar shape and the most visible, and it read as a stock app rather than the cookbook; the floating bar that docks keeps the lightness at the top of a page.
- **A dark (`inverse`) or `accent`-tinted bar.** `inverse` turns into a bright cream band in dark mode, and an `accent` bar with a white current pill inverts the app's one "you are here" idiom.
- **The bottom nav's pill for the editor's sections on a phone.** It reads as a part borrowed from elsewhere and has no room for one more section; the running head and the contents sheet hold any number.
- **Book-culture words as visible copy**, such as "Ex libris" on the login. They mean nothing to most cooks; the login's words stay plain, and the wordmark always shows.
- **Inline SVG recolored by tokens.** A painting cannot follow a token, and the box makes a dark variant unnecessary.
