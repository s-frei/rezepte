Rezepte is one repository with a Go service in `service/`, a SvelteKit SPA in `frontend/` and two documentation apps under `docs/`. The service binary embeds the built SPA, so those two version together and release together. Every tool and every command goes through mise: `mise run <task>` for a task, `mise exec -- <cmd>` for anything else. Nothing in this repository is invoked with a bare `go`, `bun`, `node` or `npm`.

## Tasks

The root `mise.toml` is the monorepo root (`monorepo_root = true`) and names its packages in `[monorepo] config_roots`: `service`, `frontend`, `docs/memory` and `docs/user`. Each of those has its own `mise.toml` holding the tasks that only make sense inside it — `//service:generate`, `//frontend:build`, `//docs/user:screenshots`. Root tasks are thin and depend on package tasks through `//package:task`:

| Task | What it pulls in |
|---|---|
| `mise run setup` | installs every package's dependencies plus the Playwright browser, installs the Git LFS hooks, then `go mod download` |
| `mise run dev` | `//service:dev` (watchexec restarts the API on `.go` changes) and `//frontend:dev` |
| `mise run check` | `guard:local-config`, `docker:compose:check` (skipped out loud where `docker compose` is missing) plus the four package `check` tasks |
| `mise run build` | `//service:build`, which depends on `//frontend:build` — the SPA lands in `service/internal/web/dist` and is embedded |
| `mise run docs` | both documentation sites |
| `mise run e2e` | builds, starts the binary on a temporary data directory, runs the frontend Playwright suite |
| `mise run demo` | builds, starts `rezepte --demo` on the demo port and keeps it up; with `-- <cmd>` it runs that command against it instead |

`//frontend:build` empties `service/internal/web/dist` before it writes, which would take the tracked `.gitkeep` with it, so the task restores that file afterwards and a clean checkout still has the directory the Go build embeds.

**A task's body lives in `mise.toml` while it is a command, and in `mise/tasks/` once it is a program.** mise reads every file under `mise/tasks/` as a task of its own: the name comes from the path (`mise/tasks/demo.sh` is `//:demo`, `mise/tasks/release/binaries.sh` is `//:release:binaries`), `#MISE description=` and `#MISE depends=[…]` in the header carry what a TOML table would, `#USAGE` lines (`//USAGE` in a Bun file) declare its arguments - without them mise still passes arguments through, but `mise run <task> --help` claims the task takes none; `//:demo` declares its wrapped command with `double_dash="required"`, so everything after `--`, flags included, reaches the script untouched - and a TOML task that takes arguments declares them in a `usage` field. That field has a catch: without it mise appends whatever follows the task name to the `run` command, with it mise appends nothing, so the command has to place them itself. The test tasks (`//frontend:test`, `//frontend:e2e`, `//service:test`, `//docs/user:screenshots`, `//docs/user:screenshots:check`) all use the same shape, `usage = 'arg "[args]..." var=#true help="..."'` and `{% for a in usage.args %} {{ a | quote }}{% endfor %}` at the end of `run`, which shell-quotes each argument so a filter with spaces or a `$` arrives as typed; a bare `{{usage.args}}` renders the list as JSON - and the file runs with the config root as its working directory and the `[env]` block already resolved - so nothing in it has to locate the repository or default a port. A body that holds state (a trap, a poll loop, a lock), that wraps a command of its own through `"$@"`, or that is simply longer than a screen belongs there; a body of one to three commands stays a string in `mise.toml`, where the task list reads as a map of the build.

`mise/lib/` holds what is not a task. `mise/lib/instance.sh` is the port guard and the `/healthz` wait that `//:demo` and `//:e2e` both source rather than run; it cannot live beside them, because a file inside `mise/tasks/` would become a task itself, and `mise/lib/` is not scanned. `mise/lib/release/` is the TypeScript behind the release tasks (`release:start`, `release:finish`, `release:notes`, which are Bun files with a `//MISE` header): version and changelog logic as pure functions with `bun test` beside them, run by `//:test:release` inside `check`, and the few git calls apart from them. There is no `scripts/` directory.

`[tools]` pins Go, Bun, golangci-lint, sqlc, watchexec and git-lfs (for the demo photo originals under `assets/demo-photos/`; `.lfsconfig` keeps every clone, CI included, from downloading them, and `mise run demo-photos:pull` fetches them when a photo is regenerated), and `[settings] lockfile = true` keeps a lockfile beside it, so adding a tool is one line and a lockfile update rather than a README instruction. `mise tasks --all` is the only authority on what tasks exist; nothing repeats that list.

**Node is deliberately not pinned.** Every JavaScript tool here - Next, Vite, svelte-check, ESLint, Prettier, Playwright - ships a `#!/usr/bin/env node` shebang, but Bun puts its own `node` shim in front of them, so the whole build, lint, test and docs-export chain runs on Bun alone and a pinned Node would only be a download CI repeats per job. The Svelte MCP server in `.mcp.json` runs through `bunx` for the same reason. Re-add Node only for a tool that actually breaks under the shim, and say in this paragraph which one.

CI installs the same pinned tools through `jdx/mise-action`, then runs `mise run setup`, regenerates the API reference and fails on any uncommitted diff, and only then runs `mise run check`, `mise run build` and `mise run e2e` — so a green gate locally does not guarantee a green `check` job: a stale API reference regeneration is the gap ([Documentation sites](/architecture/docs)). A pushed `v*` tag runs a second workflow that publishes the image and the release binaries, and that workflow can also be dispatched by hand from a branch to publish a throwaway image tag — see [Releases](/architecture/releases).

## Worktrees and ports

The unit of feature work is a git worktree under `.claude/worktrees/<name>`, branched off `develop` as `feat/<name>` and created with `mise run worktree:new <name>` (`mise/tasks/worktree/new.sh`). [Work in a worktree](/howtos/work-in-a-worktree) owns the procedure and the port table; this page is the scheme behind it.

**Every port derives from one offset.** The root `mise.toml` `[env]` block defines `RZP_BACKEND_PORT`, `RZP_FRONTEND_PORT`, `RZP_DEMO_PORT`, `RZP_DOCS_MEMORY_PORT` and `RZP_DOCS_USER_PORT` as `base + REZEPTE_PORT_OFFSET * 100`, reading the offset from `[vars]` in the worktree's `mise.local.toml`. The main checkout runs at offset 0 and keeps the project's default numbers exactly; a worktree gets an offset of its own, so two full stacks never bind the same socket. `mise run ports` (`mise/tasks/ports.sh`) prints this worktree's map — never write a port number into a file, and never assume one in a command.

Every consumer reads the variable rather than a literal: `frontend/vite.config.ts`, both Playwright configs, `mise/tasks/demo.sh`, `docs/user/scripts/fetch-openapi.ts` and both documentation `package.json` dev scripts. `REZEPTE_ADDR` is the exception and stays one: it is the operator-facing configuration of a self-hosted service and takes an address, not a port, so `//service:dev` translates instead, with a default expansion — `REZEPTE_ADDR="${REZEPTE_ADDR:-:$RZP_BACKEND_PORT}"`, so an address the operator set still wins — and no Go code knows about the offset.

**The live worktrees are the register.** `worktree:new` walks `git worktree list --porcelain`, reads each worktree's own `mise.local.toml`, and takes the lowest offset free in 1–9; removing the worktree takes that file with it and frees the offset the same moment. There is no state file to reconcile. A `mkdir` lock under the main checkout's `.git` serializes the scan-and-write, because two creations started together would otherwise both see the same lowest free offset.

**`mise.local.toml` must never be committed.** It is where the offset lives, gitignored at every depth and covered again by `.claude/worktrees/`, so the only way one reaches a commit is a deliberate `git add -f`. `mise run check` therefore depends on a `guard:local-config` task that fails when `git ls-files` reports a tracked one: an offset loose in the main checkout shifts its ports for a reason nobody can see in the diff.

## Why it is this way

The binary embeds the frontend. Splitting the two across repositories would put a cross-repo coordination step in front of every release of a single artifact, so they share a repository and a version.

One command is the gate. `mise run check` runs the same four package gates a reviewer, an agent and CI run, which is only true while the tool versions are pinned in the repository rather than installed by hand.

Deriving the port register from the worktrees that exist cannot go stale. Any scheme that records offsets separately has a cleanup obligation, and the one time it is skipped, the register hands out an offset that is still in use — which is the exact failure the scheme exists to prevent.

## Rejected

- **Separate repositories per package.** Simpler in isolation, but the binary embeds the frontend, so every release would need cross-repo coordination for one artifact.
- **A Makefile or `just`.** Both run tasks; neither pins the toolchain. mise covers tasks and tools with one lockfile.
- **An offset hashed from the worktree name.** No state and no script, but two names can hash to the same slot — a silent collision, which is the failure the scheme exists to prevent.
- **A registry file of assigned offsets.** Unique by construction, but it goes stale the first time a worktree is removed by hand, and then hands out an offset that is still in use.
- **A convention in `AGENTS.md` alone,** with each agent picking a free number by inspection. Least code, and it relies on every agent checking what is taken — an assumption that fails quietly, and exactly when several agents are running at once, which is the only case that matters.

## Limits

- The offset is a mise var, never an env. File tasks (`mise/tasks/*`) and `mise env` render the root `[env]` block before `mise.local.toml`'s `[env]` applies, so a template reading `env.REZEPTE_PORT_OFFSET` resolves to 0 there while TOML tasks see the real value — `mise run ports` and `//:demo` then report and bind offset-0 ports inside a worktree, and nothing fails until two stacks collide. `[vars]` have no such ordering. `get_env(name=…)` is wrong for the same reason: it reads only the process environment. The templates still fall back to `env.`, so a `mise.local.toml` that sets the offset under `[env]` keeps working for TOML tasks but not for file tasks; rewriting its header to `[vars]` fixes it.
- Offsets run 1–9, so nine worktrees can run beside the main checkout. A tenth has nowhere to go and `worktree:new` fails with the list of who holds what rather than guessing.
