## Conventions

### Storage

- IDs: UUIDv7 strings (`uuid.NewV7().String()` from the standard `uuid` package), sortable by creation time. `recipe_comments.id` is the one exception, below.
- Timestamps: RFC 3339 UTC strings via `db.FormatTime` / `db.ParseTime`, with **second** resolution (`time.RFC3339`, no fractional part).
  - Two writes in the same second get the same `updated_at`, so the recipe list and search queries (`queries/recipes.sql`) break ties with `id DESC`: UUIDv7 ids sort lexicographically by creation time, so the newest row still sorts first. Without that tiebreaker, two recipes saved in the same second come back oldest first.
  - If a fractional part is ever added to `FormatTime`, it must be fixed-width - `time.RFC3339Nano` trims trailing zeros, and a shortened fraction no longer sorts lexicographically the same as the full value.
- The connection DSN in `service/internal/db/db.go` sets the pragmas: `journal_mode(WAL)`, `busy_timeout(5000)`, `synchronous(NORMAL)`, `foreign_keys(ON)`, `recursive_triggers(ON)` and `_txlock=immediate`. The recursive triggers are not for the one trigger that writes (`users_change_closes_reset_link`, which deletes rows of another table and recurses into nothing) but because SQLite fires a `BEFORE DELETE` trigger for the delete half of a `REPLACE` only when that pragma is on.
- Foreign keys are enforced; deletes cascade, except three `ON DELETE SET NULL` columns and one with no constraint. `recipe_comments.author_id` is `SET NULL`, so an entry outlives its author; `comment_images.uploader_id` and `comment_images.recipe_image_id` are too, so a former member's comments keep their photos and deleting a recipe photo only clears `inRecipe`. The unconstrained one, `recipes.cover_image_id`, is a plain nullable `TEXT` with no `REFERENCES` constraint at all: it points at `images.id`, but the image service keeps it consistent itself (set on first upload, moved on delete of the cover), and a FK with `ON DELETE SET NULL` would silently clear it instead of promoting the next image (see [Images](/features/images)).
- NULL means "absent," not "empty": `prep_minutes`, `cook_minutes`, `source_url`, `source_name`, `cover_image_id`, `ingredient_groups.name`, `ingredients.unit` and `ingredients.note` are stored as `NULL`, never `''`, when unset (the service converts an empty string to `nil` on write). `recipes.description` is the exception - it defaults to `''`, not `NULL`, when omitted.
- An alphabetical `ORDER BY` over user text uses `COLLATE unicode`, which `service/internal/db/collate.go` registers on every connection the package opens: `NOCASE` and `BINARY` fold ASCII alone, so every word with a non-ASCII initial would sort after `z`. The collation exists only inside the Go driver, so a query that names it fails in a `sqlite3` CLI session ([Recipes](/features/recipes) for the title sort).
- `recipes_fts` is not in the diagram: an FTS5 virtual table is a search index rather than a relation - it holds no copy of the text and no foreign keys, so there is nothing for the diagram to connect it to. [Recipes](/features/recipes) owns how it is declared, keyed and kept in step.

### Users and credentials

- Usernames are unique case-insensitively (`COLLATE NOCASE`).
- `users.role` holds `superadmin`, `admin` or `user`, and a `CHECK` admits nothing else. `users_superadmin_idx` is unique and partial on `role = 'superadmin'`, so "at most one instance owner" is a property of the database rather than of the code writing to it.
- Two triggers carry the other half of that guarantee: `users_superadmin_undeletable` aborts a `DELETE` of the owner's row, `users_superadmin_role_locked` aborts an `UPDATE OF role` on it. They are the net underneath [Users and authentication](/features/users-and-auth), which owns the refusals a person sees; on every connection the service opens they hold for a raw query and for a code path that forgets to ask as well. They catch an `INSERT OR REPLACE` over the owner's row only because the DSN sets `recursive_triggers(ON)` - the pragma is per connection, so a `sqlite3` CLI session against the file, which defaults to off, can still `REPLACE` past a `BEFORE DELETE` trigger.
- `users.display_name`, `users.color` and `users.locale` are `NOT NULL` and carry no `CHECK`, while `role` beside them does.
  - `role` is a closed set the database itself has to hold: its values back `users_superadmin_idx` and the two triggers, so a row outside the set would quietly make all three meaningless.
  - Nothing in the schema reads the other three, so their rules live in Go - `normalizeDisplayName`, `ParseColor` and `ParseLocale` in `service/internal/user/profile.go`, over the palette `user.Colors` owns and the languages in `service/internal/i18n/locales.json`. A `CHECK` would be a second copy, and adding a color or a language would then take a migration ([Languages](/features/languages)).
  - `NOT NULL` is the half the database keeps, and it lets every reader print a name without a fallback of its own: `user.Create` is the single writer of a user row and substitutes the username when no display name is given. Neither column is unique - `username` is the only thing that identifies an account.
- `user.ErrNoSuperadmin` refuses to start against a non-empty `users` table without an owner, and it has to stay that strict: it turns a database without `users_superadmin_idx` and the two triggers into a refusal at startup rather than an instance with no storage backstop, where the Go guards would be the only thing holding the invariant. Anything that relaxes it - promoting the first admin to owner on start, say - removes that net. A database whose `users` table lacks a column the current schema has fails on the query that finds the owner instead, loudly (`no such column`); the fix for both is to delete the file and let the migrations recreate it.
- `users.email` is `NOT NULL DEFAULT ''`, profile data like `display_name`, so no migration had to backfill existing rows and no reader has to handle `NULL`; it carries no `UNIQUE` or `CHECK`, because nothing signs in by it. `users.email_verified` is `NOT NULL DEFAULT 0`; [Users and authentication](/features/users-and-auth) owns who writes each column and when the mark is dropped.
- `users.avatar_id` is nullable: `NULL` is no picture, otherwise it is the UUID that names `<REZEPTE_DATA_DIR>/avatars/<users.id>/<avatar_id>.jpg`. It carries no foreign key because the file is not a row; [Users and authentication](/features/users-and-auth) owns the order of a replace, which keeps the column from naming a missing file.
- `users.can_share_publicly` is `NOT NULL DEFAULT 1`: an admin's per-person switch for [public shares](/features/public-shares), separate from the household-wide `instance_settings.public_shares`.
- A session id is the SHA-256 digest of the session's own random token; the raw value exists only in the cookie and is never stored. Sessions and API tokens cascade with their user.
- `api_tokens.token_hash` is `UNIQUE`, which doubles as the lookup index for authentication. `id` is a separate UUIDv7 rather than the hash, because a token is deleted from a list at a moment the raw value no longer exists to hash again. `token_prefix` keeps the first 8 characters in clear, for matching a row in the list against an entry in a client configuration. See [API tokens](/features/api-tokens).
- `setup_links.id` is the SHA-256 digest of the setup token, following `sessions.id`: the raw value exists only in the link. `setup_links_user_idx` is a unique index on `user_id`, so a second `ReplaceSetupLink` for the same account is an `UPDATE` by construction - no state has two links resolving to one account. Both foreign keys cascade: deleting the account the link is for or the one that issued it removes the row. `sent_to` is `NOT NULL DEFAULT ''`, read when the link is redeemed to decide whether to verify the account's address ([Email](/features/email)).
- `setup_links.purpose` is `'setup'` or `'reset'` under a `CHECK`, `'setup'` by default: a reset link is a forgotten-password link the person asked for, valid for an hour and never usable to connect a provider. `users_change_closes_reset_link` (migration 0015) deletes an account's reset row whenever an update changes `email` (case folded) or `password_hash`, so no writer can leave one open for an address or password the account no longer has.
- `email_confirmations` follows `setup_links`: `id` is the SHA-256 of the token, `user_id` is unique so an account has at most one open confirmation, `address` is the one it was mailed to, and `DeleteExpired` sweeps the expired rows. See [Email](/features/email).
- `user_identities` is keyed by `(issuer, subject)`, the pair an OIDC ID token names a person by, so one identity belongs to at most one account; the unique `user_identities_user_idx` on `(user_id, issuer)` gives an account at most one identity per provider. `issuer` is stored although an instance has one provider, so that pointing the instance at another provider cannot match a subject some other provider issued. `user_id` cascades. Nothing is keyed by email. See [OIDC](/features/oidc).

### Recipes

- `recipes.created_by` and `recipes.updated_by` are both `NOT NULL` without `ON DELETE`; deleting a user moves every recipe they wrote **or last edited** to the acting admin (see [Users and authentication](/features/users-and-auth)).
- `updated_by` always names somebody: a new recipe seeds it from `created_by`, so "never edited" is "both columns still match their `created_*` twin" rather than a NULL. Reading it needs both — with second resolution, an edit in the same second as the create moves only `updated_by`. Every write that moves `updated_at` moves `updated_by` with it, image uploads and cover changes included (see [Recipes and search](/features/recipes)).
- `ingredient_groups.position`, `ingredients.position` and `steps.position` are 0-based integers, rewritten sequentially in full on every recipe save (see [Recipes and search](/features/recipes)) - never edited in place, so there are no gaps or renumbering to reason about between saves.
- Tags are implicit: `tags` only ever holds names currently used by at least one recipe (see [Recipes and search](/features/recipes)); there is no separate tag-management table or endpoint.
- `step_references` is keyed by `(step_id, word)`, following `recipe_tags`: a word carries at most one reference per step. Both foreign keys cascade, so deleting the step or the ingredient it names removes the reference with it - a dangling reference is a state the database cannot hold. See [Ingredient references](/features/ingredient-references).
- `step_times` is keyed by `(step_id, phrase)`, like `step_references`: a phrase carries at most one time per step. The foreign key cascades with `DeleteStepsByRecipe`, which every save runs. `seconds` is the duration (the lower end of a range) and `max_seconds` its upper end, `NULL` for a single duration; the phrase is the anchor, no unit text or ISO 8601 string is stored. See [Step times](/features/step-times).
- `images.filename` is `<id>.jpg`; the three variants (`<id>.jpg`, `<id>_detail.jpg`, `<id>_thumb.jpg`) live in `<REZEPTE_DATA_DIR>/images/<recipe_id>/`, outside the database; `width`/`height` are the largest variant's; `size_bytes` sums all three; `position` is compact `0..n-1` like the other position columns, rewritten on delete and reorder. See [Images](/features/images).
- `comment_images` holds a comment's photos and the unsent ones (`comment_id` NULL, `comment_images_staged_idx` serves the sweep; `comment_images_recipe_idx` serves the recipe's comment list and its cascade, `comment_images_recipe_image_idx` the `ON DELETE SET NULL` from `images`). It is a table of its own, not rows of `images`, so the recipe photo cap, the cover, the export and the public pages never see it; files live in `images/<recipe_id>/comments/<id>/`. See [Images](/features/images) and [Recipe comments](/features/recipe-comments).
- `favorites` is keyed by `(user_id, recipe_id)` and both foreign keys cascade, so a star never outlives the user or the recipe it belongs to. The primary key serves lookups by user; `favorites_recipe_idx` on `recipe_id` serves the reverse direction, which the per-page card lookup uses. See [Favorites](/features/favorites).
- `tasty` has the same key, cascades and reverse index (`tasty_recipe_idx`); the index also serves the correlated count behind `sort=tasty`. Unlike a favorite, a row's `created_at` is read: it orders the people a recipe names as having marked it. See [Tasty](/features/tasty).
- `recipe_comments.id` is `INTEGER PRIMARY KEY AUTOINCREMENT`, because it doubles as the watermark and must never be handed out twice - without `AUTOINCREMENT` SQLite reuses a deleted newest row's id. `recipe_comments_recipe_idx` on `(recipe_id, id)` serves a recipe's list and the card batch, `recipe_comments_author_idx` the "has a comment here" check. `author_id` is `SET NULL`: deleting a member leaves their comments as a former member's rather than giving them to the admin who inherits their recipes. `recipe_comment_reads` keeps one `last_seen` per (user, recipe), both keys cascading; a comment is new when its `id` is above it. See [Recipe comments](/features/recipe-comments).
- `notification_optouts` holds one row per (user, kind, channel) an account switched off, and `notification_group_optouts` one per (user, group, channel) whose master switch is off (`grp`: `group` is an SQL keyword); both cascade with the user, and `channel` is `mail` or `push` under a `CHECK`, while kinds and groups have none, so a new one needs no migration. Every switchable notification is on until a row says otherwise, so a new kind or a new account needs no rows; a group row silences every kind of the group on that channel, later kinds too, and leaves the kind rows alone. See [Notifications](/features/notifications).
- `recipes.announce_pending` is `NOT NULL DEFAULT FALSE`, so an upgraded instance announces nothing it already had. `recipe.Service.CreateAnnounced` sets it in the create's own insert, and only the HTTP `create-recipe` and MCP `create_recipe` call that; archive import and the demo seed use `Create` and leave it false. `ListDueAnnouncements` reads the pending rows older than a cutoff, oldest first, through the partial index `recipes_announce_pending_idx` on `created_at WHERE announce_pending`, and `ClearAnnouncements` drops the mark. A deleted recipe takes its mark with it. See [Notifications](/features/notifications).
- `recipes.edit_policy` is `NULL`, `'open'` or `'locked'` (a `CHECK` constraint); `NULL` means "follow the household setting" and is never written as a string. [Editing rights](/features/editing-rights) owns what it decides.

### Settings and shares

- `instance_settings` holds exactly one row: `id INTEGER PRIMARY KEY CHECK (id = 1)`, inserted by the migration that creates the table, so reading it never has to handle "no row" and writing it is an `UPDATE`. It stands alone in the diagram because nothing references it. Its columns belong to their features:
  - `recipes_locked_by_default` to [Editing rights](/features/editing-rights).
  - `link_previews` (off by default), `link_preview_minutes` (15, 60 or 1440 under a `CHECK`, 15 by default) and `link_preview_key` to [Link previews](/features/link-previews), whose key the unsubscribe links of [Notifications](/features/notifications) sign with too, under their own label. The key is 32 random bytes the migration writes with `randomblob`, since SQLite refuses a non-constant default in `ADD COLUMN`; `GetInstanceSettings` names its columns so the key never rides along.
  - `public_shares`, `public_share_default_days`, `public_share_max_days` and `public_share_attribution` to [Public shares](/features/public-shares). The rule that the default may never exceed the maximum is a `CHECK` on `public_share_max_days` alone, since SQLite's `ALTER TABLE` cannot add a table-level constraint and a column constraint may only name a column that already exists by the time it is added.
  - `recipe_digest_hour` and `recipe_digest_last_day` to [Notifications](/features/notifications): the owner's hour of the new recipes digest in the server's time zone (`settings.Service.SetRecipeDigestHour`, 0 to 23, `ErrUnknownHour` otherwise) and the local date of the last run. `ClaimRecipeDigestDay` writes the date only when it differs and reports the rows it changed, so of two runs on one day only the first gets a row back.
  - `mail_failing_since` and `mail_alert_last_at` to [Notifications](/features/notifications): the state of the owner's mail-failing push, kept here so a restart does not re-arm it, both `TEXT NOT NULL DEFAULT ''` (empty: mail works, no alert yet). `GetMailAlertState` reads and `SetMailAlertState` writes both; nothing writes them yet.
  - The seven `smtp_*` columns to [Email](/features/email): the mail configuration the owner saves in the UI, `smtp_host = ''` meaning not configured here, the password stored as plain text like `link_preview_key`, and `GetMailSettings` the one query that reads them.
  - The four `oidc_*` columns to [OIDC](/features/oidc): the provider the owner saves in the UI, `oidc_issuer = ''` meaning not configured here, the client secret plain text like `smtp_password`, and `GetOIDCSettings` the one query that reads them.
  - `vapid_key` to [Cook timers](/features/cook-timers): the VAPID signing key as the raw 32-byte P-256 scalar, `NULL` until the push service first needs it and then generated and stored, so a migration does not have to make a key and an instance that never pushes never has one.
- `push_subscriptions.endpoint` is `UNIQUE`: one device belongs to one account at a time, and subscribing it for another account moves the row and deletes the previous account's `timer_alarms`. `p256dh` and `auth` are the raw bytes the browser handed out, base64url only on the wire. `timer_alarms` cascades with its subscription, which cascades with its user; `fire_at` is an RFC 3339 `TEXT` like every timestamp, indexed for the sender's due query, and `title`, `body` and `url` are the copy the browser built. Nothing stores a timer. See [Cook timers](/features/cook-timers).
- `shares.token` is a plain `UNIQUE TEXT`, not a hash: unlike a session id or an API token, this credential is a link a member sends to someone else and has to be able to read again to copy it a second time. `UNIQUE (recipe_id, created_by)` caps a person at one live link per recipe; both foreign keys cascade. `shares_created_by_idx` serves the member's own list; there is no index on `token` beyond the `UNIQUE` constraint's own, which is what a public request resolves against. See [Public shares](/features/public-shares) for the validity rule.

## Why it is this way

A recipe collection for one household has no use for a database server. SQLite is a file beside the images directory, and `modernc.org/sqlite` is a pure-Go driver, so `CGO_ENABLED=0` holds: the binary is static and the runtime image is `distroless/static`, with no C toolchain anywhere in the build and no libraries to match at runtime.

Queries are hand-written SQL under `service/internal/db/queries/`, compiled by sqlc into typed Go under `service/internal/db/sqlc/`, and the generated code is committed. Writing the SQL by hand is what keeps FTS5 and the recipe aggregate's whole-document write expressible at all; generating the scanning is what makes the compiler check that a query's columns and the struct receiving them still agree after an edit. Committing the output means a checkout builds without sqlc installed, and a query changed without regenerating shows up as a diff the gate fails on rather than as a surprise at runtime. A handful of statements sqlc cannot express are hand-written in the same package against the same `DBTX`; [Recipes and search](/features/recipes) lists them and says why.

Within one statement, parameters are either all `sqlc.arg()` or all plain `?`. `sqlc.arg()` compiles to an explicitly numbered `?N`, SQLite numbers the plain placeholders after the highest explicit index, and the driver never binds them — a silent mismatch rather than an error at generation or at run time.

sqlc reads the goose migration files themselves as its schema - `service/sqlc.yaml` points `schema` at `internal/db/migrations` - so the schema has exactly one source of truth and there is no second declaration to drift from the one that actually runs.

Migrations are embedded with `go:embed` and applied by `db.Migrate` as the process starts, so deploying is one binary and no separate migration step for an operator who runs this at home. They are numbered sequentially rather than by timestamp: timestamps exist to stop migrations authored on parallel branches from colliding, and a single migration stream gains nothing from them but an unreadable filename.

Tests run against a real migrated database rather than mocks. `dbtest.Open` opens a throwaway file in the test's own temp directory and applies every migration to it, so a query test meets the same SQLite, the same pragmas and the same schema as production - including the FTS5 table and the `_txlock=immediate` transaction behavior that the rank guards on the `users` table lean on.

[Add a database migration](/howtos/add-migration) owns the procedure, and the rule that a migration which has shipped in a release is never edited: every schema change is a new migration on top.

## Rejected

- **A CGO SQLite driver (`mattn/go-sqlite3`).** It needs a C toolchain in the build image and gives up the static binary, in exchange for performance nothing here is waiting on.
- **Hand-written scanning.** Boilerplate for every query and no compile-time check that a query and its destination still match.
- **An ORM (GORM, ent).** It hides the SQL and fights the two things this schema leans on hardest: an FTS5 virtual table maintained by hand, and a save that rewrites the recipe row, every child table and the search index in one transaction.
