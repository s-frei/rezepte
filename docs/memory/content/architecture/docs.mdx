description: Two Fumadocs apps under docs/, committed screenshots and a generated API reference, the user docs published to GitHub Pages

`docs/` holds two independent Fumadocs apps. `docs/memory/` renders this memory for the people and agents developing Rezepte; `docs/user/` renders the end-user manual for the people who cook from Rezepte and the people who host it, and is the only one that is published. Both are English, and a sentence in the wrong one reaches the wrong audience: nothing about developing Rezepte belongs in the user docs, nothing about cooking belongs here.

## The two apps

Each app is Fumadocs on the Next.js static template (`output: 'export'`) with its own `package.json`, `mise.toml`, `app/` and `content/` directory. Nothing is shared between them — not a build, not a dependency list, not a deployment. `mise run //docs/memory:check` and `mise run //docs/user:check` each lint, audit and build their own site, so broken MDX in either fails the gate. Both dev servers take their port from the worktree's offset ([Toolchain](/architecture/toolchain)).

## Sections

The user docs come in four sections, one per reader: **Guide** (`content/(guide)/`: the overview, the tour and every feature, and contributing - for the people cooking), **Hosting** (`content/(hosting)/`: getting started and operations - for whoever runs the instance), **API** (`content/api/`) and **Changelog** (`content/(releases)/`: a page per release and the roadmap). Each is a root folder (`"root": true` in its `meta.json`) with a Lucide `icon` name, turned into an icon by `lucideIconsPlugin` in `docs/user/lib/source.ts`.

- **Folders in parentheses are groups, not addresses.** Fumadocs leaves them out of the URL, so `content/(guide)/guide/cook-mode.mdx` is still `/guide/cook-mode/`. That is what let the sections form without moving a single published address; a group is the tool for regrouping, renaming a real folder never is.
- **`docs/user/app/[...slug]/layout.tsx` uses Fumadocs' notebook layout with `tabMode="navbar"`**: the sections are tabs in the navbar, and the sidebar lists only the open one. The navbar tabs render a section's title and nothing else, so the layout's `tabs.transform` puts the icon into the title; on phones the tabs become the sidebar's dropdown, which shows the icon by itself, so the one in the title is hidden there. The notebook layout needs its own page components: `page.tsx` imports from `fumadocs-ui/layouts/notebook/page`, and the docs layout's ones refuse to render under it.
- **Inside a section, separators group the pages** (`---Recipes---` in `guide/meta.json`), rather than more folders, which would add a level to every address below them.
- `contributing/` holds only what someone outside the project can do without knowing the code. There is no FAQ or troubleshooting section.

## The changelog chapter

`content/(releases)/changelog/` holds one page per release ([Releases](/architecture/releases)), titled `v1.3.0 — <what it is about>` by the release tooling. `docs/user/components/releases.tsx` splits that title and shows the two parts at their own sizes: the version large in the display face and the name beneath it in the sidebar (the layout swaps each release's name in the page tree), the same pair as a release page's heading, and every release newest first as a timeline on the changelog page (`<ReleaseTimeline />` in its `index.mdx`). A title not in that form shows as it is.

**A release's address is permanent, and so is every address linked from outside.** The GitHub release notes link `/changelog/<version>/` and its Markdown view, the app links the guide, the changelog and the MCP page from `frontend/src/lib/docs.ts`, and `README.md` and `CONTRIBUTING.md` link pages down to their headings; none of them changes when the docs do. `docs/user/scripts/published-urls-audit.ts`, run by `//docs/user:check` after the build, fails when any of those addresses, or an anchor the two Markdown files use, is missing from the export, so a regrouping that moves one fails the gate instead of a reader's link.

**Who a user-docs page is for is a word badge, not a warning box.**

- A page that only admins or only the instance owner can act on sets `audience: admin` or `audience: owner` in its frontmatter (declared in `docs/user/source.config.ts`); `page.tsx` renders the badge from `docs/user/components/audience.tsx`, and `lib/source.ts` writes it as a line into the page's Markdown view.
- A section of an otherwise open page puts `<Audience role="…" />` straight after its heading text - no space, or the heading's anchor gains a trailing hyphen and every link to it breaks.
- That page imports the component at the top of the file, because Fumadocs evaluates headings for the table of contents at module level, where the MDX components are not in scope yet.
- The sidebar carries no badge: a mark beside one entry among many reads as noise rather than as a hint.

Each serves the agent-facing routes for its own content: `/llms.txt`, `/llms-full.txt`, raw markdown per page under `/llms.mdx/<path>/content.md`, and a static search index at `/api/search`. Agents normally read the MDX out of the repository; the rendered sites are for humans, for those routes, and — for `docs/user/` — for end users.

**A collection's `dir` must point at a content-only directory, never a package root.** Both apps set `dir: 'content'` in their `source.config.ts`, so neither collection can see the other's files. The rule is a constraint, not a preference: fumadocs-mdx hands chokidar the `dir` itself, not the filtered file list, so a collection's `files` globs filter what fumadocs *processes* and nothing about what the watcher opens. Point `dir` at a package root and the watcher takes `node_modules` and `.next` with it, until the dev server dies with `spawn EBADF` or floods the log with `EMFILE`.

The user docs wear the app's "Warm & handmade" palette, mapped onto Fumadocs' `--color-fd-*` variables in `docs/user/app/global.css`, while the memory app stays neutral. [Design system](/architecture/design-system) owns those values and the handful of places the docs deliberately differ. `global.css` imports `fumadocs-ui/css/lib/default-colors.css` rather than the `neutral.css` preset it replaces: `neutral.css` carries a `.dark #nd-sidebar` rule whose id selector would outweigh any `.dark` override placed after it. The overrides themselves sit in plain `:root` and `.dark` blocks rather than in `@theme`, because unlayered declarations beat Tailwind's `@layer theme` and so win regardless of import order.

## The landing page

The user docs open on a landing page, not on a docs page: `docs/user/app/page.tsx`, a React page inside Fumadocs' `HomeLayout` (the same nav, search and theme switch, no sidebar), written to make someone who has never heard of Rezepte want to try it. The docs themselves live under the required catch-all `app/[...slug]/`, and `content/(guide)/overview.mdx` is their first page - the lockup leads back to the landing page. `app/sitemap.ts` lists the root by hand, because it is not a content page.

- **A hero, a bento of features with screenshots, small idea cards, and the self-hosting pitch** with the one-line `docker run … --demo`. The bento is the core: `TILES` in `page.tsx` names each feature, the guide page it links to and the screenshot it shows. Below `lg` a tile shows the mobile screenshot in a phone-shaped frame; from `lg` up it shows the desktop one, and `focus` / `zoom` pick and enlarge the part worth seeing, since a 1440px page is unreadable at tile size. A tile marked `phone` shows the mobile screenshot at every width.
- **The pictures are the committed screenshots**, read from `public/screenshots` by name, so `mise run //docs/user:screenshots` keeps the landing page current along with the docs, and `screenshots-audit.ts` fails on a tile whose name has no test, as it does for a `<Screenshot>` tag. A `focus` or `zoom` is tuned to the picture as it is; when a regenerated screenshot moves its content, check the tile.
- **Only design tokens.** Colors, radii and type come from the `--color-fd-*` palette and the `@theme` scale in `docs/user/app/global.css`, like everything else in the docs ([Design system](/architecture/design-system)).

## Screenshots

Screenshots are Playwright snapshot tests in `docs/user/screenshots/`, one `test('<name>')` per screenshot, run against `rezepte --demo` through `mise run demo -- bunx playwright test` (see [Demo mode](/features/demo-mode) for what that instance contains). `docs/user/playwright.config.ts` defines four projects — `desktop-light`, `desktop-dark`, `mobile-light`, `mobile-dark` — and a `snapshotPathTemplate` that writes straight into `docs/user/public/screenshots/` as `<name>-<project>.png`. The PNGs are committed, because the docs build must not need a browser. The suite runs single-worker and unparallelized: every spec shares one demo database and the settings spec creates a user, so determinism beats speed.

Pages reference a screenshot by name, `<Screenshot name="…" caption="…" />`. `docs/user/components/screenshot.tsx` checks `public/screenshots` for `<name>-<device>-<scheme>.png` at build time and renders a dashed placeholder frame carrying the caption for every variant it does not find, rather than failing the build.

`docs/user/scripts/screenshots-audit.ts` cross-checks the three places a name lives — `<Screenshot name>` in the content, `test('<name>')` in the specs, and the files on disk. It reads the names the landing page's tiles use too, and **fails** when a referenced name has no matching test or is not `a-z0-9-`; it only **warns** about missing PNGs and about files nothing references, because PNGs can only be produced where Chromium starts.

`mise run //docs/user:screenshots` regenerates every PNG (`--update-snapshots=all`, so a change too small for the diff tolerance cannot leave a stale file behind) and `mise run //docs/user:screenshots:check` reports drift. Neither runs in CI. [Add a screenshot](/howtos/add-screenshot) owns the procedure.

## API reference

`docs/user/content/api/reference/` is generated and never hand-edited. `mise run //docs/user:openapi` builds the binary, starts it with `--demo` through `//:demo`, and runs two scripts: `docs/user/scripts/fetch-openapi.ts` writes the served document to `docs/user/public/openapi.json`, then `docs/user/scripts/generate-api.ts` hands it to `fumadocs-openapi`'s `generateFiles`. That writes a page per operation foldered by tag (`per: 'operation'`, `groupBy: 'tag'`), a card page per folder, one over all of them, and the `meta.json` files that order them. Each page carries frontmatter and a single `<OpenAPIPage>` tag; the operations, schemas and code samples are rendered from `public/openapi.json` at build time by `docs/user/components/api-page.tsx`. The output is committed, and a regeneration that changes nothing produces no diff.

**A page is titled by its route, not by its summary.** The sidebar lists `/api/v1/recipes` with a method badge rather than "List and search recipes", which is what keeps a sidebar of every operation scannable; the summary becomes the page description. `generateFiles` cannot do this through its `frontmatter` option — that callback is handed a title and a description, never the route — so `beforeWrite` maps each output file back to the operation it came from and swaps the two. The method badges come from `openapiPlugin()` in `docs/user/lib/source.ts`, which reads the `_openapi.method` that only operation pages carry.

**Tag declarations shape the reference but do not gate it.** `groupBy: 'tag'` groups by the tags an operation carries, so an undeclared tag still produces a folder — with the raw tag name as its title, no description on its card, and a position at the end, because the declaration order in `service/internal/httpserver/api.go` is what `beforeWrite` restores onto the top-level `meta.json` and the top-level card page. `TestEveryTagIsDeclared` fails on a used-but-undeclared tag as well as on a declaration nothing uses, so the gate catches it before a reader sees it.

The playground is off (`playground: { enabled: false }`). It would have to reach a target instance straight from the browser, because `openapi.createProxy()` is a route handler and this app is a static export, and the service sends no CORS headers, so that request fails from the published domain to any self-hosted instance. The app's own Scalar page at `/api/v1/docs` runs same-origin and does reach one.

`fumadocs-openapi` renders through a React component, not Markdown, so the generated pages carry no prose. `docsLlms.renderPage` in `docs/user/lib/source.ts` gives every page under `/api/reference` a body that names the page and links `openapi.json` — the machine-readable form a reader of those routes wants anyway.

The fetch logs in as the demo admin and replays the session cookie, because the specification routes require authentication too - a session of any role, or a valid API token with no scope required ([Users and auth](/features/users-and-auth)). That is also why the task needs a demo instance rather than any running server: it has to be one whose credentials are known. CI runs the same task and then fails on any uncommitted change it produced, so a forgotten regeneration fails the build rather than a review. [Regenerate the API reference](/howtos/regenerate-api-reference) owns the procedure; [Keep the user docs in step with the UI](/howtos/update-user-docs) owns when to run it.

## Publishing

`.github/workflows/pages.yml` builds `docs/user/` and uploads `docs/user/out` with `actions/upload-pages-artifact`, which `actions/deploy-pages` then publishes — the artifact-based Pages deploy, with no branch holding built output. It is its own workflow rather than a job in the gate, for the reasons [GitHub Actions conventions](/conventions/github-actions) gives, and it has two entry points.

`.github/workflows/ci.yml` calls it through `workflow_call`, from a job carrying `if: github.ref == 'refs/heads/main'` and `needs: check`, so `develop` and pull requests build and check the docs but never publish them, and every push to `main` republishes the site once the gate is green. [Release](/howtos/release) owns the release procedure that ends in such a push.

A `workflow_dispatch` is the other entry point, and it publishes the ref it was started from without waiting for a merge or a release. It exists for the two cases the automatic path cannot serve: a wording fix that should be live now, and a change to `pages.yml` itself, which can only be exercised from the branch carrying it, since a dispatch runs the workflow as it exists on the chosen ref. The job's first step fails the run for any ref but `main` and `develop` — those two are the branches whose content is meant to be readable, and from anywhere else a dispatch would put an unreviewed branch on a public address, where the only recovery is a second dispatch. Both entry points share the `pages` concurrency group, so a manual run and a push-triggered one queue instead of racing for the same deployment.

**The Pages build is served under a sub-path, everything else at the root.** `docs/user/next.config.mjs` sets `basePath: '/rezepte'` only when `RZP_DOCS_PAGES` is set, and puts the same value into `NEXT_PUBLIC_BASE_PATH`. Two places set it: the build step of `pages.yml`, and `//docs/user:check`, so the base-path audit below has a prefix to check before CI does. The dev server and a plain `//docs/user:build` answer at `/`.

- Components that build their own root-relative URLs read it from there: `<Screenshot>`, because `next/image` under `images: { unoptimized: true }` returns `src` verbatim and prefixes nothing, and `docs/user/app/layout.tsx`, which hands the static search client its endpoint explicitly rather than relying on the builder to polyfill one.
- `docs/user/scripts/base-path-audit.ts`, wired into `//docs/user:check`, walks the built export and fails on any root-relative `src` or `href` that lacks the prefix. It imports the value from the config instead of repeating it, refuses to run when there is none (without a prefix every path would pass), and skips the two things that legitimately lack it — resource hints such as `preconnect`, and protocol-relative URLs on another origin.
- The llms routes are Markdown read by assistants that know nothing of the base path, so `absoluteLinks` in `docs/user/lib/source.ts` turns every root-relative link they serve into a full `SITE_URL` address, and the audit fails on any `](/` left in `llms.txt` or `llms-full.txt`.

Every address the app links to outside itself is a constant in `frontend/src/lib/docs.ts`. Every self-hosted instance points at the same public site, so the URLs are constants rather than configuration, and the site's carry the trailing slash the export uses, since Pages redirects the bare path.

`docs/memory/` is never published. `pages.yml` runs `//docs/user:install` and `//docs/user:build` and nothing else; no step uploads or deploys the memory export.

One repository setting no workflow can perform: in Settings → Pages, Source must be **GitHub Actions**. Until it is set by hand, `deploy-pages` fails with "Get Pages site failed", and no API call inside the job can set it.

**The landing page is titled for search, not by its heading.** "Rezepte" is an everyday German word that recipe sites rank for, so a result titled with the name alone is never found. `SITE_TITLE` in `docs/user/lib/shared.ts` carries the words people search with — self-hosted, recipe manager — and the landing page takes it whole (`{ absolute: … }`), because the `%s — Rezepte` template every other page uses would append the name a second time. `SITE_DESCRIPTION` beside it is the site-wide meta description, owned by the landing page. Every page names its published address, slashed like the export, as its canonical URL and `og:url` (`publishedUrl` in the same file, which the sitemap uses too), so the redirecting unslashed form never counts as a page of its own. The landing page also carries a schema.org `SoftwareApplication` block (`JSON_LD` in `app/page.tsx`) for a software result in search.

## Why it is this way

Internal memory and a public manual have different audiences and different deployment targets. Two apps mean `docs/user/` carries the dependencies the memory has no reason to hold — Playwright, a generated reference, three Fontsource packages for its typefaces (OFL-1.1, like the two the frontend already carries) — and an independent static export deploys without ever putting the internal memory on a public address.

The base path belongs to one host, GitHub Pages, so only the Pages build carries it: locally the docs open at the root like every other dev server here. What a prefix everywhere bought - a link that forgets it breaks locally, before it breaks in production - the audit still buys, because `check` builds the way Pages does and fails on the missing prefix before a commit.

The landing page is a page of its own rather than an MDX page with a hero, because a docs page always wears the sidebar, the table of contents and the Markdown buttons; a first impression meant to make someone want Rezepte has no use for any of them.

The API reference is rendered by the official integration rather than by a generator of this project's own. A hand-rolled OpenAPI reader has to be taught every schema shape huma starts emitting before it renders correctly, and that teaching never ends; `fumadocs-openapi` already reads the whole of OpenAPI 3.1 and renders code samples in seven languages beside each operation. What made it a bad fit was one feature, and that feature is a flag.

## Rejected

- **The sections as a dropdown in the sidebar** (Fumadocs' default for root folders). The same split, but the other sections are a click away and the navbar stays as it was; the navbar tabs show all four at once, which is what makes the changelog read as a chapter of its own.
- **One tree with every section collapsed but the open one.** Everything stays a click away in one place, but the tree grows long again as soon as a reader opens two sections.
- **Moving the content into new real folders.** Cleaner paths, but every moved page changes its published address; the groups in parentheses regroup without that.
- **The base path on the dev server too.** It kept dev and production identical, but every local address carried `/rezepte` for a host the dev server never is; the audit under `check` covers what it guarded against.
- **The landing page as `content/index.mdx` with a hero and cards.** One file fewer, but a docs page carries the sidebar and the page chrome, and MDX has no grid of screenshots without a component of its own anyway.
- **One Fumadocs app for memory and user docs.** Simplest, but internal and public content would share a build and a deployment, and only one of the two is meant to be published.
- **Generating screenshots during the docs build.** Couples the build to Go, Bun and Chromium, and a docs build has to work where none of the three is available.
- **Keeping the screenshot project in `frontend/e2e`.** Reuses one Playwright config, but makes the frontend the owner of documentation assets.
- **The `fumadocs-openapi` playground.** An interactive request form beside each operation, which cannot work here: a static export has no route handler to proxy through, and the service sends no CORS headers for the browser to go direct. The running app serves a working one at `/api/v1/docs`.
- **A generator of our own.** Full control over the output, but every new schema shape costs a patch to its type and constraint rendering first, where `fumadocs-openapi` already renders what the document describes.
- **Failing the build when a screenshot PNG is missing.** It blocks every docs build in an environment without a working Chromium, CI included. A placeholder frame plus an audit warning keeps the build green and the gap visible.
- **The Pages deploy as a job inside `ci.yml`.** The gate is what starts it on `main`, so the job would sit close to its trigger — but a deployment's permissions, environment and concurrency group would then live in the gate, and publishing the docs would only be reachable by running the whole gate.
- **A branch-based `gh-pages` deploy.** A branch of built output to keep in sync, where the artifact actions upload the export straight from the job that produced it.
- **Embedding the docs in the Go binary under `/docs`.** It would inherit the app's own auth and TLS and need no base path, but it ties every documentation change to a service rebuild and deploy, and self-hosted instances would serve docs nobody asked them for.
- **A custom domain.** It would remove the base path and everything threaded through for it. There is no domain to point at the site; nothing here blocks adding one later, since the published origin is defined in `docs/user/lib/shared.ts` for the docs and in `frontend/src/lib/docs.ts` for the app.

## Limits

- The dev server cannot show a missing base path, since it has none; only `//docs/user:check` (and CI) can. Run it before committing anything that builds a URL by hand.
- `docs/user/app/robots.ts` exports to a robots file under the base path, which crawlers never read: robots.txt is honored only at the origin root, and that origin belongs to another repository. The file is kept because it becomes correct behind a custom domain, but the sitemap it points at has to be submitted to search engines by hand.
- Screenshot comparison stays local. Font rendering differs between platforms, so a comparison run in CI would fail on rendering rather than on content; `screenshots:check` is the local drift report and CI never runs it.
- The committed PNGs can only be produced where Chromium starts. Everywhere else the audit warns, the pages show placeholder frames and `mise run //docs/user:check` still passes — so someone with a working browser has to regenerate them before a release.
- `docs/user/source.config.ts` sets `rehypeCodeOptions.themes` to a light/dark Shiki pair, which replaces Fumadocs' defaults wholesale, so `defaultColor: false` has to be repeated alongside it. Omit it and Shiki emits fixed colors instead of the `--shiki-light` / `--shiki-dark` variables dark mode reads, and code blocks stop switching with the theme.
