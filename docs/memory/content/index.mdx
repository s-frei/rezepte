<Callout type="info">

  This section is the long-term memory for AI coding agents working on Rezepte. It is written for agents first, but stays readable for humans.

  It is not the end-user documentation. `docs/user/` is written for the people who cook from Rezepte and the people who host it for them - installing, configuring, using the app. Nothing about developing Rezepte belongs there, and nothing about cooking belongs here. The two sites are deployed separately (see [Documentation sites](/architecture/docs)), so a sentence in the wrong one reaches the wrong audience.

</Callout>

## What Rezepte is

A self-hosted recipe manager for a household: a Go service serving a bundled SvelteKit SPA, SQLite for storage, sessions for login. The UI is English or German, per account; everything in the repository is American English ([Language](/conventions/language)).

## What belongs here

This memory describes **the repository, not the machine and not the day**.

<Steps>
  <Step>

    ### Write the present
    Every page says what is true now. When something changes, rewrite the sentence - do not append a correction, and do not leave the old claim standing beside the new one. A page that reads as a changelog has stopped being memory.

    There is **one document per thing that exists**, never one per event. A feature has a page under `features/`, the shape of the system has a page under `architecture/`, a recurring task has a how-to. A page is rewritten when its subject changes and deleted when its subject is gone, so the number of pages follows the size of the system rather than the age of the project.

    Reasoning is not lost to that rule, it moves with its subject: why a thing is shaped the way it is, and which alternatives were weighed and refused, live on the page for that thing under `## Why it is this way` and `## Rejected`. Keep a rejected option only while someone might still propose it. See [Update the memory](/howtos/update-the-memory).

  </Step>
  <Step>

    ### Write the constraint, not the event
    "macOS binds port 5000 system-wide to the AirPlay receiver, which answers every request with 403" is durable: it explains the choice and stops anyone picking 5000 again. "We moved off 5000 on 2026-09-18" is the same fact with a shelf life, and git already records it.

    So: no dates, no "originally", no "used to", no "no longer, since". If a sentence only makes sense to someone who knows what the repository looked like before, it is an event - rewrite it as the constraint that outlived it. Where a concrete incident is what makes a rule credible, keep it to one sentence and lead with the rule.

  </Step>
  <Step>

    ### One fact, one owner
    A value written in two places will rot in one of them. Ports, paths, task names and commands are named where they belong and linked from everywhere else - for ports that means `mise run ports`, never a copied number. This is the same rule `docs/user/scripts/base-path-audit.ts` follows when it imports the base path from the config instead of repeating it.

  </Step>
  <Step>

    ### Never record one machine's setup
    No absolute paths, usernames, hostnames, or "on the development machine" quirks - this repository is meant to be readable by anyone, on any machine, and it may become public. A workaround that is true only of one laptop belongs in that developer's own notes. Ports named here are the project's own defaults (offset 0), not a fact about anyone's setup.

  </Step>
</Steps>

## How to read this memory

<Steps>
  <Step>

    ### Start with the architecture overview
    Read [Architecture overview](/architecture/overview) to see how `service/`, `frontend/` and `docs/` fit together.

  </Step>
  <Step>

    ### Read the feature page before changing a feature
    [Features](/features/recipes) says how each capability behaves and why, [Architecture](/architecture/overview) says how the parts fit together, and both name the options already weighed and refused. A change to behavior is not done until its page says the new thing.

  </Step>
  <Step>

    ### Use the design system, never ad-hoc colors
    Every color, radius, shadow and font comes from the tokens in [Design system](/architecture/design-system). Components wrap Bits UI primitives.

  </Step>
  <Step>

    ### Follow the how-tos for repetitive work
    Adding a migration, an endpoint, a component or a translation each has a how-to under [How-tos](/howtos).

  </Step>
  <Step>

    ### Run the gate
    `mise run check` must pass before every commit.

  </Step>
</Steps>
