Format: `type(scope): summary` following [semantic commit messages](https://gist.github.com/joshbuchea/6f47e86d2510bce28f8e7f42ae84c716).

| Type | Use for |
|---|---|
| `feat` | new user-facing capability |
| `fix` | bug fix |
| `docs` | documentation only (including `docs/memory`) |
| `chore` | tooling, dependencies, config |
| `refactor` | code change without behavior change |
| `test` | tests only |
| `style` | formatting only |
| `ci` | the GitHub Actions workflows |
| `build` | the build and the gates: mise tasks, scripts, bundler and lint configuration |

**`check` enforces these rules before a branch lands**: `commits:check` (`mise/tasks/commits/check.ts`) reads every commit from `develop` to `HEAD` and fails on an unknown type, a title past 70 characters, a `Co-Authored-By` or generated-with trailer, or a `!` without a `Breaking:` line. It skips merge commits and `git revert`'s `Revert "…"` titles, ignores `fixup!`, `squash!` and `amend!` commits, and it does nothing on `develop` itself, without a local `develop` ref or in a shallow clone - so in CI it passes without looking ([Toolchain](/architecture/toolchain)).

Scopes name the area a commit touches - a part of the repository (`service`, `frontend`, `docs`, `memory`, `e2e`, `mise`, `demo`) or a feature area (`api`, `settings`, `user`, `i18n`) - or are left out when no one area fits.

## Breaking changes

A change is breaking when someone who runs Rezepte, or a script that talks to it, has to do something for an upgrade to keep working. That covers:

- the REST API: a field, parameter, endpoint or status code renamed, removed, retyped or given a different meaning;
- configuration: an environment variable or flag renamed or removed, or a default that changes behavior;
- deployment: the image, the binary's arguments, ports, the data directory layout, or a migration that needs a step or a backup beyond the usual;
- a feature removed that people may rely on.

A changed UI, new optional fields and additive endpoints are not breaking. When unsure, mark it: a false `!` costs a larger version number, a missing one costs someone a broken upgrade.

Such a commit carries `!` right before the colon, and it always has a body whose first line starts with `Breaking:` and says what a person running Rezepte has to do, in their words rather than the code's:

```text
refactor(api)!: say username where a login name is meant

Breaking: API clients that send or read `login` on tokens or recipe
filters must use `username` instead.
```

`release:start` reads the `!` to suggest a major version, `release:finish` then requires the release's upgrade notice, and the `Breaking:` line is what that notice is written from - see [Write release notes](/howtos/write-release-notes).

<Callout type="warn" title="Hard rules">

  - Title at most 70 characters, imperative mood, no trailing period.
  - Body only when the title cannot explain the why - or when the commit is breaking, which always needs the `Breaking:` line.
  - No `Co-Authored-By` or tool trailers.
  - Every commit is signed: the repository's ruleset rejects unsigned commits on every branch. When signing does not answer, leave the work staged, carry on, and commit once it does - never `--no-gpg-sign` or `-c commit.gpgsign=false`.
  - Every commit has a human author. A cloud session commits as its agent; before such a branch lands, `git log --format=%ae develop..<branch>` shows it, and `git rebase develop --exec 'git commit --amend --no-edit --reset-author'` fixes it while the branch is still unmerged.
  - Never commit `docs/superpowers/` (local specs and plans) or `docs/design_handoff_rezepte/` (local design mockups).

</Callout>

## What belongs in one commit

A commit is one finished change, not one working step. It stands on its own:
`mise run check` passes on it, and it can be reverted without dragging
unrelated work out with it. Committing often is good; committing a keystroke
log is not.

Fold these into the commit that causes them. They never earn a commit of their
own:

| Follow-up | Belongs to |
|---|---|
| Tests for a behavior | the commit that introduces the behavior |
| Regenerated screenshots, API reference, sqlc output | the commit that changes the source they are generated from |
| Memory and user-doc pages | the commit that changes the thing they describe |
| A correction to code that is not pushed yet | the commit that introduced it |

Correct an unpushed commit with `git commit --amend`, or stage the fix as
`git commit --fixup <sha>` and collapse it before the branch lands
([Tidy the branch before it lands](#tidy-the-branch-before-it-lands)).

A change earns its own commit when it could be reverted on its own and the
rest would still make sense. Two unrelated subsystems in one commit is the
opposite failure — split those.

<Callout type="warn" title="The shape to avoid">

  Three commits for one change:

  ```
  feat(ui): let a member set their display name and color
  fix(ui): right-align the profile save button
  docs(user): regenerate the screenshots
  ```

  The button alignment and the screenshots are not separate changes; they are
  the same change, finished. One commit.

</Callout>

## Tidy the branch before it lands

**A branch gets its final shape in its worktree, and lands on `develop` as a fast-forward whose tip passes `mise run check`.** The gate runs once, on the rebased tip, not on every commit: re-running it per commit costs minutes of full load each for a `bisect` guarantee that `git bisect skip` already covers. Each commit is still meant to stand on its own, because `check` runs before it is made. Until the merge, rewriting the branch is free and expected. Squash the fixups, fold regenerated artifacts into the commits that caused them, and leave each commit with a title that still makes sense in a year.

A branch lands only after the maintainer says yes to that landing ([Work in a worktree](/howtos/work-in-a-worktree)). The full sequence:

```bash
# in the worktree, while working: mark a fix for an earlier commit
git commit --fixup=<sha>

# in the worktree, before landing: fold the fixups onto the current develop
# (no editor needed), then run the gate once on the tip
GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash develop
mise run check

# in the main checkout, on a clean develop
git merge --ff-only feat/<name>
```

An agent cannot drive an interactive editor, so it tidies through `--fixup` and `--autosquash`; a person can run `git rebase -i develop` and reorder by hand. When the tip check fails, fix it with a `--fixup` for the commit that broke it and run the sequence again. If `--ff-only` refuses, `develop` moved meanwhile; rebase again in the worktree.

<Callout type="warn" title="Hard rule">

  `develop` is never rewritten. No squash, no rebase, no amend, no force-push
  on a commit that has landed - not to tidy it, not to fix a title. Every live
  worktree is branched off `develop`; rewriting it strands each one on a parent
  that no longer exists and turns the next merge into conflict archaeology.

  An agent rewrites `develop` only when the maintainer asks for it in so many
  words. "This history is messy" is an observation, not that request.

</Callout>

## Branches (git flow)

- `develop` is the integration branch. Features, fixes and docs are written on a short-lived `feat/<name>` branch in its own worktree ([Work in a worktree](/howtos/work-in-a-worktree)), branched from `develop` and landed back on it as a fast-forward ([Tidy the branch before it lands](#tidy-the-branch-before-it-lands)).
- `main` holds releases only. A release is a fast-forward from `develop` into `main`, done by `mise run release:finish` and tagged with a version (see [Release](/howtos/release)); `main` never gets its own merge commits or direct commits.
- Agents never merge to `main`, push, tag or open pull requests on their own. Releases are triggered by the maintainer.
