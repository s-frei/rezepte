Format: `type(scope): summary` following [semantic commit messages](https://gist.github.com/joshbuchea/6f47e86d2510bce28f8e7f42ae84c716).

| Type | Use for |
|---|---|
| `feat` | new user-facing capability |
| `fix` | bug fix |
| `docs` | documentation only (including `docs/memory`) |
| `chore` | tooling, dependencies, config |
| `refactor` | code change without behavior change |
| `test` | tests only |
| `style` | formatting only |

Scopes: `service`, `frontend`, `docs`, or none.

<Callout type="warn" title="Hard rules">

  - Title at most 70 characters, imperative mood, no trailing period.
  - Body only when the title cannot explain the why.
  - No `Co-Authored-By` or tool trailers.
  - Never commit `docs/superpowers/`.

</Callout>

## What belongs in one commit

A commit is one finished change, not one working step. It stands on its own:
`mise run check` passes on it, and it can be reverted without dragging
unrelated work out with it. Committing often is good; committing a keystroke
log is not.

Fold these into the commit that causes them. They never earn a commit of their
own:

| Follow-up | Belongs to |
|---|---|
| Tests for a behavior | the commit that introduces the behavior |
| Regenerated screenshots, API reference, sqlc output | the commit that changes the source they are generated from |
| Memory and user-doc pages | the commit that changes the thing they describe |
| A correction to code that is not pushed yet | the commit that introduced it |

Correct an unpushed commit with `git commit --amend`, or stage the fix as
`git commit --fixup <sha>` and collapse it with
`git rebase --autosquash <base>` before the branch leaves your machine.

A change earns its own commit when it could be reverted on its own and the
rest would still make sense. Two unrelated subsystems in one commit is the
opposite failure — split those.

<Callout type="warn" title="The shape to avoid">

  Three commits for one change:

  ```
  feat(ui): let a member set their display name and color
  fix(ui): right-align the profile save button
  docs(user): regenerate the screenshots
  ```

  The button alignment and the screenshots are not separate changes; they are
  the same change, finished. One commit.

</Callout>

## Tidy the branch before it lands

Feature work happens in a worktree, and that is where a branch's history gets
its final shape. Until the branch is merged, rewriting it is free and
expected:

```bash
git rebase -i develop        # on feat/<name>, before merging
```

Squash the fixups, fold regenerated artifacts into the commits that caused
them, and leave each remaining commit with a title that still makes sense in a
year. Merge only once the branch reads the way you want `develop` to read.

<Callout type="warn" title="Hard rule">

  `develop` is never rewritten. No squash, no rebase, no amend, no force-push
  on a commit that has landed - not to tidy it, not to fix a title. Every live
  worktree is branched off `develop`; rewriting it strands each one on a parent
  that no longer exists and turns the next merge into conflict archaeology.

  An agent rewrites `develop` only when the maintainer asks for it in so many
  words. "This history is messy" is an observation, not that request.

</Callout>

## Branches (git flow)

- All development happens on `develop`. Phases, fixes and docs land there as ordinary commits.
- `main` holds releases only. A release is a fast-forward merge from `develop` into `main` (see [Release](/howtos/release)), tagged with a version; `main` never gets its own merge commits or direct commits.
- Feature branches are optional and short-lived; they branch from and merge back into `develop`.
- Agents never merge to `main`, push, tag or open pull requests on their own. Releases are triggered by the maintainer.
