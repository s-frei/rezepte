---
title: Development credentials
description: Every user a local instance is bootstrapped with has the username with 1234 appended as its password
---

**The password of a bootstrapped user is its username with `1234` appended.** `admin` has `admin1234`, `demo` has `demo1234`, a user the end-to-end suite calls `e2eab12cd34` has `e2eab12cd341234`. Where a flow has to rotate a password, the replacement is the username with `5678`. Usernames are still free to choose; the password is not, so nothing has to be invented, remembered or grepped for.

## Where it applies

Every user created against a running instance:

- The instance owner of a dev instance, which `//service:dev` defaults to on its own command line, so `mise run dev` needs nothing set ([Run the app locally](/howtos/run-dev)).
- The owner the end-to-end task creates, in `mise/tasks/e2e.sh`, which `frontend/e2e/helpers.ts` logs in as.
- Every user an end-to-end spec creates, through `createUser` and `login` in `frontend/e2e/helpers.ts`.
- Every user a screenshot spec creates, through `ensureUser` in `docs/user/screenshots/helpers.ts`.
- Demo mode's own account, `demo` / `demo1234`, declared in `service/internal/demo/seed.go` — the rule is the generalization of what that flag already did ([Demo mode](/features/demo-mode)).

**The rule is code, not discipline.** `devPassword(username)` exists in `frontend/e2e/helpers.ts` and in `docs/user/screenshots/helpers.ts`, `devPasswordNext(username)` beside the first for the rotation case, and `createUser`, `login` and `ensureUser` default to them. A test passes a password explicitly only where the test is *about* a password.

**A bootstrapped username is at least four characters long.** `POST /api/v1/users` declares `minLength:"8"` on the password (`service/internal/userapi/handler.go`), and the settings forms enforce the same minimum through `frontend/src/lib/settings/password.ts`, so a three-letter name would derive a password the API rejects. That is why the second account on the users screenshot is `mila` rather than a shorter name.

## Go unit tests

**A new fixture follows the rule; the existing literals stay as they are.** Write `Password: "sam1234"` for a user named `sam` in a test that needs one, so nothing has to be invented there either. The `"pw"`, `"sam-password"` and `"lea-password"` already spread across `service/internal/**/*_test.go` are not worth converting, and a sweep over them is the wrong instinct rather than a chore nobody got to.

Three things make that conversion expensive and worthless at once:

- **The password lives in two places per fixture, in four textual forms.** It is written where the user is created and again where the user is used — `svc.Login(ctx, "sam", "pw")`, a `{"username":"sam","password":"pw"}` request body, a `{"currentPassword":"pw",…}` patch. Changing one side without the other is a red test, and the forms do not match one pattern.
- **The username is not in the line.** `Password: "pw"` says nothing about whose password it is; the name sits anywhere above it, and a single file carries several (`sam`, `kim`, `lea`, `ida`, `anna`).
- **Some of those literals have to break the rule.** `"short"`, `"x"` and `"nope"` exist to be rejected, and telling them apart from a real fixture means reading what each test asserts.

The payoff would be zero regardless: these tests create users in-process through `user.Service`, which enforces no minimum length, nobody ever types the value into a login form, and it never leaves the file that writes it. The rule exists so a person or an agent can log in to a running instance without looking anything up, and none of that applies here.

## Why it is this way

Accounts get bootstrapped constantly — a dev instance, an end-to-end run, one more fixture in a spec — and by whoever is working, agent or person. The username belongs to the task at hand, so it has to stay free. The password carries no information at all, which is exactly why every session invented a different one: `e2e-password`, `member-password-1`, `first-password-1`, `mia-demo-1234`. Deriving it from the username ends that without a lookup table, and makes a forgotten password a thing you can compute rather than a thing you have to reset.

## Limits

- These credentials are public by construction, and so is `demo1234` in the user documentation. They belong to local instances. An instance reachable beyond the household sets a `REZEPTE_ADMIN_PASSWORD` of its own, seeded or not ([Demo mode](/features/demo-mode)).
- The rule says nothing about API tokens; those are created and read back per test ([Users and auth](/features/users-and-auth)).
