Everything in the repository is written in **American English**: code, identifiers, JSON keys, URL paths and query parameters, SQL, comments, commits, both docs sites and the English UI copy in `frontend/messages/en.json`. **German appears only where its reader or its input is German** - the German UI, German sample and test data, and the code that has to understand German text - and never in an identifier, a comment or a doc. Where it lives:

- **The German catalog:** `frontend/messages/de.json`, and the copies generated from it, which are never edited by hand: `service/internal/mail/messages/de.json` ([Email](/features/email#the-copy)) and `frontend/static/manifest.de.webmanifest` ([Installable app](/features/installable-app)).
- **Word tables for German input:** the units, numbers and phrases a parser matches in recipe text a person typed or imported, such as `service/internal/recipeimport/lang_de.go`, `frontend/src/lib/recipe/measures.ts`, `service/internal/shopping/freetext.go` and the umlaut spellings in `service/internal/recipe/search.go`. The words are data; the identifiers and comments around them stay English.
- **Sample and seed data:** the German sample recipes in `service/internal/recipe/testdata/recipes.de.json`, the German demo in `service/internal/demo/seed.go`, the German preview mails in `service/internal/mail/samples.go`, and the German dish names the demo photos in `assets/demo-photos/de/` are filed and prompted under.
- **Tests** whose data or assertions exercise the German interface.

## Why one variety, and why this one

A rule that applies to every word can be followed without thinking about any of them. The split alternative - American identifiers, British prose - asks for a decision on every line and drifts into both at once: an API answering with `favourite` beside `color`, or a comment saying "colour" about a field named `color`. The interface language is plain `en`, not `en-GB`, so nothing asks for British spelling in the first place. American is the variety the web platform, the libraries and API consumers already use - CSS `color`, `center`, `gray` - so identifiers read like the code around them.

## The pairs that come up

| Write | Not |
|---|---|
| color, colors, colored | colour |
| favorite, favorites | favourite |
| behavior | behaviour |
| center, centered | centre, centred |
| liter, meter, milliliter, fiber | litre, metre, millilitre, fibre |
| gray | grey |
| catalog | catalogue |
| artifact | artefact |
| canceled, labeled, signaling, traveling | cancelled, labelled, signalling, travelling |
| normalize, serialize, recognize, optimize, synchronize, authorization | normalise, serialise, recognise, optimise, synchronise, authorisation |

**`check` enforces the table** through the spelling check over every tracked file, except `frontend/messages/de.json`, the German sample data (`*.de.json`), this page, which quotes the British forms, lockfiles and binaries.

The *-ize* column covers every verb of that family; words that end in *-ise* in American English as well - *promise*, *exercise*, *advise*, *surprise*, *mise* - stay as they are. A recipe's own vocabulary is not spelling: the English sample recipes are British dishes and keep their *caster sugar* and *double cream*.
