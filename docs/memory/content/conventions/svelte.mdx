---
title: Svelte conventions
description: Runes, Bits UI, Tailwind, i18n
---

- Svelte 5 runes only (`$state`, `$derived`, `$props`, `$effect`). No `export let`, no stores for local state.
- TypeScript in every component: `<script lang="ts">`.
- Props are typed inline: `let { title, onSave }: { title: string; onSave: () => void } = $props();`.
- UI text comes from Paraglide: `import { m } from '$lib/paraglide/messages'` and `m.key()`. Never hard-code a string in either language directly in a component - new text means a new message key in both `en.json` and `de.json`, see [Add a translation](/howtos/add-translation).
- Components wrap Bits UI primitives when one exists; put reusable styled wrappers in `src/lib/components/ui`.
- Tailwind utility classes in markup; every color, radius, shadow and font is a token from `src/app.css` (`@theme`). No raw hex values or arbitrary colors in components. See [Design system](/architecture/design-system).
- Data access goes through `src/lib/api`; components never call `fetch` directly.
- Reactive state that lives outside a single component goes in a `*.svelte.ts` file (plain `.ts` files cannot use runes) exporting `$state`/`$derived` values and the functions that mutate them - e.g. `src/lib/auth.svelte.ts`, `src/lib/shell.svelte.ts`, `src/lib/recipe/checked.svelte.ts`.
- Filterable/paginated views keep their filter state in the URL query string rather than only in component state: a small `parse*Query`/`build*Query` pair (e.g. `src/lib/recipe/query.ts`) reads it in `+page.ts` and the component writes it back with `goto(url, { replaceState: true, keepFocus: true, noScroll: true })` on every change, so filtering never grows browser history or steals focus/scroll, and a shared link reproduces the same view.
- Reorderable lists (ingredient rows, editor steps) use `svelte-dnd-action`'s `dragHandleZone`/`dragHandle`, with the Lucide `grip-vertical` icon in `text-handle` as the drag handle. Every zone names its kind in `type` (`ingredient`, `step`, `photo`): zones without one all share the library's default type, so an item can be carried into any other list on the page. Zones that should trade items share a type, the way every ingredient group does.
- Where the design calls for "pick one or type your own" (a tag, an ingredient unit), use a plain text input with its own suggestion affordance instead of Bits UI's `Combobox`: a native `<datalist>` for a short fixed suggestion list (ingredient unit), or a custom filtered `role="listbox"`/`option` dropdown for something assembled from live data (`TagInput` against `listTags()`). `Combobox` is for picking from a closed list; these fields must also accept a brand-new value.
- Theme: read `theme.value`, change with `setTheme()` from `$lib/theme.svelte`; never touch `data-theme` or `localStorage` directly.
- Sign-out is `signOut()` in `$lib/sign-out.ts` (used by `UserMenu` and `SettingsLayout`); one call, one `goto`.
- Global keyboard shortcuts live in the root `+layout.svelte` (`<svelte:window onkeydown>`), guarded against the login route; shared open-state for overlays goes in a `*.svelte.ts` (`$lib/palette.svelte.ts`).
- Full-screen routes (cooking mode) opt out of the app shell in the root `+layout.svelte` by route id (`page.route.id === '/recipes/[slug]/cook'`, next to the `/login` check): they render bare - no `TopBar`, no `BottomNav`, no command palette or Cmd+K - and own the viewport with an `h-dvh` flex column. Add a new full-screen route to that check; never hide shell parts from inside a page.
- Every route, `+error.svelte` included, renders its own `<svelte:head><title>`: usually `<page> · {m.app_name()}` (editor and cooking mode use `<recipe> · <mode>`), and `{m.app_name()}` alone for the overview and the error page. A route without one does not fall back to the `Rezepte` in `app.html` after client-side navigation - the tab keeps the title of whatever route came before. `e2e/titles.test.ts` walks the routes through client-side navigation.
- Per-recipe client state: ingredient ticks in `sessionStorage` (`$lib/recipe/checked.svelte.ts`), chosen servings in `localStorage` under `rezepte-servings:<id>` (`$lib/recipe/servings.svelte.ts`, a `$state` class created per page with `createServings(recipe.id, recipe.servings)`). Both are cleared in the detail page's delete flow. Pure storage rules live in a plain `.ts` sibling so vitest can cover them (`*.svelte.test.ts` is excluded from the unit project).
- Validate every changed `.svelte` file with the svelte MCP `svelte-autofixer` tool before committing.
- Run `mise run //frontend:fmt` then `mise run //frontend:check`.
