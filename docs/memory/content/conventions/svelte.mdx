<Callout type="warn" title="Traps">

- A drag handle is a `<div role="button" tabindex="0">` with an `aria-label`, never a `<button>`: `svelte-dnd-action` ignores Space and Enter on a target with a `disabled` property, so a `<button>` handle never starts a keyboard drag.
- Every drag zone names its kind in `type` (`ingredient`, `step`): zones without one share the library's default type, so an item can be carried into any other list on the page.
- Every drag zone passes `zoneTabIndex: -1`, or the library makes the list itself a Tab stop beside the handles.
- On Escape `svelte-dnd-action` just drops the item where it stands; `applyDrag` notes the Escape in the capture phase to put the lists back ([Reorderable lists](#reorderable-lists)).
- The library ends a keyboard drag on a window click that comes after the real click, so a click into another item silently dropped the drag; `applyDrag` sends the library its window click first ([Reorderable lists](#reorderable-lists)).
- Under reduced motion `getAnimations()` still lists `flashPlaced`'s light for 800 ms though nothing moves; a test must not read it as motion ([Reorderable lists](#reorderable-lists)).
- A Bits UI `RadioGroup` inside another one loses its arrow keys to the outer group; the inner choice is native radios ([Bits UI](#bits-ui)).
- A Combobox's `inputValue` overrides Bits UI's own copy of the field's text only when it changes; clearing after a pick needs the label, `tick()`, `''`, `tick()`, then the input element's own `value` emptied ([Bits UI](#bits-ui)).

</Callout>

- Svelte 5 runes only (`$state`, `$derived`, `$props`, `$effect`). No `export let`, no stores for local state.
- TypeScript in every component: `<script lang="ts">`.
- Props are typed inline: `let { title, onSave }: { title: string; onSave: () => void } = $props();`.
- UI text comes from Paraglide: `import { m } from '#lib/paraglide/messages.js'` and `m.key()`. Never hard-code a string in either language directly in a component - new text means a new message key in both `en.json` and `de.json`, see [Add a translation](/howtos/add-translation).
- `src/lib` is imported as `#lib/...`, a subpath import declared in `frontend/package.json` (SvelteKit 3 no longer generates `$lib`), with the file's extension: `.js` for a `.ts` module (`#lib/api/client.js`, `#lib/auth.svelte.js`), `.svelte` for a component.
- `resolve()` from `$app/paths` takes a route id, which starts with `/` (`resolve('/recipes/[slug]', { slug })`, `resolve('/settings')`), or a plain path, which does not (`` resolve(`settings/api?${qs}`) ``, `cookPath()`'s `recipes/<slug>/cook?step=<n>`). A path with a query or one built from `location` goes without its leading `/`; with one it is read as a route id.
- Shallow routing stays on `replaceState` from `$app/navigation` (the cook mode's step, the detail page's `fromOverview`), deprecated in SvelteKit 3 but kept: its replacement, `goto(url, { shallow: true })`, runs every `beforeNavigate`, `onNavigate` and `afterNavigate` callback, so the layout's page transition and each overlay that closes on navigation would fire on every step. Moving over means a `shallow` guard in each of those callbacks first. `replaceState` leaves `page.url` at the address the page loaded with; the address it wrote is `page.shallow.url`, also on a back or forward onto the entry, so read `page.shallow?.url ?? page.url`.
- A path known only at runtime (a `?next=`, a navigation's target) goes through `resolvePath()` from `#lib/paths.js`, not `resolve(x as Path)`: TypeScript checks a union argument against `resolve`'s per-route signatures only while the app has at most 25 routes; it has more, so such a cast fails `svelte-check`.
- `goto` in SvelteKit 3 rejects a path no route matches. A `goto` to a path from outside, such as a `?next=`, asks `match()` from `$app/paths` first and takes `location.assign` when it finds nothing.
- Components wrap Bits UI primitives when one exists; put reusable styled wrappers in `src/lib/components/ui`.
- Tailwind utility classes in markup; every color, radius, shadow and font is a token from `src/app.css` (`@theme`). No raw hex values or arbitrary colors in components. See [Design system](/architecture/design-system).
- Data access goes through `src/lib/api`; components never call `fetch` directly.
- Reactive state that lives outside a single component goes in a `*.svelte.ts` file (plain `.ts` files cannot use runes) exporting `$state`/`$derived` values and the functions that mutate them - e.g. `src/lib/auth.svelte.ts`, `src/lib/shell.svelte.ts`, `src/lib/recipe/checked.svelte.ts`.
- Filterable/paginated views keep their filter state in the URL query string rather than only in component state: a small `parse*Query`/`build*Query` pair (e.g. `src/lib/recipe/query.ts`) reads it in `+page.ts` and the component writes it back with `goto(url, { replace: true, reset: false })` on every change, so filtering never grows browser history or steals focus/scroll, and a shared link reproduces the same view. An overlay that closes on navigation therefore ignores a `goto` that keeps the pathname, as `YouSheet.svelte`, `NewSheet.svelte`, `UserMenu.svelte` and the command palette do. An overlay in the shell, which every page keeps, closes in `afterNavigate` that way, or the back button leaves it open over the page before.
- Reorderable lists of editable rows use `svelte-dnd-action`, see [Reorderable lists](#reorderable-lists).
- Keyed photo grids (the editor's photos, the diary photos, the collage) sort with `#lib/sortable` instead ([Images](/features/images)): `svelte-dnd-action` removes its dragged element on drop while Svelte reuses it by key, so every drag deleted a tile.
- Where the design calls for "pick one or type your own" (a tag, an ingredient unit), use a plain text input with its own filtered `role="listbox"`/`option` dropdown (`TagInput`, `UnitInput`): Bits UI's `Combobox` is for picking from a closed list, and a native `<datalist>` falls short in ways `UnitInput.svelte` lists. Opening a field lists every suggestion, whatever it holds; only typing narrows the list. The units come from each catalog's comma-separated `editor_unit_options`, so every language suggests its own.
- Theme: read `theme.value`, change with `setTheme()` from `#lib/theme.svelte`; never touch `data-theme` or `localStorage` directly.
- Sign-out is `signOut()` in `#lib/sign-out.ts` (used by `UserMenu`, `YouSheet` and `SettingsLayout`); one call, one `goto`.
- Global keyboard shortcuts live in the root `+layout.svelte` (`<svelte:window onkeydown>`), guarded against the login route; shared open-state for overlays goes in a `*.svelte.ts` (`#lib/palette.svelte.ts`).
- Full-screen routes (cooking mode) opt out of the app shell by route id in the root `+layout.svelte`, never by hiding shell parts from inside a page - see [Add a route](/howtos/add-route).
- Every route, `+error.svelte` included, renders its own `<svelte:head><title>`: usually `<page> · {m.app_name()}` (editor and cooking mode use `<recipe> · <mode>`), and `{m.app_name()}` alone for the overview; the error page uses its heading. A route without one does not fall back to the `Rezepte` in `app.html` after client-side navigation - the tab keeps the title of whatever route came before. `e2e/titles.test.ts` walks the routes through client-side navigation.
- Per-device choices in `localStorage` go through `load` and `save` from `#lib/storage`, which guard the property access itself (a browser that blocks site data throws on `window.localStorage`) and return `null` or do nothing outside the browser. Code that must reach `localStorage` or `sessionStorage` itself wraps every read and write in `try`/`catch` the same way (`ShareSheet.svelte`'s remembered tab, `markArrival` in `frontend/src/lib/arrival.ts`, `loadCheckedKeys` and `saveCheckedKeys` in `frontend/src/lib/recipe/checked.ts` for the ingredient ticks), and the page works without the stored value.
- Per-recipe browser state - ingredient ticks in `sessionStorage` (`#lib/recipe/checked.svelte.ts`), servings in `localStorage` ([Cooking](/features/cooking)) - is cleared in the detail page's delete flow. Pure storage rules live in a plain `.ts` sibling so vitest can cover them: `*.svelte.test.ts` is excluded from the unit project.
- A native listener on an ancestor runs **before** a descendant's `onclick`: Svelte 5 delegates `onclick` to the root, so while the click bubbles through the ancestor the handler has not run and `tick()` has no update to wait for. To react to what the click changed, wait a task instead (`setTimeout`, see `keepFocus` in `ActiveFilters.svelte`).
- Validate every changed `.svelte` file with the svelte MCP `svelte-autofixer` tool before committing.
- Run `mise run //frontend:fmt` then `mise run //frontend:check`.

## Reorderable lists

**Rows of editable fields (ingredient rows, editor steps) reorder with `svelte-dnd-action`'s `dragHandleZone`/`dragHandle`, and every zone's `consider` and `finalize` go through `applyDrag` (`#lib/recipe/dnd`).**

- The handle's `onpointerdown` is `pickUp`: the press lifts the item (`data-lift="up"`) before the library starts its drag; `liftDragged` (`transformDraggedElement`) marks the drag's copy should the press have been missed.
- The item `li` has `outline-none`, because the library focuses the drag's copy and the browser drew its focus ring around the card.
- `applyDrag` adds what the library lacks for a keyboard drag: Escape puts back every list the drag touched (noted in the capture phase, since the library drops the item where it stands), focus returns to the handle when it fell to the page, and while a keyboard drag runs it sends the library its window click ahead of the real one, or a click into another item reached that item first and silently dropped the drag.
- Where a drag places an item, `flashPlaced` lights it up as an 800 ms Web Animation; under reduced motion the light holds and goes out at once, so `getAnimations()` still lists it.
- Zones that trade items share a `type`, the way every ingredient group does.

## Bits UI

- **Bits UI's escape layer calls `preventDefault` on the `Escape` it handles**, so a page's `svelte:window` key handler that skips `defaultPrevented` events needs no guard of its own for an open popover, menu or dialog (the cook page and `TypeSpecimen`, [Cooking](/features/cooking#keyboard-pointer-and-motion)).
- **A Combobox's `inputValue` goes stale after a pick.** Bits writes the picked label into its own copy of the field's text, and `inputValue` overrides that copy only when its value changes; to empty the field after a pick, set it to the label, `tick()`, set it to `''`, `tick()` again, and empty the `<input>`'s own `value` (`cleared` in `frontend/src/lib/components/shopping/InvitePicker.svelte`, which does all five steps). With a stale copy a Backspace on the empty field reopened the list.
- **A Combobox's list opens on click, never on focus.** Bits picks on `pointerup`; in a centered dialog a list opened on `pointerdown` grows the dialog and moves the field up, and the `pointerup` lands on the first suggestion.
- **A Combobox inside a sheet uses `Combobox.ContentStatic`**, in the flow under the field: floating content is clipped by the sheet's scroll area, while a static list pushes the rest down where scrolling reaches it.
- **A `RadioGroup` never sits inside another `RadioGroup`.** The outer group's arrow keys take the nested Bits radios for its own, so the inner choice is native `<input type="radio">` cells (`LifetimePicker.svelte`, [Public shares](/features/public-shares#the-link-tab-on-the-recipe-page)).

## Accessibility

Focus is handed on whenever a control removes itself or its opener disappears, never left to fall to `<body>`. A dialog returns focus to its opener; when the opener is gone at close (a "Create link" that became "Manage", a row that left with its data), the page moves focus to its replacement, from an effect that waits out the close animation and acts only when focus fell to `<body>`. The same holds after a delete (focus goes to the next row's control, or to "add") and after a drag. See [Users and authentication](/features/users-and-auth), [User switch](/features/user-switch), [Public shares](/features/public-shares) and [Design system](/architecture/design-system) for each component's target.

After a SvelteKit navigation focus resets to `<body>` (`reset_focus`), and only an element with the `autofocus` attribute is spared. A page that must start focused (the login's first field, the password field of `/login?add=1`) uses the attribute, never `focus()` in `onMount`.

A button that must keep focus while it is unavailable uses `aria-disabled` (and `aria-busy` while it works) instead of `disabled`: a truly disabled button drops keyboard focus the moment it is pressed. `ServingsStepper` at 1 or 99 uses `aria-disabled`; `Button`'s `busy` state (the login, `/welcome` and `/forgot-password` submit) stays pressable under `aria-busy`. The handler ignores the press.

**A submit or request button shows its request with `busy`, never with native `disabled`**, so pressing it keeps focus where it was. `Button`'s `disabled` is native (Bits UI passes it through), which is right for a button that cannot act yet - an empty field, nothing selected - and for the secondary button beside one that is busy, never for the one whose request is running. A raw `<button>` or a Bits trigger does the same with `aria-disabled` and `aria-busy`, and its handler returns while busy (`AvatarControl.svelte`).

A hand-rolled modal panel (one that is not a Bits UI `Dialog`) makes the rest of the page unreachable with `inert` on a `display: contents` wrapper around it: the wrapper adds no box, so the page's flex or grid layout keeps its items, and one attribute takes everything behind the panel out of focus, pointer and the accessibility tree, which is what makes its `aria-modal="true"` true (the cook page's ingredient sheet, [Cooking](/features/cooking#wake-lock-and-the-ingredient-sheet)).

## User activation

A browser API that needs the tap's user activation is called synchronously inside the event handler, before any `await`: `navigator.share`, a clipboard write, a permission prompt (`Notification.requestPermission`, which `timers.start` calls first thing), starting or unlocking audio, and focusing a field to raise the iOS keyboard (`IngredientGroupEditor`'s new group name). An await spends the activation and Safari then refuses. So whatever the call needs is prepared before the tap: the share image is drawn and the share link fetched when the page loads, and the tap only calls the API ([Recipe card](/features/recipe-card), [Link previews](/features/link-previews)).

The iOS keyboard cannot be raised by a field that appears after a navigation, since that focus comes outside the tap. A tap that navigates to a page with a field to type in calls `holdKeyboard()` from `#lib/keyboard.ts`, which focuses a hidden stand-in inside the tap, and the next page's field takes the focus with `handKeyboardTo(field)`, which keeps the keyboard up ([Shopping lists](/features/shopping-lists#the-overview-and-a-new-list)). Headless Chromium has no software keyboard, so check it on an iPhone.

## Overlapping requests

**Every optimistic switch or select that saves on change carries a sequence guard**, because a second flip can overtake the first. When several requests for one control can overlap, the newest wins: each one takes the next number from a counter (`++saveSeq`, a revision) and its answer is applied only while its number is still the latest, so a late answer is dropped. A failed optimistic change undoes its own step only while nothing newer was sent, and reloads otherwise. Examples: the shopping list page ([Shopping lists](/features/shopping-lists)), the color pickers in `frontend/src/routes/settings/+page.svelte` and on a person's settings page, and the switches and selects of the instance cards (`RecipeEditingCard.svelte`, `PublicSharingCard.svelte`, `LinkPreviewsCard.svelte`, `NotificationsCard.svelte`). A control that refuses a second change while one is saving (`LanguageControl.svelte`) needs no guard.

Requests started by a dialog are aborted by an `$effect` that fires when its `open` turns false, not on unmount: the unmount comes after the fade-out, and an answer in between would navigate or toast for a dialog the user already closed. Use one `AbortController` per read, since a dialog reopened during the fade-out keeps its form (`ImportForm.svelte`, see [Recipe import](/features/recipe-import)).
