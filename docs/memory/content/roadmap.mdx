## Instance sync

Instance A issues an [API token](/features/api-tokens) scoped to `recipes:read`. Instance B stores its URL and that token and mirrors recipes read-only. Bearer-token authentication already exists; what is missing is the `/api/v1/sync/*` endpoints themselves.

## Public REST API

Already prepared by huma: OpenAPI 3.1 and Scalar docs, and bearer [API tokens](/features/api-tokens) for programmatic access. Missing: a versioning policy and rate limits.

## MCP server

Expose recipes to AI assistants (search, read, create draft), authenticating with an [API token](/features/api-tokens). Missing: the MCP endpoint itself, and a decision on OAuth 2.1 versus the static bearer token the API tokens feature deliberately kept instead - see that page's Limits.

## OIDC login

Second authenticator next to sessions. Users are matched by the provider's subject identifier - the `users` table holds no email address to match on - and roles stay local.

## More recipe features

Personal notes, "last cooked", shopping list, meal plan.

## Recipe import from a URL

Draft a recipe from a pasted URL: fetch the page, parse schema.org `Recipe` JSON-LD (`golang.org/x/net/html` for the fallback HTML walk), pre-fill the editor for review before saving. The "Import" buttons in the top bar and on the overview stay disabled, titled "coming soon", until it lands.

## Tooling

Screenshot generation in CI: `mise run //docs/user:screenshots` needs a Chromium that starts there, and CI has none, so the committed PNGs are regenerated locally. [Documentation sites](/architecture/docs) owns the screenshot pipeline.
